# Алгебры возможностей {#capability-algebras}

![Design by meaning in Rust — building software from small capability traits](../assets/design-by-meaning-rust.png)

```admonish tip title="Связанные материалы"
«Проектирование на основе смысла в Rust»: [Семантические типы в Rust](semantic-types.md), [Производный смысл и композиция](derived-meaning.md)

```

```admonish note title="Обзор"
Трейт возможностей — это небольшая алгебра: он называет примитивные наблюдения и преобразования, необходимые для заданного смысла, и оставляет выбор представления интерпретатору. Словарь следует проектировать от смысла, а не от полей, которые случайно оказались в первой реализации.
```

В Rust нет встроенной конструкции под названием «денотационное проектирование». Семантические словари кодируются обычными средствами языка. Один из полезных способов — небольшие трейты возможностей.

Суффикс `Alg` в этой книге означает **алгебру**: связный набор примитивных операций над носителями, выбранными интерпретатором.

## Начните со смысла {#start-from-meaning}

Смысл позиции ветвления из предыдущей части можно выразить так:

```rust,noplayground
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum Direction {
    Left,
    Right,
}

pub trait BranchAlg {
    type Branch;

    fn branch_root(&self) -> Self::Branch;
    fn branch_grow(&self, branch: &Self::Branch, direction: Direction) -> Self::Branch;
    fn branch_path(&self, ancestor: &Self::Branch, descendant: &Self::Branch) -> Option<Vec<Direction>>;
}
```

Трейт задаёт три примитивных смысла:

*   создать корень
*   продолжить ветвь в одном из направлений
*   наблюдать относительный путь, если он существует

Трейт не раскрывает, где хранятся ветви и как кодируются пути.

## Возможности — не проекции полей {#capabilities-are-not-field-projections}

````admonish warning title="Проекции полей — не семантические возможности"
Сравните:

```rust,noplayground
trait BranchContext {
    fn branches(&self) -> &Vec<Vec<bool>>;
    fn branches_mut(&mut self) -> &mut Vec<Vec<bool>>;
}
```

Этот трейт скрывает структуру за методами, но по-прежнему раскрывает её представление. Любая производная логика будет зависеть от векторов, логических значений, владения и стратегии мутаций.
````

Семантическая возможность открывает наблюдение или преобразование, необходимое для последующего смысла. Спросите:

```admonish question title="Что спросить о каждой возможности"
Имела бы эта операция смысл, если бы реализация использовала базу данных, символьный терм, компактное целое число или удалённый сервис?
```

Если да, операция может относиться к этой возможности. Если же вызывающему коду нужна нынешняя схема полей, вероятно, она не относится.

## Один примитивный смысл на трейт {#one-primitive-meaning-per-trait}

Небольшие трейты делают зависимости явными:

```rust,noplayground
pub trait ClockAlg {
    type Instant;

    fn clock_now(&self) -> Self::Instant;
}

pub trait DeadlineAlg<Instant> {
    fn deadline_expired(&self, now: &Instant) -> bool;
}
```

Производная операция, которой нужны время и крайний срок, может требовать оба трейта. Ей не нужен `ApplicationContext`, объединяющий журналирование, хранение, сеть, конфигурацию и планирование.

«Небольшой» не значит механически «один метод». Группируйте операции, когда они образуют единую неразделимую семантическую структуру. Разделяйте, когда они выражают независимые смыслы или допускают независимые интерпретаторы.

## Ассоциированные типы выбирают носители {#associated-types-select-carriers}

Используйте ассоциированные типы, когда представление выбирает интерпретатор:

```rust,noplayground
pub trait SourceAlg {
    type Source;
    type Error;

    fn source_read(&self, name: &str) -> Result<Self::Source, Self::Error>;
}
```

Не требуйте `String`, `std::io::Error` или конкретное синтаксическое дерево, если они не являются устойчивой частью семантического словаря на этой границе.

При этом конкретные семантические значения вполне уместны:

```rust,noplayground
pub enum Severity {
    Warning,
    Error,
}
```

Правило не в том, чтобы «сделать абстрактным каждый тип», а в том, чтобы «не путать механизмы интерпретатора с семантическим словарём».

## Добавляйте ограничения там, где они используются {#put-bounds-where-they-are-used}

Не ограничивайте примитив без необходимости:

```rust,noplayground
pub trait CandidateAlg {
    type Candidate;

    fn candidates(&self) -> impl Iterator<Item = Self::Candidate>;
}
```

````admonish warning title="Не добавляйте ограничения заранее"
Не ограничивайте ассоциированный тип лишь потому, что это может понадобиться какому-нибудь будущему алгоритму:

```rust,noplayground
pub trait CandidateAlg {
    // not recommended: every interpreter now pays for bounds
    // most operations never use
    type Candidate: Clone + Ord + Hash + Send + Sync;

    fn candidates(&self) -> impl Iterator<Item = Self::Candidate>;
}
```

Операция сортировки кандидатов может требовать `Ord`; операции помещения в хеш-множество может требовать `Hash`.
````

Ограничения в месте использования сохраняют повторное применение примитивных смыслов и выявляют настоящий контракт производного поведения.

## Эффекты могут быть примитивным смыслом {#effects-can-be-primitive-meaning}

Трейты возможностей не подразумевают чистое выполнение:

```rust,noplayground
pub trait PublishAlg {
    type Document;
    type Error;

    async fn publish(&self, document: Self::Document) -> Result<(), Self::Error>;
}
```

Публикация — это эффект. На текущей границе она всё же может быть примитивной семантической операцией. Конкретный интерпретатор может использовать HTTP, очередь, файл или тестовый буфер.

Семантический слой не должен предписывать повторные попытки, владение сокетами, запуск задач или пулы соединений, если эти различия не входят в предполагаемый смысл.

## Обозначение границы {#naming-the-boundary}

Формулируйте возможности с точки зрения смысла для потребителя:

| Ориентированное на смысл | Ориентированное на представление |
| --- | --- |
| `closed_outcome(slot)` | `get_runtime_map(slot)` |
| `source_read(name)` | `compiler_context().sources().lookup(name)` |
| `branch_path(ancestor, descendant)` | `raw_branch_bits(id)` |

Именование — часть проектирования. Механическое имя провоцирует механическую связанность.

## Проверочные вопросы {#review-checks}

*   Выражает ли трейт один связный примитивный смысл?
*   Сможет ли независимый интерпретатор реализовать его, не копируя первое представление?
*   Используются ли ассоциированные типы как абстрактные только там, где выбор действительно за интерпретатором?
*   Являются ли конкретные типы устойчивой частью семантического словаря?
*   Отсутствуют ли ограничения до тех пор, пока они не нужны операции?
*   Избегает ли трейт возврата управляющих объектов, контекстов и сырого хранилища?
