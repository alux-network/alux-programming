# Интерпретаторы и эффекты {#interpreters-and-effects}

```admonish note title="Обзор"
Интерпретатор выбирает представление или эффект для возможности. Он реализует примитивные операции, не переопределяя выведенное выше поведение предметной области, поэтому одни и те же законы выполняются во всех интерпретаторах.
```

Интерпретатор реализует семантическую возможность с помощью конкретного представления или эффекта. Он должен выбирать механизмы, не переопределяя поведение предметной области.

## Тонкий интерпретатор {#a-thin-interpreter}

Представление ветвей в виде битовых путей может выглядеть так:

```rust,noplayground
#[derive(Clone, Debug, PartialEq, Eq)]
struct BitBranch(Vec<Direction>);

struct BitBranchImpl;

impl BranchAlg for BitBranchImpl {
    type Branch = BitBranch;

    fn branch_root(&self) -> Self::Branch {
        BitBranch(Vec::new())
    }

    fn branch_grow(&self, branch: &Self::Branch, direction: Direction) -> Self::Branch {
        let mut grown = branch.0.clone();
        grown.push(direction);
        BitBranch(grown)
    }

    fn branch_path(&self, ancestor: &Self::Branch, descendant: &Self::Branch) -> Option<Vec<Direction>> {
        descendant.0.strip_prefix(&ancestor.0[..]).map(<[Direction]>::to_vec)
    }
}
```

Реализация хранит и наблюдает примитивные факты. `branch_left`, `branch_right` и `branch_is_ancestor` остаются в общем расширении.

## Интерпретаторы зависят от границ {#interpreters-are-boundary-relative}

Один и тот же тип на одной границе может быть интерпретатором, а на другой — семантическим входом.

| Граница | Использует | Интерпретирует |
| --- | --- | --- |
| Адаптер файловой системы | Доступ к файловой системе | Поиск исходного текста |
| Среда нормализатора | Поиск исходного текста как примитивная возможность | Построение нормализованного языка |
| Конвейер компилятора | Нормализованные термы | Построение исполняемого файла |

Универсального «слоя реализации» не существует. Есть вложенные семантические границы.

## Эффекты на границе {#effects-at-the-edge}

Конкретные интерпретаторы отвечают за такие решения, как:

*   структура базы данных
*   асинхронная среда выполнения
*   владение задачами
*   стратегия повторных попыток
*   типы фреймворка HTTP или RPC
*   сериализация
*   блокировки и каналы
*   кэширование

Не включайте эти решения в семантические трейты, если вызывающему коду не нужно их наблюдать.

Например, семантическая возможность источника может возвращать исходное значение и ошибку. Промышленный интерпретатор может кэшировать файлы и читать их асинхронно. Тестовый интерпретатор может использовать неизменяемую карту. Производная логика нормализации должна работать с обоими.

## Владение средой выполнения {#runtime-ownership}

Обратные вызовы фреймворков часто требуют владеющего, клонируемого и потокобезопасного состояния. Это ограничение интерпретатора, но не обязательно предметной области.

````admonish warning title="Не помещайте типы среды выполнения в примитивы"
Не загрязняйте примитивную операцию типами фреймворка:

```rust,noplayground
async fn status(data: FrameworkData<Arc<AppState>>) -> FrameworkJson<Status>;
```
````

Предпочитайте семантическое применение:

```rust,noplayground
trait StatusAlg {
    type Status;

    async fn status(&self) -> Self::Status;
}
```

Веб-интерпретатор может выбрать `Arc<Context>`, извлечь входные данные запроса, вызвать `status` и преобразовать результат. Знание о существовании веб-сервера не требуется вызывающему коду предметной области.

## Нейтральные интерпретаторы {#neutral-interpreters}

Не каждому интерпретатору нужно выполнять эффекты.

Текстовый интерпретатор программы API может записывать:

| Метод | Путь | Входные данные | Выходные данные |
| --- | --- | --- | --- |
| `GET` | `/status` | — | JSON `Status` |
| `POST` | `/temperature` | JSON `f32` | JSON `Status` |

Интерпретатор метаданных может создавать документацию. Тестовый интерпретатор может собирать имена операций. Промышленный интерпретатор может строить маршруты сервера.

Нейтральные интерпретаторы показывают, что программа несёт смысл независимо от конкретной среды выполнения.

## Композиция интерпретаторов через делегирование {#composing-interpreters-by-delegation}

Поскольку смысл заключён в небольших трейтах возможностей, интерпретатор обычно *собирают* из компонентов, а не выписывают целиком. Носитель получает возможность, делегируя её тому, кто уже её предоставляет, поэтому перенаправление генерируется, а не пишется вручную. Почти все случаи охватывают два способа.

**Передать возможность полю.** Макрос `#[derive(Delegate)]` из ambassador передаёт целый трейт внутреннему значению. Носитель с несколькими компонентами делегирует каждую возможность полю-владельцу без ручного кода перенаправления:

```rust,noplayground
#[derive(Delegate)]
#[delegate(Clock, target = "clock")]
#[delegate(Logger, target = "logger")]
struct Service {
    clock: SystemClock,
    logger: StdoutLogger,
}
```

**Предоставить возможность через геттер.** Достаточно добавить типу один геттер — blanket-реализация предоставит всю возможность каждому типу с таким геттером:

```rust,noplayground
trait Logger {
    fn log(&self, message: &str);
}

trait HasLogger {
    type Logger;

    fn logger(&self) -> &Self::Logger;
}

// Any carrier that can hand back a logger is itself a `Logger`.
impl<T> Logger for T
where
    T: HasLogger,
    T::Logger: Logger,
{
    fn log(&self, message: &str) {
        self.logger().log(message)
    }
}
```

В результате часто можно обойтись без множества структур. Вместо монолитного объекта контекста — одного крупного трейта с несколькими ассоциированными типами и десятком методов и единственной конкретной реализации — остаётся несколько небольших трейтов возможностей и тонкий носитель, делегирующий каждую из них полю или геттеру. Производные операции, например проверка истечения срока, один раз задаются как расширения поверх примитивов, а не реализуются заново для каждого носителя.

```admonish warning title="Делегирование передаёт операции, а не смысл"
Сгенерированное делегирование убирает шаблонный код, но не доказывает семантическую взаимозаменяемость. Макрос `derive`, например `#[derive(Delegate)]` из ambassador, подтверждает, что реализации компилируются, но не то, что носитель обозначает тот же интерпретатор. Если `Shared<T>(Arc<T>)` должен подменять `T`, проверьте законы для носителя: обёртка, меняющая совместное использование или идентичность (`Arc`, пулы, кэширование), может правильно перенаправлять каждый метод и всё же нарушать закон свежести или уникальности. Если носитель просто хранит `T` среди несвязанных служб, проекция честнее делегирования.
```

## Ошибки относятся к границе {#errors-belong-to-a-boundary}

Ошибки должны сообщать о сбое на границе, которая его обрабатывает.

| Ошибка | Преобразование на границе |
| --- | --- |
| Ошибка предметной области | Транспортный интерпретатор преобразует её в ответ протокола |
| Ошибка разбора | Интерфейс компилятора преобразует её в диагностическое сообщение |
| Ошибка хранилища | Интерпретатор источника преобразует её в семантический сбой источника |

Не помещайте коды состояния HTTP, объекты ошибок RPC или ошибки базы данных в примитивные трейты предметной области. Преобразуйте их на границах интерпретатора.

## Производительность относится к интерпретации, пока не становится наблюдаемой {#performance-is-an-interpretation-concern-until-observed}

Пакетная обработка, параллелизм, кэширование и схема данных обычно относятся к интерпретаторам. Они становятся семантическими, только если спецификация гарантирует наблюдаемый порядок, время, расход ресурсов, справедливость или поведение при сбоях.

Такое разделение позволяет оптимизировать реализацию без семантического дрейфа:

*   Те же законы
*   Те же объявленные наблюдения
*   Другая операционная стратегия

## Проверочные вопросы {#review-checks}

*   Реализует ли интерпретатор примитивы, не дублируя производные операции?
*   Ограничения среды выполнения и фреймворка остаются на потребляющей границе?
*   Могут ли нейтральный или тестовый интерпретатор реализовать ту же возможность?
*   Преобразуются ли ошибки транспорта и хранилища на границе?
*   Семантически ли честно делегирование?
*   Остаются ли различия в производительности ненаблюдаемыми согласно заданной денотации?
