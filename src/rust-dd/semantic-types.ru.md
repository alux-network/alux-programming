# Семантические типы в Rust {#semantic-types-in-rust}

```admonish tip title="Связанные материалы"

«Проектирование на основе смысла в Rust»: [Алгебры возможностей](capability-algebras.md), [Программы первого порядка](first-order-programs.md), [Законы, сценарии и свидетельства](laws.md)  
«Понятия»: [Референциальная прозрачность](../concepts/referential_transparency.md)
```

```admonish note title="Обзор"
В Rust, ориентированном на смысл, типы помогают сохранять видимость семантической структуры. Ассоциированные типы называют семейства носителей, ограничения задают отношения между ними, а методы-расширения выводят новые операции из явных предпосылок. Законы по-прежнему определяют, что обязана сохранять каждая интерпретация.
```

В Rust несколько разных понятий записываются как `type`. Если различать их роли, смысл не будет сводиться к представлению.

| Роль | Пример | Что выражает |
| --- | --- | --- |
| Семантический тип | `Direction` | Какие различия предметной области важны |
| Носитель, выбранный интерпретатором | `BranchAlg::Branch` | Какое представление выбирает интерпретатор |
| Производная операция | `BranchExt::branch_child` | Что следует из объявленных возможностей |
| Тип этапа | `Syntax`, `CoreProgram`, `Executable` | Какие преобразования уже прошли значение |
| Тип представления | `BitBranch` | Как интерпретатор хранит смысл ветвления |
| Программа-свидетельство | Сценарий или повторно используемое расширение с законами | Каким наблюдениям должны соответствовать совместимые интерпретаторы |

## Семантические типы — прежде представления {#semantic-types-before-representation}

Предположим, предметная область ветвления различает два направления:

```rust,noplayground
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum Direction {
    Left,
    Right,
}
```

`Direction` напрямую задаёт это различие. Один интерпретатор может компактно кодировать путь:

```rust,noplayground
struct BitBranch(Vec<bool>);
```

Логические значения относятся к этому представлению. Они не определяют смысл направлений «влево» и «вправо» и не обязательны для других интерпретаторов.

```admonish warning title="Компактное кодирование — не семантический тип"
Не определяйте поведение предметной области через позиции битов, смещения байтов или машинные переходы. Эти артефакты должны кодировать семантические различия, а не владеть ими.
```

Такое разделение позволяет менять схемы хранения и выполнения, не изменяя незаметно предметную область.

## Ассоциированные типы выбирают носители {#associated-types-choose-carriers}

Алгебра возможностей может оставить выбор носителя каждому интерпретатору:

```rust,noplayground
trait BranchAlg {
    type Branch;

    fn branch_root(&self) -> Self::Branch;
    fn branch_grow(&self, branch: &Self::Branch, direction: Direction) -> Self::Branch;
    fn branch_path(
        &self,
        ancestor: &Self::Branch,
        descendant: &Self::Branch,
    ) -> Option<Vec<Direction>>;
}
```

`Self::Branch` — не скрытый тип поля. Это носитель, выбранный при интерпретации смысла ветвления. Одной и той же алгебре могут соответствовать путь из битов, числовая позиция в дереве, символьный терм или другое представление.

Для интерпретатора `T` запись `T::Branch` можно читать как семейство носителей $\mathsf{Branch}(T)$. При смене интерпретатора носитель может измениться, но все операции последовательно используют один и тот же выбор.

## Расширения выводят следствия {#extensions-derive-consequences}

Расширение может построить новую операцию, используя ровно те предпосылки, которые ему нужны:

```rust,noplayground
#[ext(name = BranchExt)]
pub impl<This> This
where
    This: BranchAlg,
{
    fn branch_child(
        &self,
        branch: &This::Branch,
        direction: Direction,
    ) -> This::Branch {
        self.branch_grow(branch, direction)
    }
}
```

Условие `where` — это предпосылка: `This` интерпретирует алгебру ветвления. Метод — следствие: для носителя этого интерпретатора ветвь и направление однозначно задают дочернюю ветвь.

$$ \bigl(T : \mathsf{BranchAlg}\bigr) \Longrightarrow \mathsf{branchChild}_T   : \mathsf{Branch}(T) \times \mathsf{Direction}   \to \mathsf{Branch}(T) $$

Ни в одном шаге вывода не выбирается конкретное представление ветви. Результат остаётся в семействе носителей, выбранном интерпретатором.

## Ограничения равенства задают совместимость {#equality-bounds-state-compatibility}

Двум возможностям иногда требуется общий носитель. Равенство ассоциированных типов задаёт это требование, не выбирая конкретное представление:

```rust,noplayground
Right: BranchAlg<Branch = Left::Branch>
```

Прочитайте ограничение как локальное утверждение: `Left` и `Right` интерпретируют операции ветвления над одним носителем. Указывайте это равенство при операции, которой нужно согласование, а не навязывайте его обеим алгебрам глобально.

Такое ограничение точнее и сильнее, чем принятие конкретного контекста только потому, что он случайно содержит обе реализации.

## Типы этапов делают контракты компилятора явными {#stage-types-make-compiler-contracts-visible}

В конвейере компилятора нельзя передавать одно неразличимое дерево через все фазы. Отдельные типы этапов указывают, какое преобразование уже выполнено:

| Этап | Вход | Выход | Контракт |
| --- | --- | --- | --- |
| Разбор | Исходный текст | `Syntax` | Распознаёт поверхностную грамматику |
| Нормализация | `Syntax` | `CoreProgram` | Формирует выбранный базовый смысл |
| Генерация кода | `CoreProgram` | `Executable` | Сохраняет наблюдения программы в исполняемой форме |
| Среда выполнения | `Executable` | Наблюдаемое поведение | Интерпретирует исполняемый файл в соответствии с моделью языка |

Эти типы предотвращают случайную путаницу между этапами, но одних названий недостаточно, чтобы доказать сохранение смысла. Для преобразований по-прежнему нужны сформулированные законы, характерные сценарии и свидетельства на нескольких интерпретаторах.

## Прочитайте контракт {#read-the-contract}

Структуру типов можно полезно прочитать с логической точки зрения:

| Конструкция Rust | Как её читать |
| --- | --- |
| `This: BranchAlg` | `This` предоставляет интерпретацию смысла ветвления |
| `This::Branch` | Носитель ветвления выбирает `This` |
| `Right: BranchAlg<Branch = Left::Branch>` | Две интерпретации согласованы относительно носителя |
| `-> This::Branch` | Результат остаётся в выбранном семействе носителей |

Такое прочтение помогает проектировать API, раскрывающие, что определяет тип, какие равенства нужны для композиции и какие выводы следуют из предпосылок. Ассоциированные типы, обобщённые ассоциированные типы, обобщённые константные параметры, типовые состояния и свидетели нулевого размера могут выражать части таких контрактов, если лежащее в их основе различие действительно существует.

Не создавайте типовые механизмы лишь для того, чтобы реализация выглядела формальнее. Тип должен выражать смысл или сохранять необходимое отношение, а не украшать представление.

## Типы не заменяют законы {#types-do-not-replace-laws}

Сигнатура типа ограничивает множество допустимых программ. Законы задают отношения между операциями. Нужны и то и другое.

Например, `BranchAlg::Branch` указывает, что каждый интерпретатор выбирает носитель ветвления. Само по себе это не устанавливает, что:

*   путь от ветви к ней самой пуст
*   повторное прохождение пути от корня восстанавливает ветвь
*   противоположные дочерние ветви различны

Это семантические законы, общие для совместимых интерпретаторов. Утверждения, зависящие от представления, например о нулевых неиспользуемых битах, относятся к интерпретатору, который выбрал это представление.

```admonish quote title="Читайте типы как утверждения"
Спрашивайте, что утверждает каждый тип, что определяет его, какими законами он дополняется и какой интерпретатор его реализует.
```

## Проверочные вопросы {#review-checks}

*   Появляется ли различие предметной области до его компактного машинного кодирования?
*   Является ли ассоциированный тип носителем, выбранным интерпретатором, а не замаскированным конкретным состоянием?
*   Задают ли ограничения равенства только совместимость, нужную в месте их использования?
*   Имеют ли разные этапы компилятора отдельные типы и явные контракты?
*   Отделены ли семантические утверждения от инвариантов представления?
*   Подкреплены ли повторно используемыми законами или сценариями утверждения, которые Rust не может выразить?
