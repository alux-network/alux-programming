# 意味から始めるワークフロー {#a-meaning-first-workflow}

```admonish tip title="関連項目"
意味論的な見方：[なぜ意味を先に考えるのか](../denotational-design/semantic-view.md)  
Rustで意味から設計する：[ケイパビリティ代数](capability-algebras.md)、[導出される意味と合成](derived-meaning.md)、[法則、シナリオ、証拠](laws.md)
```

```admonish note title="反復可能な規律"
Denotational Designは、完成したコードを説明するだけのものではなく、繰り返し実践できるワークフローです。意味論上の変更を述べ、最小限の基本ケイパビリティを見つけ、正確に合成し、薄いインタープリターを実装して法則を検査します。
```

Denotational Designは、完成したコードを説明するだけでなく、繰り返し実践できる開発規律として最も有用です。

## 中核となるワークフロー {#the-core-workflow}

新機能やリファクタリングでは、次のように進めます。

1.  意味論上の変更を一文で述べる。
2.  担体と観測的等値性を特定する。
3.  必要最小限の基本ケイパビリティを見つける。
4.  明示したケイパビリティに基づいて導出された振る舞いを定義する。
5.  実態に合った合成形式を選ぶ。
6.  複数の解釈が必要な場合に限り、一階プログラムとして再構化する。
7.  薄い具体インタープリターを実装する。
8.  法則または共有シナリオを追加する。
9.  代替解釈を検証する。
10.  仕組みより先に意味を文書化する。

## 意味論上の変更を述べる {#state-the-semantic-change}

弱い説明：

> キャッシュとマネージャーメソッドを追加する。

意味を中心にした説明：

> 一度のコンパイル中に同じ不変ソース名を解決すると、同じソース値が得られる。

二つ目の説明から、法則の候補が明らかになります。後でキャッシュを一つの実装として選ぶこともできます。

## 基本となる境界を見つける {#find-the-primitive-boundary}

次を問います。

*   どの新しい観測または変換が必要か。
*   この境界では基本操作なのか、既存の意味から導出できるのか。
*   新しい関連担体が必要か。
*   想定した依存関係は、単なる格納場所ではないか。
*   どの区別を見えないままにするか。

本当に新しい基本的な意味がある場合だけ、ケイパビリティを追加します。

## 実態に合わせて合成する {#choose-composition-truthfully}

次の判断表を使います。

| 問い | 選択 |
| --- | --- |
| 一つのレシーバーが必要な意味をすべて解釈するか。 | 直接境界 |
| 振る舞いを個別に選ぶか。 | 明示的なポリシー値 |
| ポリシー同士は独立に合成できるか。 | 積 |
| 環境が別のインタープリターを含むか。 | 射影 |
| ラッパーは内部のインタープリターを代用しなければならないか。 | 委譲 |

大きなコンテキストトレイトを既定の解決策として導入しないでください。

## 一度に一つの意味をリファクタリングする {#refactor-one-meaning-at-a-time}

既存コードが表現先行の場合：

1.  意味論上の観測を一つ特定する。
2.  小さなケイパビリティを一つ定義する。
3.  導出を一つ拡張に移す。
4.  現在の構造体はインタープリターとして維持する。
5.  法則形式のテストを一つ追加する。

```admonish warning title="DDは抽象化至上主義ではない"
推測上の抽象化を使ってサブシステム全体を書き直すことは避けます。DDは抽象化至上主義ではありません。
```

## 意味から仕組みへ順にレビューする {#review-from-meaning-to-machinery}

次の順にコードを読みます。

1.  ケイパビリティトレイト
2.  意味論的な値の型
3.  導出された拡張
4.  存在する場合は一階プログラム構文
5.  共有する法則とシナリオ
6.  具体的なインタープリター
7.  ランタイムのオーケストレーション

最大の状態構造体から読み始めると、表現に引きずられたレビューになります。

## よくある失敗 {#common-failure-modes}

````admonish warning title="トレイトの形をした具体状態はDenotational Designではない"
```rust,noplayground
trait ContextAlg {
    fn state(&self) -> &ConcreteState;
}
```

トレイトが構文を変えても、意味の所有関係は変わりません。意味論上の中核が、依然として具体的な表現に依存しています。
````

### 各インタープリターに導出ロジックがある {#derived-logic-in-every-interpreter}

すべての実装が同じ領域アルゴリズムを個別に定義するなら、仕様を重複させています。

### 万能ケイパビリティ {#god-capability}

無関係な操作を含むスーパー トレイトは依存関係を隠し、独立した解釈を妨げます。

### フレームワークが所有する仕様 {#framework-owned-specification}

ルートの注釈やRPC登録だけがインターフェース定義だと、ドキュメントと実行がずれることがあります。

### マクロが所有する意味 {#macro-owned-meaning}

生成コードに公開された一階の受け皿がないなら、マクロの展開結果が意図せず仕様になってしまいます。

### デフォルトに隠れたポリシー {#policy-hidden-in-defaults}

`Default`がクォーラム、再試行、順序、コンパイルのポリシーを暗黙に選ぶなら、合成が明示的ではなくなります。

### 非公開手順のテスト {#tests-of-private-steps}

フィールド配置や走査順に結び付いたテストは、妥当な代替インタープリターを妨げます。

## Pull Requestの確認項目 {#pull-request-checklist}

### 意味 {#meaning}

*   意味論上の変更を述べているか。
*   担体と等値性が明確か。
*   意図的に省いた内容に名前を付けているか。

### ケイパビリティ {#capabilities}

*   各トレイトが一貫した基本的な意味を公開しているか。
*   操作が使う場所に境界を置いているか。
*   導出コードが具体フィールドを避けているか。

### 合成 {#composition}

*   直接境界、ポリシー、積、射影、委譲を実態に合わせて使っているか。
*   領域のデフォルトを明示しているか。

### プログラムとインタープリター {#programs-and-interpreters}

*   別の解釈が必要な場合に限って、一階構造を導入しているか。
*   便利なマクロを公開されたプログラム値に展開できるか。
*   具体的なインタープリターを薄くし、境界に限定しているか。

### 証拠 {#evidence}

*   法則または焦点を絞った意味論的アサーションがあるか。
*   同じシナリオを別のインタープリターで実行できるか。
*   有限のテストを証明ではなく証拠として説明しているか。

## ALUX式コードを読む {#reading-alux-style-code}

認識すべき全体像は次のとおりです。

1.  小さな基本ケイパビリティトレイト
2.  明示的な境界を使う導出拡張
3.  検査や合成が必要な場合の一階プログラム
4.  共有する法則とシナリオ
5.  具体的なランタイム、コンパイラー、HTTP、RPC、格納用インタープリター

大規模な並行システムにも、オーケストレーションが中心となる領域はあります。既存の各インターフェースがすでに理想的な表示仕様だと決め付けないでください。意味論上の継ぎ目を探し、そこから外側へ読み進めます。

Tolangは、言語規模で同じ視点を用います。構文を意味を担う形式に正規化し、コンパイルでその意味を保ち、並行ランタイムで実行可能な表現を解釈します。操作上の説明も不可欠ですが、意味論上の契約を定めた後に続きます。

## 最後の原則 {#final-principle}

迷ったら、次の問いに立ち返ります。

```admonish quote title="立ち返る問い"
この仕組みは、どのような意味を保持するためのものか。
```

この問いだけですべてのエンジニアリング上の問題を解決できるわけではありません。問題が適切な水準で見えるようになります。
