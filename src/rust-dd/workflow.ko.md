```admonish tip title="관련 항목"

```

```admonish note title="반복 가능한 규율"
표시적 설계는 완성된 코드를 설명하는 데 그치지 않고 작업 흐름으로 활용합니다. 의미론적 변화를 명시하고, 가장 작은 기본 케이퍼빌리티를 찾고, 이를 정확히 합성한 다음 얇은 인터프리터를 구현하고 법칙을 점검합니다.
```

표시적 설계는 완성된 코드를 설명하는 데만 쓰기보다 반복 가능한 개발 규율로 사용할 때 가장 유용합니다.

## 핵심 작업 흐름 {#the-core-workflow}

새 기능이나 리팩터링을 할 때:

1.  의미론적 변화를 한 문장으로 명시합니다.
2.  기반 집합과 관찰 가능한 동등성을 파악합니다.
3.  필요한 기본 케이퍼빌리티를 최소한으로 찾습니다.
4.  명시적인 케이퍼빌리티를 바탕으로 파생 동작을 정의합니다.
5.  관계를 정확히 나타내는 합성 형태를 선택합니다.
6.  여러 해석이 구조를 필요로 하는 경우에만 일차 프로그램으로 재구화합니다.
7.  얇은 구체 인터프리터를 구현합니다.
8.  법칙이나 공유 시나리오를 추가합니다.
9.  대안적 해석을 검증합니다.
10.  구현 장치보다 의미를 먼저 문서화합니다.

## 의미론적 변화를 명시하기 {#state-the-semantic-change}

부정확한 설명:

> 캐시와 매니저 메서드를 추가합니다.

의미 중심 설명:

> 한 번의 컴파일 동안 변경 불가능한 같은 소스 이름을 확인하면 항상 같은 소스 값이 나옵니다.

두 번째 문장은 후보 법칙을 드러냅니다. 캐싱은 나중에 선택할 수 있는 구현 방법일 뿐입니다.

## 기본 경계 찾기 {#find-the-primitive-boundary}

다음 질문을 하세요:

*   새로 필요한 관찰이나 변환은 무엇인가요?
*   이 경계에서 기본 연산인가요, 기존 의미에서 도출할 수 있나요?
*   새로운 연관 기반 집합이 필요한가요?
*   의존성이라고 여긴 것이 실제로는 저장 위치일 뿐인가요?
*   어떤 구분을 보이지 않게 해야 하나요?

정말 새로운 기본 의미일 때만 케이퍼빌리티를 추가하세요.

## 합성을 정확히 선택하기 {#choose-composition-truthfully}

이 의사결정 표를 사용하세요:

| 질문 | 선택 |
| --- | --- |
| 수신자 하나가 필요한 모든 의미를 해석하나요? | 직접 바운드 |
| 동작을 독립적으로 선택하나요? | 명시적 정책 값 |
| 정책들을 독립적으로 합성하나요? | 곱 |
| 환경이 다른 인터프리터를 포함하나요? | 투영 |
| 래퍼가 내부 인터프리터를 대체해야 하나요? | 위임 |

큰 컨텍스트 트레이트를 기본 해법으로 도입하지 마세요.

## 한 번에 의미 하나씩 리팩터링하기 {#refactor-one-meaning-at-a-time}

기존 코드가 표현 우선 방식이라면:

1.  의미론적 관찰 하나를 파악합니다.
2.  작은 케이퍼빌리티 하나를 정의합니다.
3.  도출 하나를 확장으로 옮깁니다.
4.  현재 구조체는 인터프리터로 유지합니다.
5.  법칙을 확인하는 테스트 하나를 추가합니다.

```admonish warning title="표시적 설계는 추상화를 최대화하는 방법이 아닙니다"
추측에 기반한 추상화로 하위 시스템 전체를 다시 작성하지 마세요. 표시적 설계는 추상화를 최대화하는 방법이 아닙니다.
```

## 의미에서 구현 장치 방향으로 검토하기 {#review-from-meaning-to-machinery}

다음 순서로 코드를 읽으세요:

1.  케이퍼빌리티 트레이트
2.  의미 타입
3.  파생 확장
4.  존재한다면 일차 프로그램 구문
5.  공유 법칙과 시나리오
6.  구체 인터프리터
7.  런타임 오케스트레이션

가장 큰 상태 구조체부터 살펴보면 표현 방식에 치우쳐 검토하게 됩니다.

## 흔한 실패 유형 {#common-failure-modes}

````admonish warning title="트레이트 형태를 띤 구체 상태는 표시적 설계가 아닙니다"
```rust,noplayground
trait ContextAlg {
    fn state(&self) -> &ConcreteState;
}
```

트레이트를 도입해 구문만 바꾸고 의미의 소유권은 바꾸지 않은 경우입니다. 의미론적 핵심은 여전히 구체 표현에 의존합니다.
````

### 인터프리터마다 파생 로직 구현 {#derived-logic-in-every-interpreter}

모든 구현이 같은 도메인 알고리즘을 각자 정의한다면 명세가 중복된 것입니다.

### 만능 케이퍼빌리티 {#god-capability}

무관한 연산을 담은 상위 트레이트는 의존 관계를 감추고 독립적인 해석을 막습니다.

### 프레임워크가 소유한 명세 {#framework-owned-specification}

경로 어노테이션이나 RPC 등록이 유일한 인터페이스 정의라면 문서와 실행이 서로 달라질 수 있습니다.

### 매크로가 소유한 의미 {#macro-owned-meaning}

생성 코드에 공개된 일차 대상이 없으면 매크로 확장이 의도치 않게 명세가 됩니다.

### 기본값에 숨긴 정책 {#policy-hidden-in-defaults}

`Default`가 정족수, 재시도, 순서, 컴파일 정책을 소리 없이 선택한다면 합성이 더 이상 명시적이지 않습니다.

### 비공개 단계 테스트 {#tests-of-private-steps}

필드 배치나 순회 순서에 결합된 테스트는 유효한 대안 인터프리터를 막습니다.

## Pull Request 점검표 {#pull-request-checklist}

### 의미 {#meaning}

*   의미론적 변화를 명시했나요?
*   기반 집합과 동등성이 명확한가요?
*   의도적인 생략을 밝혔나요?

### 케이퍼빌리티 {#capabilities}

*   각 트레이트가 일관된 기본 의미를 드러내나요?
*   연산이 사용하는 곳에 바운드를 두었나요?
*   파생 코드가 구체 필드를 피하나요?

### 합성 {#composition}

*   직접 바운드, 정책, 곱, 투영, 위임을 정확히 사용했나요?
*   의미론적 기본값을 명시했나요?

### 프로그램과 인터프리터 {#programs-and-interpreters}

*   다른 해석이 필요할 때만 일차 구조를 도입했나요?
*   편의 매크로가 공개 프로그램 값으로 낮춰지나요?
*   구체 인터프리터가 얇고 경계에 맞게 구성되었나요?

### 증거 {#evidence}

*   법칙이나 집중된 의미 단언이 있나요?
*   다른 인터프리터에서 같은 시나리오를 실행할 수 있나요?
*   유한 테스트를 증명이 아니라 증거로 기술했나요?

## ALUX식 코드를 읽을 때 {#reading-alux-style-code}

다음과 같은 큰 구조를 알아보세요:

1.  작은 기본 케이퍼빌리티 트레이트
2.  명시된 바운드를 사용하는 파생 확장
3.  검사나 합성에 필요할 때 구성하는 일차 프로그램
4.  공유 법칙과 시나리오
5.  구체적인 런타임, 컴파일러, HTTP, RPC, 저장소 인터프리터

큰 동시성 시스템에는 오케스트레이션이 많은 영역도 있습니다. 기존 인터페이스가 모두 이상적인 표시적 명세라고 단정하지 마세요. 의미론적 접점을 찾고 거기서 바깥쪽으로 읽으세요.

Tolang은 언어 규모에서 같은 관점을 사용합니다. 구문은 의미를 담는 형식으로 정규화되고, 컴파일은 그 의미를 보존하며, 동시성 런타임은 실행 가능한 표현을 해석합니다. 작동 방식도 여전히 중요하지만 의미론적 계약 다음에 옵니다.
