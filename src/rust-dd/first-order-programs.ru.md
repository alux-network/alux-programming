```admonish note title="Когда реифицировать применение функции"
Обычные функции и методы-расширения уже позволяют выражать производное поведение. Представляйте применение функции данными первого порядка только тогда, когда другому интерпретатору нужно исследовать, компоновать, сериализовать или компилировать программу до её выполнения.
```

Обычные функции и методы-расширения обычно лучше всего выражают производное поведение. Иногда другому интерпретатору нужно исследовать, объединить, описать, сериализовать или скомпилировать структуру программы до применения функции. Тогда само применение функции должно стать данными первого порядка.

## Выполнение стирает структуру {#execution-erases-structure}

Рассмотрим следующий пример:

```rust,noplayground
#[ext(name = StatusExt)]
pub impl<This> This
where
    This: StatusAlg,
{
    async fn status_current(&self) -> This::Status {
        self.status().await
    }
}
```

Вызов этого метода возвращает статус. После начала вызова внешний интерпретатор обычно уже не может восстановить:

*   тип семантического контекста
*   порядок аргументов
*   имена исходных аргументов
*   тип результата
*   идентичность операции

Эта информация была в типе функции на уровне исходного кода, но обычное выполнение её поглощает.

## Дефункционализация приложения {#defunctionalizing-application}

Дефункционализация заменяет функцию из известного семейства функций данными первого порядка — меткой и общей операцией применения.

Минимальный словарь операций:

```rust,noplayground
trait OperationAlg {
    type Context;
    type Args;

    const ARG_NAMES: &'static [&'static str];
}

trait ApplyAlg<Handle, Args> {
    type Output;

    async fn apply(&self, handle: Handle, args: Args) -> Self::Output;
}
```

Значение нулевого размера `CurrentStatusOperation<App>` может обозначать применение исходного метода-расширения. Оно должно вызывать этот метод, а не содержать его вторую копию.

1.  Начните с метода-расширения.
2.  Представьте его как тип операции.
3.  Сохраните контекст, произведение аргументов, имена аргументов и результат.
4.  Интерпретируйте его с помощью `ApplyAlg`.

Метод остаётся удобным для обычных вызовов. Значение операции нужно тем контекстам, которым требуется структура первого порядка.

## Не реифицируйте без потребителя {#do-not-reify-without-a-consumer}

Программы первого порядка добавляют типовые механизмы. Используйте их, когда они обеспечивают реальную вторую интерпретацию:

*   регистрация во время выполнения
*   генерация документации или схемы
*   статический анализ
*   композиция программ до выполнения
*   сериализация
*   компиляция

Если коду нужно только вызвать функцию, оставьте её функцией.

## Переносимые интерфейсные программы {#portable-interface-programs}

Предположим, интерфейс HTTP содержит:

| Метод | Путь | Входные данные | Операция | Выходные данные |
| --- | --- | --- | --- | --- |
| `GET` | `/status` | — | `status_current` | JSON |
| `POST` | `/set_temperature` | Тело: `f32` | `adjust_status` | JSON |
| `GET` | `/download` | — | `current_file` | Потоковый файл |

Переносимая программа должна сохранять:

*   селекторы метода и пути
*   роли входных данных: путь, запрос, тело, заголовок и аутентификация
*   значение операции
*   роль результата, например JSON или файл
*   слияние и вложенность маршрутов

Ей не следует сохранять типы запроса, маршрутизатора или ответа конкретного фреймворка.

Например, можно использовать такую цепочку вызовов:

```rust,noplayground
self.routes()
    .get("/status", self.op(CurrentStatusOperation::<App>::default()).json())
    .post("/set_temperature", self.op(AdjustStatusOperation::<App>::default()).body::<f32>().json())
    .get("/download", self.op(CurrentFileOperation::<App>::default()).file())
```

Вызовы в цепочке строят типизированную программу. Они не обязаны сразу регистрировать маршрут сервера.

## Одна программа, несколько свёрток {#one-program-several-folds}

Одну и ту же программу первого порядка можно интерпретировать по-разному:

| Программа | Интерпретации |
| --- | --- |
| Типизированная программа HTTP | Текстовая документация, исполняемые маршруты, метаданные OpenAPI, привязки клиента, тесты на соответствие |
| Типизированная программа JSON-RPC | Реестр методов, схема, клиент, тестовая среда |

Не поддерживайте отдельные списки маршрутов или методов для выполнения и документации: это приводит к конкурирующим спецификациям.

## Роли входных и выходных данных {#input-and-output-roles}

Операция уже знает типы аргументов и результата. Объявление транспорта должно добавлять только смысл транспорта.

```rust,noplayground
self.op(FindOperation::<App>::default())
    .path::<u64>()
    .query::<String>()
    .json()
```

`path`, `query` и `json` задают роли. Не заставляйте автора повторно указывать тип результата, который уже определяется через `ApplyAlg`.

Преобразование результата относится к транспортному интерпретатору. Сервер может преобразовать один результат в JSON, а другой — в потоковое вложение. Семантические операции не должны знать ни о том, ни о другом представлении.

## Композиция — часть смысла программы {#composition-is-program-meaning}

Программы должны поддерживать общие операции композиции:

*   Пустая программа
*   Слияние программ
*   Вложение программы под префикс
*   Добавление конечной точки в программу

Это фундаментальнее методов маршрутизатора конкретного фреймворка. Привычные цепочечные имена, например `get`, `post`, `merge` и `nest`, могут быть псевдонимами для нейтральной алгебры.

Независимые спецификации могут публиковать небольшие программы:

| Входные программы | Композиция | Результат |
| --- | --- | --- |
| Программы статуса и загрузки | Слияние | Программа сервиса |
| Каталожная программа | Вложение | Программа сервиса |

Приложение выбирает и интерпретирует полученную композицию.

## Макросы должны сводиться к публичному смыслу {#macros-must-lower-to-public-meaning}

Макросы Rust могут упростить объявления первого порядка:

```rust,noplayground
#[ext(name = StatusApiExt, defunc(via = http))]
pub impl<This> This
where
    This: HttpApiAlg + JsonOutAlg,
{
    fn status_api<Alg>(&self)
    where
        Alg: StatusAlg,
    {
        self.routes().get("/status", self.op(Alg::status_current).json());
    }
}
```

Макрос хорош только тогда, когда преобразует объявление в публичную программу первого порядка, которую можно создать вручную. Сгенерированные обратные вызовы не должны становиться единственным определением интерфейса.

Предпочтительное направление:

1.  Удобный синтаксис
2.  Публичные значения операций и программ
3.  Обобщённая свёртка
4.  Конкретный фреймворк

Направление от представления:

1.  Аннотация фреймворка
2.  Непрозрачные сгенерированные обратные вызовы
3.  Документация, восстановленная обратным анализом

## Связь с существующими понятиями {#relation-to-existing-concepts}

Программы интерфейсов первого порядка опираются на методы из других глав: дефункционализация — это общее преобразование; расширяемый синтаксис и интерпретации относятся к проблеме выражения; свободная монада — лишь один конкретный вариант представления синтаксиса с последовательностью операций. Ссылки «Связанные материалы» вверху страницы ведут к каждому из этих разделов.

Не отождествляйте эти методы с самим денотационным проектированием. Оно определяет важную структуру; представления первого порядка сохраняют её, когда обычные вызовы стирают её.

## Проверочные вопросы {#review-checks}

*   Требует ли реальный второй интерпретатор реификации?
*   Вызывает ли операция метод, заданный автором, вместо его дублирования?
*   Выводятся ли типы аргументов и результата из операции?
*   Добавляет ли транспортный синтаксис только транспортные роли?
*   Можно ли создать программу без вспомогательного макроса?
*   Интерпретируют ли среда выполнения и метаданные одну и ту же программу?
