# 語義優先的工作流程 {#a-meaning-first-workflow}

```admonish tip title="相關內容"
語義視角：[為何含義優先](../denotational-design/semantic-view.md)  
Rust 中的語義驅動設計：[能力代數](capability-algebras.md)、[派生含義與組合](derived-meaning.md)、[定律、場景與證據](laws.md)
```

```admonish note title="可重複的方法"
指稱設計是一套工作流程，而不只是對已完成程式碼的解釋：陳述語義變化，找出最小基本能力，如實組合它們，再實作輕量級直譯器並檢查定律。
```

指稱設計作為一種可重複的開發方法最有用，而不只是對已完成程式碼作出解釋。

## 核心流程 {#the-core-workflow}

開發新功能或重構時：

1.  用一句話說明語義變化。
2.  確定載體與可觀察等價關係。
3.  找出所需的最小基本能力。
4.  基於明確能力定義派生行為。
5.  選擇能如實表達關係的組合形式。
6.  只有當結構需要多種解釋時，才將程式具體化為一階資料。
7.  實作輕量級具體直譯器。
8.  新增定律或共享場景。
9.  驗證不同解釋。
10.  先記錄含義，再介紹機制。

## 陳述語義變化 {#state-the-semantic-change}

較弱的表述：

> 新增快取和管理器方法。

面向含義的表述：

> 在一次編譯期間，解析同一個不可變源名稱應指稱相同的源值。

第二種表述提出了一條候選定律。之後可以選擇快取作為一種實作方式。

## 找到基本邊界 {#find-the-primitive-boundary}

請思考：

*   需要哪種新的觀察或變換？
*   它在此邊界上是基本操作，還是可以由現有含義派生？
*   是否需要新的關聯載體？
*   所謂依賴是否只是儲存位置？
*   哪些區別應當不可見？

只有確實出現新的基本含義時，才新增能力。

## 如實選擇組合形式 {#choose-composition-truthfully}

使用以下決策表：

| 問題 | 選擇 |
| --- | --- |
| 一個接收者是否解釋了所有必需含義？ | 直接約束 |
| 行為是否獨立選擇？ | 顯式策略值 |
| 策略是否可以獨立組合？ | 乘積型別 |
| 環境是否包含另一個直譯器？ | 投影 |
| 包裝器是否必須替代內部直譯器？ | 委託 |

不要預設採用大型上下文 trait。

## 一次重構一種含義 {#refactor-one-meaning-at-a-time}

當現有程式碼採用表示優先設計時：

1.  確定一項語義觀察。
2.  定義一種小型能力。
3.  將一個派生操作移入擴充。
4.  保留當前結構體，將其作為直譯器。
5.  新增一項定律式測試。

```admonish warning title="指稱設計並非抽象至上"
避免將整個子系統重寫為缺乏依據的抽象。指稱設計並非抽象至上。
```

## 從含義到機制進行審查 {#review-from-meaning-to-machinery}

按以下順序閱讀程式碼：

1.  能力 trait
2.  語義值型別
3.  派生擴充
4.  一階程式語法（如有）
5.  共享定律與場景
6.  具體直譯器
7.  執行時編排

從最大的狀態結構體開始審查，會使審查偏向其表示。

## 常見失敗模式 {#common-failure-modes}

````admonish warning title="形似 trait 的具體狀態不等於指稱設計"
```rust,noplayground
trait ContextAlg {
    fn state(&self) -> &ConcreteState;
}
```

trait 改變了語法，卻沒有改變含義的歸屬。語義核心仍然依賴具體表示。
````

### 每個直譯器都重複派生邏輯 {#derived-logic-in-every-interpreter}

如果每個實作都獨立定義相同的領域演算法，就說明規範被重複了。

### 萬能能力 {#god-capability}

包含無關操作的超 trait 會掩蓋依賴關係，也會阻止獨立解釋。

### 規範由框架掌控 {#framework-owned-specification}

如果路由註解或 RPC 註冊是唯一的介面定義方式，文件與執行就可能出現偏差。

### 含義由宏掌控 {#macro-owned-meaning}

如果生成程式碼沒有公開的一階目標，宏展開就會意外成為規範。

### 策略隱藏在預設值中 {#policy-hidden-in-defaults}

如果`Default`悄然選擇了法定人數、重試、順序或編譯策略，組合就不再是顯式的。

### 測試私有步驟 {#tests-of-private-steps}

與欄位佈局或遍歷順序耦合的測試，會妨礙有效的替代直譯器。

## Pull Request 檢查清單 {#pull-request-checklist}

### 含義 {#meaning}

*   是否陳述了語義變化？
*   載體與等價關係是否明確？
*   是否指出了有意忽略的內容？

### 能力 {#capabilities}

*   每個 trait 是否都表達了連貫的基本含義？
*   約束是否放在操作實際使用它們的位置？
*   派生程式碼是否避免存取具體欄位？

### 組合 {#composition}

*   是否如實使用直接約束、策略、乘積型別、投影與委託？
*   語義預設值是否明確？

### 程式與直譯器 {#programs-and-interpreters}

*   是否只在另一種解釋確有需要時才引入一階結構？
*   便捷宏能否降解為公開的程式值？
*   具體直譯器是否足夠輕量且限定在特定邊界內？

### 證據 {#evidence}

*   是否提供了定律或針對性的語義斷言？
*   同一場景能否在另一個直譯器上執行？
*   是否將有限測試描述為證據，而非證明？

## 閱讀 ALUX 風格的程式碼 {#reading-alux-style-code}

需要識別的整體結構是：

1.  小型基本能力 trait
2.  基於明確約束的派生擴充
3.  僅在檢查或組合需要時引入一階程式
4.  共享定律與場景
5.  具體的執行時、編譯器、HTTP、RPC 或儲存直譯器

大型併發系統仍然包含許多需要編排的區域。不要假定所有現有介面都是理想的指稱規範。尋找語義上的銜接點，並從這些位置向外閱讀。

Tolang 在語言層面採用相同視角：語法會正規化為承載含義的形式，編譯會保留這些含義，併發執行時則會解釋可執行表示。操作層面的描述仍然至關重要，但它應當位於語義契約之後。

## 最終原則 {#final-principle}

不確定時，回到一個問題：

```admonish quote title="應當反覆思考的問題"
這些機制本應保留什麼含義？
```

這個問題不能解決所有工程難題，但能讓問題在正確的層次上顯現出來。
