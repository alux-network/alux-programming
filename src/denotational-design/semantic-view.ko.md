# 왜 의미가 먼저인가 {#why-meaning-comes-first}

![The semantic view — choosing what a program means before how it runs](/semantic-view.png)

```admonish tip title="관련 항목"
의미론적 관점: [표시와 합성성](denotations.md), [표시적 설계](design.md)  
Rust에서 의미로 설계하기: [케이퍼빌리티 대수](../rust-dd/capability-algebras.md)  
개념: [소개](../concepts/index.md)
```

```admonish note title="개요"
표시적 설계에서는 프로그램의 의미를 먼저 정한 다음, 그 의미를 보존하도록 어휘, 표현, 실행 전략을 도출합니다. 이 페이지에서는 대부분의 소프트웨어가 따르는 표현 우선 순서와 이러한 의미론적 순서를 대조합니다.
```

대부분의 소프트웨어는 실행될 순서에 맞춰 설계됩니다:

1.  상태를 선택합니다.
2.  제어 흐름을 선택합니다.
3.  그 장치에 맞춰 메서드를 노출합니다.
4.  메서드가 무엇을 의미하도록 의도했는지는 나중에 설명합니다.

표시적 설계는 그 순서를 뒤집습니다:

1.  의미를 선택합니다.
2.  의미의 합성 구조를 파악합니다.
3.  그 구조에서 어휘를 도출합니다.
4.  표현과 실행 전략을 선택합니다.
5.  그 표현과 전략이 의미를 보존하는지 검증합니다.

이러한 역전이 의미론적 관점입니다.

```admonish quote title="구현 장치와 의미"
[개념](../concepts/index.md)과 [통찰](../insights/index.md)은 유용한 프로그래밍 장치를 설명합니다. [표시적 설계](design.md)는 어떤 장치가 무엇을 보존해야 하는지 결정하는 방법을 설명합니다.
```

## 세 가지 질문 {#three-questions}

프로그램을 설계할 때는 세 가지 질문을 구분하세요.

| 관점 | 질문 | 일반적인 산출물 |
| --- | --- | --- |
| 의미론적 | 이 프로그램은 무엇을 의미하는가? | 값, 관계, 함수, 등식, 법칙 |
| 표현적 | 그 의미는 어떻게 인코딩되는가? | Rust 타입, 트레이트, AST, 테이블, 트리, 바이트코드 |
| 작동적 | 그 표현은 어떻게 실행되는가? | 루프, 변경, 태스크, 메시지, 인터프리터, 가상 머신 |

세 관점은 모두 중요합니다. 표현이나 실행이 의미론적 관점을 소리 없이 정의하도록 두는 것이 문제입니다.

작동적 의미론은 실행을 정확하고 가치 있게 설명합니다. 평가기가 수행하는 모든 전이를 기술할 수 있습니다. 그러나 표시적 설명과는 다른 설계 질문에 답합니다. 표시적 관점에서 묻는 것은 프로그램 전체가 나타내는 관찰 가능한 수학적 값이 무엇인지, 그리고 실행 전략과 무관하게 어떤 등식이 성립해야 하는지입니다.

## 간단한 예 {#a-small-example}

분기 구조에서 위치를 식별하는 시스템을 생각해 봅시다.

표현 우선 설계는 비트 벡터에서 시작할 수 있습니다:

```rust,noplayground
struct BranchId(Vec<bool>);
```

그런 다음 필드에 맞춰 메서드가 늘어납니다. 비트 추가, 접두부 자르기, 벡터 비교, 바이트 직렬화 등이 그 예입니다.

의미론적 관점은 다른 곳에서 시작합니다:

*   루트 위치가 있습니다.
*   위치는 왼쪽이나 오른쪽으로 확장할 수 있습니다.
*   한 위치가 다른 위치의 조상일 수 있습니다.
*   조상과 자손 사이의 경로를 관찰할 수 있습니다.

표현이 나중에 정수, 트리 좌표, 압축 하이브리드 값, 데이터베이스 키로 바뀌더라도 이러한 설명은 여전히 의미가 있습니다. 비트 벡터는 분기 위치를 해석하는 한 가지 방법일 뿐, 그 정의 자체는 아닙니다.

## 의미는 사후 문서화가 아닙니다 {#meaning-is-not-documentation-after-the-fact}

구체적인 API를 설명하는 글을 쓴다고 설계가 표시적이 되는 것은 아닙니다. 표현을 선택하기 전에 의미가 API를 제약해야 합니다.

의미론적 설명은 다음을 알려야 합니다:

*   어떤 구분이 중요한지
*   어떤 관찰이 원시적인지
*   더 큰 의미가 어떻게 합성되는지
*   어떤 등식이 유효한지
*   모든 구현이 무엇을 보존해야 하는지
*   어떤 세부 사항을 의도적으로 버리는지

정확한 산출물이 상태 구조체나 실행 루프뿐이라면, 의미는 여전히 구현에 좌우됩니다.

## 추상화와 의미 {#abstraction-versus-meaning}

````admonish warning title="컨텍스트 트레이트는 의미를 정의하지 않습니다"
인터페이스는 의미를 설명하지 않은 채 구현 장치를 감출 수 있습니다:

```rust,noplayground
trait ApplicationContext {
    fn database(&self) -> &Database;
    fn settings(&self) -> &Settings;
    fn runtime(&self) -> &Runtime;
}
```

이 인터페이스는 구체적인 구성 요소에 대한 접근을 추상화합니다. 계산에 필요한 의미론적 관찰을 명시하지는 않습니다.
````

````admonish success title="의미를 직접 묻기"
의미 중심 인터페이스는 관찰 자체를 요청합니다:

```rust,noplayground
trait BranchAlg {
    type Branch;

    fn branch_root(&self) -> Self::Branch;
    fn branch_grow(&self, branch: &Self::Branch, direction: Direction) -> Self::Branch;
    fn branch_path(
        &self,
        ancestor: &Self::Branch,
        descendant: &Self::Branch,
    ) -> Option<Vec<Direction>>;
}
```
````

의존성 역전은 유용하지만 표시적 설계는 더 많은 것을 요구합니다. 추상화 경계는 저장 위치가 아니라 의미를 중심으로 구성해야 합니다.

## 권한의 방향 {#the-direction-of-authority}

산출물들이 서로 다를 때 실행 코드에 가장 가까운 것에 권위를 주지 마세요. 각 산출물이 무엇을 보존해야 하는지 물으세요.

| 역할 | 여기에 속하는 것 | 책임 |
| --- | --- | --- |
| **의미** | 해당 영역에서 의도한 관찰, 구분, 등식 | 정확성의 의미를 결정합니다 |
| **명세** | 의미론적 영역, 표시, 타입, 기본 연산, 법칙, 파생 합성 | 그 의미를 정확하게 기술합니다 |
| **실현** | 구체적 표현, 인터프리터, 컴파일러, 런타임, 저장소, 스케줄링 | 명세를 바꾸지 않고 구현합니다 |
| **증거** | 증명, 법칙 검사, 시나리오, 인터프리터 간 비교 | 실현을 명세와 연결하지만, 그 자체로 의미를 정의하지는 않습니다 |

이 구분은 의견이 다를 때 해결하는 실용적인 규칙을 제공합니다:

*   구현이 의미론적 법칙을 위반하면 구현을 고칩니다.
*   테스트가 검사하려던 법칙과 모순되면 테스트를 고칩니다.
*   형식 명세가 의도한 영역의 의미를 표현하지 못하면 명세를 수정합니다.

산출물은 문법이 아니라 역할에 따라 분류합니다. Rust 트레이트나 일차 프로그램은 선택한 의미 구조를 직접 보존한다면 명세에 속할 수 있고, 다른 Rust 타입은 하나의 구체적인 인코딩일 수 있습니다. 형식적 작동 의미론도 언어 명세의 일부일 수 있지만, 그 전이 역시 언어가 의도한 관찰 및 동치 관계에 부합해야 합니다.

이제 CPS, 디펑셔널라이제이션, 자유 모나드, 가상 머신, 프로토콜 런타임, 컴파일러 파이프라인 중 무엇이 최종 추상화인지 따지지 않고도 각각을 제자리에 둘 수 있습니다. 이들은 특정 사용자를 위한 유용한 표현 또는 실행 기법입니다. 의미론적 명세는 선택된 모든 기법이 무엇을 보존해야 하는지 알려줍니다.
