# 定律與解釋 {#laws-and-interpretations}

```admonish tip title="相關內容"
語義視角：[指稱設計](design.md)  
Rust 中的語義驅動設計：[定律、場景與證據](../rust-dd/laws.md)、[直譯器與效應](../rust-dd/interpreters.md)  
概念：[分支與合流](../concepts/branching.md)
```

```admonish note title="核心思想"
定律說明語義介面中的操作如何相互關聯；解釋則指定必須保留這些定律的具體載體。所選等價關係決定直譯器之間哪些差異有意義，哪些差異可以自由變化。
```

語義介面為操作命名，定律說明這些操作之間的關係。沒有定律時，兩個實作可以滿足相同的 Rust 函式簽名，卻對抽象的含義各執一詞。

## 定律補全詞彙 {#laws-complete-the-vocabulary}

對於分支位置，有用的定律包括：

$$ \begin{aligned} \operatorname{path}(b,b) &= \lbrack\,\rbrack \\ \operatorname{path}(\operatorname{root}, \operatorname{from\_path}(d_s)) &= d_s \\ \operatorname{from\_path}(\operatorname{path}(\operatorname{root},b)) &= b \\ \operatorname{is\_ancestor}(b,b) &= \mathsf{true} \\ \operatorname{left}(b) &\ne \operatorname{right}(b) \end{aligned} $$

這些定律所說明的內容，遠超方法註釋。它們描述了單位元、重構、自反性與分離性。

並非每個看起來合理的等式都有效。例如，定寬表示可能在深度極大時溢位。這可能是：

*   直譯器在其適用域之外的限制
*   介面必須暴露的語義錯誤
*   所選載體有誤的證據

設計必須說明屬於哪一種。

## 解釋 {#interpretation}

**解釋**為語義代數指定具體載體與操作。

| 語義程式 | 可能的解釋 |
| --- | --- |
| 分支位置 | 位路徑、數值樹、符號形式 |
| 表示式程式 | 求值器、漂亮列印器、最佳化器 |
| 型別化 API 程式 | 可執行的伺服器路由、文件、客戶端生成器 |

同一個程式可以有多種解釋，因為程式並不等同於某一種結果。

## 實作義務 {#implementation-obligations}

直譯器必須保留規範所聲稱的結構。

如果語義程式中的合併滿足結合律：

$$ (a \oplus b) \oplus c = a \oplus (b \oplus c) $$

那麼直譯器就應當保留這種結合方式的可觀察含義。如果路由順序也有規範要求，等價關係就必須包含順序。如果有意忽略順序，實作可以在操作層面不同，但仍保持語義等價。

因此，必須先選定語義域與等價關係，再編寫定律。

## 定律、證明與測試 {#laws-proofs-and-tests}

這些術語不能互換：

*   **定律**是抽象所普遍要求的性質。
*   **證明**在給定假設下確立某條定律。
*   **性質測試**檢查大量生成的示例。
*   **場景測試**檢查一個有意義的有限情境。
*   **單元測試**檢查一種具體行為。

測試是可執行的證據，而非普遍證明。它們仍然很有價值，因為可以用來檢查每個直譯器。

## 可執行證據 {#executable-evidence}

語義定律獨立於其實作。可執行檢查為直譯器是否保留這些定律提供有限證據：性質檢查用於考察類似等式的主張，場景則用於考察可觀察的互動。如果只使用語義操作來編寫，同一組證據就能在相容的直譯器之間複用。測試為規範提供支援，但不定義也不證明規範。

Rust 編碼方式見[《定律、場景與證據》](../rust-dd/laws.md)。

## 多個直譯器有助於澄清含義 {#multiple-interpreters-clarify-meaning}

並非每個小型 trait 都需要第二種實作，但第二種實作是一項有力的設計檢驗。

如果一條自稱抽象的定律只能用第一種實作的欄位來表述，那麼語義邊界很可能劃錯了。如果第二個直譯器無需模仿第一個表示，就能實作基本操作並滿足同一組定律，那麼這個抽象就更站得住腳。

中性直譯器尤其有用：

*   文字直譯器會揭示程式結構
*   純記憶體模型會隔離定律
*   追蹤直譯器會揭示選定的觀察
*   生產直譯器會執行真實效應

## 等價關係決定重構自由度 {#equality-determines-refactoring-freedom}

每一種語義等價都賦予實作一定自由。如果根據選定的指稱，兩個表示相等，實作就可以互換它們。

每一種被忽略的觀察也會帶來自由。如果分配順序不屬於語義，它就可以改變。如果方法順序屬於語義，就不能改變。

因此，定律不只是正確性約束。它們還界定了最佳化、替換與演進的安全空間。

## 檢查點 {#checkpoint}

繼續學習 Rust 編碼方式之前，請確認自己能回答：

1.  語義載體是什麼？
2.  抽象有意忽略了什麼？
3.  哪些操作是基本操作？
4.  哪些操作是派生操作？
5.  採用哪種等價關係？
6.  每個直譯器都必須保留哪些定律？
7.  哪些證據會在直譯器之間共享？

本書其餘部分將展示一種實用的 Rust 解法。它是這幅語義圖景的一種編碼，而非其替代品。
