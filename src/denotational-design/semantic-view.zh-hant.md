# 為何含義優先 {#why-meaning-comes-first}

![The semantic view — choosing what a program means before how it runs](/semantic-view.png)

```admonish tip title="相關內容"
語義視角：[指稱與組合性](denotations.md)、[指稱設計](design.md)  
Rust 中的語義驅動設計：[能力代數](../rust-dd/capability-algebras.md)  
概念：[簡介](../concepts/index.md)
```

```admonish note title="導讀"
指稱設計先確定程式的含義，再推導出詞彙、表示與執行策略，以保留該含義。本頁將這種語義順序與大多數軟體採用的表示優先順序作對比。
```

大多數軟體按照執行順序來設計：

1.  選擇狀態。
2.  選擇控制流。
3.  圍繞這些機制公開方法。
4.  事後再解釋這些方法原本意在表達什麼。

指稱設計將順序倒轉：

1.  選擇含義。
2.  確定其組合結構。
3.  從該結構推導詞彙。
4.  選擇表示與執行策略。
5.  驗證它們是否保留了原有含義。

這種倒轉就是語義視角。

```admonish quote title="機制與含義"
[概念](../concepts/index.md)與[洞見](../insights/index.md)用於說明實用的程式設計機制。[指稱設計](design.md)則說明如何判斷這些機制應當保留什麼。
```

## 三個問題 {#three-questions}

設計程式時，要把三個問題分開考慮。

| 視角 | 問題 | 典型產物 |
| --- | --- | --- |
| 語義 | 這個程式意味著什麼？ | 值、關係、函式、等式、定律 |
| 表示 | 這個含義如何編碼？ | Rust 型別、trait、抽象語法樹、表、樹、位元組碼 |
| 操作 | 這種表示如何執行？ | 迴圈、可變狀態、任務、訊息、直譯器、虛擬機器 |

這三種視角都很重要。錯誤在於讓表示或執行悄然替語義視角下定義。

操作語義對執行過程作出精確且有價值的說明。它可以描述求值器執行的每一次狀態轉換，但它回答的設計問題仍與指稱描述不同。指稱問題關注整個程式所指稱的可觀察數學值，以及無論採用何種執行策略都應成立的等式。

## 一個小例子 {#a-small-example}

假設某個系統要標識分支過程中的位置。

表示優先的設計可能從一個位向量開始：

```rust,noplayground
struct BranchId(Vec<bool>);
```

隨後，方法圍繞這些欄位不斷增加：追加一位、擷取字首、比較向量、序列化位元組。

語義視角從別處開始：

*   存在一個根位置。
*   位置可以向左或向右延伸。
*   一個位置可以是另一個位置的祖先。
*   可以觀察祖先與後代之間的路徑。

即便表示後來變成整數、樹座標、緊湊的混合值或資料庫鍵，這些陳述仍然有意義。位向量只是對分支位置的一種解釋，而不是它的定義。

## 含義不是事後補寫的文件 {#meaning-is-not-documentation-after-the-fact}

為具體 API 寫說明文字，並不會讓設計變成指稱式設計。含義必須先約束 API，然後才能選擇表示。

語義描述應當說明：

*   哪些區別很重要
*   哪些觀察是基本的
*   更大的含義如何組合
*   哪些等式有效
*   每種實作都必須保留什麼
*   哪些細節有意忽略

如果唯一精確的產物只是狀態結構體或執行迴圈，那麼含義仍由實作掌控。

## 抽象與含義 {#abstraction-versus-meaning}

````admonish warning title="上下文 trait 並不定義含義"
一個介面可以隱藏機制，卻不解釋含義：

```rust,noplayground
trait ApplicationContext {
    fn database(&self) -> &Database;
    fn settings(&self) -> &Settings;
    fn runtime(&self) -> &Runtime;
}
```

這個介面抽象了對具體元件的存取，但沒有說明計算所要求的語義觀察。
````

````admonish success title="直接詢問含義"
面向含義的介面會直接詢問所需的觀察：

```rust,noplayground
trait BranchAlg {
    type Branch;

    fn branch_root(&self) -> Self::Branch;
    fn branch_grow(&self, branch: &Self::Branch, direction: Direction) -> Self::Branch;
    fn branch_path(
        &self,
        ancestor: &Self::Branch,
        descendant: &Self::Branch,
    ) -> Option<Vec<Direction>>;
}
```
````

依賴倒置固然有用，但指稱設計要求更多：抽象邊界必須圍繞含義組織，而不是圍繞儲存位置。

## 權威的方向 {#the-direction-of-authority}

當各類產物彼此矛盾時，不要把權威交給最接近執行程式碼的那個。應當先問每個產物各自必須保留什麼。

| 角色 | 此處應包含什麼 | 職責 |
| --- | --- | --- |
| **含義** | 領域預期的觀察、區別與相等關係 | 決定正確性的含義 |
| **規範** | 語義域、指稱、型別、基本操作、定律與派生組合 | 精確陳述含義 |
| **實現** | 具體表示、直譯器、編譯器、執行時、儲存與排程 | 實作規範而不改變規範 |
| **證據** | 證明、定律檢查、場景與跨直譯器比較 | 將實現與規範關聯起來；它本身不定義含義 |

由此得到一條解決分歧的實用規則：

*   如果實作違反了語義定律，就修改實作。
*   如果測試與它原本要檢查的定律相矛盾，就修改測試。
*   如果形式規範未能表達預期的領域含義，就修訂規範。

產物應按其作用分類，而不是按其語法分類。Rust trait 或一階程式若直接保留了選定的語義結構，就可以屬於規範；另一個 Rust 型別則可能只是某種具體編碼。形式操作語義也可以屬於語言規範，但其中的狀態轉換仍須符合該語言所要求的觀察與等價關係。

CPS、去函式化、自由單子、虛擬機器、協議執行時和編譯器流水線，如今都可以放在適當的位置，而無須爭論哪一種才是最終抽象。它們各自是適用於特定使用者的表示或執行技術。語義規範說明每種選用的技術都必須保留什麼。
