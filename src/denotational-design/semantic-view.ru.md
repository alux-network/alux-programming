# Почему начинать нужно со смысла {#why-meaning-comes-first}

![The semantic view — choosing what a program means before how it runs](../assets/semantic-view.png)

```admonish tip title="Связанные материалы"

«Проектирование на основе смысла в Rust»: [Алгебры возможностей](../rust-dd/capability-algebras.md)  
«Понятия»: [Введение](../concepts/index.md)
```

```admonish note title="Обзор"
Денотационное проектирование сначала определяет смысл программы, а затем выводит из него словарь понятий, представление и стратегию выполнения, которые этот смысл сохраняют. На этой странице семантический порядок сопоставляется с порядком «сначала представление», которому следует большинство программных систем.
```

Большинство программ проектируют в том порядке, в котором они будут выполняться:

1.  Выбрать состояние.
2.  Выбрать поток управления.
3.  Определить методы вокруг этих механизмов.
4.  Затем объяснить, какой смысл предполагалось вложить в методы.

Денотационное проектирование меняет этот порядок на обратный:

1.  Определить смысл.
2.  Выявить его композиционную структуру.
3.  Вывести из этой структуры словарь понятий.
4.  Выбрать представления и стратегии выполнения.
5.  Проверить, что они сохраняют смысл.

Это и есть семантический взгляд.

```admonish quote title="Механизмы и смысл"
[«Понятия»](../concepts/index.md) и [«Идеи»](../insights/index.md) объясняют полезные механизмы программирования. [Денотационное проектирование](design.md) объясняет, как решить, что именно эти механизмы должны сохранять.
```

## Три вопроса {#three-questions}

При проектировании программы не смешивайте три вопроса.

| Взгляд | Вопрос | Типичные артефакты |
| --- | --- | --- |
| Семантический | Что означает эта программа? | значения, отношения, функции, уравнения, законы |
| Репрезентационный | Как закодирован этот смысл? | типы Rust, трейты, AST, таблицы, деревья, байткод |
| Операционный | Как выполняется это представление? | циклы, мутации, задачи, сообщения, интерпретаторы, виртуальные машины |

Важны все три взгляда. Ошибка — позволить представлению или выполнению незаметно определять семантический взгляд.

Операционная семантика даёт точное и ценное описание выполнения. Она может описывать каждый переход, выполняемый вычислителем. Но она отвечает на другой проектный вопрос, чем денотационное описание. Денотационный вопрос состоит в том, какому наблюдаемому математическому значению соответствует программа целиком и какие равенства должны выполняться независимо от стратегии выполнения.

## Небольшой пример {#a-small-example}

Предположим, система задаёт позиции в ветвящемся процессе.

Проектирование от представления может начаться с битового вектора:

```rust,noplayground
struct BranchId(Vec<bool>);
```

Затем вокруг полей появляются методы: добавить бит, взять префикс, сравнить векторы, сериализовать байты.

Семантический взгляд начинает с другого:

*   Есть корневая позиция.
*   Позицию можно продолжить влево или вправо.
*   Одна позиция может быть предком другой.
*   Можно наблюдать путь от предка к потомку.

Эти утверждения остаются осмысленными, даже если позднее представление станет целым числом, координатой дерева, компактным гибридным значением или ключом базы данных. Битовый вектор — одна из интерпретаций позиции в ветвлении, а не её определение.

## Смысл — не пояснение задним числом {#meaning-is-not-documentation-after-the-fact}

Описание конкретного API прозой само по себе не делает проектирование денотационным. Смысл должен ограничивать API до выбора представления.

Семантическое описание должно указывать:

*   какие различия важны
*   какие наблюдения являются первичными
*   как складываются более сложные значения
*   какие равенства верны
*   что обязана сохранять каждая реализация
*   какие детали намеренно опускаются

Если единственные точные артефакты — структура состояния или цикл выполнения, реализация по-прежнему задаёт смысл.

## Абстракция и смысл {#abstraction-versus-meaning}

````admonish warning title="Трейт контекста не определяет смысл"
Интерфейс может скрыть механизмы, не объясняя смысл:

```rust,noplayground
trait ApplicationContext {
    fn database(&self) -> &Database;
    fn settings(&self) -> &Settings;
    fn runtime(&self) -> &Runtime;
}
```

Этот интерфейс абстрагирует доступ к конкретным компонентам. Он не задаёт семантические наблюдения, необходимые вычислению.
````

````admonish success title="Запрашивать смысл напрямую"
Интерфейс, ориентированный на смысл, запрашивает само наблюдение:

```rust,noplayground
trait BranchAlg {
    type Branch;

    fn branch_root(&self) -> Self::Branch;
    fn branch_grow(&self, branch: &Self::Branch, direction: Direction) -> Self::Branch;
    fn branch_path(
        &self,
        ancestor: &Self::Branch,
        descendant: &Self::Branch,
    ) -> Option<Vec<Direction>>;
}
```
````

Инверсия зависимостей полезна, но денотационное проектирование требует большего: граница абстракции должна строиться вокруг смысла, а не места хранения.

## Кому принадлежит решающее слово {#the-direction-of-authority}

Если артефакты противоречат друг другу, не отдавайте решающее слово тому, который ближе всего к исполняемому коду. Спросите, что каждый артефакт обязан сохранять.

| Роль | Что относится к этой роли | Ответственность |
| --- | --- | --- |
| **Смысл** | Задуманные наблюдения, различия и равенства предметной области | Определяет, что считать корректностью |
| **Спецификация** | Семантические области, денотации, типы, примитивные операции, законы и производные композиции | Точно формулирует этот смысл |
| **Воплощение** | Конкретные представления, интерпретаторы, компиляторы, среды выполнения, хранение и планирование | Реализует спецификацию, не изменяя её |
| **Подтверждение** | Доказательства, проверки законов, сценарии и сравнения разных интерпретаторов | Связывает воплощение со спецификацией, но само по себе не определяет смысл |

Отсюда следует практическое правило разрешения разногласий:

*   Если реализация нарушает семантический закон, измените реализацию.
*   Если тест противоречит закону, который он должен проверять, измените тест.
*   Если формальная спецификация не выражает предполагаемый смысл предметной области, пересмотрите спецификацию.

Артефакт классифицируется по своей роли, а не по синтаксису. Трейт Rust или программа первого порядка могут относиться к спецификации, если напрямую сохраняют выбранную семантическую структуру; другой тип Rust может быть лишь одним конкретным способом кодирования. Формальная операционная семантика тоже может входить в спецификацию языка, но её переходы должны соответствовать наблюдениям и эквивалентностям, которые подразумевает язык.

Теперь CPS, дефункционализацию, свободные монады, виртуальные машины, среды выполнения протоколов и конвейеры компиляции можно рассматривать без вопроса, какой из них является окончательной абстракцией. Каждый из этих подходов — полезный способ представления или выполнения для определённых потребителей. Семантическая спецификация задаёт, что обязана сохранять каждая выбранная техника.
