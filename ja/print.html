    注記

    本書では、ALUXの意味を第一に考えるコードベースを理解し、開発に参加するための基礎を築きます。まず、Denotational Designの中心原則として、プログラムがどのように動くかを決める前に、プログラムが何を意味するかを定義します。

    Conal Elliottに倣い、計算を不透明な手順の列ではなく、明快な数学的対象として扱います。

    仕様は、プログラムが何を意味するかを記述する、単純で合成可能なケイパビリティのトレイトとして表します。インタープリターは、その意味を実現するための、互いに置き換え可能な方法を提供します。

    その結果、合成規則、実装上の責務、妥当な等式を把握し、テストしやすいソフトウェアになります。

    本書は次の三層に分けて読んでください。

    概要

    Denotational Designでは、まずプログラムの意味を定め、それを保つための語彙、表現、実行戦略を導きます。このページでは、この意味論的な順序と、多くのソフトウェアが従う表現先行の順序を対比します。

    多くのソフトウェアは、実行される順序で設計されます。

    1. 状態を選ぶ。
    2. 制御フローを選ぶ。
    3. その仕組みを囲むメソッドを公開する。
    4. そのメソッドが何を意味するはずだったのかを後から説明する。

    Denotational Designでは、この順序を逆にします。

    1. 意味を選ぶ。
    2. その合成構造を特定する。
    3. その構造から語彙を導く。
    4. 表現と実行戦略を選ぶ。
    5. それらが意味を保つことを検証する。

    この逆転が意味論的な見方です。

    仕組みと意味

    概念と洞察は、有用なプログラミングの仕組みを解説します。Denotational Designは、その仕組みに何を保持させるべきかを判断する方法を解説します。

    三つの問い

    プログラムを設計するときは、三つの問いを分けて考えます。

    観点問い典型的な成果物
    意味論このプログラムは何を意味するか。値、関係、関数、等式、法則
    表現その意味はどのように符号化されるか。Rustの型、トレイト、AST、テーブル、木構造、バイトコード
    操作その表現はどのように実行されるか。ループ、変更、タスク、メッセージ、インタープリター、仮想マシン

    三つの観点はどれも重要です。表現や実行に意味論的な見方を暗黙に定義させることが誤りです。

    操作的意味論は、実行を正確に記述する価値ある方法です。評価器が行うすべての遷移を記述できます。それでも、表示に基づく説明とは別の設計上の問いに答えています。表示に基づく問いは、プログラム全体がどの観測可能な数学的値を表すのか、そして実行戦略にかかわらずどの等式が成り立つべきか、というものです。

    小さな例

    分岐する過程の中の位置を識別するシステムを考えます。

    表現を先に考える設計では、ビットベクトルから始めるかもしれません。

    struct BranchId(Vec<bool>);

    すると各フィールドを中心に、ビットの追加、接頭部分の切り出し、ベクトルの比較、バイト列へのシリアライズといったメソッドが増えていきます。

    意味論的な見方では、別のところから始めます。

    • 根となる位置がある。
    • 位置は左または右へ伸ばせる。
    • ある位置が別の位置の祖先である場合がある。
    • 祖先と子孫の間の経路を観測できる。

    表現が後に整数、木の座標、コンパクトなハイブリッド値、データベースキーのいずれになっても、これらの記述は意味を保ちます。ビットベクトルは分岐位置の一つの解釈であり、その定義ではありません。

    意味は事後的なドキュメントではない

    具体的なAPIについて文章を書いても、設計が表示に基づくものになるわけではありません。表現を選ぶ前に、意味がAPIを制約しなければなりません。

    意味論的な説明では、次のことが分かる必要があります。

    • どの違いが重要か
    • どの観測が基本となるか
    • より大きな意味がどのように合成されるか
    • どの等式が妥当か
    • あらゆる実装が何を保持すべきか
    • どの詳細を意図的に捨てるか

    正確な成果物が状態構造体や実行ループしかないなら、意味を依然として実装が所有しています。

    抽象化と意味

    コンテキストのトレイトは意味を定義しない

    インターフェースは仕組みを隠せても、意味を説明するとは限りません。

    trait ApplicationContext {
    fn database(&self) -> &Database;
    fn settings(&self) -> &Settings;
    fn runtime(&self) -> &Runtime;
}

    このインターフェースは具体的なコンポーネントへのアクセスを抽象化しています。計算に必要な意味論的観測は述べていません。

    意味を直接問う

    意味を中心に据えたインターフェースは、観測そのものを求めます。

    trait BranchAlg {
    type Branch;

    fn branch_root(&self) -> Self::Branch;
    fn branch_grow(&self, branch: &Self::Branch, direction: Direction) -> Self::Branch;
    fn branch_path(
        &self,
        ancestor: &Self::Branch,
        descendant: &Self::Branch,
    ) -> Option<Vec<Direction>>;
}

    依存関係の逆転は有用ですが、Denotational Designではさらに、抽象化の境界を格納場所ではなく意味を中心に組織することが求められます。

    権限の所在

    成果物同士が食い違うとき、実行コードに最も近いものに権限を与えてはいけません。それぞれの成果物が何を保持する責務を負うのかを確認します。

    役割ここに含めるもの責務
    意味対象領域において意図された観測、区別、等値性正しさの意味を決める
    仕様意味論的領域、表示、型、基本操作、法則、導出される合成その意味を正確に述べる
    実現具体的な表現、インタープリター、コンパイラー、ランタイム、格納、スケジューリング仕様を変えずに実装する
    証拠証明、法則の検査、シナリオ、インタープリター間の比較実現と仕様を結び付ける。単独で意味を定義するものではない

    この区分から、意見が食い違ったときの実践的な規則が得られます。

    • 実装が意味論的な法則に違反するなら、実装を変更する。
    • テストが検証対象の法則と矛盾するなら、テストを変更する。
    • 形式仕様が意図された対象領域の意味を表現できていないなら、仕様を改訂する。

    成果物は構文ではなく役割で分類されます。選択した意味構造を直接保持するRustのトレイトや一階プログラムは仕様に含まれることがあります。一方、別のRust型は具体的な符号化の一つにすぎない場合があります。形式的な操作的意味論も言語仕様の一部になり得ますが、その遷移は、言語が意図する観測と等価性に従う必要があります。

    CPS、関数のデファンクショナライズ、自由モナド、仮想マシン、プロトコルランタイム、コンパイラーパイプラインを、どれが最終的な抽象化かと問わずに位置付けられるようになります。それぞれ特定の利用者に役立つ表現または実行技法です。意味論的な仕様が、選択したすべての技法に何を保持させるべきかを示します。

    中心となる考え方

    表示とは、構文から選択した意味論的領域への意味関数です。全体の意味が部分の意味によって定まるとき、その意味論は合成的です。これにより意味上の等値性と安全な置換が可能になります。

    表示とは、構文の一部またはプログラミング構成要素に割り当てられた意味です。通常、次のように表記します。

    [[e]]

    「式eの意味」を表します。

    この括弧は、表示が数値でなければならないという意味ではありません。意味論的領域によって、プログラムは次のものを表し得ます。

    • 値
    • 関数
    • 関係
    • 起こり得る結果の集合
    • 状態変換
    • 確率分布
    • プロセスの振る舞い
    • 部分的な結果

    したがって、最初の設計判断は「この値をどの構造体に保持させるか」ではありません。「必要な意味を含む意味論的領域は何か」です。

    意味論的領域

    算術式の場合、単純な領域として整数を選べます。

    [[e]]eval​∈Z

    書式設定では、同じ式言語をテキストとして解釈できます。

    [[e]]pretty​∈String

    副作用のある計算では、領域は状態変換かもしれません。

    [[p]]:State→Result×State

    並行言語では、領域はあらかじめ定められた一つのトレースではなく、観測可能なプロセスの振る舞いを記述する場合があります。

    選択した領域によって、どの差異に意味があるかが決まります。領域に時間が含まれなければ、実行時間の異なる二つの実装が同じプログラムを表すことがあります。リソース消費を含めた場合、同じ差異が意味論上の差異になることがあります。

    抽象化では意図的に情報を捨てる

    有用な表示は、関係のない機械上の詳細を捨てます。

    分岐位置の表示では、根からの経路を保持しつつ、次の情報を捨てる場合があります。

    • バイト配置
    • 割り当て方式
    • キャッシュの振る舞い
    • シリアライズ形式

    HTTPプログラムの移植可能な表示では、メソッド、パス、入力の役割、操作、出力の役割を保持しながら、どのルーターや実行器が処理するかを捨てることができます。

    コンパイラーステージの表示では、一時バッファーや走査順を捨て、正規化されたソースから実行可能な意味への変換を保持できます。

    情報を捨てることは欠陥ではありません。別の表現を等価とみなせるようにするものです。

    合成性

    全体の意味が部分の意味と、それらを組み合わせる方法によって定まるとき、意味論は合成的です。

    加算の場合：

    [[a+b]]=[[a]]+[[b]]

    関数の逐次合成の場合：

    [[g∘f]]=[[g]]∘[[f]]

    並列プロセス演算子の場合、意味論的領域には対応する並列合成が必要です。

    [[P∣Q]]=[[P]]⊗[[Q]]

    正確な演算子⊗は選択したプロセスモデルによって異なります。重要なのは、構文の合成が体系的に意味論上の合成へ対応することです。

    合成性が局所的な推論を可能にします。二つの部分の表示が同じなら、合成的な文脈では一方を他方で置き換えられます。

    [[P]]=[[Q]]⟹[[C(P)]]=[[C(Q)]]

    これが安全な置換と意味論に基づくリファクタリングの土台です。

    意味論的等値性

    プログラムは、テキスト上も操作上も同一でなくても、意味論的に等価であり得ます。

    分岐位置の二つの実装を考えます。

    [Left,Right,Left]

    そして同じ経路を表す整数による符号化を考えます。メモリー上の値は異なりますが、表示は等しい場合があります。

    同様に、二つのコンパイラーパスが異なる順序で構文を走査しても、指定された振る舞いが同じ実行可能ファイルを生成することがあります。バイト単位の一致が必要かどうかは、別途定めるより強い法則です。

    主張する等値性の種類は、必ず明示します。

    • 値の等価性
    • 構造的等価性
    • 正準表現の等価性
    • トレース等価性
    • 双模倣性
    • 観測的等価性
    • 表示の等値性

    これらの等値性を混同すると、誤った法則を立てることがよくあります。

    外部性は相対的

    ある計算が次の意味を持つとします。

    H×E→O

    Hに対して、証拠Eは外部にあります。新しい抽象化がH × Eを担体として選ぶと、その証拠は新たな境界の内部になります。

    この見方は、副作用やコンテキストに関わります。「環境に属する」事実というものが絶対的にあるわけではありません。現在の意味論的担体がその事実を含むか、そしてどの法則がそれを支配するかが問題です。

    万能なコンテキストオブジェクトを避ける

    この境界の問題を万能なコンテキストオブジェクトで解決しないでください。認められた各意味は、ケイパビリティまたは明示的な値として名付けます。

    基本的な意味と導出される意味

    基本操作とは、意味論的領域の語彙として選ばれた操作です。導出操作は、それらから定義されます。

    分岐位置の場合、小さな基本語彙として次のものが考えられます。

    • 根となる位置
    • 方向による拡張
    • ある位置から別の位置への経路の観測

    そこから次の操作を導出できます。

    • 左へ伸ばす
    • 右へ伸ばす
    • 経路から構築する
    • ある位置が別の位置の祖先かどうかを判定する
    • ある位置が別の位置の子孫かどうかを判定する

    この区別は設計上の選択であり、形而上学的な事実ではありません。法則と別の解釈を明確に述べられる、小さな基本操作の集合を優先してください。

    有用な確認方法

    プログラミングインターフェースを導入する前に、次の文を完成させます。

    • この抽象化の値が意味するのは……
    • 基本となる観測は……
    • 意味のある合成は……
    • 二つの値が等価なのは……の場合
    • すべての実装が保持しなければならないのは……
    • この抽象化が意図的に捨てるのは……

    これらの文を完成できないなら、不足している意味を実装の仕組みを増やして補うことはできません。

    中心となる考え方

    Denotational Designでは、単純で合成可能かつ実装に依存しない意味からプログラミングインターフェースを導きます。後付けでインターフェースを説明するのではなく、意味論を設計の指針とします。

    Denotational Designとは、単純で合成可能かつ実装に依存しない意味から、プログラミングインターフェースを導く実践です。

    この方法論はConal Elliottが開発し、命名しました。中心となるのは、既存の言語やAPIに意味論を割り当てることだけではありません。意味論をAPIそのものの設計指針にすることです。

    設計の反復手順

    次の順序で進めます。

    1. 意味論的領域を選ぶ。
    2. その領域で重要な構造を特定する。
    3. 基本操作の小さな語彙を選ぶ。
    4. 有用な操作を合成的に導出する。
    5. それらの操作が従う法則を述べる。
    6. 一つまたは複数の表現を選ぶ。
    7. 構造を保持する解釈を実装する。
    8. 法則、モデル、シナリオを使って妥当性を確認する。

    表現先行の設計では、一般に手順6から始め、後から手順1〜5を再構成しようとします。

    分岐代数を設計する

    分岐位置に戻りましょう。求める意味は、二分岐構造における有限経路です。

    基本代数の一例は次のとおりです。

    rootgrowpath​:()→Branch:Branch×Direction→Branch:Branch×Branch⇀List(Direction)​

    部分関数⇀は、最初の分岐が二つ目の祖先である場合にのみ、経路の観測が存在することを表します。

    ここから有用な操作を導けます。

    left(b)right(b)is_ancestor(a,b)from_path(ds​)​=grow(b,Left)=grow(b,Right)⟺path(a,b) is defined=fold(grow,root,ds​)​

    この代数は、ベクトル、整数、分数、データベースキー、バイト列に言及しません。そうした選択は後で行います。

    利便性より先に構造を定める

    基本語彙によって、下流のコードが依存する構造を明らかにします。一つの実装で利用できる便利なメソッドをすべて集めるのではありません。

    表現先行の基本操作を避ける

    このトレイトは、格納方法、設定の場所、ビット表現、複合ワークフローをひとまとめにしています。分岐の意味を切り分けていません。

    trait BranchManager {
    // not recommended: exposes machinery, not semantic observations
    fn storage(&self) -> &BranchTable;
    fn config(&self) -> &BranchConfig;
    fn raw_bits(&self) -> &[u64];
    fn grow_and_save(&mut self, right: bool);
}

    選択した領域に副作用が含まれるなら、意味論的APIにも副作用を含められます。「すべて純粋でなければならない」という規則ではありません。「基本操作はそれぞれ一貫した意味を述べなければならない」という規則です。

    符号化は方法論ではない

    Denotational Designが次のものを必須とするわけではありません。

    • Haskell
    • tagless-final符号化
    • オブジェクト代数
    • 自由モナド
    • 一つのAST
    • 純粋関数のみ
    • すべてのAPIに圏論の用語を使うこと

    これらは有用な符号化や説明手段になり得ますが、どれも方法論を定義するものではありません。

    Rustでの符号化

    Rustでは、小さなトレイト、関連型、拡張メソッド、ジェネリック関数、一階のプログラム値が実用的な符号化手段になります。その価値は、明確な意味論的設計を保てるかどうかで決まります。

    型クラスの準同型

    この方法を、構造を保つ写像として理解する方法があります。

    インターフェースが意味論的代数を記述するとします。実装は、その抽象値と操作を具体的な表現へ写像します。有効な実装は、関係する操作と法則を保持しなければなりません。

    encodeが抽象的な分岐を具体的な担体へ写像するとき、拡張を保持する性質は次のように表せます。

    encode(grow(b,d))=growconcrete​(encode(b),d)

    実装は、名前の一致するメソッドを集めただけのものではありません。代数構造を尊重する準同型として意図されています。

    優れた抽象化とは何か

    優れたDenotational Designの抽象化には、次のような性質があります。

    • 値が単純で意図の明確な意味を持つ。
    • 基本操作が意味論的な観測または構築を表す。
    • より大きな振る舞いが基本操作から導出される。
    • 法則が特定の表現に依存しない。
    • 独立した実装がそれを解釈できる。
    • 操作上の詳細は関係する場面でのみ現れる。

    小さいだけでは不十分です。get_manager()を公開する小さなトレイトでも、表現先行のままです。より大きな代数でも、各操作が一貫した意味論的構造を成すなら正当化できます。

    意味論的な値と抽象的な担体

    仕様に具体型を一切含めてはならないわけではありません。

    インタープリターに担体を選ばせる場合は、関連型を使います。

    trait BranchAlg {
    type Branch;
}

    安定した意味論上の語彙なら、具体型を使います。

    enum Direction {
    Left,
    Right,
}

    違いは「抽象が善で、具体が悪」ということではありません。意味論上の語彙か、偶然の機械表現かという違いです。

    仕様とは表示であり、実行可能である必要はない

    仕様とは表示、つまり各構成要素に割り当てられた数学的な意味です。その強みは、効率性や実行可能性にさえ縛られないことにあります。

    Conal Elliott

    表示を定義するほうが実装よりはるかに簡単で、理解も深まることがよくあります。効率性や実行可能性に伴う制約や雑音がないからです。

    — Denotational Design：意味からプログラムへ（LambdaJam 2015）

    典型例はFRP（関数型リアクティブプログラミング）です。Behavior aは連続時間の関数として定義されます。

    [[⋅]]:Behavior a→(R→a)

    そのモデルは正確ですが、実行できません。実数を列挙できないからです。同様に、プログラムが結果の集合を表す場合もあります。どちらのモデルも実行しませんが、それこそが要点です。計算方法ではなく、単純さと正確さを基準に意味を選びます。

    実行可能性と効率性は、意味に立ち返って正しさを保つ準同型の法則（型クラスの準同型）で制約された別個の成果物、実装に全面的に委ねられます。意味関数は、構文上の各合成を対応する意味論上の合成へ写さなければなりません。Conalの言葉を借りれば、表示によって「実装すべきものを曖昧さなく定義しつつ、実装方法には大きな創意工夫の余地を残せます」。

    Rustでは、この仕様の一部を複数の成果物で表現でき、その中には実行可能なものもあります。実行可能であることは付随的な性質であり、仕様である理由ではありません。

    • 文章は意図された意味を述べる
    • トレイトは利用可能な基本操作を述べる
    • 拡張は導出方法を述べる
    • 法則は要求される等式を述べる
    • インタープリターは実現可能性を示す
    • テストは有限の証拠を提供する

    具体的な仕組みよりも、意味と法則に権限を持たせて、これらを併せて読みます。

    中心となる考え方

    法則は意味論的インターフェースの操作同士の関係を述べ、解釈は具体的な担体を割り当てて、それらの法則を保持しなければなりません。選択した等値性によって、インタープリター間のどの差異に意味があり、どの差異が自由に変更できるかが決まります。

    意味論的インターフェースは操作に名前を付けます。法則は、それらの操作の関係を述べます。法則がなければ、二つの実装が同じRustのシグネチャを満たしながら、抽象化について異なる解釈をすることがあります。

    法則が語彙を完成させる

    分岐位置に関する有用な法則には、次のものがあります。

    path(b,b)path(root,from_path(ds​))from_path(path(root,b))is_ancestor(b,b)left(b)​=[]=ds​=b=true=right(b)​

    これらの法則は、メソッドコメント以上のことを説明します。恒等性、再構成、反射性、分離性を記述します。

    魅力的に見える等式がすべて妥当とは限りません。たとえば、固定幅の表現は極端に深い位置でオーバーフローすることがあります。それは次のいずれかです。

    • 許容された領域の外におけるインタープリターの制限
    • インターフェースで明示すべき意味論上の誤り
    • 選択した担体が適切でない証拠

    どれに当たるかを設計で示す必要があります。

    解釈

    解釈は、意味論的代数に具体的な担体と操作を割り当てます。

    意味論的プログラム考えられる解釈
    分岐位置ビット経路、数値による木構造、記号表現
    式プログラム評価器、整形表示器、最適化器
    型付きAPIプログラム実行可能なサーバールート、ドキュメント、クライアント生成器

    プログラムはどの結果とも同一ではないため、同じプログラムに複数の解釈を与えられます。

    実装上の責務

    インタープリターは、仕様が主張する構造を保持しなければなりません。

    意味論上のプログラムでmergeが結合的なら、次のようになります。

    (a⊕b)⊕c=a⊕(b⊕c)

    インタープリターは、その結び付け方が持つ観測可能な意味を保持する必要があります。ルートの順序も仕様で定めるなら、等値性に順序を含めます。順序を意図的に捨てるなら、実装上の振る舞いが異なっていても意味論的に等価な場合があります。

    そのため、法則を記述する前に意味論的領域と等値性を選ぶ必要があります。

    法則、証明、テスト

    これらの用語は同じ意味ではありません。

    • 法則とは、抽象化に普遍的に当てはまることを意図した性質です。
    • 証明とは、明示された仮定のもとで法則が成り立つことを示すものです。
    • プロパティテストは、生成した多数の例を検査します。
    • シナリオテストは、意味のある有限の状況を一つ検査します。
    • 単体テストは、具体的な振る舞いを一つ検査します。

    テストは実行可能な証拠であり、普遍的な証明ではありません。それでも、すべてのインタープリターで再利用できるため有用です。

    実行可能な証拠

    意味論的な法則は実装から独立しています。実行可能な検査は、インタープリターが法則を保持することの有限の証拠を示します。プロパティ検査は等式に似た主張を確かめ、シナリオ検査は観測可能な相互作用を確かめます。意味論的操作だけを使って書けば、互換性のあるインタープリター間で同じ証拠を再利用できます。テストは仕様を支えますが、定義したり証明したりするものではありません。

    Rustでの符号化は、法則、シナリオ、証拠で扱います。

    複数のインタープリターが意味を明確にする

    小さなトレイトすべてに二つ目の実装が必要なわけではありませんが、有力な設計検査になります。

    抽象的な法則とされるものを最初の実装のフィールドを使わないと述べられないなら、意味論的な境界が適切でない可能性があります。二つ目のインタープリターが最初の表現を模倣せずに基本操作を実装し、同じ法則を満たせるなら、その抽象化の信頼性は高まっています。

    中立的なインタープリターは特に有用です。

    • テキストインタープリターはプログラム構造を明らかにする
    • 純粋なインメモリモデルは法則を切り分ける
    • トレースインタープリターは選択された観測を明らかにする
    • 本番インタープリターは実際の副作用を実行する

    等値性がリファクタリングの自由度を決める

    あらゆる意味論的等値性が実装の自由度をもたらします。選択した表示で二つの表現が等しいなら、実装では一方を他方に置き換えられます。

    観測を一つ省くたびに自由度も得られます。割り当て順が意味論上の要件でなければ、変更できます。メソッド順が意味論上の要件なら、変更できません。

    したがって法則は、正しさの制約であるだけでなく、最適化、置換、進化を安全に行える範囲も定義します。

    Rustでの符号化に進む前に、次の問いに答えられることを確認します。

    1. 意味論的な担体は何か。
    2. 抽象化が意図的に捨てるものは何か。
    3. 基本操作はどれか。
    4. 導出される操作はどれか。
    5. どの等値性を使うか。
    6. すべてのインタープリターが保持すべき法則はどれか。
    7. どの証拠をインタープリター間で共有するか。

    本書の残りでは、Rustを使った実践的な答えを一つ示します。これは意味論的な構図の符号化であり、その置き換えではありません。

    依存型と証明

    意味論上の位置付け

    依存型は、型システムで値に応じた命題と証拠を表現します。意味論的仕様の一部を符号化できますが、仕様自体を選ぶものではありません。型に組み込む前に、意図する性質を明確にする必要があります。

    値で添字付けされた型

    値に応じて変化する型を依存型といいます。そのため依存型は、値の形だけでなく、その値が満たすべき関係も記述できます。

    例：

    • Vec<n, T> — 長さで添字付けされたベクトル n
    • Matrix<rows, cols, T> — 次元で添字付けされた行列
    • Proof<p> — 命題の証拠 p

    たとえば、次のようになります。

    append : Vec<n, T> -> Vec<m, T> -> Vec<n + m, T>

    結果の型は、長さnとmのベクトルを連結すると、長さn + mのベクトルができることを示しています。

    依存関数

    依存関数型は次のように書きます。

    Π(x:A).B(x)

    型Aの各値xに対して、結果の型はB(x)になります。次と比べてください。

    fg​:A→B:(x:A)→B(x)​

    fの結果型は固定です。gの結果型は入力によって変わることがあります。

    命題即型対応のもとでは、型で命題を述べ、その型を満たす項を証明として使えます。これにより、不正な状態、遷移、合成を構築できないAPIを実現できます。

    Denotational Designとの関係

    Denotational Designでは、まず次を問います。

    1. 意味論的領域は何か。
    2. 重要な観測と合成は何か。
    3. 満たすべき法則はどれか。

    依存型を使うと、これらの答えの一部を型の内部で表現できます。型の添字に、ベクトルの長さ、プロトコルの状態、スタックの深さ、リソース上限、二つの構成が同じ結果を表すことの証明などを記録できます。

    順序が重要です。高度な型を使っても、不足している意味は補えません。添字付きの命題が意図された意味論上の区別、または意図的に選んだ表現不変条件をすでに記述している場合に限り、仕様を強化できます。

    意味論的命題と表現不変条件を混同しない

    どちらも型に符号化できますが、権限の範囲は異なります。意味論的命題は、互換性のあるすべてのインタープリターで保持されなければなりません。表現不変条件が制約するのは、それを選んだ表現だけです。

    証明と実行可能な証拠

    証明は、明示された仮定のもとで命題が成り立つことを示します。プロパティテスト、シナリオテスト、単体テストは有限の実行可能な証拠を提供します。依存型に命題を符号化すれば、型検査で証明項を検証できる場合がありますが、テストが証明に変わるわけでも、コンパイラーが命題の出所になるわけでもありません。

    本書全体で使うのと同じ区分です。意味と法則が責務を述べ、ツールがそれを検査または実現します。

    このモデルをRustに適用する

    Rustは完全な依存型付き言語ではありませんが、constジェネリクス、typestate、関連型、トレイト境界によって有用な添字付き関係を表現できます。こうした符号化によって検査をコンパイル時に行え、多くの場合、効率的な具体表現を保てます。

    Rustで命題全体を表せない場合も、証明指向の考え方は有用です。不変条件を明示し、型システムで強制できる部分を符号化し、残りは法則やテストで検証します。符号化は仕様に役立つものであり、仕様を置き換えるものではありません。

    位置を型で添字付けした格子

    typed-grid-rsは、先ほどのMatrix<rows, cols, T>の考え方を安定版Rustで実現します。各セルは座標Pos0x0、Pos1x2などで添字付けされた型になり、移動すると別の位置型が返ります。

    Pos0x0.right()はPos1x0を表します。境界の外への移動は実行時エラーではありません。境界では該当する移動が生成されないため、型検査に通らないプログラムになります。

    これは、この節で説明した持ち上げと同じです。値の世界に置かれる座標を型へ昇格させ、有効な移動を全域的でコンパイル時に検査される関数にします。マーカー型はサイズがゼロなので、添字付き命題による実行時のコストはありません。

    概要

    ケイパビリティのトレイトは小さな代数です。必要な意味を表す基本的な観測と変換に名前を付け、表現の選択をインタープリターに委ねます。最初の実装がたまたま持つフィールドではなく、意味から語彙を設計します。

    Rustには「Denotational Design」という組み込み構文はありません。通常の言語機能で意味論上の語彙を符号化します。小さなケイパビリティのトレイトは、その有用な符号化の一つです。

    本書で接尾辞Algは代数を意味します。すなわち、インタープリターが選ぶ担体に対する、一貫した基本操作の集合です。

    意味から始める

    前のパートで扱った分岐位置の意味は、次のように表現できます。

    #[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum Direction {
    Left,
    Right,
}

pub trait BranchAlg {
    type Branch;

    fn branch_root(&self) -> Self::Branch;
    fn branch_grow(&self, branch: &Self::Branch, direction: Direction) -> Self::Branch;
    fn branch_path(&self, ancestor: &Self::Branch, descendant: &Self::Branch) -> Option<Vec<Direction>>;
}

    このトレイトは三つの基本的な意味を述べます。

    • 根を構成する
    • 一つの方向へ分岐を伸ばす
    • 経路が存在する場合に相対経路を観測する

    分岐をどこに格納するかや経路をどう符号化するかは明かしません。

    ケイパビリティはフィールド参照ではない

    フィールド参照は意味論的ケイパビリティではない

    次を比べてください。

    trait BranchContext {
    fn branches(&self) -> &Vec<Vec<bool>>;
    fn branches_mut(&mut self) -> &mut Vec<Vec<bool>>;
}

    このトレイトは構造体をメソッドの背後に隠していますが、表現を公開したままです。導出ロジックはベクトル、真偽値、所有権、変更方式に結び付いてしまいます。

    意味論的ケイパビリティは、下流の意味が必要とする観測や変換を公開します。次を考えてください。

    各ケイパビリティについて問う

    実装がデータベース、記号項、コンパクトな整数、リモートサービスのどれを使っていても、この操作には意味があるか。

    あるなら、その操作はケイパビリティに含められるかもしれません。呼び出し側が現在のフィールド配置を必要とするなら、含めないほうがよいでしょう。

    一つのトレイトにつき基本的な意味を一つ

    小さなトレイトは依存関係を見えるようにします。

    pub trait ClockAlg {
    type Instant;

    fn clock_now(&self) -> Self::Instant;
}

pub trait DeadlineAlg<Instant> {
    fn deadline_expired(&self, now: &Instant) -> bool;
}

    時間と期限を必要とする導出操作は、両方のトレイトを要求できます。ログ、格納、ネットワーク、設定、スケジューリングを含むApplicationContextを必要としません。

    「小さい」とは機械的にメソッドを一つだけにすることではありません。操作が分かちがたい一つの意味論的構造を成す場合はまとめます。独立した意味を表す場合や、別々に解釈できる場合は分けます。

    関連型で担体を選ぶ

    インタープリターが表現を選ぶときは関連型を使います。

    pub trait SourceAlg {
    type Source;
    type Error;

    fn source_read(&self, name: &str) -> Result<Self::Source, Self::Error>;
}

    この境界でString、std::io::Error、具体的な構文木が安定した意味論的語彙でない限り、それらを要求しないでください。

    一方、具体的な意味論的値を使うのは問題ありません。

    pub enum Severity {
    Warning,
    Error,
}

    規則は「すべての型を抽象化する」ことではありません。「インタープリターの仕組みと意味論的語彙を混同しない」ことです。

    境界は使う場所に置く

    基本操作には、必要のない制約を加えないでください。

    pub trait CandidateAlg {
    type Candidate;

    fn candidates(&self) -> impl Iterator<Item = Self::Candidate>;
}

    先回りして境界を追加しない

    将来のあるアルゴリズムが必要とするかもしれないというだけで、関連型に制約を加えないでください。

    pub trait CandidateAlg {
    // not recommended: every interpreter now pays for bounds
    // most operations never use
    type Candidate: Clone + Ord + Hash + Send + Sync;

    fn candidates(&self) -> impl Iterator<Item = Self::Candidate>;
}

    候補を並べ替える操作ではOrdが必要で、ハッシュ集合に入れる操作ではHashが必要になります。

    使用箇所に境界を置けば、基本的な意味を再利用しやすくなり、導出された振る舞いの実際の契約も明確になります。

    副作用も基本的な意味になり得る

    ケイパビリティのトレイトは純粋な実行を意味しません。

    pub trait PublishAlg {
    type Document;
    type Error;

    async fn publish(&self, document: Self::Document) -> Result<(), Self::Error>;
}

    公開処理は副作用です。それでも現在の境界では、基本的な意味論上の操作になり得ます。具体的なインタープリターはHTTP、キュー、ファイル、テスト用バッファーを使うかもしれません。

    意図された意味に含まれない限り、意味論的な層で再試行、ソケットの所有、タスクの起動、接続プールを規定すべきではありません。

    境界に名前を付ける

    ケイパビリティは、利用側の意味論的な視点から表現します。

    意味を中心にした名前表現を中心にした名前
    closed_outcome(slot)get_runtime_map(slot)
    source_read(name)compiler_context().sources().lookup(name)
    branch_path(ancestor, descendant)raw_branch_bits(id)

    命名も設計の一部です。機械的な名前は、機械的な結合を招きます。

    レビュー時の確認

    • このトレイトは一貫した基本的な意味を一つ公開しているか。
    • 独立したインタープリターが、最初の表現を複製せずに実装できるか。
    • インタープリターが実際に選ぶ場合に限って、関連型を抽象化しているか。
    • 具体型は安定した意味論的語彙か。
    • 操作が使うまで境界を加えていないか。
    • マネージャー、コンテキスト、生の格納領域を返していないか。

    Rustの意味論的型

    関連項目

    意味論的な見方：依存型と証明、Denotational Design
    Rustで意味から設計する：ケイパビリティ代数、一階プログラム、法則、シナリオ、証拠
    概念：参照透過性

    概要

    意味を第一に考えるRustでは、型を使って意味論的構造を見える状態に保ちます。関連型は担体の種類に名前を付け、境界は担体間の関係を述べ、拡張は明示した前提から新たな操作を導出します。すべての解釈で何を保持すべきかは、引き続き法則が定めます。

    Rustでは、役割の異なるものがいくつも同じtypeと書かれます。区別を保つことで、意味が表現に還元されるのを防げます。

    役割例表すもの
    意味論的型Directionどの領域上の区別が重要か
    インタープリターが選ぶ担体BranchAlg::Branchインタープリターが選択する表現
    導出操作BranchExt::branch_child宣言されたケイパビリティから得られるもの
    段階型Syntax, CoreProgram, Executable値にどの変換が適用されたか
    表現型BitBranch一つのインタープリターが分岐の意味をどう格納するか
    証拠プログラムシナリオまたは再利用可能な法則拡張互換性のあるインタープリターが満たすべき観測

    表現より先に意味論的な型を定める

    分岐を扱う領域で二つの方向を区別するとします。

    #[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum Direction {
    Left,
    Right,
}

    Directionはその区別を直接表します。一つのインタープリターでは、経路をコンパクトに符号化できます。

    struct BitBranch(Vec<bool>);

    真偽値はその表現に属します。左と右の定義ではなく、別のインタープリターが使う必要もありません。

    コンパクトな符号化は意味論的な型ではない

    ビット位置、バイトオフセット、機械上の分岐で領域の振る舞いを定義しないでください。それらは意味論上の区別を符号化するものであり、その区別を所有するものではありません。

    この分離により、格納方法や実行レイアウトを変えても、領域の意味を暗黙に変更せずに済みます。

    関連型で担体を選ぶ

    ケイパビリティ代数では、各インタープリターが担体を選べるようにします。

    trait BranchAlg {
    type Branch;

    fn branch_root(&self) -> Self::Branch;
    fn branch_grow(&self, branch: &Self::Branch, direction: Direction) -> Self::Branch;
    fn branch_path(
        &self,
        ancestor: &Self::Branch,
        descendant: &Self::Branch,
    ) -> Option<Vec<Direction>>;
}

    Self::Branchは隠されたフィールド型ではありません。分岐の意味を解釈する際に選ばれる担体です。ビット経路、数値で表す木の位置、記号項、その他の表現で同じ代数を満たせます。

    インタープリターTでは、T::Branchの記法を担体族Branch(T)として読めます。インタープリターを変えると担体も変わることがありますが、すべての操作は同じ選択に一貫して従います。

    拡張から結果を導く

    拡張では、必要な前提だけから新しい操作を構成できます。

    #[ext(name = BranchExt)]
pub impl<This> This
where
    This: BranchAlg,
{
    fn branch_child(
        &self,
        branch: &This::Branch,
        direction: Direction,
    ) -> This::Branch {
        self.branch_grow(branch, direction)
    }
}

    where節が前提です。つまり、Thisが分岐代数を解釈します。メソッドはそこから得られる結果で、そのインタープリターの担体について、分岐と方向から子分岐を決定できます。

    (T:BranchAlg)⟹branchChildT​:Branch(T)×Direction→Branch(T)

    この導出のどこにも、具体的な分岐表現を選ぶ処理はありません。結果は引き続きインタープリターが選んだ担体族に属します。

    等値性の境界で互換性を表す

    二つのケイパビリティで担体を一致させる必要が生じることがあります。関連型の等値性を使えば、具体的な表現を選ばずに要件を記述できます。

    Right: BranchAlg<Branch = Left::Branch>

    この境界は局所的な命題として読めます。LeftとRightは同じ担体上の分岐操作を解釈します。どちらかの代数に全体で強制するのではなく、その一致が必要な操作にこの等値性を置きます。

    こうした境界は、両方の実装をたまたま含むというだけで具体的なコンテキストを受け入れるよりも、強く正確です。

    段階型でコンパイラーの契約を見えるようにする

    コンパイラーパイプラインでは、すべての段階に同じ区別のない木を渡すべきではありません。各段階の型で、どの変換が行われたかを示します。

    段階入力出力契約
    構文解析ソーステキストSyntax表層文法を認識する
    正規化SyntaxCoreProgram選択した中核的な意味を生成する
    コード生成CoreProgramExecutable実行可能な形式でプログラムの観測を保持する
    ランタイムExecutable観測可能な振る舞い言語モデルに沿って実行可能コードを一貫して解釈する

    こうした型は段階の取り違えを防ぎますが、名前だけでは保持を証明できません。変換には明示された法則、代表的なシナリオ、インタープリター間の証拠が必要です。

    契約を読む

    型レベルの構造は、論理的には次のように読めます。

    Rustでの形式読み方
    This: BranchAlgThisは分岐の意味を解釈するものを与える
    This::Branch分岐の担体はThisによって選ばれる
    Right: BranchAlg<Branch = Left::Branch>二つの解釈で担体が一致する
    -> This::Branch結果は選択された担体族にとどまる

    この読み方を使うと、型を決定するもの、合成に必要な等値性、前提から導かれる結論をAPIに明示しやすくなります。根底の区別が実在する場合、関連型、ジェネリック関連型、constジェネリクス、typestate、サイズゼロの証明値はいずれも契約の一部を表現できます。

    実装を形式的に見せるだけの目的で、型レベルの仕組みを作り出さないでください。型が表すのは意味か、必要な関係であるべきであり、表現の飾りにしてはいけません。

    型は法則を置き換えない

    型シグネチャは、どのプログラムを構成できるかを制約します。法則は、その操作同士がどのように関係するかを制約します。両方が必要です。

    たとえば、BranchAlg::Branchは各インタープリターが分岐の担体を選ぶことを示します。それだけでは次のことは保証しません。

    • 分岐から同じ分岐への経路が空である
    • 根の経路を再生すると分岐が再構成される
    • 反対方向の子は互いに異なる

    これらは互換性のあるインタープリターが共有する意味論的法則です。未使用ビットがゼロであることなど、表現固有の主張は、その表現を選んだインタープリターに属します。

    型を主張として読む

    それぞれの型が何を主張し、何によって決まり、どの法則がその型を補い、どのインタープリターが実現するのかを確認します。

    レビュー時の確認

    • 領域上の区別を、コンパクトな機械表現より先に定めているか。
    • 関連型は、具体的な状態を偽装したものではなく、インタープリターが選ぶ担体か。
    • 等値性の境界は、その使用箇所で必要な互換性だけを述べているか。
    • コンパイラーの各段階に別々の型と明示的な契約があるか。
    • 意味論的命題と表現不変条件を分けているか。
    • Rustで表せない主張を、再利用可能な法則やシナリオで裏付けているか。

    導出される意味と合成

    関連項目

    意味論的な見方：Denotational Design
    Rustで意味から設計する：ケイパビリティ代数、インタープリターと副作用
    概念：Expression Problem

    概要

    導出された振る舞いは、それが使うケイパビリティに属します。境界を満たす拡張として一度だけ記述し、たまたまそれらを実装する具体型に持たせません。where節は、導出が依存するものを正確に表します。

    基本ケイパビリティは語彙を提供します。アプリケーションの振る舞いの大半は、その語彙から導出して、すべてのインタープリターで共有するべきです。

    導出は拡張に持たせる

    extendクレートを使うと、表現に依存せず分岐操作を導出できます。

    use extend::ext;

#[ext(name = BranchExt)]
pub impl<This> This
where
    This: BranchAlg,
{
    fn branch_child(&self, branch: &This::Branch, direction: Direction) -> This::Branch {
        self.branch_grow(branch, direction)
    }

    fn branch_left(&self, branch: &This::Branch) -> This::Branch {
        self.branch_child(branch, Direction::Left)
    }

    fn branch_right(&self, branch: &This::Branch) -> This::Branch {
        self.branch_child(branch, Direction::Right)
    }

    fn branch_is_ancestor(&self, ancestor: &This::Branch, descendant: &This::Branch) -> bool {
        self.branch_path(ancestor, descendant).is_some()
    }
}

    where節は意味論的な依存関係をすべて宣言します。BranchAlgだけで、それ以上はありません。これらの定義を所有する具体的な分岐型はありません。

    マクロが取り除くのは、トレイトや実装の定型コードだけです。通常の拡張トレイトでも同じ設計を表現できます。Denotational Designの要点は属性ではなく、意味論上の境界と導出にあります。

    なぜ構造体に持たせないのか。

    導出された意味を構造体に固定しない

    これは表現先行の設計です。数値による分岐の担体を導入すると、導出をコピーするか再実装することになり、最初の具体型が意図せず仕様になってしまいます。

    impl BitBranchStore {
    // not recommended: derived branch meaning welded to one bit representation
    fn is_ancestor(&self, a: &BitBranch, b: &BitBranch) -> bool {
        // derived branch meaning mixed with bit storage
    }
}

    拡張では所有関係を逆転させます。

    層責務
    意味論的ケイパビリティ導出される意味を所有する
    具体型基本的な意味を解釈する

    境界で合成する

    一つのレシーバーが複数のケイパビリティを解釈するなら、直接境界を使います。

    #[ext(name = PublishCurrentExt)]
pub impl<This, Document, Error> This
where
    This: DocumentAlg<Document = Document> + PublishAlg<Document = Document, Error = Error>,
{
    async fn publish_current(&self) -> Result<(), Error> {
        self.publish(self.document_current()).await
    }
}

    ケイパビリティをひとまとめにしない

    境界を短く書くためだけにスーパー トレイトを作らないでください。

    trait AppContext: DocumentAlg + PublishAlg {}

    ひとまとめにすると、どの操作がどのケイパビリティを使うかが見えなくなり、すべてのインタープリターが満たすべき別のインターフェースを生み出します。

    五種類の異なる合成上の意味

    関係を正確に表す形式を選びます。

    状況Rustでの形
    一つのレシーバーが複数のケイパビリティを解釈する直接境界
    別の値が振る舞いを選択する明示的なポリシー引数
    独立したポリシーを静的に合成するプロダクト型または通常の構造体
    環境が別のインタープリターを保持する小さなHasX射影
    ラッパーが内部のインタープリターを代用する委譲

    明示的なポリシー

    戦略を個別に選ぶなら、拡張に明示的に渡します。

    #[ext(name = CandidateSelectExt)]
pub impl<This> This
where
    This: CandidateAlg,
{
    fn select_with<Policy>(&self, policy: &Policy) -> This::Candidate
    where
        Policy: SelectionPolicyAlg<Candidate = This::Candidate>,
    {
        policy.select(self.candidates())
    }
}

    拡張が共通の導出を所有し、ポリシーは個別に選択する入力として残ります。環境内に隠すものでも、Defaultが選ぶものでもありません。

    ポリシーの積

    継承を作り出さずに、独立したポリシーを合成できます。

    struct CompilePolicy<Optimize, Diagnostics> {
    optimize: Optimize,
    diagnostics: Diagnostics,
}

    射影

    HasClockトレイトは、環境から独立した時計の値を射影できることだけを示します。

    trait HasClock {
    type Clock;

    fn clock(&self) -> &Self::Clock;
}

    時間を読む操作は、それ自身のThis::Clock: ClockAlg節にwhereを追加します。射影が表すのは包含関係であり、利用側の操作は必要なケイパビリティを明示します。この分離が実際に存在する場合に限り、このパターンを使います。フィールドを整理するためだけにHasXを導入してはいけません。

    委譲

    委譲とは、ラッパー自身が内部のインタープリターの代わりになれることです。透明なnewtype、共有ポインター、ケイパビリティの契約全体を保持するアダプターに適しています。

    射影は「持つ」を表し、委譲は「である」を表します。互いに置き換えられません。

    デフォルトも意味論上の判断

    機械的な空状態にはDefaultを実装できます。領域上のポリシーは、通常は明示します。

    有用なケースの多くは代数的に説明できます。デフォルトは、その型に自然な合成における単位元です。空バッファーの追加、空マップとの結合、診断のゼロ件の累積は、何も付け加えません。その合成が結合的なら、型と操作はモノイドを成し、Defaultはポリシーを選ぶのではなく中立元を表せます。

    適切なデフォルト：

    • 空バッファー
    • 空マップ
    • 累積された診断のゼロ件

    注意を要するデフォルト：

    • クォーラムの閾値
    • リーダーのポリシー
    • 再試行の意味
    • 確認の深さ
    • 出力形式

    重要なのは、中立元は判断を持ち込まない一方、クォーラム、リーダー戦略、再試行規則は領域の振る舞いを選ぶという違いです。デフォルトを変えると領域の意味が変わる場合は、ポリシーを明示的に合成してください。

    導出される意味は閉じたままにする

    拡張は宣言されたケイパビリティと明示的な入力だけを使わなければなりません。フィールドへの直接アクセス、グローバル状態、具体型へのダウンキャストがあると、where節が実態を表さなくなります。

    依存関係の宣言を証明するつもりで、本体を見直します。

    各導出を確認する

    この本体の各操作を、これらの境界から正当化できるか。

    できない場合は、境界が不足しているか、コードを別の層に置く必要があります。

    レビュー時の確認

    • 導出された振る舞いは、ケイパビリティに基づき一度だけ定義されているか。
    • 拡張は具体的なフィールドやコンテキスト型を避けているか。
    • 一つのインタープリターには直接境界を使っているか。
    • 個別に選ぶポリシーを、明示的な値として渡しているか。
    • 射影と委譲は正確な関係を主張しているか。
    • 領域のデフォルトを合成の中で見えるようにしているか。

    インタープリターと副作用

    関連項目

    意味論的な見方：法則と解釈
    Rustで意味から設計する：ケイパビリティ代数、法則、シナリオ、証拠
    概念：自由モナド
    洞察：EVM代数

    概要

    インタープリターは、ケイパビリティに対する表現または副作用を選びます。領域の振る舞いを再定義せずに基本操作を実現するため、その上にある導出の法則はすべてのインタープリターで成り立ちます。

    インタープリターは、意味論的ケイパビリティを具体的な表現または副作用によって実現します。領域の振る舞いを再定義せずに仕組みを選ぶべきです。

    薄いインタープリター

    分岐をビット経路で表現する例：

    #[derive(Clone, Debug, PartialEq, Eq)]
struct BitBranch(Vec<Direction>);

struct BitBranchImpl;

impl BranchAlg for BitBranchImpl {
    type Branch = BitBranch;

    fn branch_root(&self) -> Self::Branch {
        BitBranch(Vec::new())
    }

    fn branch_grow(&self, branch: &Self::Branch, direction: Direction) -> Self::Branch {
        let mut grown = branch.0.clone();
        grown.push(direction);
        BitBranch(grown)
    }

    fn branch_path(&self, ancestor: &Self::Branch, descendant: &Self::Branch) -> Option<Vec<Direction>> {
        descendant.0.strip_prefix(&ancestor.0[..]).map(<[Direction]>::to_vec)
    }
}

    実装は基本的な事実を格納して観測します。branch_left、branch_right、branch_is_ancestorは引き続き共有拡張に置きます。

    インタープリターは境界によって変わる

    同じ型が、ある境界ではインタープリターになり、別の境界では意味論上の入力になることがあります。

    境界利用するもの解釈するもの
    ファイルシステムアダプターファイルシステムへのアクセスソース検索
    正規化環境基本的なケイパビリティとしてのソース検索正規化された言語の構築
    コンパイラーパイプライン正規化された項実行可能な形式の構築

    万能な「実装層」はありません。意味論上の境界が入れ子になっています。

    境界で副作用を扱う

    具体的なインタープリターは、次のような選択を担います。

    • データベースのレイアウト
    • 非同期ランタイム
    • タスクの所有関係
    • 再試行戦略
    • HTTPまたはRPCフレームワークの型
    • シリアライズ
    • ロックとチャネル
    • キャッシュ

    呼び出し側が観測する必要のない限り、これらの選択を意味論的なトレイトに含めないでください。

    たとえば、意味論上のソースケイパビリティは、ソース値とエラーを返せます。本番インタープリターはファイルをキャッシュし、非同期に読み込むかもしれません。テスト用インタープリターは不変マップを使うかもしれません。導出された正規化ロジックは両方で動作するべきです。

    ランタイムの所有関係

    フレームワークのコールバックでは、状態の所有、複製可能性、スレッド安全性が要求されることがよくあります。それはインタープリター上の制約であり、必ずしも領域上の制約ではありません。

    基本操作にフレームワークの担体を混ぜない

    基本操作をフレームワークの担体で汚染しないでください。

    async fn status(data: FrameworkData<Arc<AppState>>) -> FrameworkJson<Status>;

    意味論的なアプリケーション処理を優先する

    trait StatusAlg {
    type Status;

    async fn status(&self) -> Self::Status;
}

    WebインタープリターはArc<Context>を選び、リクエストの入力を取り出し、statusを呼び出して結果を変換できます。領域の利用側は、Webサーバーの存在を知る必要がありません。

    中立的なインタープリター

    すべてのインタープリターが副作用を実行する必要はありません。

    APIプログラム用のテキストインタープリターは、次を記録できます。

    メソッドパス入力出力
    GET/status—JSON Status
    POST/temperatureJSON f32JSON Status

    メタデータインタープリターはドキュメントを構築できます。テスト用インタープリターは操作名を集められます。本番インタープリターはサーバールートを構築できます。

    中立的なインタープリターを使うと、プログラムが一つのランタイムに依存せず意味を持つことを示せます。

    委譲によるインタープリターの合成

    意味が小さなケイパビリティトレイトに置かれているため、インタープリターは通常、部品を組み立てて作り、各部を個別に記述しません。担体は、すでにケイパビリティを提供するものへ委譲することで、そのケイパビリティを得ます。転送コードは手書きせず生成します。ほぼすべてのケースを二つの形式で扱えます。

    フィールドへケイパビリティを転送する。 ambassadorの#[derive(Delegate)]はトレイト全体を内部値へ転送します。複数のコンポーネントを保持する担体では、各ケイパビリティをそれを所有するフィールドへ委譲し、転送用の本体を一切書かずに済みます。

    #[derive(Delegate)]
#[delegate(Clock, target = "clock")]
#[delegate(Logger, target = "logger")]
struct Service {
    clock: SystemClock,
    logger: StdoutLogger,
}

    getterを介してケイパビリティを与える。型にgetterを一つ持たせると、そのgetterを持つすべての型に包括実装でケイパビリティ全体を与えられます。

    trait Logger {
    fn log(&self, message: &str);
}

trait HasLogger {
    type Logger;

    fn logger(&self) -> &Self::Logger;
}

// Any carrier that can hand back a logger is itself a `Logger`.
impl<T> Logger for T
where
    T: HasLogger,
    T::Logger: Logger,
{
    fn log(&self, message: &str) {
        self.logger().log(message)
    }
}

    その結果、多くの構造体が不要になります。関連型と十数個のメソッドを持つ大きなトレイト一つと、その唯一の具体実装からなる一枚岩のコンテキストオブジェクトは、小さなケイパビリティトレイト群と、提供元のフィールドまたはgetterへ個別に委譲する薄い担体に置き換えられます。期限を過ぎたか調べるなどの導出操作は、担体ごとに再実装せず、基本操作を使う拡張として一度だけ記述します。

    委譲は操作を転送するもので、意味を転送するのではない

    委譲を生成すれば定型コードをなくせますが、意味論的に代用可能であるとは限りません。ambassadorのderiveのような#[derive(Delegate)]マクロが証明するのは、実装がコンパイルされることだけであり、その担体が同じインタープリターを表すことではありません。Shared<T>(Arc<T>)がTの代わりになるなら、担体上で法則を検査します。共有や同一性を変えるラッパー（Arc、プーリング、キャッシュ）は、すべてのメソッドを正しく転送していても、新鮮さや一意性に関する法則に違反することがあります。担体が無関係なサービスの一つとしてTを格納するだけなら、委譲より射影のほうが実態に即しています。

    エラーは境界に属する

    エラーは、それを処理する境界で失敗の意味を伝えるべきです。

    エラー境界での変換
    領域エラー通信インタープリターがプロトコル応答に変換する
    解析エラーコンパイラーのフロントエンドが診断に変換する
    格納エラーソースインタープリターが意味論上のソース取得失敗に変換する

    HTTPステータスコード、RPCエラーオブジェクト、データベースエラーを基本領域トレイトに押し込まないでください。インタープリターの境界で変換します。

    観測されない限り、性能は解釈上の課題

    バッチ処理、並列化、キャッシュ、データレイアウトは通常、インタープリターに属します。仕様が順序、時間、リソース使用、公平性、失敗の振る舞いを観測可能な形で保証する場合に限り、意味論上の要件になります。

    この分離により、意味を変えずに最適化できます。

    • 同じ法則
    • 同じ宣言済みの観測
    • 異なる操作戦略

    レビュー時の確認

    • インタープリターは導出を重複させず基本操作を実装しているか。
    • ランタイムとフレームワークの制約を、利用する境界に限定しているか。
    • 中立的なインタープリターやテスト用インタープリターで、同じケイパビリティを実装できるか。
    • 通信と格納のエラーを境界で変換しているか。
    • 委譲は意味論上も正確か。
    • 述べられた表示のもとで、性能差は観測できないものか。

    概要

    テストは仕様を裏付ける証拠です。非公開の実行手順ではなく、公開された観測と、選択した領域が支える法則を検査します。また、すべてのインタープリターに同じ要求を課せるよう、法則はケイパビリティに対してジェネリックに保ちます。

    意味を第一に考えるコードには、意味を第一に考えるテストが必要です。非公開の実行手順ではなく、公開された観測と法則をテストします。

    仕様の表面をテストする

    表現に結び付いたテスト

    このアサーションは一つの担体のフィールドを調べるため、ほかのインタープリターと共有できません。

    // not recommended: asserts a bit layout, not a semantic observation
assert_eq!(branch.bits, vec![false, true]);

    意味論的なテスト：

    let root = alg.branch_root();
let left = alg.branch_left(&root);
let left_right = alg.branch_right(&left);

assert_eq!(alg.branch_path(&root, &left_right), Some(vec![Direction::Left, Direction::Right]));

    ビット符号化を対象とするシリアライズモジュールなら、最初のテストが適切な場合もあります。しかし別の表現と共有できないため、分岐代数を裏付ける証拠としては弱いものです。

    再利用可能な法則拡張

    すべての互換インタープリターに当てはまる性質は、一度だけ記述します。

    use anyhow::{Result, bail, ensure};
use extend::ext;

#[ext(name = BranchLawsExt)]
pub impl<This> This
where
    This: BranchAlg,
    This::Branch: Clone + Eq,
{
    fn check_branch_root_round_trip(&self, directions: &[Direction]) -> Result<()> {
        let root = self.branch_root();
        let branch = directions.iter().copied().fold(root.clone(), |branch, direction| self.branch_grow(&branch, direction));

        let Some(path) = self.branch_path(&root, &branch) else {
            bail!("grown branch has no path from root");
        };
        ensure!(path == directions, "root path did not round-trip");
        Ok(())
    }
}

    すべてのインタープリターで同じチェッカーを実行します。anyhow::Resultは結果を運び、bail!は不足している観測を報告し、ensure!は往復法則を検査します。チェッカーは分岐表現に依存せず、二種類の失敗を区別します。

    有用な法則の類型

    意味論的な構造から導かれる性質を探します。

    • 恒等性
    • 結合性
    • 意図が真にある場合の可換性
    • 冪等性
    • 往復性
    • 正準化
    • 精緻化
    • 単調性
    • 置換
    • 解釈の一致

    領域が支える法則だけを主張する

    数学的に聞こえるからといって、馴染みのある代数用語を加えないでください。選択した領域が支える法則だけを述べます。

    法則と表現不変条件

    次のものを区別します。

    • 意味論的法則：根からの経路を使って分岐を再構成すると、同じ分岐を表す。

    • 表現不変条件：未使用の上位ビットはゼロである。

    • シリアライズ法則：

      decode(encode(b))=b

    • 正準形式の法則：

      encode(decode(x))=xfor canonical byte sequences x

    どれも重要な場合がありますが、別々の仕様に属します。

    共有シナリオ

    シナリオは、公開ケイパビリティに対して記述した、再利用可能な相互作用です。ALUXのテストフレームワークでは、シナリオの記述コードがScenario、DeployerIds、PlayAst、ScenarioScheduleのケイパビリティを使って値を構築し、具体的なランナー名を指定しません。

    #[ext(name = HelloScenarioExt)]
pub impl<This> This
where
    This: StandaloneScenario,
    This::Step: PlayAst<Ast = RProc>,
{
    fn hello(self) -> This::Scenario {
        self.scenario()
            .under_comprehensive(100)
            .step(
                self.play_ast(
                    self.deployer(0),
                    tolang! {
                        let x in {
                            x ! "hello" |
                            ? (a <- x) a.log()
                        }
                    },
                )
                .expect_log(r#""hello""#),
            )
    }
}

    各呼び出しは、ランナーの仕組みではなく記述された意味を表します。under_comprehensive(100)は、逐次実行100回、自由な並行実行100回、順列を変えた実行を最大100回行った場合に、期待するログが得られることを要求します。シナリオは観測内容を固定し、ランナーが実行順序を変えます。

    同じ原則はインタープリター間にも当てはまります。シナリオが使うケイパビリティを複数のランナーが実装するなら、同じ記述上の相互作用をそれぞれ解釈できます。ランナー固有の準備や境界の検査は、シナリオの外に置きます。

    インタープリター間の一致

    二つのインタープリターが同じ観測を公開するなら、比較します。

    interpret_text(p).route_names=interpret_server(p).registered_route_names

    こうすると、個別のスナップショットでは見つからないずれを検出できます。API定義、コンパイラーの各段階、代替データ表現で特に有用です。

    有限の証拠は証明ではない

    テストに合格しても、試した入力と実装で振る舞いが示されたにすぎません。すべての値について法則を証明するものではありません。

    意図的に確実性を高めます。

    1. 例示テスト
    2. 再利用可能なシナリオテスト
    3. 生成データを使うプロパティテスト
    4. 有限領域の網羅検査
    5. モデル比較
    6. 証明の成果物

    リスクと主張の強さに応じて水準を選びます。

    テスト名で意味を示す

    次のような名前を優先します。

    • reconstructs_every_generated_branch_from_its_root_path
    • preserves_child_programs_when_routes_are_merged
    • normalization_is_invariant_under_alpha_renaming

    実装手順を説明するだけの名前は避けます。

    • pushes_three_bits
    • calls_helper_twice
    • visits_left_node_first

    操作順そのものが仕様である場合、操作上のテストは有効です。その順序に意味が生じる観測を名前で示します。

    レビュー時の確認

    • 新たな意味論的操作ごとに、焦点を絞った法則またはアサーションがあるか。
    • 再利用可能な責務を公開ケイパビリティに対してジェネリックにしているか。
    • シナリオと具体的なランナーを分けているか。
    • 意味論的法則と表現不変条件を区別しているか。
    • 実用的な範囲で複数のインタープリターを比較しているか。
    • 有限テストを証明と呼ばないよう、ドキュメントで注意しているか。

    アプリケーションを再構化するとき

    通常の関数と拡張ですでに導出された振る舞いを表現できます。実行前に別のインタープリターがプログラムを検査、合成、シリアライズ、コンパイルする必要がある場合に限り、アプリケーションを一階データに変換します。

    通常の関数と拡張メソッドは、導出された振る舞いを表現するのに最適な方法です。プログラムを適用する前に、別のインタープリターがその構造を検査、結合、文書化、シリアライズ、コンパイルしなければならない場合もあります。そのときはアプリケーション自体を一階データにする必要があります。

    実行すると構造が消える

    次を考えてください。

    #[ext(name = StatusExt)]
pub impl<This> This
where
    This: StatusAlg,
{
    async fn status_current(&self) -> This::Status {
        self.status().await
    }
}

    このメソッドを呼び出すと状態が返ります。呼び出しが始まると、外部のインタープリターは一般に次の情報を復元できません。

    • 意味論的なコンテキスト型
    • 順序付きの引数
    • ソース上の引数名
    • 結果の型
    • 操作の識別情報

    その情報はソースレベルの関数型に含まれていましたが、通常の実行によって消費されます。

    アプリケーションをデファンクショナライズする

    デファンクショナライズでは、既知の関数族の要素を一階のタグと共有の適用操作に置き換えます。

    最小限の操作語彙は次のとおりです。

    trait OperationAlg {
    type Context;
    type Args;

    const ARG_NAMES: &'static [&'static str];
}

trait ApplyAlg<Handle, Args> {
    type Output;

    async fn apply(&self, handle: Handle, args: Args) -> Self::Output;
}

    サイズゼロのCurrentStatusOperation<App>は、元の拡張メソッドの適用を表せます。メソッド本体を二重に持つのではなく、そのメソッドを呼び出すべきです。

    1. 拡張メソッドから始める。
    2. それを操作型として再構化する。
    3. コンテキスト、引数の積、引数名、出力を保持する。
    4. ApplyAlgを通じて解釈する。

    通常の呼び出しでは、引き続き使いやすいメソッドを使えます。一階の構造を必要とする場面では、操作値を使います。

    利用側がないなら再構化しない

    一階プログラムを使うと型の仕組みが増えます。次のように、実際に二つ目の解釈が可能になる場合に使います。

    • ランタイム登録
    • ドキュメントまたはスキーマ生成
    • 静的検査
    • 実行前のプログラム合成
    • シリアライズ
    • コンパイル

    コードが関数を呼び出すだけなら、その関数のままにします。

    移植可能なインターフェースプログラム

    HTTPの表面に次が含まれるとします。

    メソッドパス入力操作出力
    GET/status—status_currentJSON
    POST/set_temperature本文：f32adjust_statusJSON
    GET/download—current_fileストリーミングファイル

    移植可能なプログラムは次を保持しなければなりません。

    • メソッドとパスの選択子
    • パス、クエリ、本文、ヘッダー、認証などの入力の役割
    • 操作値
    • JSONやファイルなどの出力の役割
    • ルートの結合とネスト

    特定のフレームワークのリクエスト、ルーター、レスポンス型は保持しないでください。

    たとえば、次のような流れる記法を使えます。

    self.routes()
    .get("/status", self.op(CurrentStatusOperation::<App>::default()).json())
    .post("/set_temperature", self.op(AdjustStatusOperation::<App>::default()).body::<f32>().json())
    .get("/download", self.op(CurrentFileOperation::<App>::default()).file())

    流れるように連ねた呼び出しは、型付きプログラムを構築します。サーバールートをただちに登録する必要はありません。

    一つのプログラムを複数のfoldで解釈する

    同じ一階プログラムで複数の解釈を実現できます。

    プログラム解釈
    型付きHTTPプログラムテキスト形式のドキュメント、実行可能なルート、OpenAPIメタデータ、クライアントバインディング、適合性テスト
    型付きJSON-RPCプログラムメソッド登録、スキーマ、クライアント、テストハーネス

    実行とドキュメントで別々のルート一覧やメソッド一覧を管理しないでください。仕様が競合します。

    入力と出力の役割

    操作はすでに引数型と結果型を認識しています。通信方式の宣言では、通信方式の意味だけを追加します。

    self.op(FindOperation::<App>::default())
    .path::<u64>()
    .query::<String>()
    .json()

    path、query、jsonは役割を示します。ApplyAlgによってすでに決まっている出力型を、記述者に重ねて書かせるべきではありません。

    出力変換は通信インタープリターに属します。サーバーは結果の一つをJSONに、別の結果をストリーミング添付ファイルに変換できます。意味論的な操作は、いずれの表現も意識しません。

    合成もプログラムの意味

    プログラムでは汎用的な合成を保持するべきです。

    • 空のプログラム
    • プログラムを結合する
    • プログラムを接頭辞の下にネストする
    • エンドポイントをプログラムへ持ち上げる

    これらは一つのフレームワークのルーターメソッドより基礎的な操作です。get、post、merge、nestのような馴染みのある流れる形式の名前も、中立的な代数の別名にできます。

    独立した仕様から、小さなプログラムを公開できます。

    入力プログラム合成結果
    状態取得とダウンロードのプログラム結合サービスプログラム
    カタログプログラムネストサービスプログラム

    アプリケーションが、結果の合成を選択して解釈します。

    マクロは公開された意味へ展開する

    Rustのマクロを使うと、一階宣言を簡潔に記述できます。

    #[ext(name = StatusApiExt, defunc(via = http))]
pub impl<This> This
where
    This: HttpApiAlg + JsonOutAlg,
{
    fn status_api<Alg>(&self)
    where
        Alg: StatusAlg,
    {
        self.routes().get("/status", self.op(Alg::status_current).json());
    }
}

    マクロが公開された手動構築可能な一階プログラムに展開される場合にのみ、適切に機能します。生成されたコールバックがインターフェースの唯一の定義になってはいけません。

    望ましい流れ：

    1. 簡潔な構文
    2. 公開された操作値とプログラム値
    3. ジェネリックなfold
    4. 具体的なフレームワーク

    表現先行の流れ：

    1. フレームワークの注釈
    2. 不透明な生成済みコールバック
    3. リバースエンジニアリングによるドキュメント

    既存概念との関係

    一階インターフェースプログラムは、ほかの章の技法を土台にしています。デファンクショナライズは一般的な変換であり、拡張可能な構文と解釈はExpression Problemに関わり、自由モナドは逐次合成を備えた構文表現の一種です。各項目はページ上部の関連リンクから参照できます。

    これらの技法とDDそのものを同一視しないでください。DDが重要な構造を定め、通常の呼び出しでは消えてしまう場合に、一階表現がその構造を保持します。

    レビュー時の確認

    • 実際に二つ目のインタープリターが必要であり、そのために再構化するのか。
    • 操作は記述されたメソッドを重複実装せず呼び出しているか。
    • 引数と出力は操作から推論されるか。
    • 通信方式の構文は、通信方式上の役割だけを追加するか。
    • 便利なマクロがなくてもプログラムを構築できるか。
    • ランタイムとメタデータは同じプログラムを解釈しているか。

    意味はパイプラインではない

    言語の意味をパーサー木、パス、バイトコード、機械ループと同一視しないほうが、コンパイラーは明確になります。正しさは、一つの可換法則で表せます。コンパイル済みプログラムを実行した結果が、そのプログラムの表示に一致することです。

    言語の意味をパーサー木、コンパイラーパス、バイトコード、仮想マシンループと同一視しないほうが、コンパイラーを推論しやすくなります。

    この章では、Tolangに似せた簡略化した並行言語を使い、意味論的なアーキテクチャに焦点を当てます。

    四つの異なる層

    これらの層を分けてください。

    1. ソース構文
    2. 正規化された言語
    3. 実行可能な表現
    4. 機械での実行

    典型的なパイプライン：

    ParseNormalizeCodeGenRun​:Source→Syntax:Syntax→Result(Core,Diagnostics):Core→Result(Executable,Error):Executable×RuntimeState→Observation​

    利便性のための操作は合成です。

    Compile=Parse;Normalize;CodeGen

    合成されたヘルパーが各段階の意味論的な定義になるわけではありません。

    構文はまだ意味ではない

    パーサーの出力は文法上の選択を反映します。

    • 句読点
    • 糖衣構文
    • 優先順位
    • ソース位置
    • 生成されたパーサー表現

    これらは診断やツールにとって重要ですが、中核言語を定義する必要はありません。

    正規化では、偶発的な構文上の違いを取り除き、意味を担うより小さな形式を導入します。たとえば、表層での複数の束縛形式を一つの中核的な制約操作に正規化できます。

    多数のソース形式 → 正規化後の一つの構成子

    こうすることで、後続するコンパイラーとランタイムの法則を述べる場所が一つに定まります。

    表示上の意味とコンパイル後の意味

    次のように置きます。

    [[−]]:Core→D

    意味論的領域Dで意味を割り当てる。

    コンパイルで実行可能な値を生成する。

    compile:Core→Executable

    実行時にそれらを観測する。

    run:Executable→D

    中心となる正しさの責務は可換図式です。

    run(compile(p))=[[p]]

    非決定的または並行システムでは、等値性に通常の値の一致ではなく、観測的等価性、結果集合、トレース等価性、双模倣性を使う場合があります。どれを使うかは意味論モデルで選びます。

    並行プロセスの意味

    基本となる反射計算には、次のような考え方が含まれます。

    0P∣Qx!(v)?(y←x) P​inactive processparallel compositionsend a value on a channelreceive a value and continue as P​

    Tolangは基本計算を合成的に拡張します。その拡張の一つは、次の表層形式を追加します。

    let x in Pfresh channel binding scoped over P.

    この束縛は新しいチャネルを作成し、その名前の有効範囲をP内に定めます。プロセス計算の文献では、この操作を制約と呼びます。反射的な中核には基本的な制約演算子はありません。MeredithとRadestockのA Reflective Higher-order Calculusを参照してください。

    操作機械では、タプル空間、キュー、照合用インデックス、継続レコード、並行タスクなどで実装できます。そうした仕組みが言語の定義になるわけではありません。

    意味論層では、観測可能なプロセスの振る舞いと構造法則を特定します。中核となる並列合成には、次の法則が候補となります。

    P∣0P∣Q(P∣Q)∣R​≡P≡Q∣P≡P∣(Q∣R)​

    新規束縛の拡張に関する法則は別途扱います。標準的な候補スキーマとして、α変換、異なる束縛の交換、有効範囲の押し出しがあります。

    let x in Plet x in (let y in P)let x in (P∣Q)​≡let y in P{y/x}≡let y in (let x in P)≡P∣(let x in Q)​​(y#P)(x=y)(x∈/FN(P))​

    ここでy#PはPに対してyが新鮮であること、P{y/x}は変数捕獲を避ける置換、FN(P)はPに含まれる自由なチャネル名の集合を表します。これらのスキーマが法則になるのは、選択した観測的等価性で妥当と認められる場合だけです。表層構文から自動的に前提したり、一つのバイトコードレイアウトから推論したりしてはいけません。

    意味を保持する写像としての正規化

    二つのソースプログラムs₁とs₂が、認められた糖衣構文だけで異なるなら、正規化によって共通の意味を明示できるべきです。

    s1​≡sugar​s2​⟹normalize(s1​)=normalize(s2​)

    ほかにも、次の責務が有用です。

    • α変換で正規化後の意味が保持される
    • 字句スコープで意図した束縛子が解決される
    • 診断に必要な場合にソース位置が保持される
    • コンパイル時定数が実行時の振る舞いなしに消去される
    • 不正な構文について、段階の契約に従って診断が蓄積される

    正規化後の値に正準形を求めるプロジェクトもあれば、意味論的等価性だけを求めるプロジェクトもあります。どちらかを明示します。

    段階のケイパビリティ

    万能なコンパイラーオブジェクトを作らない

    巨大なコンパイラーオブジェクトを、唯一の段階インターフェースにしてはいけません。

    正規化器には、次のようなケイパビリティが必要かもしれません。

    • 束縛スコープの読み取りと拡張
    • ソース名の解決
    • 診断の蓄積
    • 正規化された項の構築

    コード生成器には、次のものが必要かもしれません。

    • 実行可能参照の割り当て
    • 命令の出力
    • 正規化された変数の解決
    • 実行可能構造の確定

    各段階の入り口をケイパビリティ上の拡張として表します。具体的な環境はマップ、アリーナ、カウンター、診断を保持しますが、段階の意味を所有しません。

    #[ext(name = NormalizeEntryExt)]
pub impl<This> This
where
    This: BindingScopeAlg + DiagnosticAlg + NormalizeRecAlg,
{
    fn normalize(&mut self, syntax: &Syntax) -> Result<Core, BuildError> {
        // initialize the semantic stage and invoke recursive normalization
    }
}

    正確なケイパビリティ名はコンパイラーごとに異なります。重要なのは、依存関係が明示され、段階間の対応が安定していることです。

    パーサーとランタイムは操作的な設計のままでよい

    すべてのサブシステムに同じ符号化を無理に適用する必要はありません。

    パーサーは生成文法の仕組みが中心になることがあります。仮想マシンは効率的な変更とスケジューリングが中心になることがあります。十分に定義された境界を実装する限り、操作的な形のままで構いません。

    段階契約
    パーサーSyntaxを生成する
    正規化器意味を担うCoreを生成する
    コード生成器実行可能形式で意味を保持する
    ランタイム言語モデルと一貫した観測を生成する

    Denotational Designは機械を取り除くのではなく、機械が言語の意味論を暗黙に定めるのを防ぎます。

    コンパイラーの法則とテスト

    強い証拠は複数の方向から得られます。

    • 同等なソース形式に対する正規化法則
    • 意図する場合の構文解析と整形表示の往復
    • 直接的な意味評価とコンパイル後の実行の比較
    • 正準出力を保証する場合のバイトコード等価性
    • ランタイム適合性シナリオ
    • インタープリター間の差分テスト

    バイトの一致は意味の一致ではない

    バイト単位の一致と意味論的等価性を混同しないでください。正準コンパイルが仕様に含まれる場合に限り、バイト一致は有用な、より強い性質です。

    この内容が読者に与える準備

    意味を第一に考える言語実装を読むときは、次の点に注目します。

    • 意味論的構文またはケイパビリティトレイト
    • 導出される正規化操作
    • 明示的な段階契約
    • 一階の中核プログラム
    • 置換、スコープ、合成に関する法則
    • 段階のケイパビリティを解釈する薄い環境
    • 端に置かれた操作的なパーサー、コンパイラー、VMの仕組み

    この見方を使うと、一般的なDenotational DesignとTolangを結び付け、意味論上の境界が言語設計、コンパイル、ランタイム解釈をどう導くかを理解できます。

    中核となるワークフロー

    新機能やリファクタリングでは、次のように進めます。

    1. 意味論上の変更を一文で述べる。
    2. 担体と観測的等値性を特定する。
    3. 必要最小限の基本ケイパビリティを見つける。
    4. 明示したケイパビリティに基づいて導出された振る舞いを定義する。
    5. 実態に合った合成形式を選ぶ。
    6. 複数の解釈が必要な場合に限り、一階プログラムとして再構化する。
    7. 薄い具体インタープリターを実装する。
    8. 法則または共有シナリオを追加する。
    9. 代替解釈を検証する。
    10. 仕組みより先に意味を文書化する。

    意味論上の変更を述べる

    弱い説明：

    キャッシュとマネージャーメソッドを追加する。

    意味を中心にした説明：

    一度のコンパイル中に同じ不変ソース名を解決すると、同じソース値が得られる。

    二つ目の説明から、法則の候補が明らかになります。後でキャッシュを一つの実装として選ぶこともできます。

    基本となる境界を見つける

    次を問います。

    • どの新しい観測または変換が必要か。
    • この境界では基本操作なのか、既存の意味から導出できるのか。
    • 新しい関連担体が必要か。
    • 想定した依存関係は、単なる格納場所ではないか。
    • どの区別を見えないままにするか。

    本当に新しい基本的な意味がある場合だけ、ケイパビリティを追加します。

    実態に合わせて合成する

    次の判断表を使います。

    問い選択
    一つのレシーバーが必要な意味をすべて解釈するか。直接境界
    振る舞いを個別に選ぶか。明示的なポリシー値
    ポリシー同士は独立に合成できるか。積
    環境が別のインタープリターを含むか。射影
    ラッパーは内部のインタープリターを代用しなければならないか。委譲

    大きなコンテキストトレイトを既定の解決策として導入しないでください。

    一度に一つの意味をリファクタリングする

    既存コードが表現先行の場合：

    1. 意味論上の観測を一つ特定する。
    2. 小さなケイパビリティを一つ定義する。
    3. 導出を一つ拡張に移す。
    4. 現在の構造体はインタープリターとして維持する。
    5. 法則形式のテストを一つ追加する。

    DDは抽象化至上主義ではない

    推測上の抽象化を使ってサブシステム全体を書き直すことは避けます。DDは抽象化至上主義ではありません。

    意味から仕組みへ順にレビューする

    次の順にコードを読みます。

    1. ケイパビリティトレイト
    2. 意味論的な値の型
    3. 導出された拡張
    4. 存在する場合は一階プログラム構文
    5. 共有する法則とシナリオ
    6. 具体的なインタープリター
    7. ランタイムのオーケストレーション

    最大の状態構造体から読み始めると、表現に引きずられたレビューになります。

    よくある失敗

    トレイトの形をした具体状態はDenotational Designではない

    trait ContextAlg {
    fn state(&self) -> &ConcreteState;
}

    トレイトが構文を変えても、意味の所有関係は変わりません。意味論上の中核が、依然として具体的な表現に依存しています。

    各インタープリターに導出ロジックがある

    すべての実装が同じ領域アルゴリズムを個別に定義するなら、仕様を重複させています。

    万能ケイパビリティ

    無関係な操作を含むスーパー トレイトは依存関係を隠し、独立した解釈を妨げます。

    フレームワークが所有する仕様

    ルートの注釈やRPC登録だけがインターフェース定義だと、ドキュメントと実行がずれることがあります。

    マクロが所有する意味

    生成コードに公開された一階の受け皿がないなら、マクロの展開結果が意図せず仕様になってしまいます。

    デフォルトに隠れたポリシー

    Defaultがクォーラム、再試行、順序、コンパイルのポリシーを暗黙に選ぶなら、合成が明示的ではなくなります。

    非公開手順のテスト

    フィールド配置や走査順に結び付いたテストは、妥当な代替インタープリターを妨げます。

    • 担体と等値性が明確か。

    • 各トレイトが一貫した基本的な意味を公開しているか。
    • 操作が使う場所に境界を置いているか。
    • 導出コードが具体フィールドを避けているか。

    合成

    • 直接境界、ポリシー、積、射影、委譲を実態に合わせて使っているか。

    プログラムとインタープリター

    • 別の解釈が必要な場合に限って、一階構造を導入しているか。
    • 便利なマクロを公開されたプログラム値に展開できるか。

    証拠

    • 法則または焦点を絞った意味論的アサーションがあるか。
    • 同じシナリオを別のインタープリターで実行できるか。
    • 有限のテストを証明ではなく証拠として説明しているか。

    ALUX式コードを読む

    認識すべき全体像は次のとおりです。

    1. 小さな基本ケイパビリティトレイト
    2. 明示的な境界を使う導出拡張
    3. 検査や合成が必要な場合の一階プログラム
    4. 共有する法則とシナリオ
    5. 具体的なランタイム、コンパイラー、HTTP、RPC、格納用インタープリター

    大規模な並行システムにも、オーケストレーションが中心となる領域はあります。既存の各インターフェースがすでに理想的な表示仕様だと決め付けないでください。意味論上の継ぎ目を探し、そこから外側へ読み進めます。

    Tolangは、言語規模で同じ視点を用います。構文を意味を担う形式に正規化し、コンパイルでその意味を保ち、並行ランタイムで実行可能な表現を解釈します。操作上の説明も不可欠ですが、意味論上の契約を定めた後に続きます。

    概念と洞察は、有用なプログラミングの仕組みを解説します。Denotational Designは、その仕組みに何を保持させるべきかを判断する方法を解説します。

    2. どの観測と等値性を保持するか。

    定義

    操作的意味論は、評価判断または構成間の遷移によってプログラムの振る舞いを記述します。構成には、プログラム断片と環境、ストア、継続、その他の抽象機械状態を含める場合があります。

    この記述は数学的なもので、どの評価や遷移が妥当かを述べます。インタープリターや仮想マシンがその規則を実装することはありますが、特定の実装自体が定義になるわけではありません。

    意味論上の位置付け

    操作的意味論は正確な意味論であり、単なる非形式的な実装詳細ではありません。評価規則または遷移規則によって振る舞いを説明します。Denotational Designはそれを補う、より先行する設計上の問いを立てます。すなわち、どのような合成可能な意味と等式を、その規則に保持させるかです。

    操作的意味論の形式

    小ステップ意味論（構造的操作意味論）

    計算を原子的な遷移に分解します。

    2+3(2+3)⋅4​→5→5⋅4→20​

    並行性、インターリーブ、部分実行のモデル化に有用です。

    大ステップ意味論（自然意味論）

    最終結果を使って評価を記述する。

    (2+3)⋅4⇓20

    停止するプログラムについて推論する際に、明快なことが多い。

    形式規則

    操作的意味論は通常、推論規則で表されます。簡単な算術言語なら、次のようになります。

    E::=n∣E+E

    左から右への評価には、三つの規則が必要です。

    E1​+E2​→E1′​+E2​E1​→E1′​​n+E2​→n+E2′​E2​→E2′​​n1​+n2​→n3​where n3​=n1​+n2​

    最初の二つの規則は、次に簡約できる部分式を選びます。三つ目は、両方のオペランドが値になった後で加算を行います。

    評価トレース：

    (1+2)+3→3+3→6

    なぜ重要か

    • 実行について、機械を厳密に模したモデルを提供する。
    • インタープリターと仮想マシンの基盤となる。
    • 正しさ、リソース使用、安全性に関する推論を支える。

    ほかの概念との関係

    • 自由モナドは命令構文と逐次実行を提供します。その表現で書かれたプログラムの評価は、操作規則で記述できます。
    • CPSは、計算の残りを継続として明示します。値がその継続へ渡される様子は、操作規則で記述できます。
    • デファンクショナライズは既知の関数族を一階データに置き換え、apply操作を明示します。生成された機械状態は、操作規則で記述できます。

    これらは操作的意味論を与えられる対象や変換であり、それ自体が操作的意味論なのではありません。

    実践での利用

    操作規則を使うと、インタープリターを導き、照合のための厳密なモデルを提供できます。

    • EVMは小ステップの状態遷移系として自然にモデル化できます。一方、停止する実行全体は大ステップの判断でも関連付けられます。
    • 小ステップ規則は、Rustインタープリターのmatchアームとよく対応することがあります。

    enum Expr {
    Num(i64),
    Add(Box<Expr>, Box<Expr>),
}

fn step(expr: Expr) -> Option<Expr> {
    match expr {
        Expr::Num(_) => None,
        Expr::Add(left, right) => match (*left, *right) {
            (Expr::Num(a), Expr::Num(b)) => Some(Expr::Num(a + b)),
            (left @ Expr::Num(_), right) => step(right).map(|next| {
                Expr::Add(Box::new(left), Box::new(next))
            }),
            (left, right) => step(left).map(|next| {
                Expr::Add(Box::new(next), Box::new(right))
            }),
        },
    }
}

    この関数は遷移を一度だけ実行します。繰り返し適用すると表示されたトレースになり、Noneを返す場合は式がすでに値になっています。

    操作上の問いと表示上の問い

    操作規則を使うと、安全性、進行性、リソース境界、実装との対応関係を証明できます。意図された抽象的な意味を決める前に操作機構を選ぶと、実装上の選択が意図しない意味論上の約束になるおそれがあります。

    Denotational Designは操作的意味論を否定しません。先に意味論的領域、合成、法則を明示し、その後で操作モデルとの関係を定めます。

    表示上プログラム全体は何を意味するか。
    操作上どのような遷移で評価されるか。
    正しさその遷移は意図された意味を保つか。

    意味論上の位置付け

    Expression Problemは、表現と操作をモジュール式に拡張する問題です。Denotational Designは一つ手前の問いを立てます。そもそも、どの意味論上の語彙と解釈に表現する価値があるでしょうか。

    Phil Wadlerのexpression problemは、既存コードを変更せずに言語を二つの軸で同時に拡張することを扱います。

    • 新しいデータのバリアント（新しい式形式、すなわち「構文」）を追加する。
    • 新しい操作（新しい解釈、すなわち「意味論」）を追加する。

    中核となる緊張関係：

    • 関数型／ADTのスタイルでは、新しい操作を追加しやすい一方、新しいバリアントを追加すると広範な変更が必要です。
    • オブジェクト指向のスタイルでは、新しいバリアントを追加しやすい一方、新しい操作を追加すると広範な変更が必要です。

    Haskell（関数型／ADT）

    式と二つの操作を定義する、典型的なADTから始めます。

  | Add Expr Expr

pretty (Add a b) = "(" ++ pretty a ++ " + " ++ pretty b ++ ")"

    ここでは、新しい操作を追加するのは簡単です。

    しかし、新しいバリアント（例：Mul）を追加すると、すべての関数を変更する必要があります。

    Wadlerの言葉では、OO方式では操作の拡張がモジュール式ではないのです。

    まとめ（Wadlerの指摘）

    • 関数型／ADT方式は、新しい操作を追加しやすい一方、新しいバリアントを追加しにくい。
    • OO方式は、新しいバリアントを追加しやすい一方、新しい操作を追加しにくい。
    • expression problemが求めるのは、既存コードを変更せずに両方の軸を拡張できる設計です。

    Wadlerによる説明と解決策の概要（1998）

    Wadlerはこの問題を、データ型のケースの追加（新しいバリアント）と、そのデータ型を処理する関数の拡張（新しい操作）を、既存コードを再コンパイルせず、静的な型安全性（キャストなし）を保ちながら行うことと定義しています。

    「表」のたとえを使います。

    • 行＝ケース（バリアント／コンストラクター）
    • 列＝関数（操作／解釈）

    関数型／ADTの環境では、行が固定され、列を簡単に追加できます。
    OOの環境では、列が固定され、行を簡単に追加できます。
    課題は、両方向を拡張可能にすることです。

    Wadlerの提案した解決策（GJ＋virtual types）

    WadlerはGeneric Java（GJ）を使う解決策を提示しています。そこでは次のものを使います。

    • This境界付きパラメーター（This extends LangF<This>）によってThisTypeを模倣する。
    • 内部クラスとインターフェースは、This（virtual types）で添字付けされます。
    • A visitor-based structure that allows:
      • 「言語ファミリー」をサブクラス化して新しいケース（例：Plus）を追加する。
      • 新しいビジターを追加して新しい操作（例：Show）を加える。

    各拡張段階で型安全性と個別コンパイルを保つには、This.ExpとThis.Visitorを参照する方法が要点です。

    注意点（Javaの内部インターフェース）

    Wadlerは、Javaでは内部インターフェースがstaticとして扱われ、添字付けの仕組みが崩れると指摘します。
    この制限を緩めれば解決策は実用可能になると提案していますが、現在のJavaでも変わっていません（ネストしたインターフェースは暗黙にstaticです）。

    挙げられているほかの解決方針

    1. Corky Cartwrightの方法 反変な拡張が必要です。基底の式型を拡張後の型の代わりに使えるようにします。 拡張された言語ファミリーが元の言語のサブタイプではないため、ここで不動点を使う理由を説明できます。

    2. Kim Bruceの方法 高階型コンストラクター（型コンストラクターを受け取る型パラメーター）が必要です。 GJはこれを直接サポートしませんが、Wadlerはvirtual typesで模倣できると論じています。

    3. Krishnamurthiら（拡張ビジターパターン） 拡張ビジター設計によって実現します。 彼らの環境（Pizza）では静的に型付けされないため、動的キャストが必要です。

    4. 特別目的の言語拡張 Wadlerは、この問題専用に設計された言語機能に依存する二つの解決策を挙げています。 virtual typesによる方法ほど一般的ではありません。

    Wadlerの二つの指摘

    Wadlerのメールからは、二つの要点が明確に分かります。

    1. Expression Problemは、データの拡張と操作の拡張の間にある構造的な緊張関係です。
    2. Solutions are possible, but they tend to require either:
      • virtual typesを模倣する型システム機能
      • 特別目的の言語拡張
      • 静的型安全性または個別コンパイルに関する妥協

    Featherweight Goによる解決（2020）

    Wadlerは1998年に問題を定式化して命名しました。その後、Featherweight Go（FG）とそのジェネリクス拡張であるFGG（Featherweight Generic Go）が、構造的インターフェースとジェネリクスを持つGo風言語において、具体的かつ完全に静的な解決策を示しました。

    論文の解決策（図8、簡略版）には、構造NumとPlus、操作EvalとStringがそれぞれ二つあります。

    type Evaler interface { Eval() int }
type Stringer interface { String() string }

type Num struct { value int }
type Plus(type a Any) struct { left a; right a }

func (e Num) Eval() int { return e.value }
func (e Plus(type a Evaler)) Eval() int { return e.left.Eval() + e.right.Eval() }

func (e Num) String() string { return fmt.Sprintf("%d", e.value) }
func (e Plus(type a Stringer)) String() string {
    return fmt.Sprintf("(%s+%s)", e.left.String(), e.right.String())
}

type Expr interface { Evaler; Stringer }

var e Expr = Plus(Expr){Num{1}, Num{2}}

    仕組み：

    • ジェネリックな再帰表現。Plusの子要素は、Anyだけを境界とする型パラメーターaを持ちます。すべての操作を列挙した一つの閉じたインターフェースに構造を結び付けないため、後から操作を追加できます。
    • 操作ごとの制約。各メソッド宣言でaの境界を個別に定めます。EvalではPlus(type a Evaler)を、StringではPlus(type a Stringer)を使います。FGGの共変なレシーバーに依存しており、型宣言にある境界より強い境界をメソッドのレシーバーに設定できます。
    • 構造的インターフェース。構造体がインターフェースを実装するには、そのメソッドを備えていればよいため、既存のNumとPlusに触れずに後からExprを導入できます。値の構築時（Plus(Expr){...}）に限って、操作一式が固定されます。

    新しいケースは新しい構造体、新しい操作は新しいインターフェースとメソッドで追加できます。既存の宣言を変更したり再コンパイルしたりする必要はなく、型アサーションも不要です。

    意味論上の位置付け

    参照透過性は、選択した表示と等値性に依存します。式を置き換えても、意味論上の境界の内側で実装上の振る舞いが異なることはありますが、仕様で定めた意味が保たれるなら置換を認めます。

    参照透過性（RT）とは、式の置換に関する性質です。式をその表示に置き換えても、プログラムの意味は変わりません。

    今日の実践では、RTは等式による推論、安全なリファクタリング、法則に基づくAPI設計の基礎として使われています。

    中核となる意味

    RTは次のように述べます。

    • eがvを表すなら、
    • vをeの代わりに使っても意味は保たれる。

    これは意味論上の主張であり、コーディングスタイルの標語ではありません。

    純粋性

    純粋関数は、同じ入力に対して同じ出力を返し、観測可能な副作用を持ちません。RTは式に関する置換法則です。式をその表示に置き換えても意味が保たれなければなりません。そのため純粋性は、実践上RTを得る一般的な方法の一つであり、RTはより広い意味論上の基準です。DDにおける純粋性とRTの区別については、参照透過性再考を参照してください。

    歴史的背景

    プログラミング言語の意味論では、RTはChristopher Stracheyの定式化と強く結び付いています。彼の考察では、値についての推論と更新を伴う振る舞いを分けています。

    • R値：式の値。
    • L値：代入できる場所。

    要点は、値についての推論を保てば、式レベルの置換は安定しているということです。代入によって場所の更新が導入され、単純な置換による推論が難しくなったり、無効になったりします。

    ここでの代入と副作用の意味

    この文脈では：

    • 代入とは場所を更新することです（例：x := x + 1）。
    • 副作用とは、値を返すこと以外にある観測可能な変化です。

    代入は特定の種類の副作用です。

    これが多くの命令型環境でRTが成り立たない理由です。評価は、式の明示的な値のインターフェース外にある観測可能なコンテキストに依存したり、それを変更したりすることがあります。

    現代の言語でRTをどう扱うか

    Haskell

    RTは純粋な式についての標準的な推論方法として教えられています。副作用は型付き構成（IO、状態の受け渡し、関連する抽象化など）で明示するため、日常的な利用で置換法則が中心的な役割を果たします。

    Scala（Cats／Cats Effect）

    Scalaの関数型プログラミングでは、Cats Effectが一般的なRTの説明を提供します。

    • IO[A]は、副作用のある処理を純粋に記述する
    • IO値の合成にはRTが成り立つ
    • ランタイム境界（unsafeRun*）で実行を明示する

    Cats Effectは即時のFuture評価とも対比されます。そのため、ScalaでのRTの議論では遅延性と実行の先送りが強調されます。

    今日のRT

    現代のエコシステム全体で、RTは置換しても安全な振る舞いを指す略称として使われています。 複数のパラダイムを組み合わせるシステムでは、コード全体に一律に適用せず、特定のモジュール、API、副作用を型で扱う領域にRTの主張を適用するのが一般的です。

    意味論上の位置付け

    自由モナドは、自由に生成される逐次実行を伴う命令構文の表現です。命令ファンクターがすでに語彙を選び、インタープリターがその構文を意味論的領域へ写像します。強力な符号化の一つではありますが、Denotational Designの定義ではありません。

    自由モナドとは何か（Rust版）

    自由モナドを使うと、次のことができます。

    • プログラムをデータとして記述し、すぐには実行しない。
    • そのプログラムを後で、一つまたは複数の方法で解釈する。

    次のように考えてください。

    副作用のある操作のAST＋それらを連結するbind／flat_map。

    次のように分けます。

    • 構文 → 命令の列挙型。
    • 解釈 → 選択した意味論的領域への、構造を保つ写像。

    「自由」とは、モナドの法則を超える等式を加えず、ファンクターFからモナド構造を生成することです。Fを選ぶと命令構文もすでに決まっています。構築されたプログラムを解釈することで、具体的な表示が与えられます。

    Rustでの実装

    模式的な符号化

    Rustには高カインド型の型パラメーターが直接ないため、本番向けの自由モナド符号化には追加の型レベルの仕組みか、専用の命令ファンクターが必要です。次のコードは意図する構造を示すものであり、そのまま使えるジェネリック実装ではありません。

    自由モナド型

    #[derive(Clone)]
enum Free<F, A> {
    Pure(A),
    Suspend(F),
    FlatMap(Box<Free<F, A>>, Box<dyn Fn(A) -> Free<F, A>>),
}

impl<F: Clone + 'static, A: 'static> Free<F, A> {
    fn pure(a: A) -> Self {
        Free::Pure(a)
    }

    fn flat_map<B: 'static, G>(self, f: G) -> Free<F, B>
    where
        G: Fn(A) -> Free<F, B> + 'static,
        F: 'static,
    {
        match self {
            Free::Pure(a) => f(a),
            Free::Suspend(op) => {
                Free::FlatMap(Box::new(Free::Suspend(op)), Box::new(f))
            }
            Free::FlatMap(inner, g) => {
                Free::FlatMap(inner, Box::new(move |x| g(x).flat_map(f.clone())))
            }
        }
    }
}

}

    インタープリター

    fn run_console<A>(mut prog: Free<Console<A>, A>) -> A {
    loop {
        match prog {
            Free::Pure(a) => return a,
            Free::Suspend(Console::Print(s, next)) => {
                println!("{}", s);
                prog = Free::Pure(next);
            }
            Free::Suspend(Console::ReadLine(f)) => {
                let mut buf = String::new();
                std::io::stdin().read_line(&mut buf).unwrap();
                prog = f(buf.trim().to_string());
            }
            Free::FlatMap(inner, cont) => match *inner {
                Free::Pure(a) => prog = cont(a),
                Free::Suspend(op) => prog = Free::Suspend(op), // minimal handling
                _ => unimplemented!(),
            },
        }
    }
}

    継続およびCPSとの関連

    継続渡し形式（CPS）とは、関数が値を直接返さず、継続と呼ばれる別の関数へ結果を渡す形でプログラムを書く方法です。継続は「プログラムの残り」を表します。

    自由モナドとは、基本的に、手順の列として表したプログラムです。各手順は次のように述べます。

    「これを実行してから、残りに続く。」

    この「プログラムの残り」こそが継続です。現在の結果から次の手順を返す関数です。

    • Rustによる自由モナドでは：

      Free::FlatMap(Box<Free<F, A>>, Box<dyn Fn(A) -> Free<F, A>>)

      Box<dyn Fn(A) -> Free<F, A>>のが継続です。

    • 自由モナドを解釈することは、CPSで実行することです。

      • 値を直接返す代わりに、次の継続へ渡します。
      • 次のループになります。 current_instruction -> feed result into continuation -> next instruction

    • CPSとの関係：

      • 自由モナドは、CPSをデータ構造に符号化するものです。
      • CPSは、同じ考え方を表すランタイムの制御フロー表現です。

    デファンクショナライズとの関係

    デファンクショナライズとは、高階関数を、それらの関数を表す一階データ構造と、それを適用するインタープリターに置き換えるプログラム変換です。

    CPSでは継続が高階関数です。CPSプログラムをデファンクショナライズすると、継続が継続ケースの列挙型になり、apply実行する関数が用意されます。

    適切な符号化を使うと、自由モナドを、CPS変換されたプログラム内のデファンクショナライズ済み継続と関連付けられます。

    1. プログラムをCPS形式にします。「プログラムの残り」は継続関数が保持します。
    2. 継続関数をデファンクショナライズして、データ型の有限個のケースに置き換えます。
    3. こうして得られる一階データ型は、自由モナド表現と同じ命令および継続の形を取ることがあります。

    主な類似点

    • 自由モナドもデファンクショナライズも計算をデータとして表現し、そのデータに意味を与えるためのインタープリターが必要です。
    • 自由モナドのFlatMapケースには継続が格納され、デファンクショナライズではそのクロージャがデータ型のケースに置き換わります。

    継続渡し形式（CPS）

    関連項目

    Rustで意味から設計する：一階プログラム、言語とコンパイラーパイプライン
    概念：自由モナド、デファンクショナライズ
    洞察：EVM代数

    意味論上の位置付け

    CPSは、制御を明示する表現およびプログラム変換です。意味を保つかどうかは、明示されたソース意味論、ターゲット意味論、それらの対応関係によって決まります。

    定義

    継続渡し形式（CPS）は、関数が値を直接返さず、結果を継続と呼ばれる別の関数へ渡す形でプログラムを書く方法です。継続はプログラムの残りを表します。

    目的

    • 制御フローを明示し、プログラムから扱えるようにする。
    • ノンブロッキングIO、早期終了、コルーチン、バックトラッキング、並行スケジューリングなどの高度な変換を可能にする。
    • 最適化や解析を単純化する目的で、コンパイラーの中間表現に使われる。

    基本形式

    直接形式：

    fn add_one(x: i32) -> i32 {
    x + 1
}

fn main() {
    let y = add_one(41);
    println!("{}", y);
}

    CPS形式：

    fn add_one_cps(x: i32, k: impl Fn(i32)) {
    k(x + 1)
}

fn main() {
    add_one_cps(41, |y| {
        println!("{}", y);
    });
}

    ここでは、kは継続です。x + 1を返すのではなく、k(x + 1)を呼び出します。

    主な性質

    • 関数呼び出しはすべて、継続への末尾呼び出しです。
    • 現在の計算は呼び出し元に「戻り」ません。継続へ制御を移します。
    • プログラム内で制御フローが明示される。

    高階関数との関係

    • CPSでは、継続は高階関数にすぎません。
    • 計算の各段階では、次に何をするかを表す継続を受け取ります。

    デファンクショナライズとの関係

    • CPSでは、継続は実際の関数値です。
    • デファンクショナライズは、継続関数を、次のステップを表すデータ構造（列挙型）と、それを解釈するapply関数に置き換えます。

    自由モナドとの関係

    • 自由モナドのFlatMap構成子は、格納された継続そのものです。
    • 自由モナドを解釈することは、継続がプログラムデータの一部であるCPSコードを実行するようなものです。
    • 適切な自由モナド符号化は、CPSやデファンクショナライズされた継続表現と関連付けられます。

    利点

    • 柔軟な制御フロー表現。
    • 評価順を推論しやすくなる。
    • インタープリター、デバッガー、最適化器、非同期ランタイムの実装に有用。

    欠点

    • 直接形式に比べて冗長。
    • 人間には読みにくい場合がある。
    • 末尾呼び出しをネイティブにサポートしない言語では、効率のために末尾呼び出し最適化が必要。

    関数のデファンクショナライズ

    関連項目

    Rustで意味から設計する：一階プログラム、言語とコンパイラーパイプライン
    概念：自由モナド、継続渡し形式

    意味論上の位置付け

    デファンクショナライズは、関数適用の振る舞いを保つことを意図しつつ、表現を変えます。意味から始める設計では、実行前に別のインタープリターが操作を検査または合成する必要がある場合、生成された一階の値が役立ちます。

    定義

    デファンクショナライズとは、高階関数を、考えられる関数を表す一階データ構造と、それを適用するインタープリター関数に置き換えるプログラム変換です。

    目的

    言語、コンパイラー、ランタイムによっては、高階関数を効率的に扱えなかったり、まったく扱えなかったりします。デファンクショナライズすると、プログラムが一階だけになり、コンパイル、解析、シリアライズ、制限された環境での実行が容易になります。

    手順

    1. 生成され、受け渡される可能性のある高階関数をすべて特定する。
    2. 各関数に一意のタグを割り当て、列挙型または直和型と、その操作に必要なデータで表す。
    3. 関数値をこれらのタグに置き換える。
    4. タグと関数の引数を受け取り、タグでパターンマッチして適切なコードを実行するapply関数を定義する。

    Rustでの例

    変換前：クロージャを使う

    let k: Box<dyn Fn(i32) -> i32> = Box::new(|x| x + 1);
println!("{}", k(41));

    変換後：デファンクショナライズされた形式

    enum Cont {
    Add1
}

fn apply(c: Cont, x: i32) -> i32 {
    match c {
        Cont::Add1 => x + 1,
    }
}

println!("{}", apply(Cont::Add1, 41));

    性質

    • すべての関数が単純なデータで表現される。
    • プログラムが一階だけになる。
    • apply関数が直接の関数呼び出しに取って代わる。

    用途

    • コンパイラーバックエンドの単純化：多くのコンパイラーはCPSコードを生成してからデファンクショナライズします。
    • 関数のシリアライズ：列挙型のタグをネットワーク越しに送信したり、ファイルに格納したりできます。
    • 静的解析：一階コードのほうが推論しやすい。
    • インタープリターの導出：デファンクショナライズは自然にInterpreterパターンへつながる。

    CPSとの関係

    CPS（継続渡し形式）では、継続は高階関数です。CPSコードをデファンクショナライズすると、継続が有限個のケースを持つ列挙型と適用関数になります。

    自由モナドとの関係

    適切な自由モナド表現は、CPS変換されたプログラムにあるデファンクショナライズ済みの継続と関連付けられます。密接な関係ではありますが、二つの構成が常に同一というわけではありません。

    型レベルの適用

    ネイティブな高カインド型を持たない言語では、デファンクショナライズを使って型レベルの適用も符号化できます。オブジェクト代数を試すC#の実験では、この軽量な符号化をApp<F, a>に適用して、ファンクター、アプリカティブ、モナド、副作用の代数を表します。

    分岐と合流性

    関連項目

    概念：操作的意味論

    計算の選択肢には、分岐、決定性、合流性、トレース等価性、双模倣性が関わります。これらは同じ性質ではありません。

    意味論上の位置付け

    制御フローの分岐は操作上の構造です。合流性は簡約関係の性質です。トレース等価性と双模倣性は振る舞いを比較します。表示の等値性は、選択した意味論的領域で意味を比較します。健全な設計では、これらの概念を曖昧に行き来せず、必要とする等値性を明示します。

    振る舞いの等価性

    並行プログラムや対話型プログラムの結果は、一つとは限りません。標準的な出発点はラベル付き遷移系です。

    L=(S,Aτ​,→)

    Sは状態の集合、Aτ​は観測可能なアクションラベルの集合と内部アクションτ、→⊆S×Aτ​×Sは遷移関係です。状態pがアクションaを実行して状態p′になる場合、pa​p′と書きます。

    振る舞いの等価性では、こうしたシステム間でどの差異を意図的に無視するかを定めます。

    • 線形時間の観測は、完了した実行または部分実行をたどり、その途中で起きたことを記録する。
    • 分岐時間の観測は、選択肢がどこで提示され、いつ選択が決まったかも保持する。

    そのため、二つのシステムが同じトレースを持ちながら、分岐構造が異なることがあります。一方が対話の前に二つのアクションから選び、もう一方が対話の後まで選択を延期する場合です。アクションの列は同じでも、その後に可能なことは異なります。

    Van Glabbeekの線形時間・分岐時間スペクトルは、こうした振る舞いの等価性を体系的に分類した標準的な説明です。弱いものから強いものへの順位ではなく、それぞれ異なる観測の集合を保持します。

    Rustプログラムにおける分岐

    ifは条件に応じて一つの分岐を選択します。

    fn sign(x: i32) -> i32 {
    if x > 0 {
        1
    } else if x < 0 {
        -1
    } else {
        0
    }
}

    matchは値に応じて一つのアームを選択します。

    fn day_type(day: &str) -> &str {
    match day {
        "Saturday" | "Sunday" => "Weekend",
        "Monday" | "Tuesday" | "Wednesday" | "Thursday" | "Friday" => "Weekday",
        _ => "Unknown",
    }
}

    決定的な言語で入力を固定すると、これらの構文は予測可能な制御フロー経路を選びます。これは決定性であり、合流性ではありません。

    合流性の意味

    簡約関係の合流性とは、同じ項から行った二つの簡約を、さらに簡約して再び合流させられる性質です。

    b​↙∗↘∗​ad​↘∗↙∗​c​

    形式的には、次が成り立つなら：

    a→∗banda→∗c

    dが存在し、次が成り立たなければなりません。

    b→∗dandc→∗d

    合流性があっても複数の簡約経路は存在します。それらが共通の後続項へ到達できるという意味で、互いに両立することを表します。

    決定性と合流性

    決定的な簡約関係では、各状態からの次のステップは高々一つです。そのため、競合する一段階の選択肢を調整する必要がなく、単純な意味では合流的です。

    逆は成り立ちません。複数の簡約順序を許しながら、最終的にすべてが一致するため合流的なシステムがあります。

    通常のRustのif式とmatch式は、決定的な選択を示します。それだけでは、合流性の興味深い内容を説明できません。

    Church–Rosser

    Church–Rosserの定理は、ラムダ計算の簡約に関する合流性を示します。ある項が異なる簡約経路で二つの結果に簡約できるとき、それらの結果には共通の簡約形があります。

    正規形が存在する場合、合流性によってそれが一意であると分かります。評価順が最終的な正規形を変えないため、等式に基づく推論を支えます。

    この結果を任意の命令型プログラムに一般化しないでください。副作用、非決定的スケジューリング、失敗、中間状態の観測により、簡約順序の違いが意味を持つ場合があります。

    トレース

    トレースは、観測可能なアクションまたは状態の列を記録します。トレース意味論は、結果だけを見る意味論より多くの操作情報を意図的に保持します。

    二つの純粋関数は同じ結果を返しつつ、内部のステップが異なることがあります。結果のみの表示でそれらのステップを捨てるなら、その表示では等価です。トレース意味論では、必ずしも等価ではありません。

    副作用がある場合、順序を変えると観測が変わることがあります。

    fn is_admin() -> bool {
    println!("checked admin");
    true
}

fn is_user() -> bool {
    println!("checked user");
    true
}

    is_adminを先に確認するかis_userを先に確認するかで、分類結果が等価でも出力トレースが異なることがあります。

    この出力を選択した意味論的領域に含めるかが設計上の問いです。

    トレース等価性

    選択したトレースモデルで同じ観測トレースを持つとき、二つのシステムはトレース等価です。

    トレース等価性では分岐構造が無視されることがあります。一方が他方より早く選択を確定する場合も、同じトレースを生成することがあります。対話型および並行システムでは、この違いが重要な場合があります。

    双模倣性

    双模倣性は二つの遷移系を一段階ずつ関連付けます。一方のシステムが観測可能な動作を行うたびに、もう一方もそれに対応する動作を行えなければなりません。そして、遷移先の状態同士も関連したままでなければなりません。

    一般的な変種：

    • 強双模倣性：個々の遷移を対応付ける
    • 弱双模倣性：選択された内部遷移を抽象化する
    • 分岐双模倣性：重要な選択構造を保ちながら内部処理を抽象化する

    双模倣性は相互作用の間に選択肢がどう維持されるかを観測するため、トレース等価性より強い振る舞いの比較になることがよくあります。

    由来と形式的な定義

    MilnerはA Calculus of Communicating Systemsで、通信プロセスの観測的等価性を発展させました。その後ParkはConcurrency and Automata on Infinite Sequencesで対応する等価性を余帰納的に特徴付け、現在双模倣性として知られる最大不動点関係と証明方法を示しました。Milnerはこの方法を採用し、プロセスの振る舞いを推論する基盤として発展させました。

    強双模倣性。ラベル付き遷移系で、関係Rが強双模倣であるとは、pRqのとき、すべてのアクションaについて次が成り立つことです。

    • pa​p′なら、q′を満たす状態を経てqa​q′を実行し、遷移先がp′Rq′に関連付けられる状態が存在する。
    • qa​q′なら、p′を満たす状態を経てpa​p′を実行し、遷移先がp′Rq′に関連付けられる状態が存在する。

    ある双模倣関係が二つの状態を関係付けるなら、それらの状態は双模倣的です。この定義は余帰納的です。遷移に対応付けた後も、遷移先の状態は同じ振る舞い上の責務を満たさなければなりません。

    分岐双模倣性。一般的な発散を区別しない形式では、対称関係Rが分岐双模倣であるとは、pRqとpa​p′から次のいずれかが成り立つことです。

    • a=τおよびp′Rq、または

    • 状態q0​とq′が存在し、次が成り立つ。

      qτ​q0​a​q′,pRq0​,p′Rq′

    ここでτ​は内部遷移が0回以上であることを表します。中間状態q0​とpが引き続き関連することを要求するため、内部処理を無視しつつ、重要な分岐可能性を保持できます。Van GlabbeekとWeijlandはBranching Time and Abstraction in Bisimulation Semanticsで、この等価性を導入し発展させました。

    表示の等値性

    表示の等値性は、選択した意味論的領域によって決まります。

    領域自体をトレース、双模倣性で割った遷移系、結果の集合、その他の数学的モデルから構築する場合があります。Denotational Designは万能の等値性を一つ指定しません。等値性を明示的に選び、合成的に使うことを求めます。

    関係は次のとおりです。

    1. 操作系を出発点にする。
    2. 関係する観測を選ぶ。

    操作的意味論が記述するもの

    操作的意味論は、選択したプログラム表現がどう振る舞うかを定めます。評価判断、または次のような構成に対する遷移関係を定義します。

    (program,state)⟶(program′,state′)

    プログラムはソース構文、自由モナド値、CPS項、バイトコード、デファンクショナライズされた機械状態かもしれません。これらの表現はいずれも操作的意味論ではありません。操作的意味論は、選択した表現の値がどのように評価または遷移するかを説明するものです。

    この方向性は重要です。表現があれば、その振る舞いを記述できます。しかし操作上の記述を追加しても、その言語が本来持つべき意味は説明されません。

    自由モナドのプログラム

    自由モナドは命令構文と自由に生成される逐次実行を提供しますが、命令の振る舞いは定めません。

    自由モナドのプログラムに対する操作的意味論では、現在の命令、その継続、機械状態を含む構成を定義できます。たとえば、中断中の命令がどのように状態を変え、結果を残りのプログラムへ渡すかを規則で説明します。

    これは可能な解釈の一つです。同じ自由プログラムを表示モデルへfoldしたり、別の言語へコンパイルしたり、解析したり、実行せずに描画したりすることもできます。

    自由モナドからfreerへ：研究で分かったこと

    副作用のあるプログラムを構成する一般的なアーキテクチャとして自由モナドを知った読者は、なぜ後にfreer構成、拡張可能な副作用、ハンドラーへ議論が移ったのか疑問に思うかもしれません。研究は自由モナドを単に捨てたのではありません。自由モナドが実際に提供するものを切り分け、一般的な表現がうまくいかない箇所を測定し、有用な構造を引き継ぎました。

    KiselyovとIshiiは、副作用項の表現から制約や定型コードを段階的に取り除き、freerモナドを導出しました。freer表現では、命令が最終的なプログラム型からは見えない中間型の値を生成でき、明示的な継続が結果を計算の残りへ接続します。そのため、命令シグネチャにFunctorインスタンスは不要になります。

    この変更で表現力は向上しますが、それだけでは性能の問題は解決しません。素朴なfreer表現では、左結合のリスト追加と同様に継続を合成します。n件の要求列を処理するにはO(n2)の計算量がかかることがあります。継続を明示すると、実際の改善点が見えてきます。隣り合う結果型と入力型が構築時に一致する、型整列された列として継続を保持できます。この列を効率的に連結すれば、結合の仕方に依存する走査が不要になります。

    次にopen unionを使うと、拡張可能な副作用のインタープリターで、選択した要求型を追加、合成、除去できます。これによってモジュール式の副作用合成とハンドラー構造を扱えます。それでも、特定の領域の等式を提供したり、副作用を持つ二つのプログラムが同じ意味か判断したりするわけではありません。

    結論は「freerはfreeより優れている」より正確です。自由モナドは要求と解釈を分離する価値ある方法を示しました。freer符号化は不要な制約を除き、型整列キューは測定された性能問題に対処し、拡張可能な副作用は合成を改善しました。各段階は前の知見を引き継ぎながら、主張の範囲を絞りました。意味論的な解釈は最初から最後まで独立した判断でした。

    KiselyovとIshiiのFreer Monads, More Extensible Effectsを参照してください。

    CPSプログラム

    継続渡し形式（CPS）では、計算の残りを継続として明示します。CPSに対する操作的意味論では、次のような振る舞いを記述します。

    • 現在のCPS式を評価する。
    • 生成された値を継続へ渡す。
    • 継続が適用されたときに制御を移す。

    CPSは制御を操作上記述しやすい形で明らかにしますが、表現またはプログラム変換であり、操作的意味論ではありません。直接形式のプログラムとそのCPS変換を関連付けるには、ソースとターゲットの意味論を明示し、保持を示す必要があります。

    CPSを越えて：継続を検査する必要があるとき

    CPSは、結合の仕方に依存する追加やbindの負荷を抑える標準的な方法です。左結合構造を何度も走査する代わりに、関数合成によって残りの計算を表します。継続に対する操作が最終的な適用だけなら、この表現は効率的です。

    van der PloegとKiselyovはその限界を示しています。継続する前に中間結果を調べたり変更したりする必要のある利用側もあります。非決定的探索、列挙子、自由モナド、拡張可能な副作用では、このようなアクセスが必要になる場合があります。CPSでは概念的な列が関数の中に隠れるため、中間構造を復元するにはデータへの再反映が必要になり、性能上の利点が失われることがあります。

    代わりに隠れた列を、型整列されたデータ構造として直接表現します。これにより、結合の仕方によらない効率的な合成と、中間結果への効率的なアクセスを両立できます。各計算が次の計算に必要な入力を生成することは、型で保証されます。

    広い意味での結論は、型整列列がCPSを打ち負かすということではありません。CPSは継続の適用には適していますが、利用側が継続を検査する場合には適さないことがあるということです。区切られた制御に関する研究は、周囲の計算全体を一つの区別のない継続として扱う代わりに、どの範囲を捕捉し操作できるかを区切りが示すという、さらに精密な教訓を与えます。

    これらの考え方は失われていません。副作用ハンドラー、抽象機械の導出、型付き制御演算子、効率的な副作用表現に今も活かされています。変わったのは、CPSだけが最終的な抽象化であるべきだという期待です。

    van der PloegとKiselyovのReflection without Remorseを参照してください。制御全般については、Kiselyovの継続と区切られた制御の資料集を参照してください。

    デファンクショナライズされた機械

    デファンクショナライズでは、CPSの継続など、既知の関数値の族を一階構成子とapply操作に置き換えます。これにより、生成された明示的な構成間の遷移を操作的意味論で記述できます。

    具体的なCPS変換の後にデファンクショナライズを行えば、抽象機械を導出できます。これは強力な導出方法ですが、一般的な操作的意味論の定義ではありません。操作規則はCPSに由来する必要はなく、一階機械も、見た目が似ているというだけでデファンクショナライズされた継続機械になるわけではありません。

    Reynolds：デファンクショナライズの始まり

    John C. Reynoldsは、1972年の定義的インタープリターに関する研究でデファンクショナライズを導入しました。出発点は一階仮想マシンではなく、高階インタープリターでした。定義に用いる言語の関数が、定義対象の言語における環境、継続、その他の要素を表していました。

    この変換では、プログラム全体に現れ得る有限個の関数抽象を特定します。各抽象を、自由変数の値を持つ一階構成子に置き換え、関数適用を、構成子を振り分ける一つのapply操作に置き換えます。定義に用いる言語の中で暗黙だったものが、クロージャまたは継続の明示的な代数になります。

    継続に基づくインタープリターに適用すると、機械が見えてきます。継続構成子は制御状態になり、捕捉された変数は格納された機械データになり、applyは遷移の振り分け器になります。機械を先に推測するのではなく、高階評価器から導出します。

    Reynoldsは、明確さによって生じる代償も強調しました。導出される機械は正しいものの一意ではない表現上の選択を含みます。異なる構成子や先行する変換を選ぶと、振る舞いを保ったまま「機械の歯車や車輪」に似た構造が異なる形で得られます。そのため、デファンクショナライズは操作構造を明らかにしますが、その言語に不可避な唯一の意味を示すわけではありません。

    DanvyとNielsenは後に、Reynoldsの技法をプログラム全体に適用する変換として体系化し、逆変換のリファンクショナライズを研究しました。さらに深い結論として、この変換は橋渡しの役割を持ちます。高階な定義と一階機械の間で仕様や正しさの議論を移し、無関係に見えるプログラムが同じ構造の異なる表現だと明らかにできます。

    この研究の系譜は、この技法に適切な権威を与えます。デファンクショナライズはクロージャを列挙型に置き換えるだけのものより強力ですが、普遍的な基盤というには限定的です。対応関係の確立が必要な、意味を保つ表現間の移行です。

    ReynoldsのDefinitional Interpreters for Higher-Order Programming Languagesと、DanvyとNielsenのDefunctionalization at Workを参照してください。

    操作表現のサイクル

    よくある誤りは、あらゆるプログラミング上の問題を解決する一つの操作表現を探すことです。各表現は、前の表現が隠していたものを明らかにしますが、その代わり別の課題を難しくします。

    higher-order program⟶free syntax⟶CPS⟶first-order machine⟶higher abstraction

    矢印は必須のコンパイラーパイプラインを意味しません。現在の表現が隠すものを明らかにし、そのために導入した仕組みを再び隠すという、繰り返し現れる設計の動きを示します。

    表現可能になること新たに生じる負担
    高階関数直接的な合成とホスト言語の抽象化ジェネリックな利用側は関数を呼び出せるが、隠された構造を検査できない
    逐次実行を備えた自由構文合成・解釈可能なデータとしてのプログラム領域の等式、正規化、効率的な評価、格納された関数の検査は自由構文だけでは提供されない
    CPS評価順と計算の残りを明示できるプログラム全体をCPSで符号化すると、ほぼすべてのインターフェースに継続を通すことになる
    デファンクショナライズされた一階制御継続が検査・シリアライズ可能なケースになる構成子、格納した引数、遷移状態、apply操作を明示的に保守する必要がある
    機械より上位の抽象化仕組みが使いやすくなるコンパイラー、スケジューラー、デバッガー、最適化器が検査する必要があると、構造が再び隠れる

    こうした負担は構造に起因します。検査にはデータが必要です。振る舞いをデータにすると、構成子とインタープリターが加わります。それらを隠せば抽象化は使いやすくなりますが、プログラムを解析・変換する利用側が必要とするアクセスも失われます。

    自由モナドのトレードオフは特に示唆的です。自由モナドが解決するのは、命令ファンクターからモナドの法則を超える等式を課さずに逐次実行を生成するという、一つの明確な問題です。同じ保証が限界でもあります。領域の法則は分かりません。たとえば同じセルへの二回の書き込みを最後の書き込みと等価に扱うべき場合でも、領域固有の正規化または解釈で同一視するまでは、自由プログラムに両方の命令が残ります。したがって、最適化、正準形、意味論的等値性は別の場所から与える必要があります。

    命令を再構化しただけでは、プログラム全体を一様に検査できるようにもなりません。一般的な符号化では、中断中の命令は見えますが、その継続はホスト言語の関数です。ジェネリックな解析器は、結果を与えて関数を適用せずに、その関数の先にある構造を検査できません。継続をデータへ再構化して検査可能にすると、一階表現またはデファンクショナライズされた表現へ近づき、サイクルの次の段階に戻ります。

    評価コストも同様に表現に依存します。左結合されたbindの素朴な木では、繰り返し走査が必要となり、二次の計算量が生じることがあります。残余サブプログラムを複製する変換は、指数的な増大を引き起こす可能性があります。Codensity形式、freer形式、専用の符号化は特定のコストを改善できますが、それぞれ別の表現とトレードオフを選んでいます。指数的な増大は起こり得ますが、自由モナド固有の法則ではありません。

    そのため自由モナドは万能な解決策ではありません。自由モナドが提供するのは、法則に従う逐次実行を伴う構文であり、意図された領域の等式、正準形、完全な構造の可視性、自動的に効率のよい実装ではありません。同様に、CPSも局所的に使うならシステム全体へ広げる必要はありません。デファンクショナライズが煩雑かどうかは、再構化する関数族や捕捉値の規模によって決まります。

    各新しい符号化を普遍的な基盤にしようとすると、このサイクルが現れます。直前の操作上の不便を解決した結果、次の偶発的な複雑さの原因になります。

    そのため、「最良の抽象化」をめぐる議論が操作面だけにとどまると、結論に至りません。高階関数、自由構文、CPS、一階機械を、どれか一つが他より優れていなければならないかのように比べます。しかし、何を保持するかと、誰が結果を利用するかを定めない限り、よりよいの意味は定まりません。

    • 直接実行では通常の呼び出しと隠された表現が有利になる。
    • 変換と解析では検査可能な構造が必要になる。
    • シリアライズでは一階データが必要になる。
    • 拡張性のために、解釈の追加または構文の追加を容易にする設計を選べるが、通常は両方を同じように容易にはできない。
    • 並行性では、多くのスケジューリング上の選択を意図的に無視する観測が必要な場合がある。

    これらは異なる要件であり、一つの抽象化が普遍的に優れていることを順に証明するものではありません。操作上の性質は目的を定めたうえで実装選択に役立ちますが、目的を与えたり、どの区別に意味があるかを決めたりはしません。

    逐次的な考え方にも同じ注意が必要です。操作的意味論は並行・非決定的システムを記述できますが、機械のステップを一列に並べたものは、振る舞いを表現する方法の一つにすぎません。スケジュール順を早々に権威あるものとして扱うと、機械上で異なる順にインターリーブされたというだけで、等価な実行が異なるものになってしまいます。まず意味論モデルで、並行プログラム間のどの観測を違いとして扱うかを決め、その後に操作上のスケジュールを評価します。

    実例：EVM

    Ethereum Virtual Machine（EVM）は操作的に理解できます。

    • 状態：プログラムカウンター、スタック、メモリー、ストレージ、gas
    • 遷移規則：各オペコード（ADD、PUSH、SSTOREなど）につき一つ
    • 実行：停止するまで小ステップ規則を繰り返し適用する

    EVMバイトコードは一階の命令データです。操作的な説明では、各オペコードに応じてEVMの構成がどう変化するかを定め、具体的なクライアントがその振る舞いを実装します。

    EVMのディスパッチループとプログラムカウンターは、デファンクショナライズされた抽象機械に似ていることがあります。しかし、それらをデファンクショナライズされた継続と呼ぶには、具体的な高階ソース、変換、対応関係が必要です。見た目が似たループだけでは足りません。

    サイクルを断つ：仕組みより先に意味を定める

    操作上の説明と表示上の説明は、異なる問いに答えます。

    [[p]]c​∈D⟶c′​​what does the program mean?how does this representation step?​

    意味から始める開発では、機械表現を決める前に意味論的領域、合成、観測、法則を選びます。遷移系を選んだ後に、正しさの責務で二つの層をつなぎます。完全な構成に対する適切な意味を定めた場合、典型的な静かなステップの保持は次の形になります。

    c⟶c′⟹meaning(c)=meaning(c′)

    正確な関係には、観測的等価性、トレース、双模倣性を使うこともあります。重要なのは、機械が意図された意味に対して責任を負うことです。

    Denotational Designは、このサイクルの勝者を決めません。サイクルの外に安定した基準を置きます。

    1. 意味論的領域、操作、合成、法則を定義する。
    2. その意味に沿ってプログラムを書く。
    3. 具体的な利用者に合わせて表現を選ぶ。直接実行、検査、コンパイル、スケジューリング、シリアライズ、解析など。
    4. 選択した各表現と変換を、同じ意味へ結び付ける。

    高階インタープリターと一階プログラムは共存できます。どちらも言語の定義になる必要はありません。前者は直接実行に、後者は構造を必要とする利用側に役立ちます。仕組みが同じだという前提ではなく、意味論上の責務として一致を確認します。

    操作的な抽象化に最終形はない

    どの操作表現も、ある構造を明らかにする一方で別の構造を隠します。適切な表現を選び、その関係を定めるための安定した基準が意味です。

    まとめ

    • 操作的意味論は、選択した表現に対する評価や遷移を記述する。
    • 自由モナドは命令構文と逐次実行を提供するが、振る舞いの解釈は別途必要である。
    • CPSは継続を明示し、操作規則でCPSプログラムが値と制御を渡す様子を記述できる。
    • デファンクショナライズによって特定の高階プログラムを一階機械に変換でき、その遷移を操作的に述べられる。
    • いずれかの符号化を普遍的なものとして扱うと、構造を再構化したり隠したりするサイクルが生じる。
    • 表示上の意味が、遷移で保持すべきものを定める。

    意味論的な見方：Denotational Design
    Rustで意味から設計する：ケイパビリティ代数、導出される意味と合成、インタープリターと副作用
    概念：Expression Problem

    このページでは、既存コードを何度も書き直さずに、新しい式形式と新しい操作を追加する方法であるExpression Problemに対し、トレイトを使った実践的な解決策を示します。設計はConal流、符号化はtagless-final／オブジェクト代数方式です。具体的には、まず合成可能な意味（小さなケイパビリティインターフェースと拡張レベルのプログラム仕様）を定め、その後に具体的なインタープリターを提供します。具体的な符号化は、Oleg Kiselyovのtagless-final形式やオブジェクト代数と同じ系統です。コンストラクターインターフェース（LitAlg、AddAlg、MulAlg）が言語のシグネチャを定め、プログラムをこれらのインターフェースに対して多相的に記述し、具体実装（EvalやPrettyなど）が解釈を与えます。これにより、閉じた一つのASTに決め打ちせず、静的型付けと二つの軸の拡張性を保てます。

    Olegの方法は明示的に表示に基づいています。まず合成可能な意味を割り当て、その後に副作用やインタープリターをモジュール式の意味論層として実現します。Expression Problemに対してDenotational Designと歩調が合うのは、偶然ではなく、この理由によるものです。ConalのDenotational Designも、まず合成的に意味を定め、具体的な実行戦略は後から交換可能なものとして扱うという優先順位を明示します。

    式言語の例では、次のように符号化します。

    • コンストラクターの語彙を小さく独立した代数トレイトで表す。
    • 解釈を、それらのトレイトの実装で表す。
    • 新しい構文を追加すると新しいトレイトが加わり、既存コードは変更しない。
    • 新しい意味論を追加すると新しいインタープリター型が加わり、既存コードは変更しない。

    litとaddは意味論的操作であり、特権的なASTのコンストラクターではありません。ASTは複数ある解釈の一つです。

    C#におけるオブジェクト代数

    この符号化はRust固有ではありません。object-algebrasではC#でこのパターンを発展させ、ここで使う固定担体を越えて抽象化します。このページでは各インタープリターが平易な具体型であるSelf::Exprを選びます。一方C#の代数では、型コンストラクターF（FunctorAlg<F>、MonadAlg<F>、BankingDsl<F>）を抽象化し、不正なF<a>の代わりに結果をApp<F, a>として持ち運びます。

    C#に第一級の高カインド型はないため、App<F, a>が適用F(a)の代わりとなり、inject／projectラッパーを通じて実現します。このAppトリックはまさにデファンクショナライズです。言語で表現できない抽象化を一階データにし、必要に応じて適用します。Rustにも第一級の高カインド型がないため、同じ制約があります。

    小さな構文ケイパビリティを定める

    各コンストラクターを小さなトレイトにします。これが仕様（spec）です。

    trait LitAlg {
    type Expr;

    fn lit(&self, n: i64) -> Self::Expr;
}

trait AddAlg {
    type Expr;

    fn add(&self, a: Self::Expr, b: Self::Expr) -> Self::Expr;
}

    プログラムを代数トレイト上の拡張として記述します。これらの拡張も仕様の一部であり、小さな仕様を組み合わせて再利用可能なプログラムレベルの仕様にします。

    #[ext(name = ExprPrograms)]
impl<This> This
where
    This: LitAlg + AddAlg,
{
    fn expr_basic(&self) -> This::Expr {
        self.add(self.lit(2), self.lit(3))
    }
}

    #[ext(...)]はextendクレートのマクロで、implブロックから拡張メソッドを生成して定型コードを減らします。Rustの新しい言語機能ではありません。

    新しい解釈を追加する

    インタープリターが仕様を実装します。構文を変更する必要はありません。

    struct Eval;

impl LitAlg for Eval {
    type Expr = i64;

    fn lit(&self, n: i64) -> i64 { n }
}

impl AddAlg for Eval {
    type Expr = i64;

    fn add(&self, a: i64, b: i64) -> i64 { a + b }
}

struct Pretty;

impl LitAlg for Pretty {
    type Expr = String;

    fn lit(&self, n: i64) -> String { n.to_string() }
}

impl AddAlg for Pretty {
    type Expr = String;

    fn add(&self, a: String, b: String) -> String {
        format!("({a} + {b})")
    }
}

    同じ式を別の方法で解釈できます。

    let eval = Eval;
let pretty = Pretty;

let v: i64 = eval.expr_basic();        // 5
let s: String = pretty.expr_basic();   // "(2 + 3)"

    新しい構文を追加する（新しいケイパビリティトレイト）

    Mulを追加するには、新しいトレイトを定義します。既存コードは変更しません。

    trait MulAlg {
    type Expr;

    fn mul(&self, a: Self::Expr, b: Self::Expr) -> Self::Expr;
}

#[ext(name = ExprProgramsMul)]
impl<This> This
where
    This: LitAlg + AddAlg + MulAlg,
{
    fn expr_with_mul(&self) -> This::Expr {
        self.mul(self.add(self.lit(2), self.lit(3)), self.lit(4))
    }
}

    既存のインタープリターは古い式で引き続き動作します。
    新しい構文が必要なら、新しいトレイトを実装します。

    impl MulAlg for Eval {
    type Expr = i64;

    fn mul(&self, a: i64, b: i64) -> i64 { a * b }
}

impl MulAlg for Pretty {
    type Expr = String;

    fn mul(&self, a: String, b: String) -> String {
        format!("({a} * {b})")
    }
}

    Expression Problemをどう解決するか

    従来のExpression Problemは、表現に関する二つの軸を扱います。

    • 新しいバリアント（ケース）を追加する
    • 新しい操作を追加する

    Denotational Designは、軸を次のように捉え直します。

    • 意味論上の語彙を拡張する：新しいケイパビリティトレイト（MulAlg）を定義する。
    • その語彙に対する新しい解釈を追加する：新しいインタープリター型（Eval、Pretty、ASTビルダー、コード生成器など）を定義する。

    二つの軸は独立して合成できます。

    • 新しいケイパビリティが必要でない限り、既存プログラムは変更しません。expr_basicが必要とするのはLitAlg + AddAlgだけです。
    • 新しいケイパビリティを解釈する必要がない限り、既存インタープリターは変更しません。impl MulAlgを持たないEvalでも、mulを使わないすべてのプログラムを引き続き実行できます。

    実装の組み合わせ表そのものがなくなるわけではありません。EvalとPrettyの両方でmulを解釈する必要があるなら、それぞれにimpl MulAlgが要ります。変わるのは表の整理の仕方です。各セルは意味論的操作×解釈となり、特権的な表現を中心に整理せず、各プログラムは使うケイパビリティだけに依存します。

    法則は仕様に属する

    意味論的代数は、担体、操作、法則で構成されます。担体（type Expr）は解釈が選び、操作と法則は仕様に属します。たとえば、LitAlg + AddAlgの算術上の意味は次のように述べます。

    add(lit(m), lit(n)) = lit(m + n)

    Evalはこの法則を満たします。Prettyは満たしません。"(2 + 3)"は"5"ではないからです。どちらも構文シグネチャの有効なインタープリターですが、算術仕様のモデルとなるのはEvalだけです。法則はトレイトに対して一度だけ述べ、それを満たすインタープリターを選びます。どのインタープリターも法則を所有しません。

    最後の洞察：Featherweight GoとDenotational Design

    Wadlerは、静的型付けとモジュール式の拡張のもとで、行と列をどう扱うかという言語機構の水準でExpression Problemを捉えました。Featherweight Goは具体策を与えます。Plus(type a Any)では再帰表現をジェネリックに保ち、各操作がaを個別に制約します（EvalにはPlus(type a Evaler)、StringにはPlus(type a Stringer)）。表現を一つの閉じた式インターフェースに結び付けないため、両方の軸を開いたままにできます。

    従来の解決策では、表現から出発して二つの拡張軸を開いたままにする方法を問います。Featherweight Goは、再帰表現をジェネリックかつ構造的に拡張可能にして、この問題を驚くほどのところまで解決します。Denotational Designは境界を一歩手前へ移します。表現がモデルではありません。モデルは代数とその法則であり、表現は考えられる解釈の一つです。

    Featherweight Goは表現を拡張可能にし、Denotational Designは表現を任意にする。

    新しい実装新たな構造的実現新しいインタープリター

    Wadlerは、表現の両方の軸をどう拡張するかを問います。Denotational Designは、そもそも表現がいずれかの軸を所有すべきなのかを問います。

    まず合成可能な意味を定め、それから符号化を選びます。Expression Problemは、概念的な行き詰まりではなく、符号化の間で行うエンジニアリング上の選択になります。

    言語の意味は機械という考えから独立しているべきである。

    概念：参照透過性

    このページでは参照透過性をDenotational Designの観点から解釈します。 概念の章では歴史と主要な言語での使い方を扱います。 ここでは、設計上の制約としてのRTの意味に焦点を当てます。

    DDではRTは純粋性のラベルではありません。 表示に関する法則であり、置換によって指定された意味が保持されなければなりません。

    RTをDenotational Designで捉え直す

    Denotational Designでは、RTを実装スタイルではなく仕様への要件として捉え直します。 まず仕様で合成可能な意味を定め、その後で実行戦略を選びます。

    したがって、RTは意味論上の境界で検査します。

    • 同じ入力
    • 同じ宣言済みコンテキスト
    • 同じ表示

    これらが成り立つなら、置換は妥当であり、等式に基づく推論が可能です。具体的なインタープリターがIO、並行性、再試行、状態遷移を行う場合も同様です。それらの詳細は宣言されたケイパビリティの背後に委譲されるためです。

    つまりDDで問うのは「この実装は純粋か」ではありません。 DDで問うのは「表示の等式が明示され、インタープリターがそれを保持しているか」です。

    純粋性とRT

    RTと純粋性は関連しますが、同一ではありません。

    • RTは意味に関する置換法則です。
    • 純粋性は、隠れた観測可能な副作用を認めないという操作上の制約です。

    式レベルのコードでRTを得る一般的な方法は純粋性です。しかしRTは意味論上の基準として残ります。置換によって指定された表示が保たれなければなりません。

    そのためDDはRTを「純粋なコードだけ」といったスタイル上のラベルに変えません。 必要なのは、明示的な意味論的等式と、ケイパビリティ境界の背後に隔離された副作用です。

    最小限の意味論的な読み方は次のとおりです。

    fn f(a: A, io: Io) -> (Result<B, E>, Io)

    同じaと同じio入力のもとで、fは同じ(result, io')を与える。 これはDD形式で、コンテキストを添字にした置換推論です。

    RTを明確にする理由

    RTをめぐる議論では、次の有用な区別が曖昧になることがよくあります。

    • 意味論的な透明性
    • 操作上の副作用

    DDではこれらの層を分けます。

    • 意味論的な中核が意味を述べる
    • インタープリターが実行戦略を実現する

    この分離により、法則に基づく推論を保ったまま実際の副作用を扱えます。

    表現先行で設計する場合の失敗

    具体的な表現を早い段階で決めてしまうと、RTの議論がスタイル論にずれることがあります。

    • 「このスタイルは純粋だ」
    • 「あのスタイルは不純だ」
    • 「IOラッパーで解決できる」

    こうした議論の多くは符号化に関するものです。 DDでは、より単純な問いを立てます。 仕様で妥当な等式は何か。

    実践的なDDのパターン

    小さなケイパビリティトレイトを定義し、それらに基づく拡張としてプログラムの振る舞いを記述します。 その後に薄い具体インタープリターを用意します。

    trait FileSystem {
    type Error;

    fn file_read(&self, name: &str) -> Result<String, Self::Error>;
}

trait GithubPublish {
    type Error;

    fn github_publish(&self, repo: &str, files: Vec<String>) -> Result<(), Self::Error>;
}

trait Concurrent {
    fn map_concurrent<A, B, E, F>(&self, xs: &[A], f: F) -> Result<Vec<B>, E>
    where
        A: Clone,
        F: Fn(&A) -> Result<B, E>;
}

#[ext(name = PublishProjectExt)]
impl<This> This
where
    This: FileSystem<Error = String> + GithubPublish<Error = String> + Concurrent,
{
    fn publish_project(&self, files: &[&str], repo: &str) -> Result<(), String> {
        let files = self.map_concurrent(files, |name| self.file_read(*name))?;
        self.github_publish(repo, files)
    }
}

    #[ext(...)]はextendクレートのマクロで、implブロックから拡張メソッドを生成して定型コードを減らします。Rustの新しい言語機能ではありません。

    Scalaの関数型プログラミングでは、RTをF[A]型の値（例：IO[A]またはF[Either[E, A]]）で表すことがよくあります。 ここでは一段上のレベルで、ケイパビリティによって境界付けられたプログラムの意味としてRTを表します。 そのため、このRustのメソッドはF[A]と同じ符号化の意味でRTの値を格納するコンテナーではありません。明示的なケイパビリティに基づき仕様化されたRTの振る舞いであり、具体的な副作用は実装に委譲されます。

    拡張はケイパビリティに対する意味論上の振る舞いを述べます。 具体的な実装が、バッチ処理、再試行、通信方式、並列性、格納の詳細などの実行戦略を決めます。

    Rustで意味から設計する：インタープリターと副作用、一階プログラム、言語とコンパイラーパイプライン
    概念：操作的意味論、自由モナド、継続渡し形式、関数のデファンクショナライズ

    Ethereum Virtual Machine（EVM）は、Ethereumバイトコードを実行するスタックベースの仮想CPUです。このバイトコードはSolidity、Vyper、その他のEVM互換言語で書かれたスマートコントラクトのコンパイル結果です。

    最も低いレベルでは：

    • EVMはオペコード（ADD、PUSH、JUMP、SSTOREなど）を処理する。
    • Execution state includes:
      • スタック：オペランド用の後入れ先出しデータスタック。
      • メモリー：一時的な値を格納するバイト配列。
      • ストレージ：コントラクトごとに用意される永続的なキー・バリューストア。
      • プログラムカウンター：次のオペコードを指す。
      • Gas：実行ステップに課金する計量機構。

    インタープリターパターンとしてのEVM

    EVMクライアントは命令言語のインタープリターです。

    • 命令セット＝EVMオペコード（バリアントの列挙型）。
    • プログラム＝命令の列。
    • インタープリター＝各オペコードによって機械状態がどう変わるかを定める規則。
    • 複数のインタープリター＝EVMの仕様は固定されており、Geth、Nethermind、Besu、Erigonは同じインタープリターの代替実装である。

    本書で扱う三つの技法、自由モナド、継続渡し形式、デファンクショナライズを結ぶ筋道は、プログラムの残りをどう表すかの違いです。

    一つの機械を表す三つの符号化

    以下の各符号化は、同じ固定プログラムを実行します。

    push 2; push 3; add; sstore 1 5; load 1 -> v; push v

    どの形式でも同じ観測結果になります。

    stack:   [5, 5]
storage: {1: 5}

    違うのは、制御、つまり「次に何をするか」の表現方法だけです。

    自由モナド — プログラムをデータとして表し、インタープリターが意味を与える

    命令ファンクターがプログラム木を生成します。and_thenはモナド的bindで、runは一つのインタープリターです（バイトコードへのコンパイラーなど、二つ目のインタープリターでも同じ木をfoldできます）。ジェネリックなFree<A>は、この命令セットに特化することで安定版Rustでもコンパイルできます。

    use std::collections::HashMap;

struct State { stack: Vec<u64>, storage: HashMap<u64, u64> }

// The free monad over the EVM instruction set: a program is data — a tree of
// instructions ending in `Pure`, each carrying its continuation.
enum Free<A> {
    Pure(A),
    Push(u64, Box<Free<A>>),
    Add(Box<Free<A>>),
    SStore(u64, u64, Box<Free<A>>),
    SLoad(u64, Box<dyn FnOnce(u64) -> Free<A>>),
}

impl<A: 'static> Free<A> {
    // Monadic bind: graft `k` onto every leaf of the program.
    fn and_then<B: 'static>(self, k: impl FnOnce(A) -> Free<B> + 'static) -> Free<B> {
        match self {
            Free::Pure(a) => k(a),
            Free::Push(v, next) => Free::Push(v, Box::new(next.and_then(k))),
            Free::Add(next) => Free::Add(Box::new(next.and_then(k))),
            Free::SStore(x, y, next) => Free::SStore(x, y, Box::new(next.and_then(k))),
            Free::SLoad(key, cont) => Free::SLoad(key, Box::new(move |v| cont(v).and_then(k))),
        }
    }
}

fn push(v: u64) -> Free<()> { Free::Push(v, Box::new(Free::Pure(()))) }
fn add() -> Free<()> { Free::Add(Box::new(Free::Pure(()))) }
fn sstore(k: u64, v: u64) -> Free<()> { Free::SStore(k, v, Box::new(Free::Pure(()))) }
fn sload(k: u64) -> Free<u64> { Free::SLoad(k, Box::new(|v| Free::Pure(v))) }

// Interpreter: give the program data meaning against the machine state.
fn run(mut prog: Free<()>, st: &mut State) {
    loop {
        prog = match prog {
            Free::Pure(()) => return,
            Free::Push(v, next) => { st.stack.push(v); *next }
            Free::Add(next) => {
                let b = st.stack.pop().unwrap();
                let a = st.stack.pop().unwrap();
                st.stack.push(a + b);
                *next
            }
            Free::SStore(k, v, next) => { st.storage.insert(k, v); *next }
            Free::SLoad(k, cont) => { let v = *st.storage.get(&k).unwrap_or(&0); cont(v) }
        };
    }
}

fn main() {
    let program = push(2)
        .and_then(|_| push(3))
        .and_then(|_| add())
        .and_then(|_| sstore(1, 5))
        .and_then(|_| sload(1))
        .and_then(|v| push(v));

    let mut st = State { stack: vec![], storage: HashMap::new() };
    run(program, &mut st);
    println!("stack:   {:?}", st.stack);
    println!("storage: {:?}", st.storage);
}
    継続渡し形式（CPS） — 各オペコードが「プログラムの残り」を呼び出す

    各ハンドラーは処理を行い、その後継続kを呼び出します。sloadでは、読み込んだ値をそれを受け取る継続に渡します。制御はネストされた継続として明示され、プログラムのデータ構造はありません。

    use std::collections::HashMap;

struct State { stack: Vec<u64>, storage: HashMap<u64, u64> }

// Each opcode does its work, then calls the continuation `k` = "the rest of
// the program". `sload` passes the loaded value on to its continuation.
fn push(st: &mut State, v: u64, k: impl FnOnce(&mut State)) {
    st.stack.push(v);
    k(st);
}
fn add(st: &mut State, k: impl FnOnce(&mut State)) {
    let b = st.stack.pop().unwrap();
    let a = st.stack.pop().unwrap();
    st.stack.push(a + b);
    k(st);
}
fn sstore(st: &mut State, key: u64, val: u64, k: impl FnOnce(&mut State)) {
    st.storage.insert(key, val);
    k(st);
}
fn sload(st: &mut State, key: u64, k: impl FnOnce(&mut State, u64)) {
    let v = *st.storage.get(&key).unwrap_or(&0);
    k(st, v);
}

fn main() {
    let mut st = State { stack: vec![], storage: HashMap::new() };

    push(&mut st, 2, |st| {
        push(st, 3, |st| {
            add(st, |st| {
                sstore(st, 1, 5, |st| {
                    sload(st, 1, |st, v| {
                        push(st, v, |_st| {});
                    });
                });
            });
        });
    });

    println!("stack:   {:?}", st.stack);
    println!("storage: {:?}", st.storage);
}
    デファンクショナライズ — 操作の呼び出しをデータに変え、一つのapplyで実行する

    自由モナド版とCPS版は、仕様のように読める小さな代数である操作（push(2)、add()、sstore(1, 5)、sload(1)）を呼び出します。デファンクショナライズでは、各呼び出しを一階データとして再構化します。一つのapply関数でそのデータを解釈し、継続もまとめます。「プログラムの残り」は次のインデックス（pc）になります。操作の代数をデータとして記述し、apply一つのインタープリターで解釈すると考えてください。

    use std::collections::HashMap;

struct State { stack: Vec<u64>, storage: HashMap<u64, u64> }

// The EVM algebra reified: where the other encodings CALL `push(2)`, `add()`,
// `sstore(1, 5)`, `sload(1)`, each such call becomes a first-order value — a
// tag with its arguments.
enum Op {
    Push(u64),
    Add,
    SStore(u64, u64),
    SLoad(u64),
}

// `apply` is the single interpreter for the reified operations: it gives each
// tag its meaning against the machine state.
fn apply(op: &Op, st: &mut State) {
    match op {
        Op::Push(v) => st.stack.push(*v),
        Op::Add => {
            let b = st.stack.pop().unwrap();
            let a = st.stack.pop().unwrap();
            st.stack.push(a + b);
        }
        Op::SStore(k, v) => { st.storage.insert(*k, *v); }
        Op::SLoad(k) => {
            let v = *st.storage.get(k).unwrap_or(&0);
            st.stack.push(v);
        }
    }
}

fn main() {
    // The program is now data: a flat list of reified operation calls.
    let code = vec![
        Op::Push(2),
        Op::Push(3),
        Op::Add,
        Op::SStore(1, 5),
        Op::SLoad(1),
    ];

    // `pc` is the defunctionalized continuation: "the rest of the program" is
    // just the next index.
    let mut st = State { stack: vec![], storage: HashMap::new() };
    let mut pc = 0;
    while pc < code.len() {
        apply(&code[pc], &mut st);
        pc += 1;
    }

    println!("stack:   {:?}", st.stack);
    println!("storage: {:?}", st.storage);
}

    継続からバイトコードへ

    三つの符号化は、機械との距離の異なる場所から同じ計算を見たものです。

    • 自由モナドでは、プログラムを代数的にデータとして構築し、その後で解釈します。同じ木を複数のインタープリターでfoldできます。実行用、整形表示用、コンパイル用などを用意できます。
    • CPSではデータ構造を取り除き、制御を明示します。「このオペコードを実行し、その後に継続を呼び出す」。読み込んだ値は、それを必要とする継続へ流れます。
    • デファンクショナライズでは、操作の呼び出しを一階データにし、一つのapplyで読み戻します。同時に継続は、Vec<Op>上のpcへと縮約されます。ドライブループはクロージャのないCPSトランポリンです。

    類推であり、導出ではない

    EVMは、明示的なプログラムカウンターを持つ一階抽象機械として分析できます。その構造はデファンクショナライズされた制御表現に似ています。しかしこの類似だけでは、EVMバイトコードがCPS変換の後にデファンクショナライズして得られた証明にはなりません。

    Denotational Design

    プログラムの実行方法を決める前に、その意味を定義する。

    この考え方では、計算は不透明な手順の列ではなく、透明な数学的対象です。まず、プログラムが何を意味するかを純粋かつ合成可能に記述する仕様から始めます。多くの場合、代数構造、トレイト、型シグネチャで表現します。意味をどう実現するかを担う実装は、独立して交換可能な層です。

    意味と仕組みを分けることで、次の利点を得られます。

    • 明快さ — プログラムが正確な定義のように読める。
    • 合成可能性 — 部品が代数的に組み合わさる。
    • リファクタリングのしやすさ — 実装が進化しても意味は固定される。
    • 正しさ — 操作手順ではなく等式でプログラムを推論できる。

    本書のガイドラインは、数学的な基盤の優雅さと厳密さを失わずに、現代のプログラミング言語、特にRustでこの設計を実践する技法を提供します。

    本書では、意図的に三つの水準を区別します。

    • 意味では、どの値、関係、変換を設計しているかを定める。
    • 表現では、その意味を型やデータにどう符号化するかを選ぶ。
    • 実行では、機械上で表現をどう動かすかを選ぶ。

    例の多くはALUXとTolangに着想を得ていますが、この版を読むためにそれらを知る必要はありません。本書ではまず語彙を定めます。
