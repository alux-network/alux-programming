    ALUX 程式設計指南

    注

    本書將介紹理解並參與 ALUX 語義優先程式碼庫所需的基礎，從指稱設計的一項核心原則講起：先定義程式的含義，再決定程式如何執行。

    沿襲 Conal Elliott 的思路，本書將計算視為清晰的數學物件，而不是不透明的步驟序列。

    規範以簡單、可組合的能力 trait表達，用來描述程式意味著什麼。直譯器提供可互換的方式來實現這些含義。

    這樣一來，軟體的組合規則、實作義務和有效等式都更容易理解和測試。

    機制與含義

    概念與洞見用於說明實用的程式設計機制。指稱設計則說明如何判斷這些機制應當保留什麼。

    如何閱讀本書

    本書分三個層次閱讀：

    • 語義視角介紹指稱與組合性、定律與解釋，以及含義與表示之間的關係。
    • Rust 中的語義驅動設計將這一視角落實為小型能力、派生擴充、一階程式和輕量級直譯器。
    • 概念與洞見介紹重要的執行模型、編碼、變換與連結。

    語義原則不依賴特定語言。Rust 是主要實作語言；一條併發語言處理流水線將這些原則與 Tolang 連結起來。

    • 希望複雜軟體在不斷演進時仍能保持模組化、可組合、可測試且易於維護的程式設計師。

    導讀

    指稱設計先確定程式的含義，再推導出詞彙、表示與執行策略，以保留該含義。本頁將這種語義順序與大多數軟體採用的表示優先順序作對比。

    大多數軟體按照執行順序來設計：

    1. 選擇狀態。
    2. 選擇控制流。
    3. 圍繞這些機制公開方法。
    4. 事後再解釋這些方法原本意在表達什麼。

    指稱設計將順序倒轉：

    1. 選擇含義。
    2. 確定其組合結構。
    3. 從該結構推導詞彙。
    4. 選擇表示與執行策略。
    5. 驗證它們是否保留了原有含義。

    這種倒轉就是語義視角。

    機制與含義

    概念與洞見用於說明實用的程式設計機制。指稱設計則說明如何判斷這些機制應當保留什麼。

    三個問題

    設計程式時，要把三個問題分開考慮。

    視角問題典型產物
    語義這個程式意味著什麼？值、關係、函式、等式、定律
    表示這個含義如何編碼？Rust 型別、trait、抽象語法樹、表、樹、位元組碼
    操作這種表示如何執行？迴圈、可變狀態、任務、訊息、直譯器、虛擬機器

    這三種視角都很重要。錯誤在於讓表示或執行悄然替語義視角下定義。

    操作語義對執行過程作出精確且有價值的說明。它可以描述求值器執行的每一次狀態轉換，但它回答的設計問題仍與指稱描述不同。指稱問題關注整個程式所指稱的可觀察數學值，以及無論採用何種執行策略都應成立的等式。

    一個小例子

    假設某個系統要標識分支過程中的位置。

    表示優先的設計可能從一個位向量開始：

    struct BranchId(Vec<bool>);

    隨後，方法圍繞這些欄位不斷增加：追加一位、擷取字首、比較向量、序列化位元組。

    語義視角從別處開始：

    • 存在一個根位置。
    • 位置可以向左或向右延伸。
    • 一個位置可以是另一個位置的祖先。
    • 可以觀察祖先與後代之間的路徑。

    即便表示後來變成整數、樹座標、緊湊的混合值或資料庫鍵，這些陳述仍然有意義。位向量只是對分支位置的一種解釋，而不是它的定義。

    含義不是事後補寫的文件

    為具體 API 寫說明文字，並不會讓設計變成指稱式設計。含義必須先約束 API，然後才能選擇表示。

    語義描述應當說明：

    • 哪些區別很重要
    • 哪些觀察是基本的
    • 更大的含義如何組合
    • 哪些等式有效
    • 每種實作都必須保留什麼
    • 哪些細節有意忽略

    如果唯一精確的產物只是狀態結構體或執行迴圈，那麼含義仍由實作掌控。

    抽象與含義

    上下文 trait 並不定義含義

    一個介面可以隱藏機制，卻不解釋含義：

    trait ApplicationContext {
    fn database(&self) -> &Database;
    fn settings(&self) -> &Settings;
    fn runtime(&self) -> &Runtime;
}

    這個介面抽象了對具體元件的存取，但沒有說明計算所要求的語義觀察。

    直接詢問含義

    面向含義的介面會直接詢問所需的觀察：

    trait BranchAlg {
    type Branch;

    fn branch_root(&self) -> Self::Branch;
    fn branch_grow(&self, branch: &Self::Branch, direction: Direction) -> Self::Branch;
    fn branch_path(
        &self,
        ancestor: &Self::Branch,
        descendant: &Self::Branch,
    ) -> Option<Vec<Direction>>;
}

    依賴倒置固然有用，但指稱設計要求更多：抽象邊界必須圍繞含義組織，而不是圍繞儲存位置。

    權威的方向

    當各類產物彼此矛盾時，不要把權威交給最接近執行程式碼的那個。應當先問每個產物各自必須保留什麼。

    角色此處應包含什麼職責
    含義領域預期的觀察、區別與相等關係決定正確性的含義
    規範語義域、指稱、型別、基本操作、定律與派生組合精確陳述含義
    實現具體表示、直譯器、編譯器、執行時、儲存與排程實作規範而不改變規範
    證據證明、定律檢查、場景與跨直譯器比較將實現與規範關聯起來；它本身不定義含義

    由此得到一條解決分歧的實用規則：

    • 如果實作違反了語義定律，就修改實作。
    • 如果測試與它原本要檢查的定律相矛盾，就修改測試。
    • 如果形式規範未能表達預期的領域含義，就修訂規範。

    產物應按其作用分類，而不是按其語法分類。Rust trait 或一階程式若直接保留了選定的語義結構，就可以屬於規範；另一個 Rust 型別則可能只是某種具體編碼。形式操作語義也可以屬於語言規範，但其中的狀態轉換仍須符合該語言所要求的觀察與等價關係。

    CPS、去函式化、自由單子、虛擬機器、協議執行時和編譯器流水線，如今都可以放在適當的位置，而無須爭論哪一種才是最終抽象。它們各自是適用於特定使用者的表示或執行技術。語義規範說明每種選用的技術都必須保留什麼。

    指稱與組合性

    相關內容

    核心思想

    指稱是從語法對映到所選語義域的含義函式。當整體的含義由各部分的含義確定時，語義就是組合式的；這使語義等價與安全替換成為可能。

    指稱是賦予一段語法或一個程式設計構造的含義。通常記作：

    [[e]]

    表示“表示式e的含義”。

    這些括號並不要求指稱必須是一個數字。根據所選語義域，程式可以指稱：

    • 一個值
    • 一個函式
    • 一個關係
    • 一組可能結果
    • 一個狀態變換
    • 一個機率分佈
    • 一種過程行為
    • 一個部分結果

    因此，第一個設計決策不是“用哪個結構體來儲存它？”，而是“我們關心的含義屬於哪個語義域？”

    語義域

    對於算術表示式，一個簡單的語義域可以是整數：

    [[e]]eval​∈Z

    對於格式化，同一種表示式語言也可以解釋為文字：

    [[e]]pretty​∈String

    對於帶效應的計算，語義域可以是狀態變換：

    [[p]]:State→Result×State

    對於併發語言，語義域可以描述可觀察到的過程行為，而非某一條預先確定的軌跡。

    所選語義域決定哪些差異有意義。如果語義域不包含時間，那麼兩個時序不同的實作仍可能指稱同一個程式。如果把資源消耗納入語義域，這種差異就可能具有語義意義。

    抽象會有意忽略細節

    有用的指稱會忽略無關的機器細節。

    對於分支位置，指稱可以保留從根到該位置的路徑，同時忽略：

    • 位元組佈局
    • 分配策略
    • 快取行為
    • 序列化格式

    對於 HTTP 程式，可移植的指稱可以保留方法、路徑、輸入角色、操作和輸出角色，同時忽略承載它的路由器或執行器。

    對於編譯器階段，指稱可以保留從正規化原始碼到可執行含義的轉換，同時忽略臨時緩衝區與遍歷順序。

    忽略細節不是缺陷。正是如此，不同表示才可能等價。

    組合性

    當整體的含義由各部分的含義及其組合方式共同決定時，語義就是組合式的。

    對於加法：

    [[a+b]]=[[a]]+[[b]]

    對於順序函式組合：

    [[g∘f]]=[[g]]∘[[f]]

    對於並行過程運算子，語義域需要相應的並行組合：

    [[P∣Q]]=[[P]]⊗[[Q]]

    具體運算子⊗取決於所選的過程模型。關鍵在於，語法組合應系統地對映到語義組合。

    組合性支援區域性推理。如果兩個部分的指稱相同，就可以在任意組合上下文中相互替換：

    [[P]]=[[Q]]⟹[[C(P)]]=[[C(Q)]]

    這是安全替換與語義重構的基礎。

    語義等價

    程式不必在文字或操作上完全相同，才能在語義上等價。

    考慮分支位置的兩種實作：

    [Left,Right,Left]

    以及一種指稱相同路徑的整數編碼。它們的記憶體值不同，但指稱可能相等。

    同樣，兩個編譯器過程可以按不同順序遍歷語法，卻生成行為符合相同規範的可執行檔案。是否要求逐位元組相等，是另一個更強的定律。

    務必明確指出所聲稱的等價關係：

    • 值相等
    • 結構相等
    • 規範表示相等
    • 軌跡等價
    • 雙模擬
    • 觀察等價
    • 指稱相等

    混淆這些等價關係，是錯誤定律的常見來源。

    外部性是相對的

    假設某個計算具有如下含義：

    H×E→O

    相對於H而言，證據E是外部的。如果新的抽象選擇H × E作為承載物件，那麼這些證據對於新的邊界來說就變成內部的。

    這一觀察對效應與上下文都很重要。沒有任何事實絕對屬於“環境”。關鍵在於當前語義承載物件是否包含該事實，以及有哪些定律支配它。

    避免使用通用上下文物件

    不要用一個通用上下文物件來解決這個邊界問題。將每種允許的含義明確命名為一種能力或顯式值。

    基本含義與派生含義

    基本操作是選作語義域詞彙的操作。派生操作則由基本操作定義。

    對於分支位置，一組精簡的基本詞彙可以包括：

    • 一個根位置
    • 沿某個方向延伸
    • 觀察一個位置到另一個位置的路徑

    由此可以派生：

    • 向左延伸
    • 向右延伸
    • 根據路徑構造位置
    • 測試一個位置是否為另一個位置的祖先
    • 測試一個位置是否為另一個位置的後代

    這種區分是設計選擇，而非形而上學事實。應優先採用精簡的基本操作集合，讓定律與其他解釋更容易表述。

    一項實用檢驗

    在引入程式設計介面之前，先補全以下句子：

    • 這個抽象中的值意味著……
    • 基本觀察包括……
    • 有意義的組合包括……
    • 當……時，兩個值等價
    • 每種實作都必須保留……
    • 該抽象有意忽略……

    如果這些句子無法補全，再多的實作機制也無法補上缺失的含義。

    指稱設計

    相關內容

    核心思想

    指稱設計從簡單、可組合且獨立於實作的含義推導出程式設計介面，讓語義來引導設計，而不是事後描述介面。

    指稱設計是一種從簡單、可組合且獨立於實作的含義推導程式設計介面的方法。

    該方法由Conal Elliott提出並命名。它的核心做法不僅是為現有語言或 API 賦予語義，而是讓語義引導 API 本身的設計。

    設計迴圈

    按以下順序進行：

    1. 選擇語義域。
    2. 確定該語義域中重要的結構。
    3. 選擇一組精簡的基本操作詞彙。
    4. 以組合方式派生有用操作。
    5. 陳述這些操作遵循的定律。
    6. 選擇一種或多種表示。
    7. 實作能夠保留該結構的解釋。
    8. 透過定律、模型與場景進行驗證。

    表示優先的設計通常從第 6 步開始，然後試圖事後補出第 1 至第 5 步。

    設計分支代數

    回到分支位置。預期含義是二叉分支結構中的有限路徑。

    一種可能的基本代數是：

    rootgrowpath​:()→Branch:Branch×Direction→Branch:Branch×Branch⇀List(Direction)​

    偏箭頭⇀表示路徑觀察僅在第一個分支是第二個分支的祖先時才存在。

    由此可得一些有用操作：

    left(b)right(b)is_ancestor(a,b)from_path(ds​)​=grow(b,Left)=grow(b,Right)⟺path(a,b) is defined=fold(grow,root,ds​)​

    這個代數沒有提到向量、整數、分數、資料庫鍵或位元組。這些選擇留待後續。

    先結構，後便利

    基本詞彙應揭示下游程式碼所依賴的結構，而不應變成某種實作上所有便利方法的集合。

    拒絕表示優先的基本操作

    這個 trait 將儲存佈局、配置位置、位表示和複合工作流捆綁在一起，並未隔離分支含義：

    trait BranchManager {
    // not recommended: exposes machinery, not semantic observations
    fn storage(&self) -> &BranchTable;
    fn config(&self) -> &BranchConfig;
    fn raw_bits(&self) -> &[u64];
    fn grow_and_save(&mut self, right: bool);
}

    當效應屬於所選語義域時，語義 API 仍然可以包含效應。規則並不是“所有東西都必須是純函式”，而是“每個基本操作都必須表達連貫的含義”。

    編碼方式不是方法論

    指稱設計不要求使用：

    • Haskell
    • tagless-final 編碼
    • 物件代數
    • 自由單子
    • 單一抽象語法樹
    • 僅使用純函式
    • 每個 API 都採用範疇論術語

    這些可以是有用的編碼方式或解釋工具，但沒有一種能夠定義該方法。

    Rust 編碼方式

    在 Rust 中，小型 trait、關聯型別、擴充方法、泛型函式和一階程式值都是實用的編碼方式。它們的價值取決於是否保留了清晰的語義設計。

    型別類態射

    理解該方法的一種方式，是把它看作保結構對映。

    假設某個介面描述了一個語義代數。實作會將其抽象值與操作對映到具體表示中。有效實作必須保留相關操作與定律。

    如果encode將抽象分支對映到具體載體，那麼保留延伸操作的形式如下：

    encode(grow(b,d))=growconcrete​(encode(b),d)

    實作不只是一個方法名稱相同的集合。它應當是一個尊重代數結構的態射。

    什麼樣的抽象才算好

    一個好的指稱設計抽象具備以下特徵：

    • 其中的值具有簡單明確的預期含義。
    • 基本操作用於揭示語義觀察或構造。
    • 更大的行為由這些基本操作派生。
    • 其定律不依賴某一種表示。
    • 可以由彼此獨立的實作來解釋。
    • 只有在相關時才引入操作細節。

    僅僅精簡還不夠。即使一個小型 trait 暴露了get_manager()，它仍可能是表示優先的。若某個更大的代數包含的操作構成連貫的語義結構，也可能是合理的。

    語義值與抽象載體

    並非所有具體型別都不能寫入規範。

    當直譯器應當選擇載體時，使用關聯型別：

    trait BranchAlg {
    type Branch;
}

    當某個型別屬於穩定的語義詞彙時，使用具體型別：

    enum Direction {
    Left,
    Right,
}

    區別並非“抽象好，具體壞”，而是語義詞彙與偶然的機器表示之別。

    規範就是指稱，而且不必可執行

    規範就是指稱：賦予每種構造的數學含義。它的力量在於不受效率約束，甚至不必能夠執行。

    Conal Elliott

    定義指稱通常比實作容易得多，也更能帶來啟發，因為指稱不受效率或可執行性的約束，也不會受到它們的干擾。

    ——《指稱設計：從含義到程式》（LambdaJam 2015）

    經典示例是 FRP（函式式響應式程式設計）：Behavior a被定義為連續時間上的函式，

    [[⋅]]:Behavior a→(R→a)

    這個模型很精確，卻無法執行——實數無法逐個列舉。程式也可以指稱一組結果；這兩種模型都無法執行，但這正是其用意所在。選擇含義是為了簡潔和精確，而不是為了計算方式。

    可執行性與效率完全交由實作負責；實作是獨立產物，藉助將其與含義關聯起來的同態定律（型別類態射）來保證正確性：含義函式必須把每種語法組合對映為相應的語義組合。正如 Conal 所說，指稱給出了對待實作之事明確無歧義的定義，同時為如何實作留下了很大的創作空間。

    在 Rust 中，有幾種產物可以表達這份規範的部分內容，其中一些恰好可以執行。可執行性只是偶然屬性，不是它們成為規範的原因：

    • 說明文字陳述預期含義
    • trait 陳述可用的基本操作
    • 擴充陳述派生方式
    • 定律陳述必需的等式
    • 直譯器展示可實現性
    • 測試提供有限證據

    應結合起來閱讀，並讓含義與定律在權威性上優先於具體機制。

    定律與解釋

    相關內容

    核心思想

    定律說明語義介面中的操作如何相互關聯；解釋則指定必須保留這些定律的具體載體。所選等價關係決定直譯器之間哪些差異有意義，哪些差異可以自由變化。

    語義介面為操作命名，定律說明這些操作之間的關係。沒有定律時，兩個實作可以滿足相同的 Rust 函式簽名，卻對抽象的含義各執一詞。

    定律補全詞彙

    對於分支位置，有用的定律包括：

    path(b,b)path(root,from_path(ds​))from_path(path(root,b))is_ancestor(b,b)left(b)​=[]=ds​=b=true=right(b)​

    這些定律所說明的內容，遠超方法註釋。它們描述了單位元、重構、自反性與分離性。

    並非每個看起來合理的等式都有效。例如，定寬表示可能在深度極大時溢位。這可能是：

    • 直譯器在其適用域之外的限制
    • 介面必須暴露的語義錯誤
    • 所選載體有誤的證據

    設計必須說明屬於哪一種。

    解釋

    解釋為語義代數指定具體載體與操作。

    語義程式可能的解釋
    分支位置位路徑、數值樹、符號形式
    表示式程式求值器、漂亮列印器、最佳化器
    型別化 API 程式可執行的伺服器路由、文件、客戶端生成器

    同一個程式可以有多種解釋，因為程式並不等同於某一種結果。

    實作義務

    直譯器必須保留規範所聲稱的結構。

    如果語義程式中的合併滿足結合律：

    (a⊕b)⊕c=a⊕(b⊕c)

    那麼直譯器就應當保留這種結合方式的可觀察含義。如果路由順序也有規範要求，等價關係就必須包含順序。如果有意忽略順序，實作可以在操作層面不同，但仍保持語義等價。

    因此，必須先選定語義域與等價關係，再編寫定律。

    定律、證明與測試

    這些術語不能互換：

    • 定律是抽象所普遍要求的性質。
    • 證明在給定假設下確立某條定律。
    • 性質測試檢查大量生成的示例。
    • 場景測試檢查一個有意義的有限情境。
    • 單元測試檢查一種具體行為。

    測試是可執行的證據，而非普遍證明。它們仍然很有價值，因為可以用來檢查每個直譯器。

    可執行證據

    語義定律獨立於其實作。可執行檢查為直譯器是否保留這些定律提供有限證據：性質檢查用於考察類似等式的主張，場景則用於考察可觀察的互動。如果只使用語義操作來編寫，同一組證據就能在相容的直譯器之間複用。測試為規範提供支援，但不定義也不證明規範。

    Rust 編碼方式見《定律、場景與證據》。

    多個直譯器有助於澄清含義

    並非每個小型 trait 都需要第二種實作，但第二種實作是一項有力的設計檢驗。

    如果一條自稱抽象的定律只能用第一種實作的欄位來表述，那麼語義邊界很可能劃錯了。如果第二個直譯器無需模仿第一個表示，就能實作基本操作並滿足同一組定律，那麼這個抽象就更站得住腳。

    中性直譯器尤其有用：

    • 文字直譯器會揭示程式結構
    • 純記憶體模型會隔離定律
    • 追蹤直譯器會揭示選定的觀察
    • 生產直譯器會執行真實效應

    等價關係決定重構自由度

    每一種語義等價都賦予實作一定自由。如果根據選定的指稱，兩個表示相等，實作就可以互換它們。

    每一種被忽略的觀察也會帶來自由。如果分配順序不屬於語義，它就可以改變。如果方法順序屬於語義，就不能改變。

    因此，定律不只是正確性約束。它們還界定了最佳化、替換與演進的安全空間。

    1. 語義載體是什麼？
    2. 抽象有意忽略了什麼？
    3. 哪些操作是基本操作？
    4. 哪些操作是派生操作？
    5. 採用哪種等價關係？
    6. 每個直譯器都必須保留哪些定律？
    7. 哪些證據會在直譯器之間共享？

    本書其餘部分將展示一種實用的 Rust 解法。它是這幅語義圖景的一種編碼，而非其替代品。

    語義定位

    依賴型別可在型別系統中表達由值索引的命題與證據。它們可以編碼語義規範的一部分，卻不能替我們選擇規範：在把預期性質提升為型別之前，必須先弄清楚該性質。

    由值索引的型別

    當型別可以依賴某個值時，它就是依賴的。因此，依賴型別不僅能描述值的形態，還能描述該值必須滿足的關係。

    例如：

    • Vec<n, T> —— 由長度索引的向量 n
    • Matrix<rows, cols, T> —— 由維度索引的矩陣
    • Proof<p> —— 某個命題的證據 p

    例如：

    append : Vec<n, T> -> Vec<m, T> -> Vec<n + m, T>

    結果型別表明，將長度分別為n和m的向量拼接後，會得到長度為n + m的向量。

    依賴函式

    依賴函式型別寫作：

    Π(x:A).B(x)

    對於每個值x（型別為A），結果的型別為B(x)。比較：

    fg​:A→B:(x:A)→B(x)​

    f的結果型別是固定的。g的結果型別則可能隨輸入變化。

    根據“命題即型別”的對應關係，型別可以陳述一個命題，而擁有該型別的項可以充當證明。這有助於構建 API，使無效狀態、轉換或組合無法被構造出來。

    與指稱設計的關係

    指稱設計首先會問：

    1. 語義域是什麼？
    2. 哪些觀察與組合很重要？
    3. 必須滿足哪些定律？

    隨後，依賴型別可以將其中一些答案內化。型別索引可以記錄向量長度、協議狀態、棧深度、資源上限，或兩個構造指稱同一結果的證明。

    順序很重要。複雜的型別無法補上缺失的含義。只有當索引命題已經描述了預期的語義區別或刻意選擇的表示不變數時，它才會強化規範。

    不要混淆語義命題與表示不變數

    二者都可以編碼到型別中，但權威範圍不同。每個相容直譯器都必須保留語義命題；表示不變數則只約束選擇它的那種表示。

    證明與可執行證據

    證明會在給定假設下確立一個命題。性質測試、場景測試與單元測試則提供有限的可執行證據。將命題編碼為依賴型別，可能讓型別檢查器驗證證明項，但這並不會把測試變成證明，也不會讓編譯器成為命題的來源。

    本書始終採用同樣的區分：含義與定律陳述義務，工具負責檢查或實現它們。

    在 Rust 中運用該模型

    Rust 並非完全依賴型別語言，但 const 泛型、型別狀態、關聯型別與 trait 約束可以表達有用的索引關係。這些編碼方式能夠把檢查移到編譯期，而且通常保留高效的具體表示。

    即便 Rust 無法表達完整命題，證明導向的思維方式仍然有價值。明確陳述不變數，編碼型別系統能夠強制的部分，併為其餘部分保留定律或測試。編碼服務於規範，而非取代規範。

    Pos0x0.right()指稱Pos1x0；越過邊緣不是執行時錯誤，而是無法透過型別檢查的程式，因為到達邊界時不會生成相應的移動操作。

    這正是本節所述的提升：原本屬於值世界的座標被提升到型別中，有效導航於是成為總函式，並在編譯期接受檢查。這些標記型別的大小為零，因此索引命題不產生執行時開銷。

    能力代數

    導讀

    能力 trait 是一種小型代數：它為某種含義所需的基本觀察與變換命名，並將表示留給直譯器決定。應根據含義設計詞彙，而非根據首個實作恰好包含哪些欄位。

    Rust 沒有名為“指稱設計”的內建構造。我們用普通語言特性來編碼語義詞彙。小型能力 trait 是一種實用的編碼方式。

    本書中的字尾Alg表示代數：一組作用於由直譯器選擇的載體之上的連貫基本操作。

    從含義出發

    前一部分中的分支位置含義可以表示為：

    #[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum Direction {
    Left,
    Right,
}

pub trait BranchAlg {
    type Branch;

    fn branch_root(&self) -> Self::Branch;
    fn branch_grow(&self, branch: &Self::Branch, direction: Direction) -> Self::Branch;
    fn branch_path(&self, ancestor: &Self::Branch, descendant: &Self::Branch) -> Option<Vec<Direction>>;
}

    該 trait 陳述了三種基本含義：

    • 構造根位置
    • 沿一個方向延伸分支
    • 在路徑存在時觀察相對路徑

    它不會暴露分支儲存在哪裡，也不會暴露路徑如何編碼。

    能力不等於欄位投影

    欄位投影不是語義能力

    比較：

    trait BranchContext {
    fn branches(&self) -> &Vec<Vec<bool>>;
    fn branches_mut(&mut self) -> &mut Vec<Vec<bool>>;
}

    這個 trait 用方法隱藏了結構體，卻仍然暴露其表示。任何派生邏輯都會與向量、布林值、所有權和修改策略耦合。

    語義能力暴露的是下游含義所需的觀察或變換。請思考：

    審視每種能力

    如果實作改用資料庫、符號項、緊湊整數或遠端服務，這個操作是否仍然說得通？

    如果答案是肯定的，該操作就可能屬於此能力。如果呼叫者必須依賴當前欄位佈局，那它很可能不該屬於此處。

    每個 trait 表達一種基本含義

    小型 trait 能讓依賴一目瞭然：

    pub trait ClockAlg {
    type Instant;

    fn clock_now(&self) -> Self::Instant;
}

pub trait DeadlineAlg<Instant> {
    fn deadline_expired(&self, now: &Instant) -> bool;
}

    需要時間與截止時間的派生操作可以同時要求這兩種 trait。它不需要一個ApplicationContext囊括日誌、儲存、網路、配置和排程的上下文。

    “小”不等於機械地只包含一個方法。當操作構成不可分割的語義結構時，應將它們放在一起；當它們表達彼此獨立的含義或允許獨立直譯器時，應將它們拆開。

    關聯型別選擇載體

    當表示由直譯器選擇時，使用關聯型別：

    pub trait SourceAlg {
    type Source;
    type Error;

    fn source_read(&self, name: &str) -> Result<Self::Source, Self::Error>;
}

    除非String、std::io::Error或具體語法樹在此邊界上屬於穩定的語義詞彙，否則不要要求它們。

    反過來，具體語義值也完全可以使用：

    pub enum Severity {
    Warning,
    Error,
}

    規則不是“讓所有型別都抽象”，而是“不要混淆直譯器機制與語義詞彙”。

    在使用處新增約束

    讓基本操作不受它用不到的約束：

    pub trait CandidateAlg {
    type Candidate;

    fn candidates(&self) -> impl Iterator<Item = Self::Candidate>;
}

    不要預先新增約束

    不要僅僅因為某個未來演算法可能需要某項能力，就限制關聯型別：

    pub trait CandidateAlg {
    // not recommended: every interpreter now pays for bounds
    // most operations never use
    type Candidate: Clone + Ord + Hash + Send + Sync;

    fn candidates(&self) -> impl Iterator<Item = Self::Candidate>;
}

    對候選項排序的操作可以要求Ord；將它們放入雜湊集合的操作則可以要求Hash。

    在使用處新增約束，能讓基本含義便於複用，也能揭示派生行為真正的契約。

    效應可以是基本含義

    能力 trait 並不意味著純執行：

    pub trait PublishAlg {
    type Document;
    type Error;

    async fn publish(&self, document: Self::Document) -> Result<(), Self::Error>;
}

    釋出是一種效應。它仍然可以是當前邊界上的基本語義操作。具體直譯器可以使用 HTTP、佇列、檔案或測試緩衝區。

    除非重試、套接字所有權、任務生成或連線池屬於預期含義，否則語義層不應規定這些內容。

    為邊界命名

    應從使用者的語義視角描述能力：

    面向含義面向表示
    closed_outcome(slot)get_runtime_map(slot)
    source_read(name)compiler_context().sources().lookup(name)
    branch_path(ancestor, descendant)raw_branch_bits(id)

    命名本身就是設計。機械式名稱容易引入機械式耦合。

    審查要點

    • 這個 trait 是否表達一種連貫的基本含義？
    • 獨立直譯器能否在不復制首個表示的情況下實作它？
    • 是否只在直譯器確實能選擇時才使用抽象關聯型別？
    • 具體型別是否屬於穩定的語義詞彙？
    • 是否等到某個操作確實用到約束時才新增？
    • 這個 trait 是否避免返回管理器、上下文物件和原始儲存？

    在 Rust 中，type一詞可以指代多種不同角色。將它們區分開，能避免含義坍縮為表示。

    角色示例表達的內容
    語義型別Direction哪些領域區別很重要
    由直譯器選擇的載體BranchAlg::Branch直譯器選擇哪種表示
    派生操作BranchExt::branch_child根據已宣告能力可以推出什麼
    階段型別Syntax, CoreProgram, Executable某個值經過了哪種變換
    表示型別BitBranch某個直譯器如何儲存分支含義
    證據程式場景或可複用的定律擴充相容直譯器必須滿足哪些觀察

    表示之前先確定語義型別

    假設某個分支領域區分兩個方向：

    #[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum Direction {
    Left,
    Right,
}

    Direction直接表達了這一區別。一種直譯器可以緊湊地編碼路徑：

    struct BitBranch(Vec<bool>);

    布林值屬於這種表示。它們並非左右方向的定義，其他直譯器也不必使用它們。

    緊湊編碼不等於語義型別

    不要根據位位置、位元組偏移或機器分支來定義領域行為。這些產物應編碼語義區別，而不是擁有這些區別的定義權。

    這種區分讓儲存與執行佈局可以改變，而不悄然改變領域本身。

    關聯型別選擇載體

    能力代數可以把載體留給各個直譯器選擇：

    trait BranchAlg {
    type Branch;

    fn branch_root(&self) -> Self::Branch;
    fn branch_grow(&self, branch: &Self::Branch, direction: Direction) -> Self::Branch;
    fn branch_path(
        &self,
        ancestor: &Self::Branch,
        descendant: &Self::Branch,
    ) -> Option<Vec<Direction>>;
}

    Self::Branch不是隱藏的欄位型別，而是對分支含義作出解釋時所選的載體。位路徑、數值樹位置、符號項或其他表示都可以滿足同一個代數。

    對於直譯器T而言，記法T::Branch可以理解為一個載體族Branch(T)。切換直譯器可能改變載體，但每種操作仍會根據同一選擇保持一致索引。

    擴充用於推導結論

    擴充可以根據它恰好需要的前提構造新操作：

    #[ext(name = BranchExt)]
pub impl<This> This
where
    This: BranchAlg,
{
    fn branch_child(
        &self,
        branch: &This::Branch,
        direction: Direction,
    ) -> This::Branch {
        self.branch_grow(branch, direction)
    }
}

    where子句是前提：This對分支代數作出解釋。方法則是結論：對於該直譯器的載體，分支與方向決定一個子分支。

    (T:BranchAlg)⟹branchChildT​:Branch(T)×Direction→Branch(T)

    推導過程沒有選擇具體的分支表示。結果仍然屬於直譯器所選的載體族。

    相等約束用於陳述相容性

    兩種能力有時需要對載體達成一致。關聯型別相等約束可以陳述這一要求，而無須選擇具體表示：

    Right: BranchAlg<Branch = Left::Branch>

    可以把這個約束讀作一個區域性命題：Left和Right在同一載體上解釋分支操作。應將這一相等要求放在需要達成一致的操作上，而不是全域性強加給任一代數。

    與僅僅因為某個具體上下文碰巧同時包含兩種實作就接受它相比，這種約束更強，也更精確。

    階段型別讓編譯器契約一目瞭然

    編譯器流水線不應讓一個無法區分階段的語法樹貫穿所有環節。不同階段型別可以說明已經發生了哪種變換：

    階段輸入輸出契約
    解析源文字Syntax識別表層語法
    正規化SyntaxCoreProgram生成所選的核心含義
    程式碼生成CoreProgramExecutable以可執行形式保留程式觀察
    執行時Executable可觀察行為依據語言模型一致地解釋可執行程式

    這些型別可防止意外混淆階段，但僅憑名稱無法證明保留性。仍需陳述變換定律、設計代表性場景，並提供跨直譯器證據。

    閱讀契約

    型別層面的結構可以作如下邏輯解讀：

    Rust 形式解讀
    This: BranchAlgThis提供了對分支含義的解釋
    This::Branch分支載體由This選擇
    Right: BranchAlg<Branch = Left::Branch>兩種解釋在載體上保持一致
    -> This::Branch結果仍屬於所選載體族

    這種解讀鼓勵 API 顯露決定型別的因素、組合所需的等式，以及這些前提能推出的結論。只要底層區別確實存在，關聯型別、泛型關聯型別、const 泛型、型別狀態與零大小見證都可以表達此類契約的一部分。

    不要僅僅為了讓實作看起來更形式化，就憑空製造型別層面的機制。型別應當顯露含義或保留必要關係，而不是裝飾一種表示。

    型別不能替代定律

    型別簽名約束哪些程式能夠構造，定律則約束這些程式的操作之間如何關聯。二者缺一不可。

    例如，BranchAlg::Branch說明每個直譯器都會選擇一種分支載體，但它本身並不能確立以下性質：

    • 從某個分支到其自身的路徑為空
    • 重放根路徑可以重構出該分支
    • 相反方向的子節點彼此不同

    這些是相容直譯器共同遵循的語義定律。特定於表示的主張（例如未使用的位必須為零）則屬於選擇該表示的直譯器。

    將型別視為主張

    詢問每種型別主張什麼、由什麼決定、需要哪些定律補全，以及由哪個直譯器實現。

    審查要點

    • 領域區別是否先於緊湊的機器編碼出現？
    • 關聯型別是否是由直譯器選擇的載體，而非偽裝的具體狀態？
    • 相等約束是否只陳述該使用位置所需的相容性？
    • 不同編譯器階段是否採用不同型別並具有明確契約？
    • 語義命題是否與表示不變數分開？
    • Rust 無法表達的主張是否有可複用定律或場景作為依據？

    派生含義與組合

    相關內容

    語義視角：指稱設計
    Rust 中的語義驅動設計：能力代數、直譯器與效應
    概念：表示式問題

    導讀

    派生行為應歸屬於它所使用的能力，並在擴充中基於這些約束定義一次，供所有直譯器共享；它不應屬於某個碰巧實作這些能力的具體型別。where子句誠實地說明了該推導依賴什麼。

    基本能力提供詞彙。大多數應用行為都應從這些詞彙派生一次，並由所有直譯器共享。

    擴充擁有派生定義

    使用extend crate，可以獨立於表示派生分支操作：

    use extend::ext;

#[ext(name = BranchExt)]
pub impl<This> This
where
    This: BranchAlg,
{
    fn branch_child(&self, branch: &This::Branch, direction: Direction) -> This::Branch {
        self.branch_grow(branch, direction)
    }

    fn branch_left(&self, branch: &This::Branch) -> This::Branch {
        self.branch_child(branch, Direction::Left)
    }

    fn branch_right(&self, branch: &This::Branch) -> This::Branch {
        self.branch_child(branch, Direction::Right)
    }

    fn branch_is_ancestor(&self, ancestor: &This::Branch, descendant: &This::Branch) -> bool {
        self.branch_path(ancestor, descendant).is_some()
    }
}

    where子句完整宣告瞭語義依賴：BranchAlg，除此之外別無其他。沒有任何具體分支型別擁有這些定義。

    宏只是省去了 trait 與 impl 的樣板程式碼。普通擴充 trait 也能表達相同設計。指稱設計體現在語義邊界與派生定義中，而不在屬性宏裡。

    為什麼不把它放進結構體？

    不要把派生含義焊死在結構體上

    這屬於表示優先設計。如果引入數值分支載體，就必須複製或重新實作派生邏輯，首個具體型別也會意外變成規範本身。

    impl BitBranchStore {
    // not recommended: derived branch meaning welded to one bit representation
    fn is_ancestor(&self, a: &BitBranch, b: &BitBranch) -> bool {
        // derived branch meaning mixed with bit storage
    }
}

    擴充反轉了歸屬關係：

    層職責
    語義能力擁有派生含義
    具體型別解釋基本含義

    基於約束組合

    當一個接收者解釋多種能力時，使用直接約束：

    #[ext(name = PublishCurrentExt)]
pub impl<This, Document, Error> This
where
    This: DocumentAlg<Document = Document> + PublishAlg<Document = Document, Error = Error>,
{
    async fn publish_current(&self) -> Result<(), Error> {
        self.publish(self.document_current()).await
    }
}

    不要捆綁能力

    不要僅僅為了縮短約束就建立超 trait：

    trait AppContext: DocumentAlg + PublishAlg {}

    能力捆綁會掩蓋哪個操作使用了哪些能力，還會額外建立一種所有直譯器都必須滿足的介面。

    五種不同的組合含義

    選擇能夠如實描述這種關係的形式。

    情形Rust 結構
    一個接收者解釋多種能力直接約束
    由單獨的值選擇行為顯式策略引數
    獨立策略靜態組合乘積型別或普通結構體
    環境承載另一個直譯器小型HasX投影
    包裝器替代內部直譯器委託

    顯式策略

    如果某種策略獨立選擇，就將它顯式傳入擴充：

    #[ext(name = CandidateSelectExt)]
pub impl<This> This
where
    This: CandidateAlg,
{
    fn select_with<Policy>(&self, policy: &Policy) -> This::Candidate
    where
        Policy: SelectionPolicyAlg<Candidate = This::Candidate>,
    {
        policy.select(self.candidates())
    }
}

    擴充擁有共享的派生定義，而策略仍是獨立選擇的輸入。它不會隱藏在環境中，也不會由Default選擇。

    策略乘積

    無需發明繼承機制，也能組合獨立策略：

    struct CompilePolicy<Optimize, Diagnostics> {
    optimize: Optimize,
    diagnostics: Diagnostics,
}

    投影

    一個HasClock trait 僅表明環境可以投影出一個獨立的時鐘值：

    trait HasClock {
    type Clock;

    fn clock(&self) -> &Self::Clock;
}

    讀取時間的操作會在自己的This::Clock: ClockAlg能力where子句中新增該能力。投影只說明包含關係；使用時間的操作則說明自己需要哪種能力。只有在這種分離確實存在時才採用該模式。不要僅僅為了整理欄位就引入HasX。

    委託

    委託意味著包裝器本身可以替代內部直譯器。這適用於透明新型別、共享指標，以及完整保留能力契約的介面卡。

    投影表示“擁有”。委託表示“就是”。二者不能互換。

    預設值也是語義決策

    機械的空狀態可以實作Default。領域策略通常應當顯式給出。

    有用的情形往往可以用代數解釋：預設值是該型別自然組合運算的單位元。追加空緩衝區、與空對映合併，或累積零條診斷資訊，都不會帶來額外貢獻。若這種組合滿足結合律，該型別與操作便構成么半群；此時Default可以命名其中的中性元，而非替使用者選擇策略。

    合適的預設值：

    • 空緩衝區
    • 空對映
    • 累積的診斷數量為零

    值得懷疑的預設值：

    • 法定人數閾值
    • 領導者策略
    • 重試語義
    • 確認深度
    • 輸出格式

    關鍵區別在於：中性元不會引入決策，而法定人數、領導者策略或重試規則會選擇領域行為。如果更改預設值會改變領域含義，就應顯式組合該策略。

    派生含義應保持封閉

    擴充只能使用已宣告的能力與顯式輸入。直接存取欄位、全域性狀態和具體型別向下轉型都會使where子句變得不誠實。

    審查函式體時，應把它看作對依賴宣告的證明：

    逐項檢查推導

    函式體中的每個操作，是否都能由這些約束證明合理？

    如果不能，要麼約束不完整，要麼程式碼屬於其他層。

    審查要點

    • 派生行為是否只在能力之上定義一次？
    • 擴充是否避免依賴具體欄位與上下文型別？
    • 單個直譯器是否使用直接約束？
    • 獨立選擇的策略是否以顯式值傳入？
    • 投影與委託所表達的關係是否準確？
    • 領域預設值是否在組合中清晰可見？

    直譯器與效應

    相關內容

    語義視角：定律與解釋
    Rust 中的語義驅動設計：能力代數、定律、場景與證據
    概念：自由單子
    洞見：EVM 代數

    導讀

    直譯器為某種能力選擇表示或效應。它實現基本操作，但不會重新定義其上層派生出的領域行為，因此所有直譯器都遵循相同定律。

    直譯器使用具體表示或效應來實現語義能力。它應選擇實現機制，而不重新定義領域行為。

    輕量級直譯器

    分支的一種位路徑表示可以是：

    #[derive(Clone, Debug, PartialEq, Eq)]
struct BitBranch(Vec<Direction>);

struct BitBranchImpl;

impl BranchAlg for BitBranchImpl {
    type Branch = BitBranch;

    fn branch_root(&self) -> Self::Branch {
        BitBranch(Vec::new())
    }

    fn branch_grow(&self, branch: &Self::Branch, direction: Direction) -> Self::Branch {
        let mut grown = branch.0.clone();
        grown.push(direction);
        BitBranch(grown)
    }

    fn branch_path(&self, ancestor: &Self::Branch, descendant: &Self::Branch) -> Option<Vec<Direction>> {
        descendant.0.strip_prefix(&ancestor.0[..]).map(<[Direction]>::to_vec)
    }
}

    實作負責儲存和觀察基本事實。branch_left、branch_right和branch_is_ancestor仍留在共享擴充中。

    直譯器取決於邊界

    同一種型別在一個邊界上可以是直譯器，在另一個邊界上則可以是語義輸入。

    邊界使用解釋
    檔案系統介面卡檔案系統存取原始碼查詢
    正規化器環境將原始碼查詢作為基本能力正規化語言構造
    編譯器流水線正規化項可執行程式構造

    不存在唯一通用的“實作層”，而是存在巢狀的語義邊界。

    邊界處的效應

    具體直譯器負責選擇以下內容：

    • 資料庫佈局
    • 非同步執行時
    • 任務所有權
    • 重試策略
    • HTTP 或 RPC 框架型別
    • 序列化
    • 鎖與通道
    • 快取

    除非呼叫者需要觀察這些選擇，否則應讓它們留在語義 trait 之外。

    例如，語義原始碼能力可以返回原始碼值與錯誤。生產直譯器可以快取檔案並非同步讀取；測試直譯器則可以使用不可變對映。派生的正規化邏輯應能同時適用於二者。

    執行時所有權

    框架回撥通常要求狀態具備所有權、可克隆且執行緒安全。這是直譯器的約束，不一定是領域約束。

    不要讓框架載體汙染基本操作

    避免在基本操作中混入框架載體：

    async fn status(data: FrameworkData<Arc<AppState>>) -> FrameworkJson<Status>;

    優先採用語義應用方式：

    trait StatusAlg {
    type Status;

    async fn status(&self) -> Self::Status;
}

    Web 直譯器可以選擇Arc<Context>、提取請求輸入、呼叫status並轉換結果。領域呼叫方無需知道 Web 伺服器存在。

    中性直譯器

    並非所有直譯器都需要執行效應。

    API 程式的文字直譯器可以記錄：

    方法路徑輸入輸出
    GET/status—JSON Status
    POST/temperatureJSON f32JSON Status

    後設資料直譯器可以生成文件。測試直譯器可以收集操作名稱。生產直譯器可以構造伺服器路由。

    中性直譯器能夠證明，程式的含義獨立於任何特定執行時。

    透過委託組合直譯器

    由於含義存在於小型能力 trait 中，直譯器通常是組裝而成，而非從頭寫出。載體透過委託給已有的能力來獲得新能力，因此轉發程式碼由工具生成，無需手寫。兩種形式幾乎就能覆蓋所有情況。

    將能力轉發給欄位。ambassador 的#[derive(Delegate)]會把整個 trait 轉發給內部值。持有多個元件的載體可以將各項能力委託給擁有它的欄位，無需編寫轉發函式體：

    #[derive(Delegate)]
#[delegate(Clock, target = "clock")]
#[delegate(Logger, target = "logger")]
struct Service {
    clock: SystemClock,
    logger: StdoutLogger,
}

    透過 getter 授予能力。為型別提供一個 getter，再由整體實現為所有具有該 getter 的型別提供完整能力：

    trait Logger {
    fn log(&self, message: &str);
}

trait HasLogger {
    type Logger;

    fn logger(&self) -> &Self::Logger;
}

// Any carrier that can hand back a logger is itself a `Logger`.
impl<T> Logger for T
where
    T: HasLogger,
    T::Logger: Logger,
{
    fn log(&self, message: &str) {
        self.logger().log(message)
    }
}

    這樣一來，許多結構體根本無需存在。龐大的上下文物件——一個攜帶多個關聯型別與十幾個方法的大型 trait，再加上唯一的具體實作——可以化為幾個小型能力 trait，以及一個精簡載體；載體將每種能力委託給提供該能力的欄位或 getter。檢查截止時間是否已過之類的派生操作，只需作為基本操作之上的擴充編寫一次，無需在每個載體上重新實作。

    委託轉發的是操作，而非含義

    生成委託程式碼可以省去樣板工作，卻不能確立語義上的可替代性。derive諸如 ambassador 的#[derive(Delegate)]宏只能證明實現能夠編譯，不能證明該載體指稱相同的直譯器。如果Shared<T>(Arc<T>)要替代T，就應在載體上檢查定律——會改變共享性或身份的包裝器（Arc、池化、快取）可能正確轉發每個方法，卻仍違反新鮮度或唯一性定律。如果載體只是在其他服務之間存放了T，使用投影會比委託更誠實。

    錯誤屬於特定邊界

    錯誤應當在負責處理它的邊界上傳達失敗的含義。

    錯誤邊界轉換
    領域錯誤傳輸直譯器將其對映為協議響應
    解析錯誤編譯器前端將其對映為診斷資訊
    儲存錯誤原始碼直譯器將其對映為語義層面的原始碼失敗

    不要把 HTTP 狀態碼、RPC 錯誤物件或資料庫錯誤強加給基本領域 trait。應在直譯器邊界處轉換它們。

    在效能可觀察之前，它屬於解釋範疇

    批次處理、並行、快取與資料佈局通常屬於直譯器。只有當規範承諾了可觀察的順序、時間、資源使用、公平性或失敗行為時，它們才成為語義的一部分。

    這種區分能夠在避免語義漂移的同時進行最佳化：

    • 遵循相同定律
    • 宣告相同觀察
    • 採用不同操作策略

    審查要點

    • 直譯器是否實作基本操作，而非重複派生邏輯？
    • 執行時與框架約束是否限定在使用這些約束的邊界內？
    • 中性直譯器或測試直譯器能否實作同一能力？
    • 傳輸與儲存錯誤是否在邊界處轉換？
    • 委託表達的語義關係是否準確？
    • 根據所述指稱，效能差異是否不可觀察？

    定律、場景與證據

    相關內容

    語義視角：定律與解釋

    概念：分支與合流、引用透明性

    導讀

    測試為規範提供證據。應針對公開可觀察的結果，以及所選語義域支持的定律撰寫斷言，而非針對私有執行步驟；並將這些定律以針對該能力的泛型形式表述，讓每個直譯器都接受同樣的檢驗。

    語義優先的程式碼需要語義優先的測試。測試公開可觀察的結果與定律，而非私有執行步驟。

    測試規範介面

    與表示耦合的測試

    這個斷言深入存取某個載體的欄位，因此其他直譯器無法複用：

    // not recommended: asserts a bit layout, not a semantic observation
assert_eq!(branch.bits, vec![false, true]);

    語義測試：

    let root = alg.branch_root();
let left = alg.branch_left(&root);
let left_right = alg.branch_right(&left);

assert_eq!(alg.branch_path(&root, &left_right), Some(vec![Direction::Left, Direction::Right]));

    如果測試物件是位編碼的序列化模組，第一個測試可能合適。但對於分支代數，它提供的證據較弱，因為替代表示無法複用它。

    可複用的定律擴充

    如果某項性質適用於所有相容直譯器，就把它寫一次：

    use anyhow::{Result, bail, ensure};
use extend::ext;

#[ext(name = BranchLawsExt)]
pub impl<This> This
where
    This: BranchAlg,
    This::Branch: Clone + Eq,
{
    fn check_branch_root_round_trip(&self, directions: &[Direction]) -> Result<()> {
        let root = self.branch_root();
        let branch = directions.iter().copied().fold(root.clone(), |branch, direction| self.branch_grow(&branch, direction));

        let Some(path) = self.branch_path(&root, &branch) else {
            bail!("grown branch has no path from root");
        };
        ensure!(path == directions, "root path did not round-trip");
        Ok(())
    }
}

    每個直譯器都執行同一個檢查器。anyhow::Result承載結果；bail!報告缺失的觀察，而ensure!檢查往返定律。該檢查器無需依賴某一種分支表示，就能區分這兩種失敗。

    有用的定律類別

    尋找語義結構已經暗示的性質：

    • 單位元
    • 結合性
    • 確實有意要求時的交換性
    • 冪等性
    • 往返
    • 正規化
    • 細化
    • 單調性
    • 替換
    • 解釋一致性

    只主張該領域支援的定律

    不要僅僅因為熟悉或聽起來很數學，就新增代數術語。只陳述所選領域支援的定律。

    定律與表示不變數

    請將以下內容區分開：

    • 語義定律：根據根路徑重構一個分支時，所指稱的仍是同一個分支。

    • 表示不變數：未使用的高位為零。

    • 序列化定律：

      decode(encode(b))=b

    • 規範格式定律：

      encode(decode(x))=xfor canonical byte sequences x

    這些都可能很重要，但各自屬於不同的規範。

    共享場景

    場景是針對公共能力編寫的可複用互動。ALUX 測試框架以這種方式表示場景：編寫場景的程式碼透過Scenario、DeployerIds、PlayAst和ScenarioSchedule能力構造一個值，無需點名具體執行器。

    #[ext(name = HelloScenarioExt)]
pub impl<This> This
where
    This: StandaloneScenario,
    This::Step: PlayAst<Ast = RProc>,
{
    fn hello(self) -> This::Scenario {
        self.scenario()
            .under_comprehensive(100)
            .step(
                self.play_ast(
                    self.deployer(0),
                    tolang! {
                        let x in {
                            x ! "hello" |
                            ? (a <- x) a.log()
                        }
                    },
                )
                .expect_log(r#""hello""#),
            )
    }
}

    每次呼叫都描述作者定義的含義，而不是執行器機制。under_comprehensive(100)要求在一次順序執行、100 次完全併發執行以及最多 100 次亂序執行中都得到預期日誌。場景固定所觀察的內容，執行器則改變執行順序。

    同一原則也適用於不同直譯器：如果多個執行器都實作了場景所用的能力，它們就都可以解釋同一個編寫好的互動。執行器特有的設定與邊界檢查應留在場景之外。

    跨直譯器一致性

    當兩個直譯器提供相同觀察時，可以比較它們：

    interpret_text(p).route_names=interpret_server(p).registered_route_names

    這可以捕捉獨立快照遺漏的漂移。對於 API 定義、編譯器階段與替代資料表示，這尤其有價值。

    有限證據並非證明

    測試透過，只能證明在受測輸入與實作下觀察到了相應行為，不能證明某條定律對所有值都成立。

    有計劃地提升保證強度：

    1. 示例測試
    2. 可複用場景測試
    3. 生成式性質測試
    4. 對有限域進行窮舉檢查
    5. 模型比較
    6. 證明產物

    根據風險與主張強度選擇層級。

    讓測試名稱表達含義

    優先使用：

    • reconstructs_every_generated_branch_from_its_root_path
    • preserves_child_programs_when_routes_are_merged
    • normalization_is_invariant_under_alpha_renaming

    避免只敘述實作過程的名稱：

    • pushes_three_bits
    • calls_helper_twice
    • visits_left_node_first

    如果操作順序本身有規範規定，操作測試仍然有效。此時應在名稱中指出讓該順序具有意義的觀察。

    審查要點

    • 每個新增的語義操作是否都有針對性的定律或斷言？
    • 可複用義務是否針對公共能力以泛型方式表達？
    • 場景是否與具體執行器分離？
    • 是否區分了語義定律與表示不變數？
    • 在可行時是否比較了多個直譯器？
    • 文件是否避免把有限測試稱作證明？

    一階程式

    相關內容

    Rust 中的語義驅動設計：派生含義與組合、語言與編譯器流水線
    概念：延續傳遞風格、去函式化、自由單子
    洞見：重新審視表示式問題

    何時將應用具體化為資料

    普通函式與擴充已經可以表達派生行為。只有當另一個直譯器必須在執行前檢查、組合、序列化或編譯程式時，才應將應用轉換為一階資料。

    普通函式與擴充方法通常是表達派生行為的最佳方式。但有時另一個直譯器必須在執行程式之前，先檢查、組合、產生文件、序列化或編譯程式結構。這時，應用本身必須成為一階資料。

    執行會抹去結構

    考慮：

    #[ext(name = StatusExt)]
pub impl<This> This
where
    This: StatusAlg,
{
    async fn status_current(&self) -> This::Status {
        self.status().await
    }
}

    呼叫此方法會得到一個狀態。呼叫開始後，外部直譯器通常無法再恢復以下資訊：

    • 語義上下文型別
    • 有序引數
    • 源引數名稱
    • 結果型別
    • 操作的身份

    這些資訊原本存在於原始碼級別的函式型別中，但普通執行過程會消耗掉它們。

    對應用進行去函式化

    去函式化會將某個已知函式族中的成員替換為一階標籤，並提供一個共享的應用操作。

    一組最小操作詞彙如下：

    trait OperationAlg {
    type Context;
    type Args;

    const ARG_NAMES: &'static [&'static str];
}

trait ApplyAlg<Handle, Args> {
    type Output;

    async fn apply(&self, handle: Handle, args: Args) -> Self::Output;
}

    零大小的CurrentStatusOperation<App>可以表示對原擴充方法的呼叫。它應當呼叫該方法，而不是包含一份重複的函式體。

    1. 從擴充方法開始。
    2. 將其具體化為操作型別。
    3. 保留其上下文、引數乘積、引數名稱與輸出。
    4. 透過ApplyAlg對其進行解釋。

    普通呼叫仍可使用原有便捷方法。只有需要一階結構的上下文才會用到操作值。

    沒有使用者時，不要具體化為資料

    一階程式會增加型別機制。只有當它們能支援真正的第二種解釋時才使用：

    • 執行時註冊
    • 生成文件或模式
    • 靜態檢查
    • 執行前組合程式
    • 序列化
    • 編譯

    如果程式碼只需呼叫函式，就保留函式即可。

    可移植介面程式

    假設 HTTP 介面包含：

    方法路徑輸入操作輸出
    GET/status—status_currentJSON
    POST/set_temperature正文：f32adjust_statusJSON
    GET/download—current_file流式檔案

    可移植程式必須保留：

    • 方法與路徑選擇器
    • 輸入角色，例如路徑、查詢引數、正文、請求頭與身份驗證
    • 操作值
    • 輸出角色，例如 JSON 或檔案
    • 路由合併與巢狀

    不應保留某個特定框架的請求、路由器或響應型別。

    一種流暢記法可以是：

    self.routes()
    .get("/status", self.op(CurrentStatusOperation::<App>::default()).json())
    .post("/set_temperature", self.op(AdjustStatusOperation::<App>::default()).body::<f32>().json())
    .get("/download", self.op(CurrentFileOperation::<App>::default()).file())

    這些流暢呼叫會構造一個有型別的程式，不必立即註冊伺服器路由。

    一個程式，多種摺疊解釋

    同一個一階程式可以支援多種解釋：

    程式解釋
    有型別的 HTTP 程式文字文件、可執行路由、OpenAPI 後設資料、客戶端繫結、符合性測試
    有型別的 JSON-RPC 程式方法登錄檔、模式、客戶端、測試框架

    不要為執行與文件分別維護路由或方法清單，否則會產生彼此競爭的規範。

    輸入與輸出角色

    操作已經知道自身的引數與結果型別。傳輸宣告只應新增傳輸含義。

    self.op(FindOperation::<App>::default())
    .path::<u64>()
    .query::<String>()
    .json()

    path、query和json用於標識角色，不應要求作者重新宣告已經由ApplyAlg決定的輸出型別。

    輸出轉換屬於傳輸直譯器。伺服器可以將一種結果轉換為 JSON，將另一種結果轉換為流式附件。語義操作無需瞭解任何一種表示。

    組合本身就是程式含義

    程式應保留通用組合操作：

    • 空程式
    • 合併程式
    • 將程式巢狀在某個字首下
    • 將端點提升為程式

    這些操作比某個框架的路由器方法更基礎。熟悉的流暢名稱，例如get、post、merge和nest，都可以作為中性代數的別名。

    獨立規範可以釋出小型程式：

    輸入程式組合結果
    狀態與下載程式合併服務程式
    目錄程式巢狀服務程式

    應用程式負責選擇並解釋最終的組合。

    宏必須展開為公開的語義結構

    Rust 宏可以讓一階宣告更加簡潔：

    #[ext(name = StatusApiExt, defunc(via = http))]
pub impl<This> This
where
    This: HttpApiAlg + JsonOutAlg,
{
    fn status_api<Alg>(&self)
    where
        Alg: StatusAlg,
    {
        self.routes().get("/status", self.op(Alg::status_current).json());
    }
}

    只有當宏展開後得到公開且可手動構造的一階程式時，宏設計才算健全。生成的回呼不應成為介面的唯一規範定義。

    良好方向：

    1. 便捷語法
    2. 公開的操作值與程式值
    3. 泛型摺疊解釋
    4. 具體框架

    表示優先的方向：

    1. 框架註解
    2. 不透明的生成回撥
    3. 逆向整理的文件

    與既有概念的關係

    一階介面程式建立在其他章節介紹的技術之上：去函式化是通用變換；可擴充語法與解釋對應表示式問題；自由單子則是一種特定的“帶順序的語法”表示。頁面頂部的“相關內容”連結可以跳轉到各自章節。

    不要把這些技術等同於指稱設計本身。指稱設計決定哪些結構很重要；當普通呼叫會抹去這些結構時，一階表示負責保留它們。

    審查要點

    • 是否有真實的第二種直譯器需要將程式具體化？
    • 操作是否呼叫作者定義的方法，而非複製其實現？
    • 引數與輸出是否從操作中推斷得出？
    • 傳輸語法是否只新增了傳輸角色？
    • 程式是否可以在不使用便捷宏的情況下構造？
    • 執行時與後設資料是否解釋同一個程式？

    語言與編譯器流水線

    相關內容

    Rust 中的語義驅動設計：一階程式、直譯器與效應
    概念：操作語義、去函式化
    洞見：EVM 代數

    含義並非流水線本身

    當語言含義不與解析器語法樹、編譯過程、位元組碼或機器迴圈混為一談時，編譯器就更清晰。正確性可由一條交換律表達：執行編譯後的程式，應與該程式的指稱一致。

    如果語言含義不等同於解析器語法樹、編譯器過程、位元組碼或虛擬機器迴圈，推理編譯器就會容易得多。

    本章採用一種類似 Tolang 的簡化併發語言，重點放在語義架構上。

    四個不同層次

    請將以下層次分開：

    1. 源語言語法
    2. 正規化語言
    3. 可執行表示
    4. 機器執行

    典型流水線如下：

    ParseNormalizeCodeGenRun​:Source→Syntax:Syntax→Result(Core,Diagnostics):Core→Result(Executable,Error):Executable×RuntimeState→Observation​

    便捷操作就是組合：

    Compile=Parse;Normalize;CodeGen

    組合後的輔助函式並非每個階段的語義定義。

    語法尚未成為含義

    解析器輸出會映照語法選擇：

    • 標點
    • 語法糖
    • 優先順序
    • 原始碼區間
    • 生成的解析器表示

    這些資訊對診斷與工具很重要，但不必用來定義核心語言。

    正規化會移除偶然的語法差異，並引入一種更精簡、承載含義的形式。例如，多種表層繫結形式可以正規化為同一個核心限制操作。

    多種源形式 → 一個正規化構造

    這樣一來，編譯器後續階段與執行時定律便有了統一的陳述位置。

    指稱含義與編譯含義

    令：

    [[−]]:Core→D

    在語義域D中賦予含義。

    編譯會生成可執行值：

    compile:Core→Executable

    執行時會觀察這些值：

    run:Executable→D

    核心正確性義務是一張交換圖：

    run(compile(p))=[[p]]

    對於非確定性或併發系統，等價關係可能是觀察等價、結果集合、軌跡等價或雙模擬，而非普通的值相等。必須由語義模型作出選擇。

    併發過程含義

    基礎反射演算包含以下思想：

    0P∣Qx!(v)?(y←x) P​inactive processparallel compositionsend a value on a channelreceive a value and continue as P​

    Tolang 以組合方式擴充基礎演算。其中一種擴充增加了表層形式

    let x in Pfresh channel binding scoped over P.

    這個繫結會建立一個新通道，並將其名稱的作用域限定在P之內；過程演算文獻將此操作稱為限制。反射核心沒有基本限制運算子。參見 Meredith 與 Radestock 的論文《反射式高階演算》。

    操作機器可以透過元組空間、佇列、匹配索引、延續記錄與併發任務來實作這些功能。這些機制並非語言定義。

    語義層負責確定可觀察的過程行為與結構定律。核心並行組合可能遵循以下定律：

    P∣0P∣Q(P∣Q)∣R​≡P≡Q∣P≡P∣(Q∣R)​

    這種新鮮繫結擴充還具有獨立的定律。常見候選模式包括 α 重新命名、不同繫結的交換，以及作用域外提：

    let x in Plet x in (let y in P)let x in (P∣Q)​≡let y in P{y/x}≡let y in (let x in P)≡P∣(let x in Q)​​(y#P)(x=y)(x∈/FN(P))​

    這裡，y#P表示y對P來說是新鮮的；P{y/x}表示避免變數捕獲的重新命名；FN(P)表示P中的自由通道名稱集合。只有在選定的觀察等價關係認可這些模式時，它們才成為定律；不能僅憑表層語法或某種位元組碼佈局就作此假設。

    正規化是一種保持含義的映射

    如果源程式s₁與s₂的區別僅在於所接受的語法糖，正規化就應顯式呈現它們共同的含義：

    s1​≡sugar​s2​⟹normalize(s1​)=normalize(s2​)

    其他有用的義務包括：

    • α 重新命名保留正規化含義
    • 詞法作用域應繫結到預期的繫結項
    • 診斷所需的原始碼位置應予保留
    • 編譯期常量應被擦除，不產生執行時行為
    • 畸形語法應依階段契約累積診斷資訊

    有些專案要求正規化值具有規範形式，有些專案只要求語義等價。應明確選擇哪一種。

    階段能力

    不要使用萬能編譯器物件

    不要讓一個巨型編譯器物件成為唯一的階段介面。

    正規化器可能需要以下能力：

    • 讀取並擴充繫結作用域
    • 解析原始碼名稱
    • 累積診斷資訊
    • 構造正規化項

    程式碼生成器可能需要：

    • 分配可執行引用
    • 生成指令
    • 解析正規化變數
    • 完成可執行結構

    將各階段入口表達為基於這些能力的擴充。具體環境可以儲存對映、區域分配器、計數器與診斷資訊，但它們並不擁有階段含義。

    解析器與執行時可以保持操作式設計

    並非每個子系統都必須被強制納入同一種編碼。

    解析器可能主要由生成式語法機制主導。虛擬機器可能主要依賴高效的狀態變更與排程。它們可以保留操作式設計，同時實作定義清晰的邊界：

    階段契約
    解析器生成Syntax
    正規化器生成承載含義的Core
    程式碼生成器以可執行形式保留含義
    執行時生成符合語言模型的觀察

    指稱設計不會移除機器，而是防止機器悄然成為語言語義。

    編譯器定律與測試

    強有力的證據來自多個方面：

    • 針對等價源形式的正規化定律
    • 在預期情況下檢查解析與漂亮列印的往返性質
    • 比較直接語義求值與編譯後執行
    • 規範承諾規範輸出時檢查位元組碼等價
    • 執行時符合性場景
    • 跨直譯器差分測試

    位元組相等不等於語義相等

    不要混淆逐位元組相等與語義相等。只有當規範要求編譯結果具有正規形式時，位元組相等才是一項有用的更強性質。

    可重複的方法

    指稱設計是一套工作流程，而不只是對已完成程式碼的解釋：陳述語義變化，找出最小基本能力，如實組合它們，再實作輕量級直譯器並檢查定律。

    指稱設計作為一種可重複的開發方法最有用，而不只是對已完成程式碼作出解釋。

    核心流程

    開發新功能或重構時：

    1. 用一句話說明語義變化。
    2. 確定載體與可觀察等價關係。
    3. 找出所需的最小基本能力。
    4. 基於明確能力定義派生行為。
    5. 選擇能如實表達關係的組合形式。
    6. 只有當結構需要多種解釋時，才將程式具體化為一階資料。
    7. 實作輕量級具體直譯器。
    8. 新增定律或共享場景。
    9. 驗證不同解釋。
    10. 先記錄含義，再介紹機制。

    陳述語義變化

    較弱的表述：

    新增快取和管理器方法。

    面向含義的表述：

    在一次編譯期間，解析同一個不可變源名稱應指稱相同的源值。

    第二種表述提出了一條候選定律。之後可以選擇快取作為一種實作方式。

    找到基本邊界

    請思考：

    • 需要哪種新的觀察或變換？
    • 它在此邊界上是基本操作，還是可以由現有含義派生？
    • 是否需要新的關聯載體？
    • 所謂依賴是否只是儲存位置？
    • 哪些區別應當不可見？

    只有確實出現新的基本含義時，才新增能力。

    問題選擇

    1. 確定一項語義觀察。
    2. 定義一種小型能力。
    3. 將一個派生操作移入擴充。
    4. 保留當前結構體，將其作為直譯器。
    5. 新增一項定律式測試。

    4. 一階程式語法（如有）
    5. 共享定律與場景

    常見失敗模式

    形似 trait 的具體狀態不等於指稱設計

    trait ContextAlg {
    fn state(&self) -> &ConcreteState;
}

    trait 改變了語法，卻沒有改變含義的歸屬。語義核心仍然依賴具體表示。

    每個直譯器都重複派生邏輯

    如果每個實作都獨立定義相同的領域演算法，就說明規範被重複了。

    萬能能力

    包含無關操作的超 trait 會掩蓋依賴關係，也會阻止獨立解釋。

    規範由框架掌控

    如果路由註解或 RPC 註冊是唯一的介面定義方式，文件與執行就可能出現偏差。

    含義由宏掌控

    如果生成程式碼沒有公開的一階目標，宏展開就會意外成為規範。

    策略隱藏在預設值中

    與欄位佈局或遍歷順序耦合的測試，會妨礙有效的替代直譯器。

    定義

    操作語義透過求值判斷或配置之間的狀態轉換來描述程式行為。配置可能包含程式片段，以及環境、儲存、延續或其他抽象機器狀態。

    這種描述具有數學性質：它陳述哪些求值或狀態轉換有效。直譯器或虛擬機器可以實作這些規則，但某個具體實作本身並非定義。

    語義定位

    操作語義是一種精確的語義，而非非正式的實作細節。它透過求值規則或轉換規則說明行為。指稱設計提出了一個互補且更早的設計問題：這些規則應保留哪些可組合含義與等式？

    操作語義的形式

    小步操作語義（結構操作語義）

    計算被拆分為原子轉換：

    2+3(2+3)⋅4​→5→5⋅4→20​

    適用於建模併發、交錯執行與部分執行。

    大步操作語義（自然語義）

    根據最終結果描述求值：

    (2+3)⋅4⇓20

    推理終止程式時通常更清晰。

    形式規則

    操作語義通常採用推理規則給出。對於簡單算術語言：

    E::=n∣E+E

    從左到右求值時，需要三條規則：

    E1​+E2​→E1′​+E2​E1​→E1′​​n+E2​→n+E2′​E2​→E2′​​n1​+n2​→n3​where n3​=n1​+n2​

    前兩條規則確定下一個可歸約子表示式。兩個運算元都成為值後，第三條規則執行加法。

    求值軌跡：

    (1+2)+3→3+3→6

    為何重要

    • 提供精確的類機器模型來描述執行。
    • 為直譯器與虛擬機器奠定基礎。
    • 支援對正確性、資源使用與安全性的推理。

    與其他概念的關係

    • 自由單子提供指令語法與順序組合。操作規則可以描述該表示中的程式如何求值。
    • CPS將計算剩餘部分顯式表示為延續。操作規則可以描述值如何傳遞給這些延續。
    • 去函式化會將已知函式族替換為一階資料，並提供一個apply操作。操作規則可以描述由此產生的顯式機器狀態。

    這些都是可以賦予操作語義的物件與變換，本身並不是操作語義。

    實踐中的應用

    操作規則可以指導直譯器實現，並提供一個用於檢查實現的精確模型：

    • EVM可以自然地建模為小步狀態轉換系統；也可以透過大步判斷描述完整的終止執行。
    • 小步規則通常與 Rust 直譯器中的match分支非常相似。

    n1​+n2​→n3​

    上文完整的從左到右求值關係可以表示為 Rust 程式碼：

    enum Expr {
    Num(i64),
    Add(Box<Expr>, Box<Expr>),
}

fn step(expr: Expr) -> Option<Expr> {
    match expr {
        Expr::Num(_) => None,
        Expr::Add(left, right) => match (*left, *right) {
            (Expr::Num(a), Expr::Num(b)) => Some(Expr::Num(a + b)),
            (left @ Expr::Num(_), right) => step(right).map(|next| {
                Expr::Add(Box::new(left), Box::new(next))
            }),
            (left, right) => step(left).map(|next| {
                Expr::Add(Box::new(next), Box::new(right))
            }),
        },
    }
}

    這個函式執行一次狀態轉換。重複應用即可得到所示軌跡；返回None表示表示式已經是一個值。

    操作規則可以證明安全性、進展性質、資源上限以及與實作的對應關係。如果在預期的抽象含義明確之前就選定了操作機制，限制便會顯現：實作選擇可能意外變成語義承諾。

    指稱設計並不否定操作語義。它要求先陳述語義域、組合與定律，再將操作模型與其關聯起來。

    語義定位

    表示式問題關注表示與操作的模組化擴充。指稱設計則更早地提出一個問題：哪些語義詞彙與解釋值得表示？

    Phil Wadler 提出的表示式問題關注如何在兩個維度上同時擴充語言，而無須修改現有程式碼：

    • 新增新的資料變體（新的表示式形式，也稱“語法”）。
    • 新增新的操作（新的解釋，也稱“語義”）。

    核心矛盾：

    • 採用函式式/代數資料型別風格時，新增新操作很容易，但新增新變體會造成侵入式修改。
    • 採用物件導向風格時，新增新變體很容易，但新增新操作會造成侵入式修改。

    Haskell（函式式/代數資料型別）

    先從一個經典的表示式代數資料型別及兩種操作開始。

    data Expr
  = Lit Int
  | Add Expr Expr

eval :: Expr -> Int
eval (Lit n)     = n
eval (Add a b)   = eval a + eval b

pretty :: Expr -> String
pretty (Lit n)   = show n
pretty (Add a b) = "(" ++ pretty a ++ " + " ++ pretty b ++ ")"

    現在，新增新操作很容易：

    size :: Expr -> Int
size (Lit _)   = 1
size (Add a b) = 1 + size a + size b

    但新增新變體（例如Mul）就要求修改每個函式：

    Java（物件導向）

    先從一個介面以及每種變體對應的具體類開始。

interface Expr {
    int eval();
    String pretty();

        this.n = n;

        return n;
    }

    private final Expr b;

        this.b = b;

    現在，新增新變體很容易：

    用 Wadler 的說法，在物件導向方法中，操作擴充不具備模組化特性。

    總結（Wadler 的觀點）

    • 函式式/代數資料型別風格傾向於新增新操作，但不利於新增新變體。
    • 物件導向風格傾向於新增新變體，但不利於新增新操作。
    • 表示式問題要求找到一種設計，使兩個維度都能擴充，而不必修改現有程式碼。

    Wadler 的解釋與解決方案概覽（1998）

    Wadler 將問題表述為：擴充資料型別的分支（新變體），並擴充該資料型別上的函式（新操作），同時不重新編譯現有程式碼，且保留靜態型別安全（無需型別轉換）。

    他用“表格”作比喻：

    • 行 = 分支（變體/構造器）
    • 列 = 函式（操作/解釋）

    在函式式/代數資料型別環境中，行固定而列易於新增。
    在物件導向環境中，列固定而行易於新增。
    挑戰在於讓兩個方向都可擴充。

    Wadler 提出的解決方案（GJ + 虛擬型別）

    Wadler 使用 GJ（泛型 Java）提出一種方案，其中包括：

    • 使用This有界引數（This extends LangF<This>）模擬ThisType。
    • 內部類與介面按This索引（虛擬型別）。
    • A visitor-based structure that allows:
      • 透過繼承“語言族”來新增新分支（例如Plus）
      • 透過新增新存取者來增加操作（例如Show）

    訣竅在於引用This.Exp與This.Visitor，使每個擴充階段都保持型別安全且可以獨立編譯。

    注意事項（Java 內部介面）

    Wadler 指出，Java 會將內部介面視為靜態的，因此破壞了索引技巧。
    他認為放寬這一限制就能使方案可行；但現代 Java 仍未改變這一點（巢狀介面依舊隱式為靜態）。

    提及的其他解決方向

    1. Corky Cartwright 的方法 要求逆變擴充：允許基礎表示式型別替代擴充型別。 這解釋了為何要使用不動點：擴充語言族不是原型別的子型別。

    2. Kim Bruce 的方法 要求使用高階型別構造器（將型別構造器作為引數的型別引數化方式）。 GJ 不直接支援這一特性，但 Wadler 認為可以用虛擬型別模擬。

    3. Krishnamurthi 等人（擴充存取者模式） 透過擴充存取者設計實現。 在他們的 Pizza 環境中缺少靜態型別，因此需要動態型別轉換。

    4. 專用語言擴充 Wadler 提到了兩種依賴於專為該問題設計的語言特性的方案。 它們不如虛擬型別方案通用。

    Wadler 的兩點總結

    Wadler 的郵件清楚地說明了兩點：

    1. 表示式問題是資料擴充與操作擴充之間的結構性矛盾。
    2. Solutions are possible, but they tend to require either:
      • 可模擬虛擬型別的型別系統特性，或
      • 專用語言擴充，或
      • 對靜態型別安全或獨立編譯作出妥協。

    輕量級 Go 方案（2020）

    Wadler 於 1998 年提出並命名了這一問題。之後，輕量級 Go（FG）及其泛型擴充 FGG（輕量級泛型 Go）在一種類似 Go、採用結構化介面與泛型的語言中，給出了具體且完全靜態的解決方案。

    論文中的方案（圖 8，簡化版）包含兩個結構Num與Plus，以及兩個操作Eval與String：

    type Evaler interface { Eval() int }
type Stringer interface { String() string }

type Num struct { value int }
type Plus(type a Any) struct { left a; right a }

func (e Num) Eval() int { return e.value }
func (e Plus(type a Evaler)) Eval() int { return e.left.Eval() + e.right.Eval() }

func (e Num) String() string { return fmt.Sprintf("%d", e.value) }
func (e Plus(type a Stringer)) String() string {
    return fmt.Sprintf("(%s+%s)", e.left.String(), e.right.String())
}

type Expr interface { Evaler; Stringer }

var e Expr = Plus(Expr){Num{1}, Num{2}}

    其機制如下：

    • 泛型遞迴表示。Plus的子項具有一個型別引數a，其唯一約束為Any。該結構不繫結到列出所有操作的封閉介面，因此後續仍可新增操作。
    • 針對操作的約束。每個方法宣告都會獨立約束a：Plus(type a Evaler)用於Eval，Plus(type a Stringer)用於String。這依賴於 FGG 的協變接收者：方法接收者的約束可以比型別宣告中的約束更強。
    • 結構化介面。結構只要具有介面的方法就算實作了該介面，因此可以在不修改Expr和Num的情況下，於之後引入Plus。只有在構造值時，才需要確定完整的操作集合（Plus(Expr){...}）。

    新分支只需增加新結構；新操作只需增加新介面與方法。二者都不需要修改或重新編譯現有宣告，也無需型別斷言。

    引用透明性

    相關內容

    語義視角：指稱與組合性、定律與解釋
    洞見：重新審視引用透明性

    語義定位

    引用透明性取決於所選指稱與等價關係。當替換表示式不會改變指定含義時，它允許進行替換，即使語義邊界背後的實作操作有所不同。

    引用透明性（RT）是表示式的替換性質：可以用一個表示式的指稱替換該表示式，而不改變程式含義。

    如今，實踐中通常將 RT 作為等式推理、安全重構與定律驅動 API 設計的基礎。

    核心含義

    RT 表示：

    • 如果e指稱v
    • 那麼，以v代替e會保留含義

    這是語義主張，而非編碼風格口號。

    純性

    純函式對相同輸入總是返回相同輸出，並且沒有可觀察的副作用。RT 是表示式的替換定律：用其指稱替換表示式必須保留含義。因此，純函式是實踐中實現 RT 的一種常見方式，而 RT 是更廣泛的語義標準。關於指稱設計中純性與 RT 的區別，請參閱《重新審視引用透明性》。

    歷史背景

    在程式語言語義中，RT 與 Christopher Strachey 的表述密切相關。他的論述將值推理與以更新為主的行為區分開來：

    • R 值：表示式的值。
    • L 值：可以賦值的位置。

    關鍵在於：當我們進行值層面的推理時，表示式級別的替換是穩定的。賦值會引入位置更新，使替換推理變得困難，甚至不再以樸素形式成立。

    這裡的賦值與副作用意味著什麼

    在此上下文中：

    • 賦值是對某個位置進行更新（例如x := x + 1）
    • 副作用是返回值之外任何可觀察的變化

    賦值是一種特定的副作用。

    這就是 RT 在許多命令式環境中失效的原因：求值可能依賴或改變表示式顯式值介面以外的可觀察上下文。

    現代語言如何呈現 RT

    Haskell

    純表示式通常被當作預設推理物件來教授 RT。效應透過型別化構造顯式表達（例如IO、狀態傳遞及相關抽象），所以替換定律在日常使用中居於核心地位。

    Scala（Cats / Cats Effect）

    在 Scala 函數語言程式設計實踐中，Cats Effect 提供了最常見的 RT 解釋方式：

    • IO[A]是對帶效應工作的純描述
    • 組合IO值滿足 RT
    • 在執行時邊界顯式執行（unsafeRun*）

    Cats Effect 也將其與急切求值Future作對比，這也是 Scala 中討論 RT 時強調惰性與延遲執行的原因之一。

    當代的 RT

    在現代生態系統中，RT 常被用作“行為可安全替換”的簡稱。 在多範式系統中，團隊通常會將 RT 主張應用於特定模組、API 或帶效應型別的區域，而不是全域性套用於所有程式碼。

    關於 RT 在指稱設計中的解讀，請參閱《重新審視引用透明性》。

    自由單子

    相關內容

    Rust 中的語義驅動設計：一階程式、直譯器與效應
    概念：延續傳遞風格、去函式化
    洞見：EVM 代數

    語義定位

    自由單子是一種表示指令語法與自由生成的順序組合的方式。指令函子已經選定了詞彙；隨後，直譯器會將該語法對映到某個語義域。它是一種強大的編碼方式，但並非指稱設計的定義。

    什麼是自由單子（Rust 版本）

    自由單子可以讓你：

    • 描述程式時使用資料，而非立即執行程式。
    • 稍後以一種或多種方式解釋該程式。

    可以將它想成：

    一個效應操作 AST + 用於串接步驟的bind/flat_map。

    將以下兩者分開：

    • 語法 → 指令列舉。
    • 解釋 → 對映到所選語義域並保留結構。

    “自由”意味著單子結構由函子F自由生成，除了單子定律之外不新增其他等式。選擇F本身就決定了指令語法；對結果程式作出解釋，則會賦予其特定指稱。

    Rust 實作

    示意性編碼

    Rust 不支援直接的高階型別引數，因此生產級自由單子編碼需要額外的型別機制，或專用指令函子。以下程式碼展示預期結構，並非可直接使用的泛型實作。

    自由單子型別

    #[derive(Clone)]
enum Free<F, A> {
    Pure(A),
    Suspend(F),
    FlatMap(Box<Free<F, A>>, Box<dyn Fn(A) -> Free<F, A>>),
}

impl<F: Clone + 'static, A: 'static> Free<F, A> {
    fn pure(a: A) -> Self {
        Free::Pure(a)
    }

    fn flat_map<B: 'static, G>(self, f: G) -> Free<F, B>
    where
        G: Fn(A) -> Free<F, B> + 'static,
        F: 'static,
    {
        match self {
            Free::Pure(a) => f(a),
            Free::Suspend(op) => {
                Free::FlatMap(Box::new(Free::Suspend(op)), Box::new(f))
            }
            Free::FlatMap(inner, g) => {
                Free::FlatMap(inner, Box::new(move |x| g(x).flat_map(f.clone())))
            }
        }
    }
}

    領域特定語言：控制檯操作

    #[derive(Clone)]
enum Console<A> {
    Print(String, A),
    ReadLine(fn(String) -> A),
}

// Smart constructors
fn print_line(s: &str) -> Free<Console<()>, ()> {
    Free::Suspend(Console::Print(s.to_string(), ()))
}

fn read_line() -> Free<Console<String>, String> {
    Free::Suspend(Console::ReadLine(|input| Free::Pure(input)))
}

    直譯器

    fn run_console<A>(mut prog: Free<Console<A>, A>) -> A {
    loop {
        match prog {
            Free::Pure(a) => return a,
            Free::Suspend(Console::Print(s, next)) => {
                println!("{}", s);
                prog = Free::Pure(next);
            }
            Free::Suspend(Console::ReadLine(f)) => {
                let mut buf = String::new();
                std::io::stdin().read_line(&mut buf).unwrap();
                prog = f(buf.trim().to_string());
            }
            Free::FlatMap(inner, cont) => match *inner {
                Free::Pure(a) => prog = cont(a),
                Free::Suspend(op) => prog = Free::Suspend(op), // minimal handling
                _ => unimplemented!(),
            },
        }
    }
}

    用法

    fn main() {
    let program =
        print_line("What is your name?")
        .flat_map(|_| read_line())
        .flat_map(|name| print_line(&format!("Hello, {name}!")));

    run_console(program);
}

    要點

    • 語法 = enum Console（可能的指令）
    • 程式 = Free<Console, A>（描述步驟的資料）
    • 具體解釋 = run_console
    • 優勢：同一個程式可以編寫多種直譯器，例如在真正的 IO 中執行、將日誌寫入檔案，或編譯為另一種語言。

    與延續及 CPS 的關聯

    延續傳遞風格（CPS）是一種程式設計方式：函式不直接返回值，而是將結果傳給另一個函式（即延續），由它表示“程式接下來的部分”。

    自由單子本質上是由一系列步驟組成的程式，每一步都會說：

    “執行此操作，然後繼續處理剩餘部分。”

    這個“程式剩餘部分”正是一個延續——從當前結果對映到下一步的函式。

    • 在我們的 Rust 自由單子中：

      Free::FlatMap(Box<Free<F, A>>, Box<dyn Fn(A) -> Free<F, A>>)

      Box<dyn Fn(A) -> Free<F, A>>就是延續。

    • 解釋自由單子時，你其實是在透過 CPS 執行：

      • 你不會直接返回值，而是將它們傳給下一個延續。
      • 最終會進入如下迴圈： current_instruction -> feed result into continuation -> next instruction

    • CPS 關係：

      • 自由單子將 CPS 編碼進資料結構。
      • CPS 則是同一思想的執行時控制流表示。

    與去函式化的關係

    去函式化是一種程式變換：它將高階函式替換為表示可能函式集合的一階資料結構，並提供一個用於應用它們的直譯器。

    在 CPS 中，延續是高階函式。對 CPS 程式去函式化，會將這些延續替換為延續分支列舉，並提供一個apply函式來執行它們。

    對於適當的編碼，自由單子可以與 CPS 變換程式內部的去函式化延續連結起來：

    1. 從程式的 CPS 版本開始。“程式剩餘部分”由延續函式承載。
    2. 將這些延續函式去函式化為資料型別中的有限分支集合。
    3. 所得的一階資料型別可以具有與自由單子表示相同的指令與延續結構。

    關鍵相似之處

    • 自由單子與去函式化都會生成計算的資料表示，並且都需要直譯器來賦予這些資料含義。
    • 自由單子中的FlatMap分支援有延續；去函式化則將該閉包替換為資料型別中的一個分支。

    關鍵區別

    方面去函式化自由單子
    目的消除高階函式的機械式編譯器技術將語法與語義分離的代數構造

    輸出函式分支列舉及應用函式Free<F, A>AST 與直譯器
    是否為單子？不一定根據構造始終是單子

    總結 去函式化是一種變換技術，自由單子是一種代數構造。在某些表示中二者關係密切，但除非附加額外假設，否則通常不能由其中一種構造推出另一種。

    延續傳遞風格（CPS）

    相關內容

    Rust 中的語義驅動設計：一階程式、語言與編譯器流水線
    概念：自由單子、去函式化
    洞見：EVM 代數

    語義定位

    CPS 是一種表示與程式變換，它會將控制流顯式化。它是否保留含義，取決於是否明確了源語義、目標語義及二者之間的對應關係。

    定義

    延續傳遞風格（CPS）是一種程式設計方式：函式不直接返回值，而是將結果傳給另一個稱為延續的函式；延續表示程式接下來的部分。

    動機

    • 使控制流顯式且可程式設計。
    • 支援非阻塞 IO、提前退出、協程、回溯與併發排程等高階變換。
    • 用於編譯器中間表示，以簡化最佳化與分析。

    基本形式

    直接風格：

    fn add_one(x: i32) -> i32 {
    x + 1
}

fn main() {
    let y = add_one(41);
    println!("{}", y);
}

    CPS 風格：

    fn add_one_cps(x: i32, k: impl Fn(i32)) {
    k(x + 1)
}

fn main() {
    add_one_cps(41, |y| {
        println!("{}", y);
    });
}

    這裡，k是延續。我們不再返回x + 1，而是呼叫k(x + 1)。

    關鍵性質

    • 所有函式呼叫都是對延續的尾呼叫。
    • 當前計算永遠不會“返回”到呼叫者，而是跳入延續。
    • 程式中的控制流變得顯式。

    與高階函式的關係

    • 在 CPS 中，延續就是高階函式。
    • 計算的每個步驟都會接收一個延續，用來表示下一步要做什麼。

    與去函式化的關係

    • 在 CPS 中，延續是實際的函式值。
    • 去函式化會把延續函式替換為表示可能後續步驟的資料結構（列舉），並提供一個apply函式來解釋這些步驟。

    與自由單子的關係

    • 自由單子中的FlatMap構造器恰好儲存了一個延續。
    • 解釋自由單子類似於執行 CPS 程式碼，只不過延續成為程式資料的一部分。
    • 適當的自由單子編碼可以與 CPS 以及去函式化的延續表示建立連結。

    優點

    • 控制流表示靈活。
    • 更容易推理求值順序。
    • 適用於實作直譯器、偵錯程式、最佳化器與非同步執行時。

    缺點

    • 比直接風格冗長。
    • 對人來說可能更難閱讀。
    • 在不提供原生支援的語言中，需要尾呼叫最佳化才能獲得較高效率。

    去函式化

    相關內容

    Rust 中的語義驅動設計：一階程式、語言與編譯器流水線
    概念：自由單子、延續傳遞風格
    洞見：EVM 代數

    語義定位

    去函式化會改變表示，同時力求保留函式應用的行為。在語義優先設計中，當另一個直譯器需要在執行前檢查或組合操作時，生成的一階值就很有用。

    定義

    去函式化是一種程式變換：它將高階函式替換為表示可能函式集合的一階資料結構，並提供一個應用這些函式的直譯器函式。

    動機

    有些語言、編譯器或執行時無法高效處理高階函式，甚至完全不支援。透過去函式化，程式會變成純一階形式，因此更容易編譯、分析、序列化，或在受限環境中執行。

    處理過程

    1. 找出所有可能被建立並傳遞的高階函式。
    2. 為每個函式分配列舉或和型別中的唯一標籤，並附上它執行時所需的資料。
    3. 用這些標籤替換函式值。
    4. 定義一個apply函式，接收標籤與函式引數，然後按標籤進行模式匹配並執行相應程式碼。

    Rust 示例

    之前：使用閉包

    let k: Box<dyn Fn(i32) -> i32> = Box::new(|x| x + 1);
println!("{}", k(41));

    之後：去函式化形式

    enum Cont {
    Add1
}

fn apply(c: Cont, x: i32) -> i32 {
    match c {
        Cont::Add1 => x + 1,
    }
}

println!("{}", apply(Cont::Add1, 41));

    性質

    • 現在所有函式都由簡單資料表示。
    • 程式變為純一階形式。
    • apply函式取代直接的函式呼叫。

    應用

    • 簡化編譯器後端：許多編譯器會生成 CPS 程式碼，然後對其去函式化。
    • 函式序列化：可以透過網路傳送列舉標籤，也可以將其存入檔案。
    • 靜態分析：一階程式碼更容易推理。
    • 推導直譯器：去函式化會自然引出直譯器模式。

    與 CPS 的關係

    在 CPS（延續傳遞風格）中，延續是高階函式。對 CPS 程式碼去函式化，會將這些延續轉換為列舉中的有限分支集合，並提供一個應用函式。

    與自由單子的關係

    適當的自由單子表示可以與 CPS 變換程式中的去函式化延續相關聯。這是一種緊密連結，但不意味著兩種構造普遍等同。

    型別層面的應用

    去函式化還可以在不原生支援高階型別的語言中編碼型別層面的應用。C# 物件代數實驗透過App<F, a>運用這種輕量級編碼，以表達函子、適用函子、單子與效應代數。

    分支與合流

    相關內容

    語義視角：指稱與組合性、定律與解釋
    Rust 中的語義驅動設計：定律、場景與證據
    概念：操作語義

    分支、確定性、合流、軌跡等價與雙模擬都涉及計算中的多種可能，但它們並非同一種性質。

    語義定位

    控制流分支屬於操作結構。合流性是歸約關係的性質。軌跡等價與雙模擬用於比較行為。指稱等價則比較所選語義域中的含義。健全的設計應明確說明所需的等價關係，而不是非正式地在這些概念之間切換。

    行為等價

    併發與互動式程式很少只有一個最終結果。一個常見的起點是標記遷移系統：

    L=(S,Aτ​,→)

    其中S是狀態集合，Aτ​是可觀察動作標籤與一個內部動作τ的集合，→⊆S×Aτ​×S是轉換關係。我們將pa​p′記作：狀態p可以執行動作a並變為p′。

    行為等價會說明有意忽略這些系統之間的哪些差異：

    • 線性時間觀察沿著已完成或部分執行記錄發生的事件
    • 分支時間觀察還會保留何時出現了哪些選擇，以及選擇何時確定

    因此，兩個系統可能有相同軌跡，卻具有不同分支結構。一個系統可能在互動前就在兩個動作間選擇，另一個系統則推遲到互動之後才選擇。動作序列相同，但後續可能性不同。

    van Glabbeek 提出的線性時間—分支時間譜，系統整理了這些行為等價關係。它並非從弱到強的排序；譜中的每一點都保留不同的觀察。

    Rust 程式中的分支

    if會根據條件選擇一個分支：

    fn sign(x: i32) -> i32 {
    if x > 0 {
        1
    } else if x < 0 {
        -1
    } else {
        0
    }
}

    match會根據某個值選擇一個分支：

    fn day_type(day: &str) -> &str {
    match day {
        "Saturday" | "Sunday" => "Weekend",
        "Monday" | "Tuesday" | "Wednesday" | "Thursday" | "Friday" => "Weekday",
        _ => "Unknown",
    }
}

    對於確定性語言中的固定輸入，這些構造會選擇可預測的控制流路徑。這種性質稱為確定性，而非合流性。

    合流性的含義

    如果某個項的兩種歸約方式最終能夠再次匯合，那麼該歸約關係就是合流的：

    b​↙∗↘∗​ad​↘∗↙∗​c​

    形式化地說，若：

    a→∗banda→∗c

    則必然存在某個d，使得：

    b→∗dandc→∗d

    合流性允許存在多條歸約路徑。它表示這些路徑能夠到達共同後繼，因此彼此相容。

    確定性與合流性

    確定性歸約關係中，每個狀態最多隻有一個後續步驟。因此它自然滿足合流性：沒有相互競爭的單步選擇需要協調。

    反過來則不成立。系統可以允許多種歸約順序，同時仍滿足合流性，因為所有順序最終都會得到相同結果。

    普通 Rust 的if與match表示式展示了確定性選擇，但單憑它們無法體現合流性的有趣之處。

    Church–Rosser 性質

    Church–Rosser 定理說明了 lambda 演算歸約的合流性質。如果一個項沿不同歸約路徑得到兩個結果，那麼這兩個結果存在共同歸約結果。

    只要正規化存在，合流性就意味著它唯一。這支援等式推理，因為求值順序不會改變最終正規化。

    不要將此結果推廣到任意命令式程式。副作用、非確定性排程、失敗以及對中間狀態的觀察，都可能使不同歸約順序產生差異。

    軌跡

    軌跡記錄一系列可觀察動作或狀態。與只記錄結果的語義相比，軌跡語義有意保留更多操作資訊。

    兩個純函式可以返回同一結果，卻經過不同內部步驟。如果結果指稱忽略了這些步驟，它們在該指稱下相等；但在軌跡語義下，它們未必相等。

    存在效應時，調整檢查順序可能改變觀察：

    fn is_admin() -> bool {
    println!("checked admin");
    true
}

fn is_user() -> bool {
    println!("checked user");
    true
}

    先檢查is_admin還是先檢查is_user，可能返回等價分類，卻列印出不同軌跡。

    設計問題在於，這些列印資訊是否屬於所選語義域。

    軌跡等價

    如果兩個系統在選定的軌跡模型下允許相同的可觀察軌跡，它們就是軌跡等價的。

    軌跡等價可能忽略分支結構。兩個系統可以生成相同軌跡，但一個比另一個更早確定選擇。在互動式與併發系統中，這種區別可能很重要。

    雙模擬

    雙模擬逐步關聯兩個遷移系統。每當一個系統執行可觀察動作，另一個系統就必須能夠匹配該動作，而且遷移後的狀態仍須保持關聯。

    常見變體包括：

    • 強雙模擬，用於匹配單個狀態轉換
    • 弱雙模擬，用於抽象選定的內部轉換
    • 分支雙模擬，用於抽象內部工作，同時保留重要的選擇結構

    雙模擬通常比軌跡等價提供更強的行為比較，因為它會觀察互動過程中各種選擇是否仍然可用。

    起源與形式定義

    Milner 在《通訊系統演算》中為通訊過程發展了觀察等價。隨後 Park 在《無限序列上的併發與自動機》中，以餘歸納方式刻畫了相應的等價關係，給出了現稱為雙模擬的最大不動點關係與證明方法。Milner 隨後採用並發展了這一方法，將其作為推理過程行為的基礎。

    強雙模擬。對於標記遷移系統，若關係R滿足以下條件，則它是強雙模擬：當pRq成立時，對於每個動作a：

    • 如果pa​p′成立，則存在某個q′，使得qa​q′與p′Rq′成立；並且
    • 如果qa​q′成立，則存在某個p′，使得pa​p′與p′Rq′成立。

    如果存在某個雙模擬關係關聯兩個狀態，那麼它們就是雙模擬等價的。這一定義是餘歸納的：匹配某個狀態轉換後，後繼狀態必須再次滿足相同的行為義務。

    分支雙模擬。在一種忽略發散的常見表述中，如果對稱關係R滿足以下條件，那麼它就是分支雙模擬：當pRq與pa​p′成立時，以下情況至少一種成立：

    • a=τ與p′Rq成立；或

    • 存在狀態q0​與q′，使得

      qτ​q0​a​q′,pRq0​,p′Rq′

    這裡，τ​表示零次或多次內部轉換。要求中間狀態q0​仍與p保持關聯，正是為了忽略內部工作時仍能保留相關的分支可能性。van Glabbeek 與 Weijland 在《雙模擬語義中的分支時間與抽象》中引入並發展了這一等價關係。

    指稱相等

    指稱相等取決於所選語義域：

    [[P]]=[[Q]]

    語義域本身可以由軌跡、以雙模擬等價關係取商的遷移系統、結果集合或其他數學模型構成。指稱設計不規定某個通用等價關係，而是要求明確選擇等價關係，並以組合方式使用它。

    其關係如下：

    1. 從作業系統開始。
    2. 選定相關觀察。
    3. 選擇語義域與等價關係。

    作為資料的分支

    分支也會以樹的結構出現。二叉路徑可以表示為一串左右選擇。這種表示適用於字首樹、執行識別符號、決策圖與記憶體定址。

    《為何含義優先》中的語義分支位置示例，特意將樹的含義與一種位向量編碼區分開來。

    Conal Elliott 曾用完美二叉葉樹結構描述記憶體定址。重點並不是每臺機器都會按字面儲存一棵源級樹，而是組合式樹模型能夠揭示扁平數值地址所隱藏的有用結構。

    一則洞見可能橫跨這三個層次。若確實如此，請判斷每項主張屬於哪個層次，以及由哪條定律連線這些層次。

    從語義到機器

    相關內容

    Rust 中的語義驅動設計：一階程式、語言與編譯器流水線
    概念：操作語義、自由單子、延續傳遞風格、去函式化

    操作語義描述什麼

    操作語義規定所選程式表示的行為。它透過判斷或配置上的轉換關係來定義求值，例如：

    (program,state)⟶(program′,state′)

    程式可以是源語法、自由單子值、CPS 項、位元組碼或去函式化的機器狀態。這些表示無一就是操作語義。操作語義是對所選表示中的值如何求值或轉換的說明。

    方向很重要。表示為我們提供了一個可描述其行為的物件；補充操作描述並不能解釋該語言應有何種含義。

    自由單子程式

    自由單子提供指令語法與自由生成的順序組合，但不會提供這些指令的行為。

    自由單子程式的操作語義可以定義包含當前指令、其延續與任意機器狀態的配置。隨後，規則會說明例如掛起的指令如何改變狀態，並將結果傳遞給程式剩餘部分。

    這是一種可能的解釋。同一個自由程式也可以摺疊為指稱模型、編譯成另一種語言、接受分析，或直接渲染，而無需執行。

    從自由到更自由：研究揭示了什麼

    曾將自由單子視為效應程式通用架構的讀者，可能會好奇，為什麼後來研究轉向 freer 構造、可擴充效應與處理器。研究並沒有簡單拋棄自由單子，而是分離出它們真正提供的內容，衡量常見表示的失效之處，並將有用結構延續下來。

    Kiselyov 與 Ishii 透過逐步移除效應項表示中的約束與樣板程式碼，推導出 freer 單子。在 freer 表示中，指令可以產生一箇中間型別，而該型別被隱藏在最終程式型別之外；顯式延續則將該結果連線到計算的其餘部分。因此，指令簽名不再需要Functor例項。

    這種變化提升了表達能力，但本身並未解決效能問題。直接的 freer 表示仍然像左結合的列表追加那樣組合延續：處理一串n請求可能需要O(n2)的工作量。將延續顯式化後，就能看見真正的機會——可以把它儲存為型別對齊序列，相鄰結果與輸入型別由構造保證匹配。高效拼接該序列即可消除對結合順序敏感的遍歷。

    開放聯合型別隨後讓可擴充效應直譯器能夠新增、組合與消除選定的請求型別。這解決了模組化效應組合與處理器結構問題，但仍未提供某個具體領域的等式，也不會決定兩個帶效應程式何時具有相同含義。

    結論比“freer 優於 free”更加精確：自由單子揭示了請求與解釋之間有價值的分離；freer 編碼去除了不必要的約束；型別對齊佇列解決了經測量確認的效能問題；可擴充效應改善了組合。每一步都保留前一步的經驗，同時縮小主張範圍。語義解釋始終是另一項獨立決定。

    參見 Kiselyov 與 Ishii 的論文《Freer 單子：更具可擴充性的效應》。

    CPS 程式

    延續傳遞風格（CPS）會將計算剩餘部分顯式表示為延續。CPS 的操作語義會描述以下行為：

    • 對當前 CPS 表示式求值；
    • 將生成的值傳遞給其延續；
    • 應用該延續時轉移控制權。

    CPS 將控制流變為便於從操作層面描述的形式，但它是一種表示或程式變換，而非操作語義。要將直接風格程式與其 CPS 翻譯關聯起來，必須明確源語義、目標語義並給出保義論證。

    超越 CPS：何時必須檢查延續

    CPS 是解決結合順序敏感的追加與 bind 的常見方法。它不再反覆遍歷左結合結構，而是透過函式組合表示剩餘計算。如果對延續唯一要做的操作是最終應用，這種表示就很高效。

    van der Ploeg 與 Kiselyov 指出了適用邊界：有些使用者必須在繼續之前檢查或修改中間結果。非確定性搜尋、迭代器、自由單子與可擴充效應都可能需要此類存取。CPS 會將概念上的序列隱藏在函式中，因此要恢復中間結構就需要反射回資料，從而可能抵消效能優勢。

    他們提出的替代方案會將隱藏序列直接表示為型別對齊資料結構。它無論結合順序如何都能高效組合，同時保留對中間結果的高效存取。型別會確保每個儲存的計算都能產生下一個計算所需的輸入。

    更廣泛的結論並非型別對齊序列擊敗 CPS，而是 CPS 擅長應用延續；當使用者必須檢查延續時，它就不那麼合適。關於帶界控制的研究進一步深化了這一教訓：不要將整個未來視作一個無法區分的延續，而應使用分界符明確可捕獲與操縱的周邊計算範圍。

    這些思想並未消失。它們的經驗繼續影響效應處理器、抽象機器推導、有型別控制運算子與高效效應表示。變化的是，人們不再認為 CPS 單獨就應成為最終抽象。

    參見 van der Ploeg 與 Kiselyov 的論文《無悔反射》。關於更廣泛的控制模型，另請參閱 Kiselyov 的延續與帶界控制文集。

    去函式化機器

    去函式化會將已知的函式值集合（例如 CPS 延續）替換為一階構造器，並提供一個apply操作。隨後，操作語義可以描述這些顯式配置之間的狀態轉換。

    在具體的 CPS 變換之後再進行去函式化，可以推導出抽象機器。這是一種強有力的推導方式，但不是操作語義的通用定義：操作規則不必源自 CPS，任意一階機器也不會因此自動成為去函式化的延續機器。

    Reynolds：去函式化的起源

    John C. Reynolds 在 1972 年關於定義直譯器的研究中引入了去函式化。他的起點並非一階虛擬機器，而是高階直譯器：定義語言中的函式表示環境、延續及所定義語言的其他部分。

    該變換會觀察整個程式中可能出現的有限函式抽象集合。它將每個抽象替換為一個一階構造器，並攜帶其自由變數的值；隨後將函式應用替換為一個按構造器分派的apply操作。原本隱含在定義語言中的內容，就此變成顯式的閉包或延續代數。

    將這一做法應用於基於延續的直譯器，可以顯露出一臺機器：延續構造器變為控制狀態，被捕獲變數變為儲存的機器資料，apply則變成轉換分派器。機器不是預先猜出來的，而是從高階求值器推導出來的。

    Reynolds 也強調了這種清晰度的代價。所得機器包含正確但不唯一的表示選擇。不同的構造器選擇或前置變換可能生成不同的、類似機器的“齒輪與部件”，但仍保留相同的行為。因此，去函式化顯露的是一種操作結構，而非語言唯一必然的含義。

    Danvy 與 Nielsen 後來將 Reynolds 的技術系統化為全程式變換，並研究了作為其逆變換的重新函式化。他們更深層的結論是：這種變換是一座橋樑，能夠在高階定義與一階機器之間傳遞規範與正確性論證，還能揭示表面上無關的程式其實是同一結構的兩種表示。

    這條研究脈絡說明了該技術應有的權威範圍。去函式化不只是把閉包替換為列舉，但也不是普遍基礎：它是在兩種表示間保義轉換，其對應關係必須得到確立。

    參見 Reynolds 的《高階程式語言的定義直譯器》，以及 Danvy 與 Nielsen 的《去函式化的實踐》。

    操作表示迴圈

    一種常見錯誤是試圖尋找能解決所有程式設計問題的單一操作表示。每種表示都會恢復前一種表示隱藏的內容，但也會使另一種關切更難處理：

    higher-order program⟶free syntax⟶CPS⟶first-order machine⟶higher abstraction

    這些箭頭並不表示編譯器必須採用某條流水線，而是展示一種反覆出現的設計演進：顯露當前表示隱藏的內容，隨後再隱藏此次顯露引入的機制。

    表示使哪些內容可見引入了何種壓力
    高階函式直接組合與宿主語言抽象泛型使用者可以呼叫函式，卻無法檢查函式隱藏的結構
    帶順序組合的自由語法以資料形式表示、可組合並可解釋的程式自由性本身不提供領域等式、正規化、高效求值，也不支援檢查已儲存的函式
    CPS求值順序與計算剩餘部分變得顯式全程式 CPS 編碼會讓延續貫穿幾乎每個介面
    去函式化的一階控制延續變成可檢查、可序列化的分支必須顯式維護構造器、已存引數、轉換狀態與一個apply操作
    對機器作更高層抽象機制變得更易使用編譯器、排程器、偵錯程式或最佳化器需要檢查結構時，它又被隱藏起來

    這些壓力來自結構本身。檢查需要資料；將行為轉為資料會引入構造器與直譯器；隱藏這些構造器可以恢復便利的抽象，卻會移除分析或變換程式的使用者所需的存取能力。

    自由單子的取捨尤其具有啟發性。自由單子解決了一個精確問題：為指令函子生成順序組合，而不施加單子定律之外的等式。這一保證也構成了它的侷限。它不瞭解領域定律。如果對同一單元格的兩次寫入應當等價於最終那次寫入，那麼自由程式仍會保留兩條指令，直到領域專用的正規化或解釋將它們識別為等價。因此，最佳化、規範形式與語義等價必須由其他機制提供。

    將指令具體化為資料，也不會讓整個程式都可檢查。在常見編碼中，掛起的指令可見，但其延續卻是宿主語言函式。泛型分析器無法檢查該函式背後的未來結構，除非提供結果並應用該函式。將延續具體化可以恢復可檢查性，但會轉向一階或去函式化表示——於是又回到了迴圈的下一環。

    求值開銷同樣取決於表示。左結合繫結構成的樸素樹可能需要反覆遍歷，導致二次複雜度。複製剩餘子程式的變換可能導致指數級增長。Codensity 風格、freer 或專用編碼可以改善特定開銷，但代價是選擇了不同的表示與取捨。指數級增長確實可能發生，但不是自由單子的固有定律。

    這就是自由單子並非通用解法的原因。它提供帶定律的順序組合語法，但不提供預期領域等式、規範正規化、完整結構可見性或自動高效的實作。同樣，區域性使用 CPS 並不需要擴散到整個系統；去函式化只有在需要具體化的函式族與捕獲值變多時才會變得繁瑣。

    當人們要求每種新編碼都成為通用基礎時，就會出現這個迴圈。它解決了上一種操作不便，隨後又成為新的偶然複雜性來源。

    因此，如果討論“最佳抽象”時只關注操作特性，爭論就難以收斂。高階函式、自由語法、CPS 與一階機器被拿來比較，彷彿其中一種必須勝過其他所有方案。但在說明必須保留什麼、結果由誰使用之前，“更好”沒有明確含義：

    • 直接執行偏好普通呼叫與隱藏表示；
    • 變換與分析需要可檢查的結構；
    • 序列化需要一階資料；
    • 可擴充性可能更偏好增加解釋，也可能更偏好增加語法，但兩者很少同樣容易；
    • 併發可能需要有意忽略許多排程選擇的觀察。

    這些是不同要求，而非某種抽象普遍更優的逐級證明。操作特性有助於為既定目的選擇實作，卻不能提供該目的，也不能決定哪些區別有意義。

    同樣的謹慎也適用於順序思維。操作語義可以描述併發與非確定性系統，但單一機器步驟序列只是表示其行為的一種可能方式。如果過早將排程順序視為權威，不同交錯機制就會讓本來等價的執行顯得不同。語義模型必須先決定哪些觀察可以區分併發程式，隨後再根據該決定評判操作排程。

    真實示例：EVM

    以操作視角理解以太坊虛擬機器（EVM）：

    • 狀態：程式計數器、棧、記憶體、儲存、Gas
    • 轉換規則：每個操作碼各有一條（ADD、PUSH、SSTORE等）
    • 執行：反覆應用小步規則，直至停止

    EVM 位元組碼是一階指令資料。操作性描述會規定每種操作碼如何改變 EVM 配置；具體客戶端則負責實作該行為。

    它的分派迴圈與程式計數器可能類似於去函式化抽象機。但若要稱其為去函式化延續，就必須提供具體高階源程式、變換與對應關係，不能只憑迴圈看起來相似。

    打破迴圈：機制之前先確定含義

    操作描述與指稱描述回答不同的問題：

    [[p]]c​∈D⟶c′​​what does the program mean?how does this representation step?​

    語義優先的開發會先選擇語義域、組合、觀察與定律，再確定機器表示。一旦選定轉換系統，其正確性義務就負責連線這兩個層次。對於恰當定義的完整配置含義，典型的靜默步驟保留主張如下：

    c⟶c′⟹meaning(c)=meaning(c′)

    具體關係也可以改用觀察等價、軌跡或雙模擬。關鍵在於，機器必須對預期含義負責。

    指稱設計不會從迴圈中選出勝者，而是在迴圈之外建立穩定的權威來源：

    1. 定義語義域、操作、組合與定律。
    2. 根據這些含義編寫程式。
    3. 針對具體使用者選擇表示：直接執行、檢查、編譯、排程、序列化或分析。
    4. 將每種選定的表示與變換都關聯回同一含義。

    因此，高階直譯器與一階程式可以共存。二者都不必成為語言定義。前者可以服務於直接執行；後者可以服務於需要結構的使用者。二者一致是一項語義義務，而非假定其機制相同。

    不存在最終的操作抽象

    每種操作表示都會顯露某些結構並隱藏另一些結構。含義是穩定的出發點，我們據此選擇恰當的表示並建立它們之間的連結。

    總結

    • 操作語義描述所選表示的求值或狀態轉換。
    • 自由單子提供指令語法與順序組合，但其行為仍需要解釋。
    • CPS 會顯露延續；操作規則可以描述 CPS 程式如何傳遞值與控制權。
    • 去函式化可以將某個高階程式轉換為一階機器，並以操作規則描述其狀態轉換。
    • 將其中任意一種編碼視為通用方案，都會造成結構不斷被具體化又被隱藏的迴圈。
    • 指稱含義決定這些狀態轉換必須保留什麼。

    概念：表示式問題

    本頁介紹一種基於 trait 的實用解法來處理表示式問題：如何新增新的表示式形式與操作，而不必反覆重寫現有程式碼。 該解法的設計遵循 Conal 風格，編碼方式則採用無標籤最終編碼/物件代數。具體而言，我們先規定可組合含義（小型能力介面與擴充層面的程式規範），再提供具體直譯器。這種編碼與 Oleg Kiselyov 的無標籤最終風格及物件代數屬於同一型別：構造器介面（LitAlg、AddAlg、MulAlg）定義語言簽名，程式以多型方式針對這些介面編寫，具體實作（例如Eval或Pretty）則提供解釋。這樣既避免繫結到某個封閉 AST，又保留了兩個維度上的靜態型別與可擴充性。

    Oleg 的方法明確採用指稱式設計：先賦予可組合含義，再將效應與直譯器實現為模組化語義層。對於表示式問題而言，這正是它與指稱設計契合的原因，而非偶然。Conal 對指稱設計的表述也明確提出相同優先順序：先以組合方式規定含義，再將具體執行策略視為次要且可替換的部分。

    對於表示式語言示例，這種編碼意味著：

    • 構造器詞彙由小型、獨立的代數 trait 建模。
    • 解釋是這些 trait 的實作。
    • 新語法會新增新 trait，而不觸碰舊程式碼。
    • 新語義會新增新的直譯器型別，而不觸碰舊程式碼。

    lit與add是語義操作，而非特權 AST 的構造器。AST 只是多種解釋中的一種。

    C# 中的物件代數

    這種編碼並非 Rust 特有。object-algebras在 C# 中發展了這一模式，並突破了本頁採用的固定載體。在本頁中，每個直譯器會選擇一個具體的Self::Expr普通型別。而 C# 代數會抽象出一個型別構造器F——FunctorAlg<F>、MonadAlg<F>、BankingDsl<F>——並將結果作為App<F, a>承載，而不是採用不合法的F<a>。

    C# 沒有一等高階型別，因此以App<F, a>代替應用F(a)，並透過注入/投影包裝器還原。這種App技巧正是去函式化：語言無法表達的抽象被轉為一階資料，並在需要時應用。Rust 也遇到了同樣的限制——它同樣缺少一等高階型別。

    規定小型語法能力

    每種構造器都會成為一個小型 trait。這就是規範。

    trait LitAlg {
    type Expr;

    fn lit(&self, n: i64) -> Self::Expr;
}

trait AddAlg {
    type Expr;

    fn add(&self, a: Self::Expr, b: Self::Expr) -> Self::Expr;
}

    程式以代數 trait 之上的擴充形式編寫。這些擴充也屬於規範，並可將較小規範組合為可複用的程式級規範：

    #[ext(name = ExprPrograms)]
impl<This> This
where
    This: LitAlg + AddAlg,
{
    fn expr_basic(&self) -> This::Expr {
        self.add(self.lit(2), self.lit(3))
    }
}

    #[ext(...)]是來自extendcrate 的宏，用於從impl塊中生成擴充方法以減少樣板程式碼；它不是新的 Rust 語言特性。

    新增新的解釋

    直譯器實作規範，無需修改語法。

    struct Eval;

impl LitAlg for Eval {
    type Expr = i64;

    fn lit(&self, n: i64) -> i64 { n }
}

impl AddAlg for Eval {
    type Expr = i64;

    fn add(&self, a: i64, b: i64) -> i64 { a + b }
}

struct Pretty;

impl LitAlg for Pretty {
    type Expr = String;

    fn lit(&self, n: i64) -> String { n.to_string() }
}

impl AddAlg for Pretty {
    type Expr = String;

    fn add(&self, a: String, b: String) -> String {
        format!("({a} + {b})")
    }
}

    現在，同一個表示式可以有不同的解釋：

    let eval = Eval;
let pretty = Pretty;

let v: i64 = eval.expr_basic();        // 5
let s: String = pretty.expr_basic();   // "(2 + 3)"

    新增新語法（新能力 trait）

    要新增Mul，只需定義一個新 trait。現有程式碼保持不變。

    trait MulAlg {
    type Expr;

    fn mul(&self, a: Self::Expr, b: Self::Expr) -> Self::Expr;
}

#[ext(name = ExprProgramsMul)]
impl<This> This
where
    This: LitAlg + AddAlg + MulAlg,
{
    fn expr_with_mul(&self) -> This::Expr {
        self.mul(self.add(self.lit(2), self.lit(3)), self.lit(4))
    }
}

    現有直譯器仍可處理舊表示式。
    如果它們需要支援新語法，就實作新 trait：

    impl MulAlg for Eval {
    type Expr = i64;

    fn mul(&self, a: i64, b: i64) -> i64 { a * b }
}

impl MulAlg for Pretty {
    type Expr = String;

    fn mul(&self, a: String, b: String) -> String {
        format!("({a} * {b})")
    }
}

    為什麼這能解決表示式問題

    傳統表示式問題包含表示上的兩個維度：

    • 新增新的變體（分支）
    • 新增新操作

    指稱設計重新詮釋了這兩個維度：

    • 擴充語義詞彙：定義新的能力 trait（MulAlg）。
    • 為該詞彙新增新的解釋：定義新的直譯器型別（Eval、Pretty、AST 構造器或程式碼生成器）。

    這兩個維度可以獨立組合：

    • 除非需要新能力，否則現有程式無需修改。expr_basic仍然只要求LitAlg + AddAlg。
    • 除非選擇解釋新能力，否則現有直譯器無需修改。Eval即使沒有impl MulAlg，仍可執行所有不使用mul的程式。

    這並沒有消除實作矩陣。如果Eval與Pretty都需要解釋mul，二者都需要impl MulAlg。變化在於矩陣的組織方式：每個單元格都是語義操作 × 解釋；沒有任何單元格圍繞特權表示組織；每個程式只依賴自己使用的能力。

    定律屬於規範

    語義代數由載體、操作與定律構成。載體（type Expr）由解釋選擇；操作與定律則屬於規範。例如，算術含義LitAlg + AddAlg規定：

    add(lit(m), lit(n)) = lit(m + n)

    Eval滿足這條定律。Pretty則不滿足："(2 + 3)"並不等於"5"。二者都是語法簽名的有效解釋，但只有Eval才是算術規範的模型。這條定律只需針對 trait 陳述一次，並由它決定哪些直譯器符合要求。它不屬於任何直譯器。

    最終洞見：輕量級 Go 與指稱設計

    Wadler 在語言機制層面診斷了表示式問題：靜態型別與模組化擴充下的行列問題。輕量級 Go給出了一種具體解法：Plus(type a Any)保持遞迴表示的泛型性，並讓每種操作獨立約束a（Plus(type a Evaler)對應Eval，Plus(type a Stringer)對應String）。表示不會繫結到某個封閉表示式介面，因此兩個維度都保持開放。

    傳統解法從表示出發，思考如何開放兩個擴充維度。輕量級 Go 將這一點推進得出人意料地遠：它讓遞迴表示具有泛型性與結構可擴充性。指稱設計則將邊界提前了一步：表示並非模型。模型是代數及其定律；表示只是可能的解釋之一。

    輕量級 Go 讓表示可以擴充。指稱設計讓表示成為可選項。

    輕量級 Go指稱設計
    語義核心可擴充表示代數與定律
    Num/Plus, lit/add結構（表示形式）語義操作
    Eval, String/Pretty方法與介面解釋
    遞迴結構泛型、開放表示（Plus(a)）無需遞迴表示
    載體所表示的表示式型別由直譯器選擇（type Expr）
    AST表示仍居於核心可選，是多種解釋之一
    矩陣單元格分支 × 操作 → 方法語義操作 × 解釋 → impl
    新行為新增方法與介面新增或組合能力
    新實作新的結構實現新的直譯器

    Wadler 詢問如何擴充表示的兩個維度。指稱設計則詢問為什麼表示應當掌握這兩個維度。

    先定義可組合含義，再選擇編碼。這樣，表示式問題就成為編碼之間的工程選擇，而不再是概念上的死結。

    語言的含義應獨立於機器這一概念。

    概念：引用透明性

    本頁介紹引用透明性的指稱設計解讀。 概念頁討論其歷史與主流語言中的用法。 本頁重點說明 RT 作為設計約束時的含義。

    在指稱設計中，RT 並非純性標籤。 它是關於指稱的一條定律：替換必須保留指定含義。

    以指稱設計重新表述 RT

    指稱設計將 RT 重新表述為規範要求，而非實作風格。 規範必須先定義可組合含義；之後才選擇執行策略。

    因此，應在語義邊界檢查 RT：

    • 相同輸入
    • 相同的已宣告上下文
    • 相同指稱

    若這些條件成立，替換就是有效的，並且可以進行等式推理。 即使具體直譯器執行 I/O、併發、重試或狀態轉換，這一點仍然成立，因為這些細節都委託給規範能力邊界之後的實現。

    換言之，指稱設計不會問“這個實作是否純？”。 它會問“指稱等式是否明確？直譯器是否保留了這些等式？”

    純性與 RT

    RT 與純性相關，但並不相同。

    • RT是關於含義的一條替換定律。
    • 純性是一項操作約束：不存在隱藏的可觀察效應。

    純性是表示式級程式碼實現 RT 的常見方式。 但 RT 仍是語義標準：替換必須保留指定指稱。

    因此，指稱設計不會把 RT 變成“只能寫純程式碼”這樣的風格標籤。 它要求指稱等式明確，並將效應隔離在能力邊界之後。

    一種最簡語義解讀是：

    fn f(a: A, io: Io) -> (Result<B, E>, Io)

    對於相同的a和相同的io輸入，f會得出相同的(result, io')。 這是指稱設計中按上下文索引的替換推理形式。

    RT 為何因此更清晰

    許多關於 RT 的爭論混淆了一項有用區別：

    • 語義透明性
    • 操作性副作用

    指稱設計將這些層次分開：

    • 語義核心陳述含義
    • 直譯器實現執行策略

    這種區分既允許實際效應存在，也不會失去基於定律的推理。

    表示優先設計的失誤模式

    如果過早確定具體表示，關於 RT 的討論就會偏離到風格爭論：

    • “這種風格是純的”
    • “那種風格不純”
    • “用 IO 包裝器就能解決”

    這些大多隻是編碼方式之爭。 指稱設計提出了一個更簡單的問題： 你的規範中哪些等式有效？

    指稱設計的實用模式

    定義小型能力 trait，並將程式行為寫成其上的擴充。 隨後提供輕量級具體直譯器。

    trait FileSystem {
    type Error;

    fn file_read(&self, name: &str) -> Result<String, Self::Error>;
}

trait GithubPublish {
    type Error;

    fn github_publish(&self, repo: &str, files: Vec<String>) -> Result<(), Self::Error>;
}

trait Concurrent {
    fn map_concurrent<A, B, E, F>(&self, xs: &[A], f: F) -> Result<Vec<B>, E>
    where
        A: Clone,
        F: Fn(&A) -> Result<B, E>;
}

#[ext(name = PublishProjectExt)]
impl<This> This
where
    This: FileSystem<Error = String> + GithubPublish<Error = String> + Concurrent,
{
    fn publish_project(&self, files: &[&str], repo: &str) -> Result<(), String> {
        let files = self.map_concurrent(files, |name| self.file_read(*name))?;
        self.github_publish(repo, files)
    }
}

    #[ext(...)]是來自extendcrate 的宏，用於從impl塊中生成擴充方法以減少樣板程式碼；它不是新的 Rust 語言特性。

    在 Scala 函數語言程式設計中，RT 常透過F[A]型別的值來介紹（例如IO[A]或F[Either[E, A]]）。 這裡的 RT 被表達在更高一層：作為受能力約束的程式含義。 因此，這種 Rust 方法並非以與F[A]相同的編碼方式實作的 RT 值容器；它是在明確能力之上規範 RT 行為，並將具體效應委託給實作。

    擴充依據能力陳述語義行為。 具體實作負責決定執行策略，例如批次處理、重試、傳輸、並行與儲存細節。

    最終洞見

    在指稱設計中，RT 是語義規範的性質。 只要保留已陳述的指稱定律，實作選擇就是次要的。

    保留定律。 不要困在標籤之爭裡。

    EVM 代數

    相關內容

    Rust 中的語義驅動設計：直譯器與效應、一階程式、語言與編譯器流水線
    概念：操作語義、自由單子、延續傳遞風格、去函式化

    以太坊虛擬機器（EVM）是一種基於棧的虛擬 CPU，用於執行以太坊位元組碼，後者是以 Solidity、Vyper 或其他相容 EVM 的語言編寫的智慧合約編譯後的形式。

    在最低層：

    • EVM 會處理操作碼（ADD、PUSH、JUMP、SSTORE 等）。
    • Execution state includes:
      • 棧：後進先出的運算元資料棧。
      • 記憶體：用於臨時值的瞬態位元組陣列。
      • 儲存：每份合約對應的持久鍵值儲存。
      • 程式計數器：指向下一條操作碼。
      • Gas：對執行步驟計量並收費。

    作為直譯器模式的 EVM

    EVM 客戶端是對一門指令語言的直譯器：

    • 指令集 = EVM 操作碼（由多個變體組成的列舉）。
    • 程式 = 一系列指令。
    • 直譯器 = 每種操作碼如何改變機器狀態的規則。
    • 多個直譯器 = EVM 規範固定，但 Geth、Nethermind、Besu 與 Erigon 是同一直譯器的不同實作。

    本書中的三種技術——自由單子、延續傳遞風格與去函式化——貫穿同一條主線；它們只在如何表示程式剩餘部分上有所不同。

    一臺機器的三種編碼

    以下每種編碼都執行同一個固定程式：

    push 2; push 3; add; sstore 1 5; load 1 -> v; push v

    而且每種編碼都會產生相同的觀察結果：

    stack:   [5, 5]
storage: {1: 5}

    它們的區別僅在於如何表示控制流——“接下來要做什麼”。

    自由單子——程式是資料；直譯器賦予它含義

    指令函子會生成程式樹。and_then是單子 bind，run是一種直譯器——另一個直譯器（編譯為位元組碼）也可以摺疊同一棵樹。泛型Free<A>針對這套指令集專門化，因此可以在穩定版 Rust 中編譯。

    use std::collections::HashMap;

struct State { stack: Vec<u64>, storage: HashMap<u64, u64> }

// The free monad over the EVM instruction set: a program is data — a tree of
// instructions ending in `Pure`, each carrying its continuation.
enum Free<A> {
    Pure(A),
    Push(u64, Box<Free<A>>),
    Add(Box<Free<A>>),
    SStore(u64, u64, Box<Free<A>>),
    SLoad(u64, Box<dyn FnOnce(u64) -> Free<A>>),
}

impl<A: 'static> Free<A> {
    // Monadic bind: graft `k` onto every leaf of the program.
    fn and_then<B: 'static>(self, k: impl FnOnce(A) -> Free<B> + 'static) -> Free<B> {
        match self {
            Free::Pure(a) => k(a),
            Free::Push(v, next) => Free::Push(v, Box::new(next.and_then(k))),
            Free::Add(next) => Free::Add(Box::new(next.and_then(k))),
            Free::SStore(x, y, next) => Free::SStore(x, y, Box::new(next.and_then(k))),
            Free::SLoad(key, cont) => Free::SLoad(key, Box::new(move |v| cont(v).and_then(k))),
        }
    }
}

fn push(v: u64) -> Free<()> { Free::Push(v, Box::new(Free::Pure(()))) }
fn add() -> Free<()> { Free::Add(Box::new(Free::Pure(()))) }
fn sstore(k: u64, v: u64) -> Free<()> { Free::SStore(k, v, Box::new(Free::Pure(()))) }
fn sload(k: u64) -> Free<u64> { Free::SLoad(k, Box::new(|v| Free::Pure(v))) }

// Interpreter: give the program data meaning against the machine state.
fn run(mut prog: Free<()>, st: &mut State) {
    loop {
        prog = match prog {
            Free::Pure(()) => return,
            Free::Push(v, next) => { st.stack.push(v); *next }
            Free::Add(next) => {
                let b = st.stack.pop().unwrap();
                let a = st.stack.pop().unwrap();
                st.stack.push(a + b);
                *next
            }
            Free::SStore(k, v, next) => { st.storage.insert(k, v); *next }
            Free::SLoad(k, cont) => { let v = *st.storage.get(&k).unwrap_or(&0); cont(v) }
        };
    }
}

fn main() {
    let program = push(2)
        .and_then(|_| push(3))
        .and_then(|_| add())
        .and_then(|_| sstore(1, 5))
        .and_then(|_| sload(1))
        .and_then(|v| push(v));

    let mut st = State { stack: vec![], storage: HashMap::new() };
    run(program, &mut st);
    println!("stack:   {:?}", st.stack);
    println!("storage: {:?}", st.storage);
}
    延續傳遞風格（CPS）——每個操作碼都會呼叫“程式剩餘部分”

    每個處理器完成工作後都會呼叫延續k。sload會將載入的值傳遞給一個需要該值的延續。控制流以巢狀延續的形式顯式表達，完全沒有程式資料結構。

    use std::collections::HashMap;

struct State { stack: Vec<u64>, storage: HashMap<u64, u64> }

// Each opcode does its work, then calls the continuation `k` = "the rest of
// the program". `sload` passes the loaded value on to its continuation.
fn push(st: &mut State, v: u64, k: impl FnOnce(&mut State)) {
    st.stack.push(v);
    k(st);
}
fn add(st: &mut State, k: impl FnOnce(&mut State)) {
    let b = st.stack.pop().unwrap();
    let a = st.stack.pop().unwrap();
    st.stack.push(a + b);
    k(st);
}
fn sstore(st: &mut State, key: u64, val: u64, k: impl FnOnce(&mut State)) {
    st.storage.insert(key, val);
    k(st);
}
fn sload(st: &mut State, key: u64, k: impl FnOnce(&mut State, u64)) {
    let v = *st.storage.get(&key).unwrap_or(&0);
    k(st, v);
}

fn main() {
    let mut st = State { stack: vec![], storage: HashMap::new() };

    push(&mut st, 2, |st| {
        push(st, 3, |st| {
            add(st, |st| {
                sstore(st, 1, 5, |st| {
                    sload(st, 1, |st, v| {
                        push(st, v, |_st| {});
                    });
                });
            });
        });
    });

    println!("stack:   {:?}", st.stack);
    println!("storage: {:?}", st.storage);
}
    去函式化——操作呼叫變成由一個apply執行的資料

    自由單子與 CPS 版本會呼叫操作（push(2)、add()、sstore(1, 5)、sload(1)）——這是一種幾乎可直接讀作規範說明的小型代數；去函式化則將每次呼叫具體化為一階資料。接著由一個apply函式解釋這些資料，延續也會隨之摺疊：「程式剩餘部分」變成下一個索引（pc）。可以把它看作以資料形式書寫的操作代數，並由apply這個單一直譯器解釋。

    use std::collections::HashMap;

struct State { stack: Vec<u64>, storage: HashMap<u64, u64> }

// The EVM algebra reified: where the other encodings CALL `push(2)`, `add()`,
// `sstore(1, 5)`, `sload(1)`, each such call becomes a first-order value — a
// tag with its arguments.
enum Op {
    Push(u64),
    Add,
    SStore(u64, u64),
    SLoad(u64),
}

// `apply` is the single interpreter for the reified operations: it gives each
// tag its meaning against the machine state.
fn apply(op: &Op, st: &mut State) {
    match op {
        Op::Push(v) => st.stack.push(*v),
        Op::Add => {
            let b = st.stack.pop().unwrap();
            let a = st.stack.pop().unwrap();
            st.stack.push(a + b);
        }
        Op::SStore(k, v) => { st.storage.insert(*k, *v); }
        Op::SLoad(k) => {
            let v = *st.storage.get(k).unwrap_or(&0);
            st.stack.push(v);
        }
    }
}

fn main() {
    // The program is now data: a flat list of reified operation calls.
    let code = vec![
        Op::Push(2),
        Op::Push(3),
        Op::Add,
        Op::SStore(1, 5),
        Op::SLoad(1),
    ];

    // `pc` is the defunctionalized continuation: "the rest of the program" is
    // just the next index.
    let mut st = State { stack: vec![], storage: HashMap::new() };
    let mut pc = 0;
    while pc < code.len() {
        apply(&code[pc], &mut st);
        pc += 1;
    }

    println!("stack:   {:?}", st.stack);
    println!("storage: {:?}", st.storage);
}

    從延續到位元組碼

    以下三種編碼呈現的是同一計算，只是各自與機器的距離不同：

    • 自由單子先以代數方式將程式構造為資料，再對其作出解釋。同一棵樹可以由多個直譯器摺疊：一個執行它，一個漂亮列印它，一個編譯它。
    • CPS會移除資料結構並顯式表示控制流：“執行此操作碼，然後呼叫延續。”載入的值會流向需要它的延續。
    • 去函式化會將操作的呼叫轉換為一階資料，並由一個apply函式解釋這些資料；延續則摺疊為一個pc，其操作對象是Vec<Op>。驅動迴圈就是一個不使用閉包的 CPS 蹦床。

    類比，而非推導

    EVM 可以分析為一階抽象機，其顯式程式計數器類似於去函式化的控制表示。但這種結構類比本身無法證明 EVM 位元組碼是經 CPS 變換再去函式化得到的。

    關鍵洞見

    概念自由單子世界EVM 實際情況
    指令型別操作碼列舉固定的 EVM 操作碼
    程式表示由Free<A>構造的樹線性位元組碼陣列
    延續指令節點中的閉包程式計數器（pc）
    直譯器對程式進行模式匹配按操作碼切換分支，並修改虛擬機器狀態
    多種直譯器對同一程式進行不同摺疊多個以太坊客戶端實作

    與真實 EVM 的對應

    • 指令集（Free的變體，或Op列舉）對應 EVM 操作碼集合。
    • 程式（Free樹、巢狀延續或Vec<Op>）表示編譯前後的合約。
    • 直譯器（run、CPS 處理器或apply）是 Geth、Besu 或 Nethermind 等客戶端所實作的部分。
    • 機器狀態（stack、storage）是 EVM 的棧、記憶體與儲存。
    • 真實的 EVM 位元組碼是去函式化後的形式：由程式計數器索引的扁平指令陣列，恰如上文展示的去函式化編碼。

    關於

    本書提煉了一種軟體思維方式，靈感來自 Conal Elliott 的指稱設計。核心思想簡單而深刻：

    指稱設計

    先定義程式的含義，再決定它如何執行。

    在這一視角下，計算不是不透明的步驟序列，而是透明的數學物件。我們從規範開始，以純粹且可組合的方式描述程式意味著什麼。這些描述採用代數結構表達，通常表現為 trait 或型別簽名。實作——這些含義如何實現出來——則是獨立且可互換的一層。

    將含義與機制分離後，我們便能獲得：

    • 清晰性——程式讀起來像精確的定義。
    • 可組合性——各部分可以按代數規則組合。
    • 可重構性——實作持續演進時，含義仍保持不變。
    • 正確性——推理程式時可以採用等式推理，而非操作層面的推理。

    這些指南旨在提供實用技術，幫助讀者在現代程式語言中運用這一風格，尤其是 Rust，同時保留其數學根基的優雅與嚴謹。

    本書有意區分三個層次：

    • 含義說明所設計的值、關係與變換。
    • 表示選擇如何將這些含義編碼為型別與資料。
    • 執行選擇如何讓一種表示在機器上執行。
