    Проблема выражения: новый взгляд

    Связанные материалы

    «Семантический взгляд»: Денотационное проектирование
    «Проектирование на основе смысла в Rust»: Алгебры возможностей, Производный смысл и композиция, Интерпретаторы и эффекты
    «Понятия»: Проблема выражения

    На этой странице представлен практический основанный на трейтах подход к проблеме выражения: как добавлять новые формы выражений и операции, не переписывая постоянно существующий код. В основе проектирования лежит подход в духе Конала, а кодирование использует стиль tagless-final / объектные алгебры. Сначала задаётся композиционный смысл (небольшие интерфейсы возможностей и спецификации программ на уровне расширений), а затем предоставляются конкретные интерпретаторы. Конкретное кодирование относится к тому же семейству, что и стиль tagless-final Олега Киселёва и объектные алгебры: интерфейсы-конструкторы (LitAlg, AddAlg, MulAlg) задают сигнатуру языка, программы записываются полиморфно через эти интерфейсы, а конкретные реализации (например, Eval или Pretty) предоставляют интерпретации. Так удаётся не привязываться к одному закрытому AST, сохраняя статическую типизацию и расширяемость по обоим измерениям.

    Подход Олега явно денотационный: сначала назначается композиционный смысл, а затем эффекты и интерпретаторы реализуются в виде модульных семантических слоёв. Для проблемы выражения именно поэтому связь с денотационным проектированием ожидаема, а не случайна. В формулировке Конала Эллиотта приоритет тот же: сначала композиционно задаётся смысл, а конкретные стратегии выполнения рассматриваются как вторичные и заменяемые.

    Для примера языка выражений это кодирование означает следующее:

    • Словарь конструкторов моделируется небольшими независимыми трейтовыми алгебрами.
    • Интерпретации являются реализациями этих трейтов.
    • Новый синтаксис добавляет новый трейт, не затрагивая старый код.
    • Новая семантика добавляет новый тип интерпретатора, не затрагивая старый код.

    lit и add — семантические операции, а не конструкторы привилегированного AST. AST — лишь одна из возможных интерпретаций.

    Объектные алгебры в C#

    Это кодирование не специфично для Rust. object-algebras развивает этот паттерн на C# и выходит за пределы фиксированного носителя, используемого здесь. На этой странице каждый интерпретатор выбирает один конкретный Self::Expr, обычный тип. Алгебры C# абстрагируются от типового конструктора F — FunctorAlg<F>, MonadAlg<F>, BankingDsl<F>, — который передаёт результаты как App<F, a> вместо недопустимого F<a>.

    В C# нет типов высшего рода первого класса, поэтому App<F, a> заменяет применение F(a), восстановленное с помощью обёрток inject/project. Этот приём с App — и есть дефункционализация: абстракция, которую язык не может выразить, становится данными первого порядка и применяется по требованию. Rust сталкивается с тем же ограничением: у него тоже нет типов высшего рода первого класса.

    Задайте небольшой синтаксис возможностей

    Каждому конструктору соответствует небольшой трейт. Это спецификация (spec).

    trait LitAlg {
    type Expr;

    fn lit(&self, n: i64) -> Self::Expr;
}

trait AddAlg {
    type Expr;

    fn add(&self, a: Self::Expr, b: Self::Expr) -> Self::Expr;
}

    Программы записываются как расширения поверх алгебр-трейтов. Эти расширения также входят в спецификацию: они компонуют небольшие спецификации в повторно используемые спецификации на уровне программы.

    #[ext(name = ExprPrograms)]
impl<This> This
where
    This: LitAlg + AddAlg,
{
    fn expr_basic(&self) -> This::Expr {
        self.add(self.lit(2), self.lit(3))
    }
}

    #[ext(...)] — макрос из крейта extendcrate, который уменьшает шаблонный код, генерируя методы-расширения из блока impl; это не новая возможность языка Rust.

    Добавьте новую интерпретацию

    Интерпретаторы реализуют спецификацию. Менять синтаксис не нужно.

    struct Eval;

impl LitAlg for Eval {
    type Expr = i64;

    fn lit(&self, n: i64) -> i64 { n }
}

impl AddAlg for Eval {
    type Expr = i64;

    fn add(&self, a: i64, b: i64) -> i64 { a + b }
}

struct Pretty;

impl LitAlg for Pretty {
    type Expr = String;

    fn lit(&self, n: i64) -> String { n.to_string() }
}

impl AddAlg for Pretty {
    type Expr = String;

    fn add(&self, a: String, b: String) -> String {
        format!("({a} + {b})")
    }
}

    Теперь одно и то же выражение можно интерпретировать по-разному:

    let eval = Eval;
let pretty = Pretty;

let v: i64 = eval.expr_basic();        // 5
let s: String = pretty.expr_basic();   // "(2 + 3)"

    Добавьте новый синтаксис (новый трейт возможности)

    Чтобы добавить Mul, определите новый трейт. Существующий код не затрагивается.

    trait MulAlg {
    type Expr;

    fn mul(&self, a: Self::Expr, b: Self::Expr) -> Self::Expr;
}

#[ext(name = ExprProgramsMul)]
impl<This> This
where
    This: LitAlg + AddAlg + MulAlg,
{
    fn expr_with_mul(&self) -> This::Expr {
        self.mul(self.add(self.lit(2), self.lit(3)), self.lit(4))
    }
}

    Существующие интерпретаторы продолжают работать с прежними выражениями.
    Если им нужен новый синтаксис, они реализуют новый трейт:

    impl MulAlg for Eval {
    type Expr = i64;

    fn mul(&self, a: i64, b: i64) -> i64 { a * b }
}

impl MulAlg for Pretty {
    type Expr = String;

    fn mul(&self, a: String, b: String) -> String {
        format!("({a} * {b})")
    }
}

    Почему это решает проблему выражения

    Традиционная проблема выражения задаёт два направления расширения представления:

    • добавление новых вариантов (случаев)
    • добавление новых операций

    Денотационное проектирование переосмысливает эти направления:

    • Расширить семантический словарь: определить новый трейт возможности (MulAlg).
    • Добавить новую интерпретацию словаря: определить новый тип интерпретатора (Eval, Pretty, построитель AST или генератор кода).

    Эти два направления компонуют независимо:

    • Существующие программы не меняются, если им не требуется новая возможность. expr_basic, как и прежде, требует только LitAlg + AddAlg.
    • Существующие интерпретаторы не меняются, пока не решат интерпретировать новую возможность. Eval без impl MulAlg по-прежнему выполняет все программы, не использующие mul.

    Матрица реализаций никуда не исчезает. Если Eval и Pretty должны интерпретировать mul, обоим нужен impl MulAlg. Меняется организация матрицы: каждая ячейка — это семантическая операция × интерпретация; ни одна не строится вокруг привилегированного представления, и каждая программа зависит только от используемых ею возможностей.

    Законы относятся к спецификации

    Семантическая алгебра состоит из носителя, операций и законов. Носитель (type Expr) выбирает интерпретация; операции и законы принадлежат спецификации. Например, арифметический смысл LitAlg + AddAlg задаёт следующее:

    add(lit(m), lit(n)) = lit(m + n)

    Eval удовлетворяет этому закону. Pretty — нет: "(2 + 3)" не равно "5". Оба интерпретатора реализуют сигнатуру синтаксиса, но моделью арифметической спецификации является только Eval. Закон один раз формулируется для трейтов и определяет, какие интерпретаторы подходят. Ни один интерпретатор не владеет законом.

    Заключительная мысль: Featherweight Go и денотационное проектирование

    Уодлер сформулировал проблему выражения на уровне механизмов языка: строки и столбцы при статической типизации и модульном расширении. Featherweight Go предлагает конкретное решение: Plus(type a Any) оставляет рекурсивное представление обобщённым, а каждая операция независимо ограничивает a (Plus(type a Evaler) для Eval, Plus(type a Stringer) для String). Представление не связано с одним закрытым интерфейсом выражений, поэтому оба направления остаются открытыми.

    Традиционные решения начинают с представления и ищут способ оставить открытыми оба направления расширения. Featherweight Go удивительно далеко продвигается, делая рекурсивное представление обобщённым и структурно расширяемым. Денотационное проектирование перемещает границу ещё на шаг раньше: представление — не модель. Модель — это алгебра и её законы; представление — лишь одна возможная интерпретация.

    Featherweight Go делает представление расширяемым. Денотационное проектирование делает его необязательным.

    Featherweight GoДенотационное проектирование
    Семантический центррасширяемое представлениеалгебра и законы
    Num/Plus, lit/addструктуры (формы представления)семантические операции
    Eval, String/Prettyметоды и интерфейсыинтерпретации
    Рекурсивная структураобобщённое открытое представление (Plus(a))не требуется
    Носительтип представления выражениявыбирается интерпретатором (type Expr)
    ASTпредставление остаётся центральнымнеобязателен, одна из многих интерпретаций
    Ячейка матрицыслучай × операция → методсемантическая операция × интерпретация → impl
    Новое поведениедобавление методов и интерфейсовдобавление или композиция возможностей
    Новая реализацияновые структурные реализацииновый интерпретатор

    Уодлер спрашивает, как расширить оба направления представления. Денотационное проектирование спрашивает, почему представление должно владеть хотя бы одним из них.

    Сначала задайте композиционный смысл, затем выбирайте кодирование. Проблема выражения становится инженерным выбором между кодированиями, а не концептуальным тупиком.

    Смысл языка должен быть независим от представления о машине.
