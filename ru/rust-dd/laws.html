    Обзор

    Тесты служат свидетельствами в поддержку спецификации. Проверяйте публично наблюдаемые свойства и законы выбранной предметной области, а не скрытые шаги выполнения; формулируйте законы обобщённо для возможности, чтобы они действовали для каждого интерпретатора.

    Код, ставящий смысл на первое место, требует таких же тестов. Проверяйте публичные наблюдения и законы, а не скрытые шаги выполнения.

    Тестируйте поверхность спецификации

    Тест, связанный с представлением

    Это утверждение обращается к полям одного носителя, поэтому его нельзя использовать с другими интерпретаторами:

    // not recommended: asserts a bit layout, not a semantic observation
assert_eq!(branch.bits, vec![false, true]);

    Семантический тест:

    let root = alg.branch_root();
let left = alg.branch_left(&root);
let left_right = alg.branch_right(&left);

assert_eq!(alg.branch_path(&root, &left_right), Some(vec![Direction::Left, Direction::Right]));

    Первый тест может подойти модулю сериализации, проверяющему кодирование битов. Но для алгебры ветвления это слабое свидетельство, поскольку альтернативные представления не могут использовать такой тест.

    Повторно используемые расширения с законами

    Если свойство применимо ко всем совместимым интерпретаторам, задайте его один раз:

    use anyhow::{Result, bail, ensure};
use extend::ext;

#[ext(name = BranchLawsExt)]
pub impl<This> This
where
    This: BranchAlg,
    This::Branch: Clone + Eq,
{
    fn check_branch_root_round_trip(&self, directions: &[Direction]) -> Result<()> {
        let root = self.branch_root();
        let branch = directions.iter().copied().fold(root.clone(), |branch, direction| self.branch_grow(&branch, direction));

        let Some(path) = self.branch_path(&root, &branch) else {
            bail!("grown branch has no path from root");
        };
        ensure!(path == directions, "root path did not round-trip");
        Ok(())
    }
}

    Каждый интерпретатор запускает одну и ту же проверку. anyhow::Result содержит результат; bail! сообщает об отсутствующем наблюдении, а ensure! проверяет закон обратного преобразования. Проверка различает два сбоя и не зависит от конкретного представления ветви.

    Полезные семейства законов

    Ищите свойства, уже подсказываемые семантической структурой:

    • тождественность
    • ассоциативность
    • коммутативность, если она действительно предполагается
    • идемпотентность
    • обратное преобразование
    • канонизация
    • уточнение
    • монотонность
    • подстановка
    • согласование интерпретаций

    Утверждайте только те законы, которые допускает предметная область

    Не добавляйте привычные алгебраические термины только потому, что они звучат математически. Формулируйте только те законы, которые допускает выбранная предметная область.

    Законы и инварианты представления

    Различайте следующие понятия:

    • Семантический закон: ветвь, восстановленная по пути от корня, обозначает ту же ветвь.

    • Инвариант представления: неиспользуемые старшие биты равны нулю.

    • Закон сериализации:

      decode(encode(b))=b

    • Закон канонического формата:

      encode(decode(x))=xfor canonical byte sequences x

    Все эти положения могут быть важны, но относятся к разным спецификациям.

    Общие сценарии

    Сценарий — это повторно используемое взаимодействие, описанное через публичные возможности. Тестовая среда ALUX представляет сценарии именно так: код автора создаёт значение с помощью возможностей Scenario, DeployerIds, PlayAst и ScenarioSchedule, не указывая конкретный исполнитель.

    #[ext(name = HelloScenarioExt)]
pub impl<This> This
where
    This: StandaloneScenario,
    This::Step: PlayAst<Ast = RProc>,
{
    fn hello(self) -> This::Scenario {
        self.scenario()
            .under_comprehensive(100)
            .step(
                self.play_ast(
                    self.deployer(0),
                    tolang! {
                        let x in {
                            x ! "hello" |
                            ? (a <- x) a.log()
                        }
                    },
                )
                .expect_log(r#""hello""#),
            )
    }
}

    Каждый вызов описывает смысл, заданный автором, а не механизмы исполнителя. under_comprehensive(100) требует ожидаемый журнал при одном последовательном запуске, 100 полностью параллельных запусках и до 100 запусков с перестановкой порядка. Сценарий фиксирует наблюдение, а исполнитель меняет порядок выполнения.

    Тот же принцип действует для разных интерпретаторов: если несколько исполнителей реализуют возможности, используемые сценарием, каждый может интерпретировать одно и то же заданное взаимодействие. Настройка конкретного исполнителя и проверка его границ остаются за пределами сценария.

    Согласование разных интерпретаторов

    Если два интерпретатора предоставляют одно и то же наблюдение, сравните их:

    interpret_text(p).route_names=interpret_server(p).registered_route_names

    Это выявляет дрейф, который не заметен при сравнении независимых снимков. Особенно полезно для определений API, этапов компилятора и альтернативных представлений данных.

    Конечное свидетельство — не доказательство

    Успешный тест демонстрирует поведение на проверенных входах и реализациях, но не доказывает закон для всех значений.

    Повышайте уверенность осознанно:

    1. тесты на примерах
    2. тесты на повторно используемых сценариях
    3. генерируемые тесты свойств
    4. исчерпывающие проверки конечных областей
    5. сравнение моделей
    6. артефакты доказательств

    Выбирайте уровень в соответствии с риском и силой утверждения.

    Названия тестов должны выражать смысл

    Предпочитайте:

    • reconstructs_every_generated_branch_from_its_root_path
    • preserves_child_programs_when_routes_are_merged
    • normalization_is_invariant_under_alpha_renaming

    Избегайте названий, которые лишь описывают реализацию:

    • pushes_three_bits
    • calls_helper_twice
    • visits_left_node_first

    Операционные тесты уместны, если порядок операций сам задан спецификацией. Называйте наблюдение, которое делает этот порядок значимым.

    Проверочные вопросы

    • Для каждой новой семантической операции есть отдельный закон или утверждение?
    • Сформулированы ли повторно используемые обязательства обобщённо через публичные возможности?
    • Отделены ли сценарии от конкретных исполнителей?
    • Отличаются ли семантические законы от инвариантов представления?
    • Сравниваются ли несколько интерпретаторов, когда это практически возможно?
    • Не называют ли документы конечные тесты доказательствами?
