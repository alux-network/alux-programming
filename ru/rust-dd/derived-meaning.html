    Производный смысл и композиция

    Обзор

    Производное поведение относится к используемым им возможностям и один раз задаётся как расширение поверх соответствующих ограничений, а не привязывается к конкретному типу, который случайно их реализует. Условие where — точное описание зависимостей вывода.

    Примитивные возможности задают словарь. Большая часть поведения приложения должна один раз выводиться из него и использоваться совместно всеми интерпретаторами.

    Расширения отвечают за выводимые операции

    С помощью крейта extend операции над ветвями можно вывести независимо от представления:

    use extend::ext;

#[ext(name = BranchExt)]
pub impl<This> This
where
    This: BranchAlg,
{
    fn branch_child(&self, branch: &This::Branch, direction: Direction) -> This::Branch {
        self.branch_grow(branch, direction)
    }

    fn branch_left(&self, branch: &This::Branch) -> This::Branch {
        self.branch_child(branch, Direction::Left)
    }

    fn branch_right(&self, branch: &This::Branch) -> This::Branch {
        self.branch_child(branch, Direction::Right)
    }

    fn branch_is_ancestor(&self, ancestor: &This::Branch, descendant: &This::Branch) -> bool {
        self.branch_path(ancestor, descendant).is_some()
    }
}

    Условие where — полное объявление семантических зависимостей: BranchAlg и ничего больше. Ни один конкретный тип ветви не владеет этими определениями.

    Макрос лишь устраняет шаблонный код трейта и его реализации. То же проектирование можно выразить обычным трейтом-расширением. Денотационное проектирование заключается в семантической границе и выводе операций, а не в атрибуте.

    Почему бы не поместить это в структуру?

    Не привязывайте производный смысл к структуре

    Это проектирование от представления. При добавлении числового носителя ветвления производный код придётся копировать или реализовывать заново, и первый конкретный тип случайно станет спецификацией.

    impl BitBranchStore {
    // not recommended: derived branch meaning welded to one bit representation
    fn is_ancestor(&self, a: &BitBranch, b: &BitBranch) -> bool {
        // derived branch meaning mixed with bit storage
    }
}

    Расширения меняют направление владения:

    СлойОтветственность
    Семантическая возможностьВладеет производным смыслом
    Конкретный типИнтерпретирует примитивный смысл

    Композиция с ограничениями

    Если один получатель интерпретирует несколько возможностей, используйте прямые ограничения:

    #[ext(name = PublishCurrentExt)]
pub impl<This, Document, Error> This
where
    This: DocumentAlg<Document = Document> + PublishAlg<Document = Document, Error = Error>,
{
    async fn publish_current(&self) -> Result<(), Error> {
        self.publish(self.document_current()).await
    }
}

    Не объединяйте возможности в пакет

    Не создавайте супертрейт только ради сокращения списка ограничений:

    trait AppContext: DocumentAlg + PublishAlg {}

    Пакет скрывает, какие операции используют какие возможности, и создаёт ещё один интерфейс, которому должен соответствовать каждый интерпретатор.

    Пять разных смыслов композиции

    Выберите форму, которая точно описывает отношение.

    СитуацияФорма Rust
    Один получатель интерпретирует несколько возможностейПрямые ограничения
    Отдельное значение выбирает поведениеЯвный параметр политики
    Независимые политики статически объединяютсяПроизведение или обычная структура
    Среда содержит другой интерпретаторНебольшая проекция HasX
    Обёртка подменяет внутренний интерпретаторДелегирование

    Явная политика

    Если стратегия выбирается независимо, явно передайте её расширению:

    #[ext(name = CandidateSelectExt)]
pub impl<This> This
where
    This: CandidateAlg,
{
    fn select_with<Policy>(&self, policy: &Policy) -> This::Candidate
    where
        Policy: SelectionPolicyAlg<Candidate = This::Candidate>,
    {
        policy.select(self.candidates())
    }
}

    Расширение владеет общей производной операцией, а политика остаётся независимо выбираемым входным значением. Она не скрыта в среде и не выбирается с помощью Default.

    Произведение политик

    Независимые политики можно объединять, не вводя наследование:

    struct CompilePolicy<Optimize, Diagnostics> {
    optimize: Optimize,
    diagnostics: Diagnostics,
}

    Проекция

    Трейт HasClock лишь указывает, что среда может извлечь отдельное значение часов:

    trait HasClock {
    type Clock;

    fn clock(&self) -> &Self::Clock;
}

    Операция, считывающая время, добавляет This::Clock: ClockAlg в собственное условие where. Проекция описывает только наличие компонента; потребляющая его операция указывает нужную возможность. Используйте этот подход, только если разделение действительно. Не вводите HasX лишь для упорядочивания полей.

    Делегирование

    Делегирование означает, что обёртка сама может подменить внутренний интерпретатор. Это уместно для прозрачных новых типов, разделяемых указателей и адаптеров, сохраняющих весь контракт возможности.

    Проекция говорит «имеет», делегирование — «является». Это не взаимозаменяемые понятия.

    Значения по умолчанию — тоже семантические решения

    Механические пустые состояния могут реализовывать Default. Политика предметной области обычно должна задаваться явно.

    У полезных случаев часто есть алгебраическое объяснение: значение по умолчанию — нейтральный элемент естественной композиции типа. Добавление пустого буфера, объединение с пустой картой или накопление нуля диагностик ничего не добавляет. Если композиция ассоциативна, тип вместе с операцией образует моноид, а Default обозначает его нейтральный элемент, а не выбирает политику.

    Хорошие значения по умолчанию:

    • Пустой буфер
    • Пустая карта
    • Нулевое число накопленных диагностик

    Подозрительные значения по умолчанию:

    • Порог кворума
    • Политика выбора лидера
    • Семантика повторных попыток
    • Глубина подтверждения
    • Формат вывода

    В этом и состоит различие: нейтральный элемент не вносит решения, а кворум, стратегия выбора лидера или правило повторных попыток задают поведение предметной области. Если изменение значения по умолчанию меняет смысл предметной области, явно включайте политику в композицию.

    Производный смысл должен оставаться замкнутым

    Расширение должно использовать только объявленные возможности и явные входы. Прямой доступ к полям, глобальное состояние и приведение к конкретному типу делают условие where нечестным.

    Проверяйте тело так, будто это доказательство объявления зависимостей:

    Проверяйте каждое выведение

    Можно ли обосновать каждую операцию в этом теле заданными ограничениями?

    Если нет, то либо ограничения неполны, либо код относится к другому слою.

    Проверочные вопросы

    • Задаётся ли производное поведение один раз поверх возможностей?
    • Избегает ли расширение конкретных полей и типов контекста?
    • Используются ли прямые ограничения для одного интерпретатора?
    • Являются ли политики явными значениями, когда выбираются независимо?
    • Правдиво ли проекция и делегирование описывают свои отношения?
    • Видны ли в композиции значения предметной области по умолчанию?
