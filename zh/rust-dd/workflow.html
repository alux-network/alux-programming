    语义优先的工作流程

    相关内容

    语义视角：为何含义优先
    Rust 中的语义驱动设计：能力代数、派生含义与组合、定律、场景与证据

    可重复的方法

    指称设计是一套工作流程，而不只是对已完成代码的解释：陈述语义变化，找出最小基本能力，如实组合它们，再实现轻量级解释器并检查定律。

    指称设计作为一种可重复的开发方法最有用，而不只是对已完成代码作出解释。

    核心流程

    开发新功能或重构时：

    1. 用一句话说明语义变化。
    2. 确定载体与可观察等价关系。
    3. 找出所需的最小基本能力。
    4. 基于明确能力定义派生行为。
    5. 选择能如实表达关系的组合形式。
    6. 只有当结构需要多种解释时，才将程序具体化为一阶数据。
    7. 实现轻量级具体解释器。
    8. 添加定律或共享场景。
    9. 验证不同解释。
    10. 先记录含义，再介绍机制。

    陈述语义变化

    较弱的表述：

    添加缓存和管理器方法。

    面向含义的表述：

    在一次编译期间，解析同一个不可变源名称应指称相同的源值。

    第二种表述提出了一条候选定律。之后可以选择缓存作为一种实现方式。

    找到基本边界

    请思考：

    • 需要哪种新的观察或变换？
    • 它在此边界上是基本操作，还是可以由现有含义派生？
    • 是否需要新的关联载体？
    • 所谓依赖是否只是存储位置？
    • 哪些区别应当不可见？

    只有确实出现新的基本含义时，才添加能力。

    如实选择组合形式

    使用以下决策表：

    问题选择
    一个接收者是否解释了所有必需含义？直接约束
    行为是否独立选择？显式策略值
    策略是否可以独立组合？乘积类型
    环境是否包含另一个解释器？投影
    包装器是否必须替代内部解释器？委托

    不要默认采用大型上下文 trait。

    一次重构一种含义

    当现有代码采用表示优先设计时：

    1. 确定一项语义观察。
    2. 定义一种小型能力。
    3. 将一个派生操作移入扩展。
    4. 保留当前结构体，将其作为解释器。
    5. 添加一项定律式测试。

    指称设计并非抽象至上

    避免将整个子系统重写为缺乏依据的抽象。指称设计并非抽象至上。

    从含义到机制进行审查

    按以下顺序阅读代码：

    1. 能力 trait
    2. 语义值类型
    3. 派生扩展
    4. 一阶程序语法（如有）
    5. 共享定律与场景
    6. 具体解释器
    7. 运行时编排

    从最大的状态结构体开始审查，会使审查偏向其表示。

    常见失败模式

    形似 trait 的具体状态不等于指称设计

    trait ContextAlg {
    fn state(&self) -> &ConcreteState;
}

    trait 改变了语法，却没有改变含义的归属。语义核心仍然依赖具体表示。

    每个解释器都重复派生逻辑

    如果每个实现都独立定义相同的领域算法，就说明规范被重复了。

    万能能力

    包含无关操作的超 trait 会掩盖依赖关系，也会阻止独立解释。

    规范由框架掌控

    如果路由注解或 RPC 注册是唯一的接口定义方式，文档与执行就可能出现偏差。

    含义由宏掌控

    如果生成代码没有公开的一阶目标，宏展开就会意外成为规范。

    策略隐藏在默认值中

    如果Default悄然选择了法定人数、重试、顺序或编译策略，组合就不再是显式的。

    测试私有步骤

    与字段布局或遍历顺序耦合的测试，会妨碍有效的替代解释器。

    Pull Request 检查清单

    含义

    • 是否陈述了语义变化？
    • 载体与等价关系是否明确？
    • 是否指出了有意忽略的内容？

    能力

    • 每个 trait 是否都表达了连贯的基本含义？
    • 约束是否放在操作实际使用它们的位置？
    • 派生代码是否避免访问具体字段？

    组合

    • 是否如实使用直接约束、策略、乘积类型、投影与委托？
    • 语义默认值是否明确？

    程序与解释器

    • 是否只在另一种解释确有需要时才引入一阶结构？
    • 便捷宏能否展开为公开的程序值？
    • 具体解释器是否足够轻量且限定在特定边界内？

    证据

    • 是否提供了定律或针对性的语义断言？
    • 同一场景能否在另一个解释器上运行？
    • 是否将有限测试描述为证据，而非证明？

    阅读 ALUX 风格的代码

    需要识别的整体结构是：

    1. 小型基本能力 trait
    2. 基于明确约束的派生扩展
    3. 仅在检查或组合需要时引入一阶程序
    4. 共享定律与场景
    5. 具体的运行时、编译器、HTTP、RPC 或存储解释器

    大型并发系统仍然包含许多需要编排的区域。不要假定所有现有接口都是理想的指称规范。寻找语义上的衔接点，并从这些位置向外阅读。

    Tolang 在语言层面采用相同视角：语法会规范化为承载含义的形式，编译会保留这些含义，并发运行时则会解释可执行表示。操作层面的描述仍然至关重要，但它应当位于语义契约之后。

    最终原则

    不确定时，回到一个问题：

    应当反复思考的问题

    这些机制本应保留什么含义？

    这个问题不能解决所有工程难题，但能让问题在正确的层次上显现出来。
