    ALUX 编程指南

    注

    本书将介绍理解并参与 ALUX 语义优先代码库所需的基础，从指称设计的一项核心原则讲起：先定义程序的含义，再决定程序如何运行。

    沿袭 Conal Elliott 的思路，本书将计算视为清晰的数学对象，而不是不透明的步骤序列。

    规范以简单、可组合的能力 trait表达，用来描述程序意味着什么。解释器提供可互换的方式来实现这些含义。

    这样一来，软件的组合规则、实现义务和有效等式都更容易理解和测试。

    为何含义优先

    导读

    指称设计先确定程序的含义，再推导出词汇、表示与执行策略，以保留该含义。本页将这种语义顺序与大多数软件采用的表示优先顺序作对比。

    大多数软件按照运行顺序来设计：

    1. 选择状态。
    2. 选择控制流。
    3. 围绕这些机制公开方法。
    4. 事后再解释这些方法原本意在表达什么。

    指称设计将顺序倒转：

    1. 选择含义。
    2. 确定其组合结构。
    3. 从该结构推导词汇。
    4. 选择表示与执行策略。
    5. 验证它们是否保留了原有含义。

    这种倒转就是语义视角。

    机制与含义

    概念与洞见用于说明实用的编程机制。指称设计则说明如何判断这些机制应当保留什么。

    三个问题

    设计程序时，要把三个问题分开考虑。

    视角问题典型产物
    语义这个程序意味着什么？值、关系、函数、等式、定律
    表示这个含义如何编码？Rust 类型、trait、抽象语法树、表、树、字节码
    操作这种表示如何执行？循环、可变状态、任务、消息、解释器、虚拟机

    这三种视角都很重要。错误在于让表示或执行悄然替语义视角下定义。

    操作语义对执行过程作出精确且有价值的说明。它可以描述求值器执行的每一次状态转换，但它回答的设计问题仍与指称描述不同。指称问题关注整个程序所指称的可观察数学值，以及无论采用何种执行策略都应成立的等式。

    一个小例子

    假设某个系统要标识分支过程中的位置。

    表示优先的设计可能从一个位向量开始：

    struct BranchId(Vec<bool>);

    随后，方法围绕这些字段不断增加：追加一位、截取前缀、比较向量、序列化字节。

    语义视角从别处开始：

    • 存在一个根位置。
    • 位置可以向左或向右延伸。
    • 一个位置可以是另一个位置的祖先。
    • 可以观察祖先与后代之间的路径。

    即便表示后来变成整数、树坐标、紧凑的混合值或数据库键，这些陈述仍然有意义。位向量只是对分支位置的一种解释，而不是它的定义。

    含义不是事后补写的文档

    为具体 API 写说明文字，并不会让设计变成指称式设计。含义必须先约束 API，然后才能选择表示。

    语义描述应当说明：

    • 哪些区别很重要
    • 哪些观察是基本的
    • 更大的含义如何组合
    • 哪些等式有效
    • 每种实现都必须保留什么
    • 哪些细节有意忽略

    如果唯一精确的产物只是状态结构体或执行循环，那么含义仍由实现掌控。

    抽象与含义

    上下文 trait 并不定义含义

    一个接口可以隐藏机制，却不解释含义：

    trait ApplicationContext {
    fn database(&self) -> &Database;
    fn settings(&self) -> &Settings;
    fn runtime(&self) -> &Runtime;
}

    这个接口抽象了对具体组件的访问，但没有说明计算所要求的语义观察。

    直接询问含义

    面向含义的接口会直接询问所需的观察：

    trait BranchAlg {
    type Branch;

    fn branch_root(&self) -> Self::Branch;
    fn branch_grow(&self, branch: &Self::Branch, direction: Direction) -> Self::Branch;
    fn branch_path(
        &self,
        ancestor: &Self::Branch,
        descendant: &Self::Branch,
    ) -> Option<Vec<Direction>>;
}

    依赖倒置固然有用，但指称设计要求更多：抽象边界必须围绕含义组织，而不是围绕存储位置。

    权威的方向

    当各类产物彼此矛盾时，不要把权威交给最接近运行代码的那个。应当先问每个产物各自必须保留什么。

    角色此处应包含什么职责
    含义领域预期的观察、区别与相等关系决定正确性的含义
    规范语义域、指称、类型、基本操作、定律与派生组合精确陈述含义
    实现具体表示、解释器、编译器、运行时、存储与调度实现规范而不改变规范
    证据证明、定律检查、场景与跨解释器比较将实现与规范关联起来；它本身不定义含义

    由此得到一条解决分歧的实用规则：

    • 如果实现违反了语义定律，就修改实现。
    • 如果测试与它原本要检查的定律相矛盾，就修改测试。
    • 如果形式规范未能表达预期的领域含义，就修订规范。

    产物应按其作用分类，而不是按其语法分类。Rust trait 或一阶程序若直接保留了选定的语义结构，就可以属于规范；另一个 Rust 类型则可能只是某种具体编码。形式操作语义也可以属于语言规范，但其中的状态转换仍须符合该语言所要求的观察与等价关系。

    CPS、去函数化、自由单子、虚拟机、协议运行时和编译器流水线，如今都可以放在适当的位置，而无须争论哪一种才是最终抽象。它们各自是适用于特定使用者的表示或执行技术。语义规范说明每种选用的技术都必须保留什么。

    指称与组合性

    相关内容

    核心思想

    指称是从语法映射到所选语义域的含义函数。当整体的含义由各部分的含义确定时，语义就是组合式的；这使语义等价与安全替换成为可能。

    指称是赋予一段语法或一个编程构造的含义。通常记作：

    [[e]]

    表示“表达式e的含义”。

    这些括号并不要求指称必须是一个数字。根据所选语义域，程序可以指称：

    • 一个值
    • 一个函数
    • 一个关系
    • 一组可能结果
    • 一个状态变换
    • 一个概率分布
    • 一种过程行为
    • 一个部分结果

    因此，第一个设计决策不是“用哪个结构体来保存它？”，而是“我们关心的含义属于哪个语义域？”

    语义域

    对于算术表达式，一个简单的语义域可以是整数：

    [[e]]eval​∈Z

    对于格式化，同一种表达式语言也可以解释为文本：

    [[e]]pretty​∈String

    对于带效应的计算，语义域可以是状态变换：

    [[p]]:State→Result×State

    对于并发语言，语义域可以描述可观察到的过程行为，而非某一条预先确定的轨迹。

    所选语义域决定哪些差异有意义。如果语义域不包含时间，那么两个时序不同的实现仍可能指称同一个程序。如果把资源消耗纳入语义域，这种差异就可能具有语义意义。

    抽象会有意忽略细节

    有用的指称会忽略无关的机器细节。

    对于分支位置，指称可以保留从根到该位置的路径，同时忽略：

    • 字节布局
    • 分配策略
    • 缓存行为
    • 序列化格式

    对于 HTTP 程序，可移植的指称可以保留方法、路径、输入角色、操作和输出角色，同时忽略承载它的路由器或执行器。

    对于编译器阶段，指称可以保留从规范化源代码到可执行含义的转换，同时忽略临时缓冲区与遍历顺序。

    忽略细节不是缺陷。正是如此，不同表示才可能等价。

    组合性

    当整体的含义由各部分的含义及其组合方式共同决定时，语义就是组合式的。

    对于加法：

    [[a+b]]=[[a]]+[[b]]

    对于顺序函数组合：

    [[g∘f]]=[[g]]∘[[f]]

    对于并行过程运算符，语义域需要相应的并行组合：

    [[P∣Q]]=[[P]]⊗[[Q]]

    具体运算符⊗取决于所选的过程模型。关键在于，语法组合应系统地映射到语义组合。

    组合性支持局部推理。如果两个部分的指称相同，就可以在任意组合上下文中相互替换：

    [[P]]=[[Q]]⟹[[C(P)]]=[[C(Q)]]

    这是安全替换与语义重构的基础。

    语义等价

    程序不必在文本或操作上完全相同，才能在语义上等价。

    考虑分支位置的两种实现：

    [Left,Right,Left]

    以及一种指称相同路径的整数编码。它们的内存值不同，但指称可能相等。

    同样，两个编译器过程可以按不同顺序遍历语法，却生成行为符合相同规范的可执行文件。是否要求逐字节相等，是另一个更强的定律。

    务必明确指出所声称的等价关系：

    • 值相等
    • 结构相等
    • 规范表示相等
    • 轨迹等价
    • 双模拟
    • 观察等价
    • 指称相等

    混淆这些等价关系，是错误定律的常见来源。

    外部性是相对的

    假设某个计算具有如下含义：

    H×E→O

    相对于H而言，证据E是外部的。如果新的抽象选择H × E作为承载对象，那么这些证据对于新的边界来说就变成内部的。

    这一观察对效应与上下文都很重要。没有任何事实绝对属于“环境”。关键在于当前语义承载对象是否包含该事实，以及有哪些定律支配它。

    避免使用通用上下文对象

    不要用一个通用上下文对象来解决这个边界问题。将每种允许的含义明确命名为一种能力或显式值。

    基本含义与派生含义

    基本操作是选作语义域词汇的操作。派生操作则由基本操作定义。

    对于分支位置，一组精简的基本词汇可以包括：

    • 一个根位置
    • 沿某个方向延伸
    • 观察一个位置到另一个位置的路径

    由此可以派生：

    • 向左延伸
    • 向右延伸
    • 根据路径构造位置
    • 测试一个位置是否为另一个位置的祖先
    • 测试一个位置是否为另一个位置的后代

    这种区分是设计选择，而非形而上学事实。应优先采用精简的基本操作集合，让定律与其他解释更容易表述。

    一项实用检验

    在引入编程接口之前，先补全以下句子：

    • 这个抽象中的值意味着……
    • 基本观察包括……
    • 有意义的组合包括……
    • 当……时，两个值等价
    • 每种实现都必须保留……
    • 该抽象有意忽略……

    如果这些句子无法补全，再多的实现机制也无法补上缺失的含义。

    指称设计

    相关内容

    语义视角：指称与组合性、定律与解释

    核心思想

    指称设计从简单、可组合且独立于实现的含义推导出编程接口，让语义来引导设计，而不是事后描述接口。

    指称设计是一种从简单、可组合且独立于实现的含义推导编程接口的方法。

    该方法由Conal Elliott提出并命名。它的核心做法不仅是为现有语言或 API 赋予语义，而是让语义引导 API 本身的设计。

    设计循环

    按以下顺序进行：

    1. 选择语义域。
    2. 确定该语义域中重要的结构。
    3. 选择一组精简的基本操作词汇。
    4. 以组合方式派生有用操作。
    5. 陈述这些操作遵循的定律。
    6. 选择一种或多种表示。
    7. 实现能够保留该结构的解释。
    8. 通过定律、模型与场景进行验证。

    表示优先的设计通常从第 6 步开始，然后试图事后补出第 1 至第 5 步。

    设计分支代数

    回到分支位置。预期含义是二叉分支结构中的有限路径。

    一种可能的基本代数是：

    rootgrowpath​:()→Branch:Branch×Direction→Branch:Branch×Branch⇀List(Direction)​

    偏箭头⇀表示路径观察仅在第一个分支是第二个分支的祖先时才存在。

    由此可得一些有用操作：

    left(b)right(b)is_ancestor(a,b)from_path(ds​)​=grow(b,Left)=grow(b,Right)⟺path(a,b) is defined=fold(grow,root,ds​)​

    这个代数没有提到向量、整数、分数、数据库键或字节。这些选择留待后续。

    先结构，后便利

    基本词汇应揭示下游代码所依赖的结构，而不应变成某种实现上所有便利方法的集合。

    拒绝表示优先的基本操作

    这个 trait 将存储布局、配置位置、位表示和复合工作流捆绑在一起，并未隔离分支含义：

    trait BranchManager {
    // not recommended: exposes machinery, not semantic observations
    fn storage(&self) -> &BranchTable;
    fn config(&self) -> &BranchConfig;
    fn raw_bits(&self) -> &[u64];
    fn grow_and_save(&mut self, right: bool);
}

    当效应属于所选语义域时，语义 API 仍然可以包含效应。规则并不是“所有东西都必须是纯函数”，而是“每个基本操作都必须表达连贯的含义”。

    编码方式不是方法论

    指称设计不要求使用：

    • Haskell
    • tagless-final 编码
    • 对象代数
    • 自由单子
    • 单一抽象语法树
    • 仅使用纯函数
    • 每个 API 都采用范畴论术语

    这些可以是有用的编码方式或解释工具，但没有一种能够定义该方法。

    Rust 编码方式

    在 Rust 中，小型 trait、关联类型、扩展方法、泛型函数和一阶程序值都是实用的编码方式。它们的价值取决于是否保留了清晰的语义设计。

    类型类态射

    理解该方法的一种方式，是把它看作保结构映射。

    假设某个接口描述了一个语义代数。实现会将其抽象值与操作映射到具体表示中。有效实现必须保留相关操作与定律。

    如果encode将抽象分支映射到具体载体，那么保留延伸操作的形式如下：

    encode(grow(b,d))=growconcrete​(encode(b),d)

    实现不只是一个方法名称相同的集合。它应当是一个尊重代数结构的态射。

    什么样的抽象才算好

    一个好的指称设计抽象具备以下特征：

    • 其中的值具有简单明确的预期含义。
    • 基本操作用于揭示语义观察或构造。
    • 更大的行为由这些基本操作派生。
    • 其定律不依赖某一种表示。
    • 可以由彼此独立的实现来解释。
    • 只有在相关时才引入操作细节。

    仅仅精简还不够。即使一个小型 trait 暴露了get_manager()，它仍可能是表示优先的。若某个更大的代数包含的操作构成连贯的语义结构，也可能是合理的。

    语义值与抽象载体

    并非所有具体类型都不能写入规范。

    当解释器应当选择载体时，使用关联类型：

    trait BranchAlg {
    type Branch;
}

    当某个类型属于稳定的语义词汇时，使用具体类型：

    enum Direction {
    Left,
    Right,
}

    区别并非“抽象好，具体坏”，而是语义词汇与偶然的机器表示之别。

    规范就是指称，而且不必可执行

    规范就是指称：赋予每种构造的数学含义。它的力量在于不受效率约束，甚至不必能够执行。

    Conal Elliott

    定义指称通常比实现容易得多，也更能带来启发，因为指称不受效率或可执行性的约束，也不会受到它们的干扰。

    ——《指称设计：从含义到程序》（LambdaJam 2015）

    经典示例是 FRP（函数式响应式编程）：Behavior a被定义为连续时间上的函数，

    [[⋅]]:Behavior a→(R→a)

    这个模型很精确，却无法执行——实数无法逐个枚举。程序也可以指称一组结果；这两种模型都无法运行，但这正是其用意所在。选择含义是为了简洁和精确，而不是为了计算方式。

    可执行性与效率完全交由实现负责；实现是独立产物，借助将其与含义关联起来的同态定律（类型类态射）来保证正确性：含义函数必须把每种语法组合映射为相应的语义组合。正如 Conal 所说，指称给出了对待实现之事明确无歧义的定义，同时为如何实现留下了很大的创作空间。

    在 Rust 中，有几种产物可以表达这份规范的部分内容，其中一些恰好可以执行。可执行性只是偶然属性，不是它们成为规范的原因：

    • 说明文字陈述预期含义
    • trait 陈述可用的基本操作
    • 扩展陈述派生方式
    • 定律陈述必需的等式
    • 解释器展示可实现性
    • 测试提供有限证据

    应结合起来阅读，并让含义与定律在权威性上优先于具体机制。

    定律与解释

    相关内容

    语义视角：指称设计

    核心思想

    定律说明语义接口中的操作如何相互关联；解释则指定必须保留这些定律的具体载体。所选等价关系决定解释器之间哪些差异有意义，哪些差异可以自由变化。

    语义接口为操作命名，定律说明这些操作之间的关系。没有定律时，两个实现可以满足相同的 Rust 函数签名，却对抽象的含义各执一词。

    定律补全词汇

    对于分支位置，有用的定律包括：

    path(b,b)path(root,from_path(ds​))from_path(path(root,b))is_ancestor(b,b)left(b)​=[]=ds​=b=true=right(b)​

    这些定律所说明的内容，远超方法注释。它们描述了单位元、重构、自反性与分离性。

    并非每个看起来合理的等式都有效。例如，定宽表示可能在深度极大时溢出。这可能是：

    • 解释器在其适用域之外的限制
    • 接口必须暴露的语义错误
    • 所选载体有误的证据

    设计必须说明属于哪一种。

    解释

    解释为语义代数指定具体载体与操作。

    语义程序可能的解释
    分支位置位路径、数值树、符号形式
    表达式程序求值器、漂亮打印器、优化器
    类型化 API 程序可执行的服务器路由、文档、客户端生成器

    同一个程序可以有多种解释，因为程序并不等同于某一种结果。

    实现义务

    解释器必须保留规范所声称的结构。

    如果语义程序中的合并满足结合律：

    (a⊕b)⊕c=a⊕(b⊕c)

    那么解释器就应当保留这种结合方式的可观察含义。如果路由顺序也有规范要求，等价关系就必须包含顺序。如果有意忽略顺序，实现可以在操作层面不同，但仍保持语义等价。

    因此，必须先选定语义域与等价关系，再编写定律。

    定律、证明与测试

    这些术语不能互换：

    • 定律是抽象所普遍要求的性质。
    • 证明在给定假设下确立某条定律。
    • 性质测试检查大量生成的示例。
    • 场景测试检查一个有意义的有限情境。
    • 单元测试检查一种具体行为。

    测试是可执行的证据，而非普遍证明。它们仍然很有价值，因为可以用来检查每个解释器。

    可执行证据

    语义定律独立于其实现。可执行检查为解释器是否保留这些定律提供有限证据：性质检查用于考察类似等式的主张，场景则用于考察可观察的交互。如果只使用语义操作来编写，同一组证据就能在兼容的解释器之间复用。测试为规范提供支持，但不定义也不证明规范。

    Rust 编码方式见《定律、场景与证据》。

    多个解释器有助于澄清含义

    并非每个小型 trait 都需要第二种实现，但第二种实现是一项有力的设计检验。

    如果一条自称抽象的定律只能用第一种实现的字段来表述，那么语义边界很可能划错了。如果第二个解释器无需模仿第一个表示，就能实现基本操作并满足同一组定律，那么这个抽象就更站得住脚。

    中性解释器尤其有用：

    • 文本解释器会揭示程序结构
    • 纯内存模型会隔离定律
    • 追踪解释器会揭示选定的观察
    • 生产解释器会执行真实效应

    等价关系决定重构自由度

    每一种语义等价都赋予实现一定自由。如果根据选定的指称，两个表示相等，实现就可以互换它们。

    每一种被忽略的观察也会带来自由。如果分配顺序不属于语义，它就可以改变。如果方法顺序属于语义，就不能改变。

    因此，定律不只是正确性约束。它们还界定了优化、替换与演进的安全空间。

    3. 哪些操作是基本操作？
    4. 哪些操作是派生操作？
    5. 采用哪种等价关系？
    6. 每个解释器都必须保留哪些定律？

    依赖类型与证明

    相关内容

    语义视角：指称设计、定律与解释

    语义定位

    依赖类型可在类型系统中表达由值索引的命题与证据。它们可以编码语义规范的一部分，却不能替我们选择规范：在把预期性质提升为类型之前，必须先弄清楚该性质。

    由值索引的类型

    当类型可以依赖某个值时，它就是依赖的。因此，依赖类型不仅能描述值的形态，还能描述该值必须满足的关系。

    例如：

    • Vec<n, T> —— 由长度索引的向量 n
    • Matrix<rows, cols, T> —— 由维度索引的矩阵
    • Proof<p> —— 某个命题的证据 p

    例如：

    append : Vec<n, T> -> Vec<m, T> -> Vec<n + m, T>

    结果类型表明，将长度分别为n和m的向量拼接后，会得到长度为n + m的向量。

    依赖函数

    依赖函数类型写作：

    Π(x:A).B(x)

    对于每个值x（类型为A），结果的类型为B(x)。比较：

    fg​:A→B:(x:A)→B(x)​

    f的结果类型是固定的。g的结果类型则可能随输入变化。

    根据“命题即类型”的对应关系，类型可以陈述一个命题，而拥有该类型的项可以充当证明。这有助于构建 API，使无效状态、转换或组合无法被构造出来。

    与指称设计的关系

    指称设计首先会问：

    1. 语义域是什么？
    2. 哪些观察与组合很重要？
    3. 必须满足哪些定律？

    随后，依赖类型可以将其中一些答案内化。类型索引可以记录向量长度、协议状态、栈深度、资源上限，或两个构造指称同一结果的证明。

    顺序很重要。复杂的类型无法补上缺失的含义。只有当索引命题已经描述了预期的语义区别或刻意选择的表示不变量时，它才会强化规范。

    不要混淆语义命题与表示不变量

    二者都可以编码到类型中，但权威范围不同。每个兼容解释器都必须保留语义命题；表示不变量则只约束选择它的那种表示。

    证明与可执行证据

    证明会在给定假设下确立一个命题。性质测试、场景测试与单元测试则提供有限的可执行证据。将命题编码为依赖类型，可能让类型检查器验证证明项，但这并不会把测试变成证明，也不会让编译器成为命题的来源。

    本书始终采用同样的区分：含义与定律陈述义务，工具负责检查或实现它们。

    在 Rust 中运用该模型

    Rust 并非完全依赖类型语言，但 const 泛型、类型状态、关联类型与 trait 约束可以表达有用的索引关系。这些编码方式能够把检查移到编译期，而且通常保留高效的具体表示。

    即便 Rust 无法表达完整命题，证明导向的思维方式仍然有价值。明确陈述不变量，编码类型系统能够强制的部分，并为其余部分保留定律或测试。编码服务于规范，而非取代规范。

    这正是本节所述的提升：原本属于值世界的坐标被提升到类型中，有效导航于是成为总函数，并在编译期接受检查。这些标记类型的大小为零，因此索引命题不产生运行时开销。

    能力代数

    相关内容

    导读

    能力 trait 是一种小型代数：它为某种含义所需的基本观察与变换命名，并将表示留给解释器决定。应根据含义设计词汇，而非根据首个实现恰好包含哪些字段。

    Rust 没有名为“指称设计”的内置构造。我们用普通语言特性来编码语义词汇。小型能力 trait 是一种实用的编码方式。

    本书中的后缀Alg表示代数：一组作用于由解释器选择的载体之上的连贯基本操作。

    从含义出发

    前一部分中的分支位置含义可以表示为：

    #[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum Direction {
    Left,
    Right,
}

pub trait BranchAlg {
    type Branch;

    fn branch_root(&self) -> Self::Branch;
    fn branch_grow(&self, branch: &Self::Branch, direction: Direction) -> Self::Branch;
    fn branch_path(&self, ancestor: &Self::Branch, descendant: &Self::Branch) -> Option<Vec<Direction>>;
}

    该 trait 陈述了三种基本含义：

    • 构造根位置
    • 沿一个方向延伸分支
    • 在路径存在时观察相对路径

    它不会暴露分支存储在哪里，也不会暴露路径如何编码。

    能力不等于字段投影

    字段投影不是语义能力

    比较：

    trait BranchContext {
    fn branches(&self) -> &Vec<Vec<bool>>;
    fn branches_mut(&mut self) -> &mut Vec<Vec<bool>>;
}

    这个 trait 用方法隐藏了结构体，却仍然暴露其表示。任何派生逻辑都会与向量、布尔值、所有权和修改策略耦合。

    语义能力暴露的是下游含义所需的观察或变换。请思考：

    审视每种能力

    如果实现改用数据库、符号项、紧凑整数或远程服务，这个操作是否仍然说得通？

    如果答案是肯定的，该操作就可能属于此能力。如果调用者必须依赖当前字段布局，那它很可能不该属于此处。

    每个 trait 表达一种基本含义

    小型 trait 能让依赖一目了然：

    pub trait ClockAlg {
    type Instant;

    fn clock_now(&self) -> Self::Instant;
}

pub trait DeadlineAlg<Instant> {
    fn deadline_expired(&self, now: &Instant) -> bool;
}

    需要时间与截止时间的派生操作可以同时要求这两种 trait。它不需要一个ApplicationContext囊括日志、存储、网络、配置和调度的上下文。

    “小”不等于机械地只包含一个方法。当操作构成不可分割的语义结构时，应将它们放在一起；当它们表达彼此独立的含义或允许独立解释器时，应将它们拆开。

    关联类型选择载体

    当表示由解释器选择时，使用关联类型：

    pub trait SourceAlg {
    type Source;
    type Error;

    fn source_read(&self, name: &str) -> Result<Self::Source, Self::Error>;
}

    除非String、std::io::Error或具体语法树在此边界上属于稳定的语义词汇，否则不要要求它们。

    反过来，具体语义值也完全可以使用：

    pub enum Severity {
    Warning,
    Error,
}

    规则不是“让所有类型都抽象”，而是“不要混淆解释器机制与语义词汇”。

    在使用处添加约束

    让基本操作不受它用不到的约束：

    pub trait CandidateAlg {
    type Candidate;

    fn candidates(&self) -> impl Iterator<Item = Self::Candidate>;
}

    不要预先添加约束

    不要仅仅因为某个未来算法可能需要某项能力，就限制关联类型：

    pub trait CandidateAlg {
    // not recommended: every interpreter now pays for bounds
    // most operations never use
    type Candidate: Clone + Ord + Hash + Send + Sync;

    fn candidates(&self) -> impl Iterator<Item = Self::Candidate>;
}

    对候选项排序的操作可以要求Ord；将它们放入哈希集合的操作则可以要求Hash。

    在使用处添加约束，能让基本含义便于复用，也能揭示派生行为真正的契约。

    效应可以是基本含义

    能力 trait 并不意味着纯执行：

    pub trait PublishAlg {
    type Document;
    type Error;

    async fn publish(&self, document: Self::Document) -> Result<(), Self::Error>;
}

    发布是一种效应。它仍然可以是当前边界上的基本语义操作。具体解释器可以使用 HTTP、队列、文件或测试缓冲区。

    除非重试、套接字所有权、任务生成或连接池属于预期含义，否则语义层不应规定这些内容。

    为边界命名

    应从使用者的语义视角描述能力：

    面向含义面向表示
    closed_outcome(slot)get_runtime_map(slot)
    source_read(name)compiler_context().sources().lookup(name)
    branch_path(ancestor, descendant)raw_branch_bits(id)

    命名本身就是设计。机械式名称容易引入机械式耦合。

    审查要点

    • 这个 trait 是否表达一种连贯的基本含义？
    • 独立解释器能否在不复制首个表示的情况下实现它？
    • 是否只在解释器确实能选择时才使用抽象关联类型？
    • 具体类型是否属于稳定的语义词汇？
    • 是否等到某个操作确实用到约束时才添加？
    • 这个 trait 是否避免返回管理器、上下文对象和原始存储？

    Rust 中的语义类型

    相关内容

    语义视角：依赖类型与证明、指称设计

    概念：引用透明性

    导读

    依义设计优先的 Rust 使用类型来显露语义结构。关联类型为载体族命名，约束陈述它们之间的关系，扩展则从明确前提推导出新操作。定律仍然决定每种解释都必须保留什么。

    在 Rust 中，type一词可以指代多种不同角色。将它们区分开，能避免含义坍缩为表示。

    角色示例表达的内容
    语义类型Direction哪些领域区别很重要
    由解释器选择的载体BranchAlg::Branch解释器选择哪种表示
    派生操作BranchExt::branch_child根据已声明能力可以推出什么
    阶段类型Syntax, CoreProgram, Executable某个值经过了哪种变换
    表示类型BitBranch某个解释器如何存储分支含义
    证据程序场景或可复用的定律扩展兼容解释器必须满足哪些观察

    表示之前先确定语义类型

    假设某个分支领域区分两个方向：

    #[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum Direction {
    Left,
    Right,
}

    Direction直接表达了这一区别。一种解释器可以紧凑地编码路径：

    struct BitBranch(Vec<bool>);

    布尔值属于这种表示。它们并非左右方向的定义，其他解释器也不必使用它们。

    紧凑编码不等于语义类型

    不要根据位位置、字节偏移或机器分支来定义领域行为。这些产物应编码语义区别，而不是拥有这些区别的定义权。

    这种区分让存储与执行布局可以改变，而不悄然改变领域本身。

    关联类型选择载体

    能力代数可以把载体留给各个解释器选择：

    trait BranchAlg {
    type Branch;

    fn branch_root(&self) -> Self::Branch;
    fn branch_grow(&self, branch: &Self::Branch, direction: Direction) -> Self::Branch;
    fn branch_path(
        &self,
        ancestor: &Self::Branch,
        descendant: &Self::Branch,
    ) -> Option<Vec<Direction>>;
}

    Self::Branch不是隐藏的字段类型，而是对分支含义作出解释时所选的载体。位路径、数值树位置、符号项或其他表示都可以满足同一个代数。

    对于解释器T而言，记法T::Branch可以理解为一个载体族Branch(T)。切换解释器可能改变载体，但每种操作仍会根据同一选择保持一致索引。

    扩展用于推导结论

    扩展可以根据它恰好需要的前提构造新操作：

    #[ext(name = BranchExt)]
pub impl<This> This
where
    This: BranchAlg,
{
    fn branch_child(
        &self,
        branch: &This::Branch,
        direction: Direction,
    ) -> This::Branch {
        self.branch_grow(branch, direction)
    }
}

    where子句是前提：This对分支代数作出解释。方法则是结论：对于该解释器的载体，分支与方向决定一个子分支。

    (T:BranchAlg)⟹branchChildT​:Branch(T)×Direction→Branch(T)

    推导过程没有选择具体的分支表示。结果仍然属于解释器所选的载体族。

    相等约束用于陈述兼容性

    两种能力有时需要对载体达成一致。关联类型相等约束可以陈述这一要求，而无须选择具体表示：

    Right: BranchAlg<Branch = Left::Branch>

    可以把这个约束读作一个局部命题：Left和Right在同一载体上解释分支操作。应将这一相等要求放在需要达成一致的操作上，而不是全局强加给任一代数。

    与仅仅因为某个具体上下文碰巧同时包含两种实现就接受它相比，这种约束更强，也更精确。

    阶段类型让编译器契约一目了然

    编译器流水线不应让一个无法区分阶段的语法树贯穿所有环节。不同阶段类型可以说明已经发生了哪种变换：

    阶段输入输出契约
    解析源文本Syntax识别表层语法
    规范化SyntaxCoreProgram生成所选的核心含义
    代码生成CoreProgramExecutable以可执行形式保留程序观察
    运行时Executable可观察行为依据语言模型一致地解释可执行程序

    这些类型可防止意外混淆阶段，但仅凭名称无法证明保留性。仍需陈述变换定律、设计代表性场景，并提供跨解释器证据。

    阅读契约

    类型层面的结构可以作如下逻辑解读：

    Rust 形式解读
    This: BranchAlgThis提供了对分支含义的解释
    This::Branch分支载体由This选择
    Right: BranchAlg<Branch = Left::Branch>两种解释在载体上保持一致
    -> This::Branch结果仍属于所选载体族

    这种解读鼓励 API 显露决定类型的因素、组合所需的等式，以及这些前提能推出的结论。只要底层区别确实存在，关联类型、泛型关联类型、const 泛型、类型状态与零大小见证都可以表达此类契约的一部分。

    不要仅仅为了让实现看起来更形式化，就凭空制造类型层面的机制。类型应当显露含义或保留必要关系，而不是装饰一种表示。

    类型不能替代定律

    类型签名约束哪些程序能够构造，定律则约束这些程序的操作之间如何关联。二者缺一不可。

    例如，BranchAlg::Branch说明每个解释器都会选择一种分支载体，但它本身并不能确立以下性质：

    • 从某个分支到其自身的路径为空
    • 重放根路径可以重构出该分支
    • 相反方向的子节点彼此不同

    这些是兼容解释器共同遵循的语义定律。特定于表示的主张（例如未使用的位必须为零）则属于选择该表示的解释器。

    将类型视为主张

    询问每种类型主张什么、由什么决定、需要哪些定律补全，以及由哪个解释器实现。

    审查要点

    • 领域区别是否先于紧凑的机器编码出现？
    • 关联类型是否是由解释器选择的载体，而非伪装的具体状态？
    • 相等约束是否只陈述该使用位置所需的兼容性？
    • 不同编译器阶段是否采用不同类型并具有明确契约？
    • 语义命题是否与表示不变量分开？
    • Rust 无法表达的主张是否有可复用定律或场景作为依据？

    派生含义与组合

    相关内容

    概念：表达式问题

    导读

    派生行为应归属于它所使用的能力，并在扩展中基于这些约束定义一次，供所有解释器共享；它不应属于某个碰巧实现这些能力的具体类型。where子句诚实地说明了该推导依赖什么。

    基本能力提供词汇。大多数应用行为都应从这些词汇派生一次，并由所有解释器共享。

    扩展拥有派生定义

    使用extend crate，可以独立于表示派生分支操作：

    use extend::ext;

#[ext(name = BranchExt)]
pub impl<This> This
where
    This: BranchAlg,
{
    fn branch_child(&self, branch: &This::Branch, direction: Direction) -> This::Branch {
        self.branch_grow(branch, direction)
    }

    fn branch_left(&self, branch: &This::Branch) -> This::Branch {
        self.branch_child(branch, Direction::Left)
    }

    fn branch_right(&self, branch: &This::Branch) -> This::Branch {
        self.branch_child(branch, Direction::Right)
    }

    fn branch_is_ancestor(&self, ancestor: &This::Branch, descendant: &This::Branch) -> bool {
        self.branch_path(ancestor, descendant).is_some()
    }
}

    where子句完整声明了语义依赖：BranchAlg，除此之外别无其他。没有任何具体分支类型拥有这些定义。

    宏只是省去了 trait 与 impl 的样板代码。普通扩展 trait 也能表达相同设计。指称设计体现在语义边界与派生定义中，而不在属性宏里。

    为什么不把它放进结构体？

    不要把派生含义焊死在结构体上

    这属于表示优先设计。如果引入数值分支载体，就必须复制或重新实现派生逻辑，首个具体类型也会意外变成规范本身。

    impl BitBranchStore {
    // not recommended: derived branch meaning welded to one bit representation
    fn is_ancestor(&self, a: &BitBranch, b: &BitBranch) -> bool {
        // derived branch meaning mixed with bit storage
    }
}

    扩展反转了归属关系：

    层职责
    语义能力拥有派生含义
    具体类型解释基本含义

    基于约束组合

    当一个接收者解释多种能力时，使用直接约束：

    #[ext(name = PublishCurrentExt)]
pub impl<This, Document, Error> This
where
    This: DocumentAlg<Document = Document> + PublishAlg<Document = Document, Error = Error>,
{
    async fn publish_current(&self) -> Result<(), Error> {
        self.publish(self.document_current()).await
    }
}

    不要捆绑能力

    不要仅仅为了缩短约束就创建超 trait：

    trait AppContext: DocumentAlg + PublishAlg {}

    能力捆绑会掩盖哪个操作使用了哪些能力，还会额外创建一种所有解释器都必须满足的接口。

    五种不同的组合含义

    选择能够如实描述这种关系的形式。

    情形Rust 结构
    一个接收者解释多种能力直接约束
    由单独的值选择行为显式策略参数
    独立策略静态组合乘积类型或普通结构体
    环境承载另一个解释器小型HasX投影
    包装器替代内部解释器委托

    显式策略

    如果某种策略独立选择，就将它显式传入扩展：

    #[ext(name = CandidateSelectExt)]
pub impl<This> This
where
    This: CandidateAlg,
{
    fn select_with<Policy>(&self, policy: &Policy) -> This::Candidate
    where
        Policy: SelectionPolicyAlg<Candidate = This::Candidate>,
    {
        policy.select(self.candidates())
    }
}

    扩展拥有共享的派生定义，而策略仍是独立选择的输入。它不会隐藏在环境中，也不会由Default选择。

    策略乘积

    无需发明继承机制，也能组合独立策略：

    struct CompilePolicy<Optimize, Diagnostics> {
    optimize: Optimize,
    diagnostics: Diagnostics,
}

    投影

    一个HasClock trait 仅表明环境可以投影出一个独立的时钟值：

    trait HasClock {
    type Clock;

    fn clock(&self) -> &Self::Clock;
}

    读取时间的操作会在自己的This::Clock: ClockAlg能力where子句中添加该能力。投影只说明包含关系；使用时间的操作则说明自己需要哪种能力。只有在这种分离确实存在时才采用该模式。不要仅仅为了整理字段就引入HasX。

    委托

    委托意味着包装器本身可以替代内部解释器。这适用于透明新类型、共享指针，以及完整保留能力契约的适配器。

    投影表示“拥有”。委托表示“就是”。二者不能互换。

    默认值也是语义决策

    机械的空状态可以实现Default。领域策略通常应当显式给出。

    有用的情形往往可以用代数解释：默认值是该类型自然组合运算的单位元。追加空缓冲区、与空映射合并，或累积零条诊断信息，都不会带来额外贡献。若这种组合满足结合律，该类型与操作便构成幺半群；此时Default可以命名其中的中性元，而非替使用者选择策略。

    合适的默认值：

    • 空缓冲区
    • 空映射
    • 累积的诊断数量为零

    值得怀疑的默认值：

    • 法定人数阈值
    • 领导者策略
    • 重试语义
    • 确认深度
    • 输出格式

    关键区别在于：中性元不会引入决策，而法定人数、领导者策略或重试规则会选择领域行为。如果更改默认值会改变领域含义，就应显式组合该策略。

    派生含义应保持封闭

    扩展只能使用已声明的能力与显式输入。直接访问字段、全局状态和具体类型向下转型都会使where子句变得不诚实。

    审查函数体时，应把它看作对依赖声明的证明：

    逐项检查推导

    函数体中的每个操作，是否都能由这些约束证明合理？

    如果不能，要么约束不完整，要么代码属于其他层。

    审查要点

    • 派生行为是否只在能力之上定义一次？
    • 扩展是否避免依赖具体字段与上下文类型？
    • 单个解释器是否使用直接约束？
    • 独立选择的策略是否以显式值传入？
    • 投影与委托所表达的关系是否准确？
    • 领域默认值是否在组合中清晰可见？

    解释器与效应

    相关内容

    洞见：EVM 代数

    导读

    解释器为某种能力选择表示或效应。它实现基本操作，但不会重新定义其上层派生出的领域行为，因此所有解释器都遵循相同定律。

    解释器使用具体表示或效应来实现语义能力。它应选择实现机制，而不重新定义领域行为。

    轻量级解释器

    分支的一种位路径表示可以是：

    #[derive(Clone, Debug, PartialEq, Eq)]
struct BitBranch(Vec<Direction>);

struct BitBranchImpl;

impl BranchAlg for BitBranchImpl {
    type Branch = BitBranch;

    fn branch_root(&self) -> Self::Branch {
        BitBranch(Vec::new())
    }

    fn branch_grow(&self, branch: &Self::Branch, direction: Direction) -> Self::Branch {
        let mut grown = branch.0.clone();
        grown.push(direction);
        BitBranch(grown)
    }

    fn branch_path(&self, ancestor: &Self::Branch, descendant: &Self::Branch) -> Option<Vec<Direction>> {
        descendant.0.strip_prefix(&ancestor.0[..]).map(<[Direction]>::to_vec)
    }
}

    实现负责存储和观察基本事实。branch_left、branch_right和branch_is_ancestor仍留在共享扩展中。

    解释器取决于边界

    同一种类型在一个边界上可以是解释器，在另一个边界上则可以是语义输入。

    边界使用解释
    文件系统适配器文件系统访问源代码查找
    规范化器环境将源代码查找作为基本能力规范化语言构造
    编译器流水线规范化项可执行程序构造

    不存在唯一通用的“实现层”，而是存在嵌套的语义边界。

    边界处的效应

    具体解释器负责选择以下内容：

    • 数据库布局
    • 异步运行时
    • 任务所有权
    • 重试策略
    • HTTP 或 RPC 框架类型
    • 序列化
    • 锁与通道
    • 缓存

    除非调用者需要观察这些选择，否则应让它们留在语义 trait 之外。

    例如，语义源代码能力可以返回源代码值与错误。生产解释器可以缓存文件并异步读取；测试解释器则可以使用不可变映射。派生的规范化逻辑应能同时适用于二者。

    运行时所有权

    框架回调通常要求状态具备所有权、可克隆且线程安全。这是解释器的约束，不一定是领域约束。

    不要让框架载体污染基本操作

    避免在基本操作中混入框架载体：

    async fn status(data: FrameworkData<Arc<AppState>>) -> FrameworkJson<Status>;

    优先采用语义应用方式：

    trait StatusAlg {
    type Status;

    async fn status(&self) -> Self::Status;
}

    Web 解释器可以选择Arc<Context>、提取请求输入、调用status并转换结果。领域调用方无需知道 Web 服务器存在。

    中性解释器

    并非所有解释器都需要执行效应。

    API 程序的文本解释器可以记录：

    方法路径输入输出
    GET/status—JSON Status
    POST/temperatureJSON f32JSON Status

    元数据解释器可以生成文档。测试解释器可以收集操作名称。生产解释器可以构造服务器路由。

    中性解释器能够证明，程序的含义独立于任何特定运行时。

    通过委托组合解释器

    由于含义存在于小型能力 trait 中，解释器通常是组装而成，而非从头写出。载体通过委托给已有的能力来获得新能力，因此转发代码由工具生成，无需手写。两种形式几乎就能覆盖所有情况。

    将能力转发给字段。ambassador 的#[derive(Delegate)]会把整个 trait 转发给内部值。持有多个组件的载体可以将各项能力委托给拥有它的字段，无需编写转发函数体：

    #[derive(Delegate)]
#[delegate(Clock, target = "clock")]
#[delegate(Logger, target = "logger")]
struct Service {
    clock: SystemClock,
    logger: StdoutLogger,
}

    通过 getter 授予能力。为类型提供一个 getter，再由整体实现为所有具有该 getter 的类型提供完整能力：

    trait Logger {
    fn log(&self, message: &str);
}

trait HasLogger {
    type Logger;

    fn logger(&self) -> &Self::Logger;
}

// Any carrier that can hand back a logger is itself a `Logger`.
impl<T> Logger for T
where
    T: HasLogger,
    T::Logger: Logger,
{
    fn log(&self, message: &str) {
        self.logger().log(message)
    }
}

    这样一来，许多结构体根本无需存在。庞大的上下文对象——一个携带多个关联类型与十几个方法的大型 trait，再加上唯一的具体实现——可以化为几个小型能力 trait，以及一个轻量载体；载体将每种能力委托给提供该能力的字段或 getter。检查截止时间是否已过之类的派生操作，只需作为基本操作之上的扩展编写一次，无需在每个载体上重新实现。

    委托转发的是操作，而非含义

    生成委托代码可以省去样板工作，却不能确立语义上的可替代性。derive诸如 ambassador 的#[derive(Delegate)]宏只能证明实现能够编译，不能证明该载体指称相同的解释器。如果Shared<T>(Arc<T>)要替代T，就应在载体上检查定律——会改变共享性或身份的包装器（Arc、池化、缓存）可能正确转发每个方法，却仍违反新鲜度或唯一性定律。如果载体只是在其他服务之间存放了T，使用投影会比委托更诚实。

    错误属于特定边界

    错误应当在负责处理它的边界上传达失败的含义。

    错误边界转换
    领域错误传输解释器将其映射为协议响应
    解析错误编译器前端将其映射为诊断信息
    存储错误源代码解释器将其映射为语义层面的源代码失败

    不要把 HTTP 状态码、RPC 错误对象或数据库错误强加给基本领域 trait。应在解释器边界处转换它们。

    在性能可观察之前，它属于解释范畴

    批处理、并行、缓存与数据布局通常属于解释器。只有当规范承诺了可观察的顺序、时间、资源使用、公平性或失败行为时，它们才成为语义的一部分。

    这种区分能够在避免语义漂移的同时进行优化：

    • 遵循相同定律
    • 声明相同观察
    • 采用不同操作策略

    审查要点

    • 解释器是否实现基本操作，而非重复派生逻辑？
    • 运行时与框架约束是否限定在使用这些约束的边界内？
    • 中性解释器或测试解释器能否实现同一能力？
    • 传输与存储错误是否在边界处转换？
    • 委托表达的语义关系是否准确？
    • 根据所述指称，性能差异是否不可观察？

    导读

    测试为规范提供证据。应针对公开可观察的结果以及所选语义域支持的定律编写断言，而不是针对私有执行步骤；并将这些定律写成针对该能力的泛型形式，使每个解释器都接受同样的检验。

    语义优先的代码需要语义优先的测试。测试公开可观察的结果与定律，而非私有执行步骤。

    测试规范接口

    与表示耦合的测试

    这个断言深入访问某个载体的字段，因此其他解释器无法复用：

    // not recommended: asserts a bit layout, not a semantic observation
assert_eq!(branch.bits, vec![false, true]);

    语义测试：

    let root = alg.branch_root();
let left = alg.branch_left(&root);
let left_right = alg.branch_right(&left);

assert_eq!(alg.branch_path(&root, &left_right), Some(vec![Direction::Left, Direction::Right]));

    如果测试对象是位编码的序列化模块，第一个测试可能合适。但对于分支代数，它提供的证据较弱，因为替代表示无法复用它。

    可复用的定律扩展

    如果某项性质适用于所有兼容解释器，就把它写一次：

    use anyhow::{Result, bail, ensure};
use extend::ext;

#[ext(name = BranchLawsExt)]
pub impl<This> This
where
    This: BranchAlg,
    This::Branch: Clone + Eq,
{
    fn check_branch_root_round_trip(&self, directions: &[Direction]) -> Result<()> {
        let root = self.branch_root();
        let branch = directions.iter().copied().fold(root.clone(), |branch, direction| self.branch_grow(&branch, direction));

        let Some(path) = self.branch_path(&root, &branch) else {
            bail!("grown branch has no path from root");
        };
        ensure!(path == directions, "root path did not round-trip");
        Ok(())
    }
}

    每个解释器都运行同一个检查器。anyhow::Result承载结果；bail!报告缺失的观察，而ensure!检查往返定律。该检查器无需依赖某一种分支表示，就能区分这两种失败。

    有用的定律类别

    寻找语义结构已经暗示的性质：

    • 单位元
    • 结合性
    • 确实有意要求时的交换性
    • 幂等性
    • 往返
    • 规范化
    • 细化
    • 单调性
    • 替换
    • 解释一致性

    只主张该领域支持的定律

    不要仅仅因为熟悉或听起来很数学，就添加代数术语。只陈述所选领域支持的定律。

    定律与表示不变量

    请将以下内容区分开：

    • 语义定律：根据根路径重构一个分支时，所指称的仍是同一个分支。

    • 表示不变量：未使用的高位为零。

    • 序列化定律：

      decode(encode(b))=b

    • 规范格式定律：

      encode(decode(x))=xfor canonical byte sequences x

    这些都可能很重要，但各自属于不同的规范。

    共享场景

    场景是针对公共能力编写的可复用交互。ALUX 测试框架以这种方式表示场景：编写场景的代码通过Scenario、DeployerIds、PlayAst和ScenarioSchedule能力构造一个值，无需点名具体运行器。

    #[ext(name = HelloScenarioExt)]
pub impl<This> This
where
    This: StandaloneScenario,
    This::Step: PlayAst<Ast = RProc>,
{
    fn hello(self) -> This::Scenario {
        self.scenario()
            .under_comprehensive(100)
            .step(
                self.play_ast(
                    self.deployer(0),
                    tolang! {
                        let x in {
                            x ! "hello" |
                            ? (a <- x) a.log()
                        }
                    },
                )
                .expect_log(r#""hello""#),
            )
    }
}

    每次调用都描述作者定义的含义，而不是运行器机制。under_comprehensive(100)要求在一次顺序运行、100 次完全并发运行以及最多 100 次乱序运行中都得到预期日志。场景固定所观察的内容，运行器则改变执行顺序。

    同一原则也适用于不同解释器：如果多个运行器都实现了场景所用的能力，它们就都可以解释同一个编写好的交互。运行器特有的设置与边界检查应留在场景之外。

    跨解释器一致性

    当两个解释器提供相同观察时，可以比较它们：

    interpret_text(p).route_names=interpret_server(p).registered_route_names

    这可以捕捉独立快照遗漏的漂移。对于 API 定义、编译器阶段与替代数据表示，这尤其有价值。

    有限证据并非证明

    测试通过，只能证明在受测输入与实现下观察到了相应行为，不能证明某条定律对所有值都成立。

    有计划地提升保证强度：

    1. 示例测试
    2. 可复用场景测试
    3. 生成式性质测试
    4. 对有限域进行穷举检查
    5. 模型比较
    6. 证明产物

    根据风险与主张强度选择层级。

    让测试名称表达含义

    优先使用：

    • reconstructs_every_generated_branch_from_its_root_path
    • preserves_child_programs_when_routes_are_merged
    • normalization_is_invariant_under_alpha_renaming

    避免只叙述实现过程的名称：

    • pushes_three_bits
    • calls_helper_twice
    • visits_left_node_first

    如果操作顺序本身有规范规定，操作测试仍然有效。此时应在名称中指出让该顺序具有意义的观察。

    审查要点

    • 每个新增的语义操作是否都有针对性的定律或断言？
    • 可复用义务是否针对公共能力以泛型方式表达？
    • 场景是否与具体运行器分离？
    • 是否区分了语义定律与表示不变量？
    • 在可行时是否比较了多个解释器？
    • 文档是否避免把有限测试称作证明？

    一阶程序

    相关内容

    Rust 中的语义驱动设计：派生含义与组合、语言与编译器流水线
    概念：延续传递风格、去函数化、自由单子
    洞见：重新审视表达式问题

    何时将应用具体化为数据

    普通函数与扩展已经可以表达派生行为。只有当另一个解释器必须在运行前检查、组合、序列化或编译程序时，才应将应用转换为一阶数据。

    普通函数与扩展方法通常是表达派生行为的最佳方式。但有时另一个解释器必须在执行程序之前，先检查、组合、生成文档、序列化或编译程序结构。这时，应用本身必须成为一阶数据。

    执行会抹去结构

    考虑：

    #[ext(name = StatusExt)]
pub impl<This> This
where
    This: StatusAlg,
{
    async fn status_current(&self) -> This::Status {
        self.status().await
    }
}

    调用此方法会得到一个状态。调用开始后，外部解释器通常无法再恢复以下信息：

    • 语义上下文类型
    • 有序参数
    • 源参数名称
    • 结果类型
    • 操作的身份

    这些信息原本存在于源代码级别的函数类型中，但普通执行过程会消耗掉它们。

    对应用进行去函数化

    去函数化会将某个已知函数族中的成员替换为一阶标签，并提供一个共享的应用操作。

    一组最小操作词汇如下：

    trait OperationAlg {
    type Context;
    type Args;

    const ARG_NAMES: &'static [&'static str];
}

trait ApplyAlg<Handle, Args> {
    type Output;

    async fn apply(&self, handle: Handle, args: Args) -> Self::Output;
}

    零大小的CurrentStatusOperation<App>可以表示对原扩展方法的调用。它应当调用该方法，而不是包含一份重复的函数体。

    1. 从扩展方法开始。
    2. 将其具体化为操作类型。
    3. 保留其上下文、参数乘积、参数名称与输出。
    4. 通过ApplyAlg对其进行解释。

    普通调用仍可使用原有便捷方法。只有需要一阶结构的上下文才会用到操作值。

    没有使用者时，不要具体化为数据

    一阶程序会增加类型机制。只有当它们能支持真正的第二种解释时才使用：

    • 运行时注册
    • 生成文档或模式
    • 静态检查
    • 执行前组合程序
    • 序列化
    • 编译

    如果代码只需调用函数，就保留函数即可。

    可移植接口程序

    假设 HTTP 接口包含：

    方法路径输入操作输出
    GET/status—status_currentJSON
    POST/set_temperature正文：f32adjust_statusJSON
    GET/download—current_file流式文件

    可移植程序必须保留：

    • 方法与路径选择器
    • 输入角色，例如路径、查询参数、正文、请求头与身份验证
    • 操作值
    • 输出角色，例如 JSON 或文件
    • 路由合并与嵌套

    不应保留某个特定框架的请求、路由器或响应类型。

    一种流畅记法可以是：

    self.routes()
    .get("/status", self.op(CurrentStatusOperation::<App>::default()).json())
    .post("/set_temperature", self.op(AdjustStatusOperation::<App>::default()).body::<f32>().json())
    .get("/download", self.op(CurrentFileOperation::<App>::default()).file())

    这些流畅调用会构造一个有类型的程序，不必立即注册服务器路由。

    一个程序，多种折叠解释

    同一个一阶程序可以支持多种解释：

    程序解释
    有类型的 HTTP 程序文本文档、可执行路由、OpenAPI 元数据、客户端绑定、符合性测试
    有类型的 JSON-RPC 程序方法注册表、模式、客户端、测试框架

    不要为执行与文档分别维护路由或方法清单，否则会产生彼此竞争的规范。

    输入与输出角色

    操作已经知道自身的参数与结果类型。传输声明只应添加传输含义。

    self.op(FindOperation::<App>::default())
    .path::<u64>()
    .query::<String>()
    .json()

    path、query和json用于标识角色，不应要求作者重新声明已经由ApplyAlg决定的输出类型。

    输出转换属于传输解释器。服务器可以将一种结果转换为 JSON，将另一种结果转换为流式附件。语义操作无需了解任何一种表示。

    组合本身就是程序含义

    程序应保留通用组合操作：

    • 空程序
    • 合并程序
    • 将程序嵌套在某个前缀下
    • 将端点提升为程序

    这些操作比某个框架的路由器方法更基础。熟悉的流畅名称，例如get、post、merge和nest，都可以作为中性代数的别名。

    独立规范可以发布小型程序：

    输入程序组合结果
    状态与下载程序合并服务程序
    目录程序嵌套服务程序

    应用程序负责选择并解释最终的组合。

    宏必须展开为公开的语义结构

    Rust 宏可以让一阶声明更加简洁：

    #[ext(name = StatusApiExt, defunc(via = http))]
pub impl<This> This
where
    This: HttpApiAlg + JsonOutAlg,
{
    fn status_api<Alg>(&self)
    where
        Alg: StatusAlg,
    {
        self.routes().get("/status", self.op(Alg::status_current).json());
    }
}

    只有当宏展开后得到公开且可手动构造的一阶程序时，宏设计才算健全。生成的回调不应成为接口的唯一规范定义。

    良好方向：

    1. 便捷语法
    2. 公开的操作值与程序值
    3. 泛型折叠解释
    4. 具体框架

    表示优先的方向：

    1. 框架注解
    2. 不透明的生成回调
    3. 逆向整理的文档

    与既有概念的关系

    一阶接口程序建立在其他章节介绍的技术之上：去函数化是通用变换；可扩展语法与解释对应表达式问题；自由单子则是一种特定的“带顺序的语法”表示。页面顶部的“相关内容”链接可以跳转到各自章节。

    不要把这些技术等同于指称设计本身。指称设计决定哪些结构很重要；当普通调用会抹去这些结构时，一阶表示负责保留它们。

    审查要点

    • 是否有真实的第二种解释器需要将程序具体化？
    • 操作是否调用作者定义的方法，而非复制其实现？
    • 参数与输出是否从操作中推断得出？
    • 传输语法是否只添加了传输角色？
    • 程序是否可以在不使用便捷宏的情况下构造？
    • 运行时与元数据是否解释同一个程序？

    语言与编译器流水线

    相关内容

    Rust 中的语义驱动设计：一阶程序、解释器与效应
    概念：操作语义、去函数化
    洞见：EVM 代数

    含义并非流水线本身

    当语言含义不与解析器语法树、编译过程、字节码或机器循环混为一谈时，编译器就更清晰。正确性可由一条交换律表达：运行编译后的程序，应与该程序的指称一致。

    如果语言含义不等同于解析器语法树、编译器过程、字节码或虚拟机循环，推理编译器就会容易得多。

    本章采用一种类似 Tolang 的简化并发语言，重点放在语义架构上。

    四个不同层次

    请将以下层次分开：

    1. 源语言语法
    2. 规范化语言
    3. 可执行表示
    4. 机器执行

    典型流水线如下：

    ParseNormalizeCodeGenRun​:Source→Syntax:Syntax→Result(Core,Diagnostics):Core→Result(Executable,Error):Executable×RuntimeState→Observation​

    便捷操作就是组合：

    Compile=Parse;Normalize;CodeGen

    组合后的辅助函数并非每个阶段的语义定义。

    语法尚未成为含义

    解析器输出会映照语法选择：

    • 标点
    • 语法糖
    • 优先级
    • 源代码区间
    • 生成的解析器表示

    这些信息对诊断与工具很重要，但不必用来定义核心语言。

    规范化会移除偶然的语法差异，并引入一种更精简、承载含义的形式。例如，多种表层绑定形式可以规范化为同一个核心限制操作。

    多种源形式 → 一个规范化构造

    这样一来，编译器后续阶段与运行时定律便有了统一的陈述位置。

    指称含义与编译含义

    令：

    [[−]]:Core→D

    在语义域D中赋予含义。

    编译会生成可执行值：

    compile:Core→Executable

    执行时会观察这些值：

    run:Executable→D

    核心正确性义务是一张交换图：

    run(compile(p))=[[p]]

    对于非确定性或并发系统，等价关系可能是观察等价、结果集合、轨迹等价或双模拟，而非普通的值相等。必须由语义模型作出选择。

    并发过程含义

    基础反射演算包含以下思想：

    0P∣Qx!(v)?(y←x) P​inactive processparallel compositionsend a value on a channelreceive a value and continue as P​

    Tolang 以组合方式扩展基础演算。其中一种扩展增加了表层形式

    let x in Pfresh channel binding scoped over P.

    这个绑定会创建一个新通道，并将其名称的作用域限定在P之内；过程演算文献将此操作称为限制。反射核心没有基本限制运算符。参见 Meredith 与 Radestock 的论文《反射式高阶演算》。

    操作机器可以通过元组空间、队列、匹配索引、延续记录与并发任务来实现这些功能。这些机制并非语言定义。

    语义层负责确定可观察的过程行为与结构定律。核心并行组合可能遵循以下定律：

    P∣0P∣Q(P∣Q)∣R​≡P≡Q∣P≡P∣(Q∣R)​

    这种新鲜绑定扩展还具有独立的定律。常见候选模式包括α 重命名、不同绑定的交换，以及作用域外提：

    let x in Plet x in (let y in P)let x in (P∣Q)​≡let y in P{y/x}≡let y in (let x in P)≡P∣(let x in Q)​​(y#P)(x=y)(x∈/FN(P))​

    这里，y#P表示y对P来说是新鲜的；P{y/x}表示避免变量捕获的重命名；FN(P)表示P中的自由通道名称集合。只有在选定的观察等价关系认可这些模式时，它们才成为定律；不能仅凭表层语法或某种字节码布局就作此假设。

    规范化是一种保持含义的映射

    如果源程序s₁与s₂的区别仅在于所接受的语法糖，规范化就应显式呈现它们共同的含义：

    s1​≡sugar​s2​⟹normalize(s1​)=normalize(s2​)

    其他有用的义务包括：

    • α 重命名保留规范化含义
    • 词法作用域应绑定到预期的绑定项
    • 诊断所需的源代码位置应予保留
    • 编译期常量应被擦除，不产生运行时行为
    • 畸形语法应依阶段契约累积诊断信息

    有些项目要求规范化值具有规范形式，有些项目只要求语义等价。应明确选择哪一种。

    阶段能力

    不要使用万能编译器对象

    不要让一个巨型编译器对象成为唯一的阶段接口。

    规范化器可能需要以下能力：

    • 读取并扩展绑定作用域
    • 解析源代码名称
    • 累积诊断信息
    • 构造规范化项

    代码生成器可能需要：

    • 分配可执行引用
    • 生成指令
    • 解析规范化变量
    • 完成可执行结构

    将各阶段入口表达为基于这些能力的扩展。具体环境可以存储映射、区域分配器、计数器与诊断信息，但它们并不拥有阶段含义。

    #[ext(name = NormalizeEntryExt)]
pub impl<This> This
where
    This: BindingScopeAlg + DiagnosticAlg + NormalizeRecAlg,
{
    fn normalize(&mut self, syntax: &Syntax) -> Result<Core, BuildError> {
        // initialize the semantic stage and invoke recursive normalization
    }
}

    各编译器的精确能力名称会有所不同。重要的是依赖明确，阶段映射稳定。

    解析器与运行时可以保持操作式设计

    并非每个子系统都必须被强制纳入同一种编码。

    解析器可能主要由生成式语法机制主导。虚拟机可能主要依赖高效的状态变更与调度。它们可以保留操作式设计，同时实现定义清晰的边界：

    阶段契约
    解析器生成Syntax
    规范化器生成承载含义的Core
    代码生成器以可执行形式保留含义
    运行时生成符合语言模型的观察

    指称设计不会移除机器，而是防止机器悄然成为语言语义。

    编译器定律与测试

    强有力的证据来自多个方面：

    • 针对等价源形式的规范化定律
    • 在预期情况下检查解析与漂亮打印的往返性质
    • 比较直接语义求值与编译后执行
    • 规范承诺规范输出时检查字节码等价
    • 运行时符合性场景
    • 跨解释器差分测试

    字节相等不等于语义相等

    不要混淆逐字节相等与语义相等。只有当规范要求编译结果具有规范形式时，字节相等才是一项有用的更强性质。

    这对读者有何帮助

    阅读语义优先的语言实现时，请留意：

    • 语义语法或能力 trait
    • 派生的规范化操作
    • 明确的阶段契约
    • 一阶核心程序
    • 替换、作用域与组合定律
    • 解释阶段能力的轻量环境
    • 位于边界处的操作式解析器、编译器与虚拟机机制

    这个视角连接了一般的指称设计与 Tolang，展示语义边界如何引导语言设计、编译与运行时解释。

    语义优先的工作流程

    相关内容

    语义视角：为何含义优先

    可重复的方法

    指称设计是一套工作流程，而不只是对已完成代码的解释：陈述语义变化，找出最小基本能力，如实组合它们，再实现轻量级解释器并检查定律。

    指称设计作为一种可重复的开发方法最有用，而不只是对已完成代码作出解释。

    核心流程

    开发新功能或重构时：

    1. 用一句话说明语义变化。
    2. 确定载体与可观察等价关系。
    3. 找出所需的最小基本能力。
    4. 基于明确能力定义派生行为。
    5. 选择能如实表达关系的组合形式。
    6. 只有当结构需要多种解释时，才将程序具体化为一阶数据。
    7. 实现轻量级具体解释器。
    8. 添加定律或共享场景。
    9. 验证不同解释。
    10. 先记录含义，再介绍机制。

    陈述语义变化

    较弱的表述：

    添加缓存和管理器方法。

    面向含义的表述：

    在一次编译期间，解析同一个不可变源名称应指称相同的源值。

    第二种表述提出了一条候选定律。之后可以选择缓存作为一种实现方式。

    找到基本边界

    请思考：

    • 需要哪种新的观察或变换？
    • 它在此边界上是基本操作，还是可以由现有含义派生？
    • 是否需要新的关联载体？
    • 所谓依赖是否只是存储位置？
    • 哪些区别应当不可见？

    只有确实出现新的基本含义时，才添加能力。

    如实选择组合形式

    定义

    操作语义通过求值判断或配置之间的状态转换来描述程序行为。配置可能包含程序片段，以及环境、存储、延续或其他抽象机器状态。

    这种描述具有数学性质：它陈述哪些求值或状态转换有效。解释器或虚拟机可以实现这些规则，但某个具体实现本身并非定义。

    语义定位

    操作语义是一种精确的语义，不只是非正式的实现细节。它通过求值规则或状态转换规则说明行为。指称设计提出了一个互补且更早的设计问题：这些规则应保留哪些可组合含义与等式？

    操作语义的形式

    小步操作语义（结构操作语义）

    计算被拆分为原子转换：

    2+3(2+3)⋅4​→5→5⋅4→20​

    适用于建模并发、交错执行与部分执行。

    大步操作语义（自然语义）

    根据最终结果描述求值：

    (2+3)⋅4⇓20

    推理终止程序时通常更清晰。

    形式规则

    操作语义通常采用推理规则给出。对于简单算术语言：

    E::=n∣E+E

    从左到右求值时，需要三条规则：

    E1​+E2​→E1′​+E2​E1​→E1′​​n+E2​→n+E2′​E2​→E2′​​n1​+n2​→n3​where n3​=n1​+n2​

    前两条规则确定下一个可归约子表达式。两个操作数都成为值后，第三条规则执行加法。

    求值轨迹：

    (1+2)+3→3+3→6

    为何重要

    • 提供精确的类机器模型来描述执行。
    • 为解释器与虚拟机奠定基础。
    • 支持对正确性、资源使用与安全性的推理。

    与其他概念的关系

    • 自由单子提供指令语法与顺序组合。操作规则可以描述该表示中的程序如何求值。
    • CPS将计算剩余部分显式表示为延续。操作规则可以描述值如何传递给这些延续。
    • 去函数化会将已知函数族替换为一阶数据，并提供一个apply操作。操作规则可以描述由此产生的显式机器状态。

    这些都是可以赋予操作语义的对象与变换，本身并不是操作语义。

    实践中的应用

    操作规则可以指导解释器实现，并提供一个用于检查实现的精确模型：

    • EVM可以自然地建模为小步状态转换系统；也可以通过大步判断描述完整的终止执行。
    • 小步规则通常与 Rust 解释器中的match分支非常相似。

    n1​+n2​→n3​

    上文完整的从左到右求值关系可以表示为 Rust 代码：

    enum Expr {
    Num(i64),
    Add(Box<Expr>, Box<Expr>),
}

fn step(expr: Expr) -> Option<Expr> {
    match expr {
        Expr::Num(_) => None,
        Expr::Add(left, right) => match (*left, *right) {
            (Expr::Num(a), Expr::Num(b)) => Some(Expr::Num(a + b)),
            (left @ Expr::Num(_), right) => step(right).map(|next| {
                Expr::Add(Box::new(left), Box::new(next))
            }),
            (left, right) => step(left).map(|next| {
                Expr::Add(Box::new(next), Box::new(right))
            }),
        },
    }
}

    这个函数执行一次状态转换。重复应用即可得到所示轨迹；返回None表示表达式已经是一个值。

    操作问题与指称问题

    操作规则可以证明安全性、进展性质、资源上限以及与实现的对应关系。如果在预期的抽象含义明确之前就选定了操作机制，限制便会显现：实现选择可能意外变成语义承诺。

    指称设计并不否定操作语义。它要求先陈述语义域、组合与定律，再将操作模型与其关联起来。

    语义定位

    表达式问题关注表示与操作的模块化扩展。指称设计则更早地提出一个问题：哪些语义词汇与解释值得表示？

    Phil Wadler 提出的表达式问题关注如何在两个维度上同时扩展语言，而无须修改现有代码：

    • 添加新的数据变体（新的表达式形式，也称“语法”）。
    • 添加新的操作（新的解释，也称“语义”）。

    核心矛盾：

    • 采用函数式/代数数据类型风格时，添加新操作很容易，但添加新变体会造成侵入式修改。
    • 采用面向对象风格时，添加新变体很容易，但添加新操作会造成侵入式修改。

    本节用简短的 Haskell 与 Java 示例展示两面。

    Haskell（函数式/代数数据类型）

    先从一个经典的表达式代数数据类型及两种操作开始。

    data Expr
  = Lit Int
  | Add Expr Expr

eval :: Expr -> Int
eval (Lit n)     = n
eval (Add a b)   = eval a + eval b

pretty :: Expr -> String
pretty (Lit n)   = show n
pretty (Add a b) = "(" ++ pretty a ++ " + " ++ pretty b ++ ")"

    现在，添加新操作很容易：

    size :: Expr -> Int
size (Lit _)   = 1
size (Add a b) = 1 + size a + size b

    但添加新变体（例如Mul）就要求修改每个函数：

    data Expr
  = Lit Int
  | Add Expr Expr
  | Mul Expr Expr

eval :: Expr -> Int
eval (Lit n)     = n
eval (Add a b)   = eval a + eval b
eval (Mul a b)   = eval a * eval b  -- ✏️ UPDATE: new case

pretty :: Expr -> String
pretty (Lit n)   = show n
pretty (Add a b) = "(" ++ pretty a ++ " + " ++ pretty b ++ ")"
pretty (Mul a b) = "(" ++ pretty a ++ " * " ++ pretty b ++ ")"  -- ✏️ UPDATE: new case

size :: Expr -> Int
size (Lit _)   = 1
size (Add a b) = 1 + size a + size b
size (Mul a b) = 1 + size a + size b  -- ✏️ UPDATE: new case

    用 Wadler 的说法，在代数数据类型方法中，数据扩展不具备模块化特性。

    Java（面向对象）

    先从一个接口以及每种变体对应的具体类开始。

    // Expression variants
interface Expr {
    int eval();
    String pretty();
}

final class Lit implements Expr {
    private final int n;

    Lit(int n) {
        this.n = n;
    }

    public int eval() {
        return n;
    }

    public String pretty() {
        return Integer.toString(n);
    }
}

final class Add implements Expr {
    private final Expr a;
    private final Expr b;

    Add(Expr a, Expr b) {
        this.a = a;
        this.b = b;
    }

    public int eval() {
        return a.eval() + b.eval();
    }

    public String pretty() {
        return "(" + a.pretty() + " + " + b.pretty() + ")";
    }
}

    现在，添加新变体很容易：

    final class Mul implements Expr {
    private final Expr a;
    private final Expr b;

    Mul(Expr a, Expr b) {
        this.a = a;
        this.b = b;
    }

    public int eval() {
        return a.eval() * b.eval();
    }

    public String pretty() {
        return "(" + a.pretty() + " * " + b.pretty() + ")";
    }
}

    但添加新操作（例如size）则具有侵入性。你必须修改接口与每个类：

    interface Expr {
    int eval();
    String pretty();
    int size(); // ✏️ UPDATE: new operation added here
}

final class Lit implements Expr {
    private final int n;

    Lit(int n) { this.n = n; }

    public int eval() { return n; }
    public String pretty() { return Integer.toString(n); }
    public int size() { return 1; } // ✏️ UPDATE: new method in every class
}

final class Add implements Expr {
    private final Expr a;
    private final Expr b;

    Add(Expr a, Expr b) { this.a = a; this.b = b; }

    public int eval() { return a.eval() + b.eval(); }
    public String pretty() { return "(" + a.pretty() + " + " + b.pretty() + ")"; }
    public int size() { return 1 + a.size() + b.size(); } // ✏️ UPDATE: new method in every class
}

final class Mul implements Expr {
    private final Expr a;
    private final Expr b;

    Mul(Expr a, Expr b) { this.a = a; this.b = b; }

    public int eval() { return a.eval() * b.eval(); }
    public String pretty() { return "(" + a.pretty() + " * " + b.pretty() + ")"; }
    public int size() { return 1 + a.size() + b.size(); } // ✏️ UPDATE: new method in every class
}

    用 Wadler 的说法，在面向对象方法中，操作扩展不具备模块化特性。

    总结（Wadler 的观点）

    • 函数式/代数数据类型风格倾向于添加新操作，但不利于添加新变体。
    • 面向对象风格倾向于添加新变体，但不利于添加新操作。
    • 表达式问题要求找到一种设计，使两个维度都能扩展，而不必修改现有代码。

    Wadler 的解释与解决方案概览（1998）

    Wadler 将问题表述为：扩展数据类型的分支（新变体），并扩展该数据类型上的函数（新操作），同时不重新编译现有代码，且保留静态类型安全（无需类型转换）。

    他用“表格”作比喻：

    • 行 = 分支（变体/构造器）
    • 列 = 函数（操作/解释）

    在函数式/代数数据类型环境中，行固定而列易于添加。
    在面向对象环境中，列固定而行易于添加。
    挑战在于让两个方向都可扩展。

    Wadler 提出的解决方案（GJ + 虚拟类型）

    Wadler 使用 GJ（泛型 Java）提出一种方案，其中包括：

    • 使用This有界参数（This extends LangF<This>）模拟ThisType。
    • 内部类与接口按This索引（虚拟类型）。
    • A visitor-based structure that allows:
      • 通过继承“语言族”来添加新分支（例如Plus）
      • 通过添加新访问者来增加操作（例如Show）

    诀窍在于引用This.Exp与This.Visitor，使每个扩展阶段都保持类型安全且可以独立编译。

    注意事项（Java 内部接口）

    Wadler 指出，Java 会将内部接口视为静态的，因此破坏了索引技巧。
    他认为放宽这一限制就能使方案可行；但现代 Java 仍未改变这一点（嵌套接口依旧隐式为静态）。

    提及的其他解决方向

    1. Corky Cartwright 的方法 要求逆变扩展：允许基础表达式类型替代扩展类型。 这解释了为何要使用不动点：扩展语言族不是原类型的子类型。

    2. Kim Bruce 的方法 要求使用高阶类型构造器（将类型构造器作为参数的类型参数化方式）。 GJ 不直接支持这一特性，但 Wadler 认为可以用虚拟类型模拟。

    3. Krishnamurthi 等人（扩展访问者模式） 通过扩展访问者设计实现。 在他们的 Pizza 环境中缺少静态类型，因此需要动态类型转换。

    4. 专用语言扩展 Wadler 提到了两种依赖于专为该问题设计的语言特性的方案。 它们不如虚拟类型方案通用。

    Wadler 的两点总结

    Wadler 的邮件清楚地说明了两点：

    1. 表达式问题是数据扩展与操作扩展之间的结构性矛盾。
    2. Solutions are possible, but they tend to require either:
      • 可模拟虚拟类型的类型系统特性，或
      • 专用语言扩展，或
      • 对静态类型安全或独立编译作出妥协。

    轻量级 Go 方案（2020）

    Wadler 于 1998 年提出并命名了这一问题。之后，轻量级 Go（FG）及其泛型扩展 FGG（轻量级泛型 Go）在一种类似 Go、采用结构化接口与泛型的语言中，给出了具体且完全静态的解决方案。

    论文中的方案（图 8，简化版）包含两个结构Num与Plus，以及两个操作Eval与String：

    type Evaler interface { Eval() int }
type Stringer interface { String() string }

type Num struct { value int }
type Plus(type a Any) struct { left a; right a }

func (e Num) Eval() int { return e.value }
func (e Plus(type a Evaler)) Eval() int { return e.left.Eval() + e.right.Eval() }

func (e Num) String() string { return fmt.Sprintf("%d", e.value) }
func (e Plus(type a Stringer)) String() string {
    return fmt.Sprintf("(%s+%s)", e.left.String(), e.right.String())
}

type Expr interface { Evaler; Stringer }

var e Expr = Plus(Expr){Num{1}, Num{2}}

    其机制如下：

    • 泛型递归表示。Plus的子项具有一个类型参数a，其唯一约束为Any。该结构不绑定到列出所有操作的封闭接口，因此后续仍可添加操作。
    • 针对操作的约束。每个方法声明都会独立约束a：Plus(type a Evaler)用于Eval，Plus(type a Stringer)用于String。这依赖于 FGG 的协变接收者：方法接收者的约束可以比类型声明中的约束更强。
    • 结构化接口。结构只要具有接口的方法就算实现了该接口，因此可以在不修改Expr和Num的情况下，于之后引入Plus。只有在构造值时，才需要确定完整的操作集合（Plus(Expr){...}）。

    新分支只需增加新结构；新操作只需增加新接口与方法。二者都不需要修改或重新编译现有声明，也无需类型断言。

    引用透明性

    相关内容

    语义视角：指称与组合性、定律与解释
    洞见：重新审视引用透明性

    语义定位

    引用透明性取决于所选指称与等价关系。当替换表达式不会改变指定含义时，它允许进行替换，即使语义边界背后的实现操作有所不同。

    引用透明性（RT）是表达式的替换性质：可以用一个表达式的指称替换该表达式，而不改变程序含义。

    如今，实践中通常将 RT 作为等式推理、安全重构与定律驱动 API 设计的基础。

    核心含义

    RT 表示：

    • 如果e指称v
    • 那么，以v代替e会保留含义

    这是语义主张，而非编码风格口号。

    纯性

    纯函数对相同输入总是返回相同输出，并且没有可观察的副作用。RT 是表达式的替换定律：用其指称替换表达式必须保留含义。因此，纯函数是实践中实现 RT 的一种常见方式，而 RT 是更广泛的语义标准。关于指称设计中纯性与 RT 的区别，请参阅《重新审视引用透明性》。

    历史背景

    在编程语言语义中，RT 与 Christopher Strachey 的表述密切相关。他的论述将值推理与以更新为主的行为区分开来：

    • R 值：表达式的值。
    • L 值：可以赋值的位置。

    关键在于：当我们进行值层面的推理时，表达式级别的替换是稳定的。赋值会引入位置更新，使替换推理变得困难，甚至不再以朴素形式成立。

    这里的赋值与副作用意味着什么

    在此上下文中：

    • 赋值是对某个位置进行更新（例如x := x + 1）
    • 副作用是返回值之外任何可观察的变化

    赋值是一种特定的副作用。

    这就是 RT 在许多命令式环境中失效的原因：求值可能依赖或改变表达式显式值接口以外的可观察上下文。

    现代语言如何呈现 RT

    Haskell

    纯表达式通常被当作默认推理对象来教授 RT。效应通过类型化构造显式表达（例如IO、状态传递及相关抽象），所以替换定律在日常使用中居于核心地位。

    Scala（Cats / Cats Effect）

    在 Scala 函数式编程实践中，Cats Effect 提供了最常见的 RT 解释方式：

    • IO[A]是对带效应工作的纯描述
    • 组合IO值满足 RT
    • 在运行时边界显式执行（unsafeRun*）

    Cats Effect 也将其与急切求值Future作对比，这也是 Scala 中讨论 RT 时强调惰性与延迟执行的原因之一。

    当代的 RT

    在现代生态系统中，RT 常被用作“行为可安全替换”的简称。 在多范式系统中，团队通常会将 RT 主张应用于特定模块、API 或带效应类型的区域，而不是全局套用于所有代码。

    关于 RT 在指称设计中的解读，请参阅《重新审视引用透明性》。

    自由单子

    相关内容

    Rust 中的语义驱动设计：一阶程序、解释器与效应
    概念：延续传递风格、去函数化
    洞见：EVM 代数

    语义定位

    自由单子是一种表示指令语法与自由生成的顺序组合的方式。指令函子已经选定了词汇；随后，解释器会将该语法映射到某个语义域。它是一种强大的编码方式，但并非指称设计的定义。

    什么是自由单子（Rust 版本）

    自由单子可以让你：

    • 描述程序时使用数据，而非立即运行程序。
    • 稍后以一种或多种方式解释该程序。

    可以将它想成：

    一个效应操作 AST + 用于串接步骤的bind/flat_map。

    将以下两者分开：

    • 语法 → 指令枚举。
    • 解释 → 映射到所选语义域并保留结构。

    “自由”意味着单子结构由函子F自由生成，除了单子定律之外不添加其他等式。选择F本身就决定了指令语法；对结果程序作出解释，则会赋予其特定指称。

    Rust 实现

    示意性编码

    Rust 不支持直接的高阶类型参数，因此生产级自由单子编码需要额外的类型机制，或专用指令函子。以下代码展示预期结构，并非可直接使用的泛型实现。

    自由单子类型

    #[derive(Clone)]
enum Free<F, A> {
    Pure(A),
    Suspend(F),
    FlatMap(Box<Free<F, A>>, Box<dyn Fn(A) -> Free<F, A>>),
}

impl<F: Clone + 'static, A: 'static> Free<F, A> {
    fn pure(a: A) -> Self {
        Free::Pure(a)
    }

    fn flat_map<B: 'static, G>(self, f: G) -> Free<F, B>
    where
        G: Fn(A) -> Free<F, B> + 'static,
        F: 'static,
    {
        match self {
            Free::Pure(a) => f(a),
            Free::Suspend(op) => {
                Free::FlatMap(Box::new(Free::Suspend(op)), Box::new(f))
            }
            Free::FlatMap(inner, g) => {
                Free::FlatMap(inner, Box::new(move |x| g(x).flat_map(f.clone())))
            }
        }
    }
}

    领域特定语言：控制台操作

    #[derive(Clone)]
enum Console<A> {
    Print(String, A),
    ReadLine(fn(String) -> A),
}

// Smart constructors
fn print_line(s: &str) -> Free<Console<()>, ()> {
    Free::Suspend(Console::Print(s.to_string(), ()))
}

fn read_line() -> Free<Console<String>, String> {
    Free::Suspend(Console::ReadLine(|input| Free::Pure(input)))
}

    解释器

    fn run_console<A>(mut prog: Free<Console<A>, A>) -> A {
    loop {
        match prog {
            Free::Pure(a) => return a,
            Free::Suspend(Console::Print(s, next)) => {
                println!("{}", s);
                prog = Free::Pure(next);
            }
            Free::Suspend(Console::ReadLine(f)) => {
                let mut buf = String::new();
                std::io::stdin().read_line(&mut buf).unwrap();
                prog = f(buf.trim().to_string());
            }
            Free::FlatMap(inner, cont) => match *inner {
                Free::Pure(a) => prog = cont(a),
                Free::Suspend(op) => prog = Free::Suspend(op), // minimal handling
                _ => unimplemented!(),
            },
        }
    }
}

    用法

    fn main() {
    let program =
        print_line("What is your name?")
        .flat_map(|_| read_line())
        .flat_map(|name| print_line(&format!("Hello, {name}!")));

    run_console(program);
}

    要点

    • 语法 = enum Console（可能的指令）
    • 程序 = Free<Console, A>（描述步骤的数据）
    • 具体解释 = run_console
    • 优势：同一个程序可以编写多种解释器，例如在真正的 IO 中运行、将日志写入文件，或编译为另一种语言。

    与延续及 CPS 的关联

    延续传递风格（CPS）是一种编程方式：函数不直接返回值，而是将结果传给另一个函数（即延续），由它表示“程序接下来的部分”。

    自由单子本质上是由一系列步骤组成的程序，每一步都会说：

    “执行此操作，然后继续处理剩余部分。”

    这个“程序剩余部分”正是一个延续——从当前结果映射到下一步的函数。

    • 在我们的 Rust 自由单子中：

      Free::FlatMap(Box<Free<F, A>>, Box<dyn Fn(A) -> Free<F, A>>)

      Box<dyn Fn(A) -> Free<F, A>>就是延续。

    • 解释自由单子时，你其实是在通过 CPS 运行：

      • 你不会直接返回值，而是将它们传给下一个延续。
      • 最终会进入如下循环： current_instruction -> feed result into continuation -> next instruction

    • CPS 关系：

      • 自由单子将 CPS 编码进数据结构。
      • CPS 则是同一思想的运行时控制流表示。

    与去函数化的关系

    去函数化是一种程序变换：它将高阶函数替换为表示可能函数集合的一阶数据结构，并提供一个用于应用它们的解释器。

    在 CPS 中，延续是高阶函数。对 CPS 程序去函数化，会将这些延续替换为延续分支枚举，并提供一个apply函数来运行它们。

    对于适当的编码，自由单子可以与 CPS 变换程序内部的去函数化延续联系起来：

    1. 从程序的 CPS 版本开始。“程序剩余部分”由延续函数承载。
    2. 将这些延续函数去函数化为数据类型中的有限分支集合。
    3. 所得的一阶数据类型可以具有与自由单子表示相同的指令与延续结构。

    关键相似之处

    • 自由单子与去函数化都会生成计算的数据表示，并且都需要解释器来赋予这些数据含义。
    • 自由单子中的FlatMap分支持有延续；去函数化则将该闭包替换为数据类型中的一个分支。

    关键区别

    方面去函数化自由单子
    目的消除高阶函数的机械式编译器技术将语法与语义分离的代数构造
    输入任意高阶程序，通常采用 CPS 形式描述可能指令的函子 F
    输出函数分支枚举及应用函数Free<F, A>AST 与解释器
    是否为单子？不一定根据构造始终是单子
    范围通用变换特定的函数式编程模式

    总结 去函数化是一种变换技术，自由单子是一种代数构造。在某些表示中二者关系密切，但除非附加额外假设，否则通常不能由其中一种构造推出另一种。

    延续传递风格（CPS）

    相关内容

    Rust 中的语义驱动设计：一阶程序、语言与编译器流水线
    概念：自由单子、去函数化
    洞见：EVM 代数

    语义定位

    CPS 是一种表示与程序变换，它会将控制流显式化。它是否保留含义，取决于是否明确了源语义、目标语义及二者之间的对应关系。

    定义

    延续传递风格（CPS）是一种编程方式：函数不直接返回值，而是将结果传给另一个称为延续的函数；延续表示程序接下来的部分。

    动机

    • 使控制流显式且可编程。
    • 支持非阻塞 IO、提前退出、协程、回溯与并发调度等高级变换。
    • 用于编译器中间表示，以简化优化与分析。

    基本形式

    直接风格：

    fn add_one(x: i32) -> i32 {
    x + 1
}

fn main() {
    let y = add_one(41);
    println!("{}", y);
}

    CPS 风格：

    fn add_one_cps(x: i32, k: impl Fn(i32)) {
    k(x + 1)
}

fn main() {
    add_one_cps(41, |y| {
        println!("{}", y);
    });
}

    这里，k是延续。我们不再返回x + 1，而是调用k(x + 1)。

    关键性质

    • 所有函数调用都是对延续的尾调用。
    • 当前计算永远不会“返回”到调用者，而是跳入延续。
    • 程序中的控制流变得显式。

    与高阶函数的关系

    • 在 CPS 中，延续就是高阶函数。
    • 计算的每个步骤都会接收一个延续，用来表示下一步要做什么。

    与去函数化的关系

    • 在 CPS 中，延续是实际的函数值。
    • 去函数化会把延续函数替换为表示可能后续步骤的数据结构（枚举），并提供一个apply函数来解释这些步骤。

    与自由单子的关系

    • 自由单子中的FlatMap构造器恰好存储了一个延续。
    • 解释自由单子类似于执行 CPS 代码，只不过延续成为程序数据的一部分。
    • 适当的自由单子编码可以与 CPS 以及去函数化的延续表示建立联系。

    优点

    • 控制流表示灵活。
    • 更容易推理求值顺序。
    • 适用于实现解释器、调试器、优化器与异步运行时。

    缺点

    • 比直接风格冗长。
    • 对人来说可能更难阅读。
    • 在不提供原生支持的语言中，需要尾调用优化才能获得较高效率。

    去函数化

    相关内容

    Rust 中的语义驱动设计：一阶程序、语言与编译器流水线
    概念：自由单子、延续传递风格
    洞见：EVM 代数

    语义定位

    去函数化会改变表示，同时力求保留函数应用的行为。在语义优先设计中，当另一个解释器需要在执行前检查或组合操作时，生成的一阶值就很有用。

    定义

    去函数化是一种程序变换：它将高阶函数替换为表示可能函数集合的一阶数据结构，并提供一个应用这些函数的解释器函数。

    动机

    有些语言、编译器或运行时无法高效处理高阶函数，甚至完全不支持。通过去函数化，程序会变成纯一阶形式，因此更容易编译、分析、序列化，或在受限环境中运行。

    处理过程

    1. 找出所有可能被创建并传递的高阶函数。
    2. 为每个函数分配枚举或和类型中的唯一标签，并附上它运行时所需的数据。
    3. 用这些标签替换函数值。
    4. 定义一个apply函数，接收标签与函数参数，然后按标签进行模式匹配并运行相应代码。

    Rust 示例

    之前：使用闭包

    let k: Box<dyn Fn(i32) -> i32> = Box::new(|x| x + 1);
println!("{}", k(41));

    之后：去函数化形式

    enum Cont {
    Add1
}

fn apply(c: Cont, x: i32) -> i32 {
    match c {
        Cont::Add1 => x + 1,
    }
}

println!("{}", apply(Cont::Add1, 41));

    性质

    • 现在所有函数都由简单数据表示。
    • 程序变为纯一阶形式。
    • apply函数取代直接的函数调用。

    应用

    • 简化编译器后端：许多编译器会生成 CPS 代码，然后对其去函数化。
    • 函数序列化：可以通过网络发送枚举标签，也可以将其存入文件。
    • 静态分析：一阶代码更容易推理。
    • 推导解释器：去函数化会自然引出解释器模式。

    与 CPS 的关系

    在 CPS（延续传递风格）中，延续是高阶函数。对 CPS 代码去函数化，会将这些延续转换为枚举中的有限分支集合，并提供一个应用函数。

    与自由单子的关系

    适当的自由单子表示可以与 CPS 变换程序中的去函数化延续相关联。这是一种紧密联系，但不意味着两种构造普遍等同。

    类型层面的应用

    去函数化还可以在不原生支持高阶类型的语言中编码类型层面的应用。C# 对象代数实验通过App<F, a>运用这种轻量级编码，以表达函子、适用函子、单子与效应代数。

    分支与合流

    相关内容

    语义视角：指称与组合性、定律与解释
    Rust 中的语义驱动设计：定律、场景与证据
    概念：操作语义

    分支、确定性、合流、轨迹等价与双模拟都涉及计算中的多种可能，但它们并非同一种性质。

    语义定位

    控制流分支属于操作结构。合流性是归约关系的性质。轨迹等价与双模拟用于比较行为。指称等价则比较所选语义域中的含义。健全的设计应明确说明所需的等价关系，而不是非正式地在这些概念之间切换。

    行为等价

    并发与交互式程序很少只有一个最终结果。一个常见的起点是标记迁移系统：

    L=(S,Aτ​,→)

    其中S是状态集合，Aτ​是可观察动作标签与一个内部动作τ的集合，→⊆S×Aτ​×S是转换关系。我们将pa​p′记作：状态p可以执行动作a并变为p′。

    行为等价会说明有意忽略这些系统之间的哪些差异：

    • 线性时间观察沿着已完成或部分执行记录发生的事件
    • 分支时间观察还会保留何时出现了哪些选择，以及选择何时确定

    因此，两个系统可能有相同轨迹，却具有不同分支结构。一个系统可能在交互前就在两个动作间选择，另一个系统则推迟到交互之后才选择。动作序列相同，但后续可能性不同。

    van Glabbeek 提出的线性时间—分支时间谱，系统整理了这些行为等价关系。它并非从弱到强的排序；谱系中的每一点都保留不同的观察。

    Rust 程序中的分支

    if会根据条件选择一个分支：

    fn sign(x: i32) -> i32 {
    if x > 0 {
        1
    } else if x < 0 {
        -1
    } else {
        0
    }
}

    match会根据某个值选择一个分支：

    fn day_type(day: &str) -> &str {
    match day {
        "Saturday" | "Sunday" => "Weekend",
        "Monday" | "Tuesday" | "Wednesday" | "Thursday" | "Friday" => "Weekday",
        _ => "Unknown",
    }
}

    对于确定性语言中的固定输入，这些构造会选择可预测的控制流路径。这种性质称为确定性，而非合流性。

    合流性的含义

    如果某个项的两种归约方式最终能够再次汇合，那么该归约关系就是合流的：

    b​↙∗↘∗​ad​↘∗↙∗​c​

    形式化地说，若：

    a→∗banda→∗c

    则必然存在某个d，使得：

    b→∗dandc→∗d

    合流性允许存在多条归约路径。它表示这些路径能够到达共同后继，因此彼此兼容。

    确定性与合流性

    确定性归约关系中，每个状态最多只有一个后续步骤。因此它自然满足合流性：没有相互竞争的单步选择需要协调。

    反过来则不成立。系统可以允许多种归约顺序，同时仍满足合流性，因为所有顺序最终都会得到相同结果。

    普通 Rust 的if与match表达式展示了确定性选择，但单凭它们无法体现合流性的有趣之处。

    Church–Rosser 性质

    Church–Rosser 定理说明了 lambda 演算归约的合流性质。如果一个项沿不同归约路径得到两个结果，那么这两个结果存在共同归约结果。

    只要范式存在，合流性就意味着它唯一。这支持等式推理，因为求值顺序不会改变最终范式。

    不要将此结果推广到任意命令式程序。副作用、非确定性调度、失败以及对中间状态的观察，都可能使不同归约顺序产生差异。

    轨迹

    轨迹记录一系列可观察动作或状态。与只记录结果的语义相比，轨迹语义有意保留更多操作信息。

    两个纯函数可以返回同一结果，却经过不同内部步骤。如果结果指称忽略了这些步骤，它们在该指称下相等；但在轨迹语义下，它们未必相等。

    存在效应时，调整检查顺序可能改变观察：

    fn is_admin() -> bool {
    println!("checked admin");
    true
}

fn is_user() -> bool {
    println!("checked user");
    true
}

    先检查is_admin还是先检查is_user，可能返回等价分类，却打印出不同轨迹。

    设计问题在于，这些打印信息是否属于所选语义域。

    轨迹等价

    如果两个系统在选定的轨迹模型下允许相同的可观察轨迹，它们就是轨迹等价的。

    轨迹等价可能忽略分支结构。两个系统可以生成相同轨迹，但一个比另一个更早确定选择。在交互式与并发系统中，这种区别可能很重要。

    双模拟

    双模拟逐步关联两个迁移系统。每当一个系统执行可观察动作，另一个系统就必须能够匹配该动作，而且转换后的状态仍须保持关联。

    常见变体包括：

    • 强双模拟，用于匹配单个状态转换
    • 弱双模拟，用于抽象选定的内部转换
    • 分支双模拟，用于抽象内部工作，同时保留重要的选择结构

    双模拟通常比轨迹等价提供更强的行为比较，因为它会观察交互过程中各种选择是否仍然可用。

    起源与形式定义

    Milner 在《通信系统演算》中为通信过程发展了观察等价。随后 Park 在《无限序列上的并发与自动机》中，以余归纳方式刻画了相应的等价关系，给出了现称为双模拟的最大不动点关系与证明方法。Milner 随后采用并发展了这一方法，将其作为推理过程行为的基础。

    强双模拟。对于标记迁移系统，若关系R满足以下条件，则它是强双模拟：当pRq成立时，对于每个动作a：

    • 如果pa​p′成立，则存在某个q′，使得qa​q′与p′Rq′成立；并且
    • 如果qa​q′成立，则存在某个p′，使得pa​p′与p′Rq′成立。

    如果存在某个双模拟关系关联两个状态，那么它们就是双模拟等价的。这一定义是余归纳的：匹配某个状态转换后，后继状态必须再次满足相同的行为义务。

    分支双模拟。在一种忽略发散的常见表述中，如果对称关系R满足以下条件，那么它就是分支双模拟：当pRq与pa​p′成立时，以下情况至少一种成立：

    • a=τ与p′Rq成立；或

    • 存在状态q0​与q′，使得

      qτ​q0​a​q′,pRq0​,p′Rq′

    这里，τ​表示零次或多次内部转换。要求中间状态q0​仍与p保持关联，正是为了忽略内部工作时仍能保留相关的分支可能性。van Glabbeek 与 Weijland 在《双模拟语义中的分支时间与抽象》中引入并发展了这一等价关系。

    指称相等

    指称相等取决于所选语义域：

    [[P]]=[[Q]]

    语义域本身可以由轨迹、按双模拟等价取商后的迁移系统、结果集合或其他数学模型构成。指称设计不规定某个通用等价关系，而是要求明确选择等价关系，并以组合方式使用它。

    其关系如下：

    1. 从操作系统开始。
    2. 选定相关观察。
    3. 选择语义域与等价关系。

    作为数据的分支

    分支也会以树的结构出现。二叉路径可以表示为一串左右选择。这种表示适用于前缀树、执行标识符、决策图与内存寻址。

    《为何含义优先》中的语义分支位置示例，特意将树的含义与一种位向量编码区分开来。

    Conal Elliott 曾用完美二叉叶树结构描述内存寻址。重点并不是每台机器都会按字面存储一棵源级树，而是组合式树模型能够揭示扁平数值地址所隐藏的有用结构。

    从语义到机器

    相关内容

    Rust 中的语义驱动设计：一阶程序、语言与编译器流水线
    概念：操作语义、自由单子、延续传递风格、去函数化

    操作语义描述什么

    操作语义规定所选程序表示的行为。它通过判断或配置上的转换关系来定义求值，例如：

    (program,state)⟶(program′,state′)

    程序可以是源语法、自由单子值、CPS 项、字节码或去函数化的机器状态。这些表示无一就是操作语义。操作语义是对所选表示中的值如何求值或转换的说明。

    方向很重要。表示为我们提供了一个可描述其行为的对象；补充操作描述并不能解释该语言应有何种含义。

    自由单子程序

    自由单子提供指令语法与自由生成的顺序组合，但不会提供这些指令的行为。

    自由单子程序的操作语义可以定义包含当前指令、其延续与任意机器状态的配置。随后，规则会说明例如挂起的指令如何改变状态，并将结果传递给程序剩余部分。

    这是一种可能的解释。同一个自由程序也可以折叠为指称模型、编译成另一种语言、接受分析，或直接渲染，而无需执行。

    从自由到更自由：研究揭示了什么

    曾将自由单子视为效应程序通用架构的读者，可能会好奇，为什么后来研究转向 freer 构造、可扩展效应与处理器。研究并没有简单抛弃自由单子，而是分离出它们真正提供的内容，衡量常见表示的失效之处，并将有用结构延续下来。

    Kiselyov 与 Ishii 通过逐步移除效应项表示中的约束与样板代码，推导出 freer 单子。在 freer 表示中，指令可以产生一个中间类型，而该类型被隐藏在最终程序类型之外；显式延续则将该结果连接到计算的其余部分。因此，指令签名不再需要Functor实例。

    这种变化提升了表达能力，但本身并未解决性能问题。直接的 freer 表示仍然像左结合的列表追加那样组合延续：处理一串n请求可能需要O(n2)的工作量。将延续显式化后，就能看见真正的机会——可以把它存储为类型对齐序列，相邻结果与输入类型由构造保证匹配。高效拼接该序列即可消除对结合顺序敏感的遍历。

    开放联合类型随后让可扩展效应解释器能够添加、组合与消除选定的请求类型。这解决了模块化效应组合与处理器结构问题，但仍未提供某个具体领域的等式，也不会决定两个带效应程序何时具有相同含义。

    结论比“freer 优于 free”更加精确：自由单子揭示了请求与解释之间有价值的分离；freer 编码去除了不必要的约束；类型对齐队列解决了经测量确认的性能问题；可扩展效应改善了组合。每一步都保留前一步的经验，同时缩小主张范围。语义解释始终是另一项独立决定。

    参见 Kiselyov 与 Ishii 的论文《Freer 单子：更具可扩展性的效应》。

    CPS 程序

    延续传递风格（CPS）会将计算剩余部分显式表示为延续。CPS 的操作语义会描述以下行为：

    • 对当前 CPS 表达式求值；
    • 将生成的值传递给其延续；
    • 应用该延续时转移控制权。

    CPS 将控制流变为便于从操作层面描述的形式，但它是一种表示或程序变换，而非操作语义。要将直接风格程序与其 CPS 翻译关联起来，必须明确源语义、目标语义并给出保义论证。

    超越 CPS：何时必须检查延续

    CPS 是解决结合顺序敏感的追加与 bind 的常见方法。它不再反复遍历左结合结构，而是通过函数组合表示剩余计算。如果对延续唯一要做的操作是最终应用，这种表示就很高效。

    van der Ploeg 与 Kiselyov 指出了适用边界：有些使用者必须在继续之前检查或修改中间结果。非确定性搜索、迭代器、自由单子与可扩展效应都可能需要此类访问。CPS 会将概念上的序列隐藏在函数中，因此要恢复中间结构就需要反射回数据，从而可能抵消性能优势。

    他们提出的替代方案会将隐藏序列直接表示为类型对齐数据结构。它无论结合顺序如何都能高效组合，同时保留对中间结果的高效访问。类型会确保每个存储的计算都能产生下一个计算所需的输入。

    更广泛的结论并非类型对齐序列击败 CPS，而是 CPS 擅长应用延续；当使用者必须检查延续时，它就不那么合适。关于带界控制的研究进一步深化了这一教训：不要将整个未来视作一个无法区分的延续，而应使用分界符明确可捕获与操纵的周边计算范围。

    这些思想并未消失。它们的经验继续影响效应处理器、抽象机器推导、有类型控制运算符与高效效应表示。变化的是，人们不再认为 CPS 单独就应成为最终抽象。

    参见 van der Ploeg 与 Kiselyov 的论文《无悔反射》。关于更广泛的控制模型，另请参阅 Kiselyov 的延续与带界控制文集。

    去函数化机器

    去函数化会将已知的函数值集合（例如 CPS 延续）替换为一阶构造器，并提供一个apply操作。随后，操作语义可以描述这些显式配置之间的状态转换。

    在具体的 CPS 变换之后再进行去函数化，可以推导出抽象机器。这是一种强有力的推导方式，但不是操作语义的通用定义：操作规则不必源自 CPS，任意一阶机器也不会因此自动成为去函数化的延续机器。

    Reynolds：去函数化的起源

    John C. Reynolds 在 1972 年关于定义解释器的研究中引入了去函数化。他的起点并非一阶虚拟机，而是高阶解释器：定义语言中的函数表示环境、延续及所定义语言的其他部分。

    该变换会观察整个程序中可能出现的有限函数抽象集合。它将每个抽象替换为一个一阶构造器，并携带其自由变量的值；随后将函数应用替换为一个按构造器分派的apply操作。原本隐含在定义语言中的内容，就此变成显式的闭包或延续代数。

    将这一做法应用于基于延续的解释器，可以显露出一台机器：延续构造器变为控制状态，被捕获变量变为存储的机器数据，apply则变成转换分派器。机器不是预先猜出来的，而是从高阶求值器推导出来的。

    Reynolds 也强调了这种清晰度的代价。所得机器包含正确但不唯一的表示选择。不同的构造器选择或前置变换可能生成不同的、类似机器的“齿轮与部件”，但仍保留相同的行为。因此，去函数化显露的是一种操作结构，而非语言唯一必然的含义。

    Danvy 与 Nielsen 后来将 Reynolds 的技术系统化为全程序变换，并研究了作为其逆变换的重新函数化。他们更深层的结论是：这种变换是一座桥梁，能够在高阶定义与一阶机器之间传递规范与正确性论证，还能揭示表面上无关的程序其实是同一结构的两种表示。

    这条研究脉络说明了该技术应有的权威范围。去函数化不只是把闭包替换为枚举，但也不是普遍基础：它是在两种表示间保义转换，其对应关系必须得到确立。

    参见 Reynolds 的《高阶编程语言的定义解释器》，以及 Danvy 与 Nielsen 的《去函数化的实践》。

    操作表示循环

    一种常见错误是试图寻找能解决所有编程问题的单一操作表示。每种表示都会恢复前一种表示隐藏的内容，但也会使另一种关切更难处理：

    higher-order program⟶free syntax⟶CPS⟶first-order machine⟶higher abstraction

    这些箭头并不表示编译器必须采用某条流水线，而是展示一种反复出现的设计演进：显露当前表示隐藏的内容，随后再隐藏此次显露引入的机制。

    表示使哪些内容可见引入了何种压力
    高阶函数直接组合与宿主语言抽象泛型使用者可以调用函数，却无法检查函数隐藏的结构
    带顺序组合的自由语法以数据形式表示、可组合并可解释的程序自由性本身不提供领域等式、规范化、高效求值，也不支持检查已存储的函数
    CPS求值顺序与计算剩余部分变得显式全程序 CPS 编码会让延续贯穿几乎每个接口
    去函数化的一阶控制延续变成可检查、可序列化的分支必须显式维护构造器、已存参数、转换状态与一个apply操作
    对机器作更高层抽象机制变得更易使用编译器、调度器、调试器或优化器需要检查结构时，它又被隐藏起来

    这些压力来自结构本身。检查需要数据；将行为转为数据会引入构造器与解释器；隐藏这些构造器可以恢复便利的抽象，却会移除分析或变换程序的使用者所需的访问能力。

    自由单子的取舍尤其具有启发性。自由单子解决了一个精确问题：为指令函子生成顺序组合，而不施加单子定律之外的等式。这一保证也构成了它的局限。它不了解领域定律。如果对同一单元格的两次写入应当等价于最终那次写入，那么自由程序仍会保留两条指令，直到领域专用的规范化或解释将它们识别为等价。因此，优化、规范形式与语义等价必须由其他机制提供。

    将指令具体化为数据，也不会让整个程序都可检查。在常见编码中，挂起的指令可见，但其延续却是宿主语言函数。泛型分析器无法检查该函数背后的未来结构，除非提供结果并应用该函数。将延续具体化可以恢复可检查性，但会转向一阶或去函数化表示——于是又回到了循环的下一环。

    求值开销同样取决于表示。左结合绑定构成的朴素树可能需要反复遍历，导致二次复杂度。复制剩余子程序的变换可能导致指数级增长。Codensity 风格、freer 或专用编码可以改善特定开销，但代价是选择了不同的表示与取舍。指数级增长确实可能发生，但不是自由单子的固有定律。

    这就是自由单子并非通用解法的原因。它提供带定律的顺序组合语法，但不提供预期领域等式、规范范式、完整结构可见性或自动高效的实现。同样，局部使用 CPS 并不需要扩散到整个系统；去函数化只有在需要具体化的函数族与捕获值变多时才会变得繁琐。

    当人们要求每种新编码都成为通用基础时，就会出现这个循环。它解决了上一种操作不便，随后又成为新的偶然复杂性来源。

    因此，如果讨论“最佳抽象”时只关注操作特性，争论就难以收敛。高阶函数、自由语法、CPS 与一阶机器被拿来比较，仿佛其中一种必须胜过其他所有方案。但在说明必须保留什么、结果由谁使用之前，“更好”没有明确含义：

    • 直接执行偏好普通调用与隐藏表示；
    • 变换与分析需要可检查的结构；
    • 序列化需要一阶数据；
    • 可扩展性可能更偏好增加解释，也可能更偏好增加语法，但两者很少同样容易；
    • 并发可能需要有意忽略许多调度选择的观察。

    这些是不同要求，而非某种抽象普遍更优的逐级证明。操作特性有助于为既定目的选择实现，却不能提供该目的，也不能决定哪些区别有意义。

    同样的谨慎也适用于顺序思维。操作语义可以描述并发与非确定性系统，但单一机器步骤序列只是表示其行为的一种可能方式。如果过早将调度顺序视为权威，不同交错机制就会让本来等价的执行显得不同。语义模型必须先决定哪些观察可以区分并发程序，随后再根据该决定评判操作调度。

    真实示例：EVM

    以操作视角理解以太坊虚拟机（EVM）：

    • 状态：程序计数器、栈、内存、存储、Gas
    • 转换规则：每个操作码各有一条（ADD、PUSH、SSTORE等）
    • 执行：反复应用小步规则，直至停止

    EVM 字节码是一阶指令数据。操作性描述会规定每种操作码如何改变 EVM 配置；具体客户端则负责实现该行为。

    它的分派循环与程序计数器可能类似于去函数化抽象机。但若要称其为去函数化延续，就必须提供具体高阶源程序、变换与对应关系，不能只凭循环看起来相似。

    打破循环：机制之前先确定含义

    操作描述与指称描述回答不同的问题：

    [[p]]c​∈D⟶c′​​what does the program mean?how does this representation step?​

    语义优先的开发会先选择语义域、组合、观察与定律，再确定机器表示。一旦选定转换系统，其正确性义务就负责连接这两个层次。对于恰当定义的完整配置含义，典型的静默步骤保留主张如下：

    c⟶c′⟹meaning(c)=meaning(c′)

    具体关系也可以改用观察等价、轨迹或双模拟。关键在于，机器必须对预期含义负责。

    指称设计不会从循环中选出胜者，而是在循环之外建立稳定的权威来源：

    1. 定义语义域、操作、组合与定律。
    2. 根据这些含义编写程序。
    3. 针对具体使用者选择表示：直接执行、检查、编译、调度、序列化或分析。
    4. 将每种选定的表示与变换都关联回同一含义。

    因此，高阶解释器与一阶程序可以共存。二者都不必成为语言定义。前者可以服务于直接执行；后者可以服务于需要结构的使用者。二者一致是一项语义义务，而非假定其机制相同。

    不存在最终的操作抽象

    每种操作表示都会显露某些结构并隐藏另一些结构。含义是稳定的出发点，我们据此选择恰当的表示并建立它们之间的联系。

    总结

    • 操作语义描述所选表示的求值或状态转换。
    • 自由单子提供指令语法与顺序组合，但其行为仍需要解释。
    • CPS 会显露延续；操作规则可以描述 CPS 程序如何传递值与控制权。
    • 去函数化可以将某个高阶程序转换为一阶机器，并以操作规则描述其状态转换。
    • 将其中任意一种编码视为通用方案，都会造成结构不断被具体化又被隐藏的循环。
    • 指称含义决定这些状态转换必须保留什么。

    重新审视表达式问题

    相关内容

    语义视角：指称设计
    Rust 中的语义驱动设计：能力代数、派生含义与组合、解释器与效应
    概念：表达式问题

    本页介绍一种基于 trait 的实用解法来处理表达式问题：如何添加新的表达式形式与操作，而不必反复重写现有代码。 该解法的设计遵循 Conal 风格，编码方式则采用无标签最终编码/对象代数。具体而言，我们先规定可组合含义（小型能力接口与扩展层面的程序规范），再提供具体解释器。这种编码与 Oleg Kiselyov 的无标签最终风格及对象代数属于同一类型：构造器接口（LitAlg、AddAlg、MulAlg）定义语言签名，程序以多态方式针对这些接口编写，具体实现（例如Eval或Pretty）则提供解释。这样既避免绑定到某个封闭 AST，又保留了两个维度上的静态类型与可扩展性。

    Oleg 的方法明确采用指称式设计：先赋予可组合含义，再将效应与解释器实现为模块化语义层。对于表达式问题而言，这正是它与指称设计契合的原因，而非偶然。Conal 对指称设计的表述也明确提出相同优先级：先以组合方式规定含义，再将具体执行策略视为次要且可替换的部分。

    对于表达式语言示例，这种编码意味着：

    • 构造器词汇由小型、独立的代数 trait 建模。
    • 解释是这些 trait 的实现。
    • 新语法会添加新 trait，而不触碰旧代码。
    • 新语义会添加新的解释器类型，而不触碰旧代码。

    lit与add是语义操作，而非特权 AST 的构造器。AST 只是多种解释中的一种。

    C# 中的对象代数

    这种编码并非 Rust 特有。object-algebras在 C# 中发展了这一模式，并突破了本页采用的固定载体。在本页中，每个解释器会选择一个具体的Self::Expr普通类型。而 C# 代数会抽象出一个类型构造器F——FunctorAlg<F>、MonadAlg<F>、BankingDsl<F>——并将结果作为App<F, a>承载，而不是采用不合法的F<a>。

    C# 没有一等高阶类型，因此以App<F, a>代替应用F(a)，并通过注入/投影包装器还原。这种App技巧正是去函数化：语言无法表达的抽象被转为一阶数据，并在需要时应用。Rust 也遇到了同样的限制——它同样缺少一等高阶类型。

    规定小型语法能力

    每种构造器都会成为一个小型 trait。这就是规范。

    trait LitAlg {
    type Expr;

    fn lit(&self, n: i64) -> Self::Expr;
}

trait AddAlg {
    type Expr;

    fn add(&self, a: Self::Expr, b: Self::Expr) -> Self::Expr;
}

    程序以代数 trait 之上的扩展形式编写。这些扩展也属于规范，并可将较小规范组合为可复用的程序级规范：

    #[ext(name = ExprPrograms)]
impl<This> This
where
    This: LitAlg + AddAlg,
{
    fn expr_basic(&self) -> This::Expr {
        self.add(self.lit(2), self.lit(3))
    }
}

    #[ext(...)]是来自extendcrate 的宏，用于从impl块中生成扩展方法以减少样板代码；它不是新的 Rust 语言特性。

    添加新的解释

    解释器实现规范，无需修改语法。

    struct Eval;

impl LitAlg for Eval {
    type Expr = i64;

    fn lit(&self, n: i64) -> i64 { n }
}

impl AddAlg for Eval {
    type Expr = i64;

    fn add(&self, a: i64, b: i64) -> i64 { a + b }
}

struct Pretty;

impl LitAlg for Pretty {
    type Expr = String;

    fn lit(&self, n: i64) -> String { n.to_string() }
}

impl AddAlg for Pretty {
    type Expr = String;

    fn add(&self, a: String, b: String) -> String {
        format!("({a} + {b})")
    }
}

    现在，同一个表达式可以有不同的解释：

    let eval = Eval;
let pretty = Pretty;

let v: i64 = eval.expr_basic();        // 5
let s: String = pretty.expr_basic();   // "(2 + 3)"

    添加新语法（新能力 trait）

    要添加Mul，只需定义一个新 trait。现有代码保持不变。

    trait MulAlg {
    type Expr;

    fn mul(&self, a: Self::Expr, b: Self::Expr) -> Self::Expr;
}

#[ext(name = ExprProgramsMul)]
impl<This> This
where
    This: LitAlg + AddAlg + MulAlg,
{
    fn expr_with_mul(&self) -> This::Expr {
        self.mul(self.add(self.lit(2), self.lit(3)), self.lit(4))
    }
}

    现有解释器仍可处理旧表达式。
    如果它们需要支持新语法，就实现新 trait：

    impl MulAlg for Eval {
    type Expr = i64;

    fn mul(&self, a: i64, b: i64) -> i64 { a * b }
}

impl MulAlg for Pretty {
    type Expr = String;

    fn mul(&self, a: String, b: String) -> String {
        format!("({a} * {b})")
    }
}

    为什么这能解决表达式问题

    传统表达式问题包含表示上的两个维度：

    • 添加新的变体（分支）
    • 添加新操作

    指称设计重新诠释了这两个维度：

    • 扩展语义词汇：定义新的能力 trait（MulAlg）。
    • 为该词汇添加新的解释：定义新的解释器类型（Eval、Pretty、AST 构造器或代码生成器）。

    这两个维度可以独立组合：

    • 除非需要新能力，否则现有程序无需修改。expr_basic仍然只要求LitAlg + AddAlg。
    • 除非选择解释新能力，否则现有解释器无需修改。Eval即使没有impl MulAlg，仍可运行所有不使用mul的程序。

    这并没有消除实现矩阵。如果Eval与Pretty都需要解释mul，二者都需要impl MulAlg。变化在于矩阵的组织方式：每个单元格都是语义操作 × 解释；没有任何单元格围绕特权表示组织；每个程序只依赖自己使用的能力。

    定律属于规范

    语义代数由载体、操作与定律构成。载体（type Expr）由解释选择；操作与定律则属于规范。例如，算术含义LitAlg + AddAlg规定：

    add(lit(m), lit(n)) = lit(m + n)

    Eval满足这条定律。Pretty则不满足："(2 + 3)"并不等于"5"。二者都是语法签名的有效解释，但只有Eval才是算术规范的模型。这条定律只需针对 trait 陈述一次，并由它决定哪些解释器符合要求。它不属于任何解释器。

    最终洞见：轻量级 Go 与指称设计

    Wadler 在语言机制层面诊断了表达式问题：静态类型与模块化扩展下的行列问题。轻量级 Go给出了一种具体解法：Plus(type a Any)保持递归表示的泛型性，并让每种操作独立约束a（Plus(type a Evaler)对应Eval，Plus(type a Stringer)对应String）。表示不会绑定到某个封闭表达式接口，因此两个维度都保持开放。

    传统解法从表示出发，思考如何开放两个扩展维度。轻量级 Go 将这一点推进得出人意料地远：它让递归表示具有泛型性与结构可扩展性。指称设计则将边界提前了一步：表示并非模型。模型是代数及其定律；表示只是可能的解释之一。

    轻量级 Go 让表示可以扩展。指称设计让表示成为可选项。

    轻量级 Go指称设计
    语义核心可扩展表示代数与定律
    Num/Plus, lit/add结构（表示形式）语义操作
    Eval, String/Pretty方法与接口解释
    递归结构泛型、开放表示（Plus(a)）无需递归表示
    载体所表示的表达式类型由解释器选择（type Expr）
    AST表示仍居于核心可选，是多种解释之一
    矩阵单元格分支 × 操作 → 方法语义操作 × 解释 → impl
    新行为添加方法与接口添加或组合能力
    新实现新的结构实现新的解释器

    Wadler 询问如何扩展表示的两个维度。指称设计则询问为什么表示应当掌握这两个维度。

    先定义可组合含义，再选择编码。这样，表达式问题就成为编码之间的工程选择，而不再是概念上的死结。

    语言的含义应独立于机器这一概念。

    重新审视引用透明性

    相关内容

    语义视角：指称与组合性、定律与解释
    Rust 中的语义驱动设计：能力代数、派生含义与组合
    概念：引用透明性

    本页介绍引用透明性的指称设计解读。 概念页讨论其历史与主流语言中的用法。 本页重点说明 RT 作为设计约束时的含义。

    在指称设计中，RT 并非纯性标签。 它是关于指称的一条定律：替换必须保留指定含义。

    以指称设计重新表述 RT

    指称设计将 RT 重新表述为规范要求，而非实现风格。 规范必须先定义可组合含义；之后才选择执行策略。

    因此，应在语义边界检查 RT：

    • 相同输入
    • 相同的已声明上下文
    • 相同指称

    若这些条件成立，替换就是有效的，并且可以进行等式推理。 即使具体解释器执行 I/O、并发、重试或状态转换，这一点仍然成立，因为这些细节都委托给规范能力边界之后的实现。

    换言之，指称设计不会问“这个实现是否纯？”。 它会问“指称等式是否明确？解释器是否保留了这些等式？”

    纯性与 RT

    RT 与纯性相关，但并不相同。

    • RT是关于含义的一条替换定律。
    • 纯性是一项操作约束：不存在隐藏的可观察效应。

    纯性是表达式级代码实现 RT 的常见方式。 但 RT 仍是语义标准：替换必须保留指定指称。

    因此，指称设计不会把 RT 变成“只能写纯代码”这样的风格标签。 它要求指称等式明确，并将效应隔离在能力边界之后。

    一种最简语义解读是：

    fn f(a: A, io: Io) -> (Result<B, E>, Io)

    对于相同的a和相同的io输入，f会得出相同的(result, io')。 这是指称设计中按上下文索引的替换推理形式。

    RT 为何因此更清晰

    许多关于 RT 的争论混淆了一项有用区别：

    • 语义透明性
    • 操作性副作用

    指称设计将这些层次分开：

    • 语义核心陈述含义
    • 解释器实现执行策略

    这种区分既允许实际效应存在，也不会失去基于定律的推理。

    表示优先设计的失误模式

    如果过早确定具体表示，关于 RT 的讨论就会偏离到风格争论：

    • “这种风格是纯的”
    • “那种风格不纯”
    • “用 IO 包装器就能解决”

    这些大多只是编码方式之争。 指称设计提出了一个更简单的问题： 你的规范中哪些等式有效？

    指称设计的实用模式

    定义小型能力 trait，并将程序行为写成其上的扩展。 随后提供轻量级具体解释器。

    trait FileSystem {
    type Error;

    fn file_read(&self, name: &str) -> Result<String, Self::Error>;
}

trait GithubPublish {
    type Error;

    fn github_publish(&self, repo: &str, files: Vec<String>) -> Result<(), Self::Error>;
}

trait Concurrent {
    fn map_concurrent<A, B, E, F>(&self, xs: &[A], f: F) -> Result<Vec<B>, E>
    where
        A: Clone,
        F: Fn(&A) -> Result<B, E>;
}

#[ext(name = PublishProjectExt)]
impl<This> This
where
    This: FileSystem<Error = String> + GithubPublish<Error = String> + Concurrent,
{
    fn publish_project(&self, files: &[&str], repo: &str) -> Result<(), String> {
        let files = self.map_concurrent(files, |name| self.file_read(*name))?;
        self.github_publish(repo, files)
    }
}

    #[ext(...)]是来自extendcrate 的宏，用于从impl块中生成扩展方法以减少样板代码；它不是新的 Rust 语言特性。

    在 Scala 函数式编程中，RT 常通过F[A]类型的值来介绍（例如IO[A]或F[Either[E, A]]）。 这里的 RT 被表达在更高一层：作为受能力约束的程序含义。 因此，这种 Rust 方法并非以与F[A]相同的编码方式实现的 RT 值容器；它是在明确能力之上规范 RT 行为，并将具体效应委托给实现。

    扩展依据能力陈述语义行为。 具体实现负责决定执行策略，例如批处理、重试、传输、并行与存储细节。

    最终洞见

    在指称设计中，RT 是语义规范的性质。 只要保留已陈述的指称定律，实现选择就是次要的。

    EVM 代数

    相关内容

    Rust 中的语义驱动设计：解释器与效应、一阶程序、语言与编译器流水线
    概念：操作语义、自由单子、延续传递风格、去函数化

    以太坊虚拟机（EVM）是一种基于栈的虚拟 CPU，用于执行以太坊字节码，后者是以 Solidity、Vyper 或其他兼容 EVM 的语言编写的智能合约编译后的形式。

    在最低层：

    • EVM 会处理操作码（ADD、PUSH、JUMP、SSTORE 等）。
    • Execution state includes:
      • 栈：后进先出的操作数数据栈。
      • 内存：用于临时值的瞬态字节数组。
      • 存储：每份合约对应的持久键值存储。
      • 程序计数器：指向下一条操作码。
      • Gas：对执行步骤计量并收费。

    作为解释器模式的 EVM

    EVM 客户端是对一门指令语言的解释器：

    • 指令集 = EVM 操作码（由多个变体组成的枚举）。
    • 程序 = 一系列指令。
    • 解释器 = 每种操作码如何改变机器状态的规则。
    • 多个解释器 = EVM 规范固定，但 Geth、Nethermind、Besu 与 Erigon 是同一解释器的不同实现。

    本书中的三种技术——自由单子、延续传递风格与去函数化——贯穿同一条主线；它们只在如何表示程序剩余部分上有所不同。

    一台机器的三种编码

    以下每种编码都运行同一个固定程序：

    push 2; push 3; add; sstore 1 5; load 1 -> v; push v

    而且每种编码都会产生相同的观察结果：

    stack:   [5, 5]
storage: {1: 5}

    它们的区别仅在于如何表示控制流——“接下来要做什么”。

    自由单子——程序是数据；解释器赋予它含义

    指令函子会生成程序树。and_then是单子 bind，run是一种解释器——另一个解释器（编译为字节码）也可以折叠同一棵树。泛型Free<A>针对这套指令集专门化，因此可以在稳定版 Rust 中编译。

    use std::collections::HashMap;

struct State { stack: Vec<u64>, storage: HashMap<u64, u64> }

// The free monad over the EVM instruction set: a program is data — a tree of
// instructions ending in `Pure`, each carrying its continuation.
enum Free<A> {
    Pure(A),
    Push(u64, Box<Free<A>>),
    Add(Box<Free<A>>),
    SStore(u64, u64, Box<Free<A>>),
    SLoad(u64, Box<dyn FnOnce(u64) -> Free<A>>),
}

impl<A: 'static> Free<A> {
    // Monadic bind: graft `k` onto every leaf of the program.
    fn and_then<B: 'static>(self, k: impl FnOnce(A) -> Free<B> + 'static) -> Free<B> {
        match self {
            Free::Pure(a) => k(a),
            Free::Push(v, next) => Free::Push(v, Box::new(next.and_then(k))),
            Free::Add(next) => Free::Add(Box::new(next.and_then(k))),
            Free::SStore(x, y, next) => Free::SStore(x, y, Box::new(next.and_then(k))),
            Free::SLoad(key, cont) => Free::SLoad(key, Box::new(move |v| cont(v).and_then(k))),
        }
    }
}

fn push(v: u64) -> Free<()> { Free::Push(v, Box::new(Free::Pure(()))) }
fn add() -> Free<()> { Free::Add(Box::new(Free::Pure(()))) }
fn sstore(k: u64, v: u64) -> Free<()> { Free::SStore(k, v, Box::new(Free::Pure(()))) }
fn sload(k: u64) -> Free<u64> { Free::SLoad(k, Box::new(|v| Free::Pure(v))) }

// Interpreter: give the program data meaning against the machine state.
fn run(mut prog: Free<()>, st: &mut State) {
    loop {
        prog = match prog {
            Free::Pure(()) => return,
            Free::Push(v, next) => { st.stack.push(v); *next }
            Free::Add(next) => {
                let b = st.stack.pop().unwrap();
                let a = st.stack.pop().unwrap();
                st.stack.push(a + b);
                *next
            }
            Free::SStore(k, v, next) => { st.storage.insert(k, v); *next }
            Free::SLoad(k, cont) => { let v = *st.storage.get(&k).unwrap_or(&0); cont(v) }
        };
    }
}

fn main() {
    let program = push(2)
        .and_then(|_| push(3))
        .and_then(|_| add())
        .and_then(|_| sstore(1, 5))
        .and_then(|_| sload(1))
        .and_then(|v| push(v));

    let mut st = State { stack: vec![], storage: HashMap::new() };
    run(program, &mut st);
    println!("stack:   {:?}", st.stack);
    println!("storage: {:?}", st.storage);
}
    延续传递风格（CPS）——每个操作码都会调用“程序剩余部分”

    每个处理器完成工作后都会调用延续k。sload会将加载的值传递给一个需要该值的延续。控制流以嵌套延续的形式显式表达，完全没有程序数据结构。

    use std::collections::HashMap;

struct State { stack: Vec<u64>, storage: HashMap<u64, u64> }

// Each opcode does its work, then calls the continuation `k` = "the rest of
// the program". `sload` passes the loaded value on to its continuation.
fn push(st: &mut State, v: u64, k: impl FnOnce(&mut State)) {
    st.stack.push(v);
    k(st);
}
fn add(st: &mut State, k: impl FnOnce(&mut State)) {
    let b = st.stack.pop().unwrap();
    let a = st.stack.pop().unwrap();
    st.stack.push(a + b);
    k(st);
}
fn sstore(st: &mut State, key: u64, val: u64, k: impl FnOnce(&mut State)) {
    st.storage.insert(key, val);
    k(st);
}
fn sload(st: &mut State, key: u64, k: impl FnOnce(&mut State, u64)) {
    let v = *st.storage.get(&key).unwrap_or(&0);
    k(st, v);
}

fn main() {
    let mut st = State { stack: vec![], storage: HashMap::new() };

    push(&mut st, 2, |st| {
        push(st, 3, |st| {
            add(st, |st| {
                sstore(st, 1, 5, |st| {
                    sload(st, 1, |st, v| {
                        push(st, v, |_st| {});
                    });
                });
            });
        });
    });

    println!("stack:   {:?}", st.stack);
    println!("storage: {:?}", st.storage);
}
    去函数化——操作调用变成由一个apply执行的数据

    自由单子与 CPS 版本会调用操作（push(2)、add()、sstore(1, 5)、sload(1)）——这是一种几乎可直接读作规范说明的小型代数；去函数化则将每次调用具体化为一阶数据。随后由一个apply函数解释这些数据，延续也会随之折叠：“程序剩余部分”变成下一个索引（pc）。可以把它看作以数据形式书写的操作代数，并由apply这个单一解释器解释。

    use std::collections::HashMap;

struct State { stack: Vec<u64>, storage: HashMap<u64, u64> }

// The EVM algebra reified: where the other encodings CALL `push(2)`, `add()`,
// `sstore(1, 5)`, `sload(1)`, each such call becomes a first-order value — a
// tag with its arguments.
enum Op {
    Push(u64),
    Add,
    SStore(u64, u64),
    SLoad(u64),
}

// `apply` is the single interpreter for the reified operations: it gives each
// tag its meaning against the machine state.
fn apply(op: &Op, st: &mut State) {
    match op {
        Op::Push(v) => st.stack.push(*v),
        Op::Add => {
            let b = st.stack.pop().unwrap();
            let a = st.stack.pop().unwrap();
            st.stack.push(a + b);
        }
        Op::SStore(k, v) => { st.storage.insert(*k, *v); }
        Op::SLoad(k) => {
            let v = *st.storage.get(k).unwrap_or(&0);
            st.stack.push(v);
        }
    }
}

fn main() {
    // The program is now data: a flat list of reified operation calls.
    let code = vec![
        Op::Push(2),
        Op::Push(3),
        Op::Add,
        Op::SStore(1, 5),
        Op::SLoad(1),
    ];

    // `pc` is the defunctionalized continuation: "the rest of the program" is
    // just the next index.
    let mut st = State { stack: vec![], storage: HashMap::new() };
    let mut pc = 0;
    while pc < code.len() {
        apply(&code[pc], &mut st);
        pc += 1;
    }

    println!("stack:   {:?}", st.stack);
    println!("storage: {:?}", st.storage);
}

    从延续到字节码

    以下三种编码是同一计算在距机器远近不同的视角下呈现的形式：

    • 自由单子先以代数方式将程序构造为数据，再对其作出解释。同一棵树可以由多个解释器折叠：一个运行它，一个漂亮打印它，一个编译它。
    • CPS会移除数据结构并显式表示控制流：“执行此操作码，然后调用延续。”加载的值会流向需要它的延续。
    • 去函数化会将操作的调用转换为一阶数据，并由一个apply函数解释这些数据；延续则折叠为一个pc，其操作对象是Vec<Op>。驱动循环就是一个不使用闭包的 CPS 蹦床。

    类比，而非推导

    EVM 可以分析为一阶抽象机，其显式程序计数器类似于去函数化的控制表示。但这种结构类比本身无法证明 EVM 字节码是经 CPS 变换再去函数化得到的。

    关键洞见

    概念自由单子世界EVM 实际情况
    指令类型操作码枚举固定的 EVM 操作码
    程序表示由Free<A>构造的树线性字节码数组
    延续指令节点中的闭包程序计数器（pc）
    解释器对程序进行模式匹配按操作码切换分支，并修改虚拟机状态
    多种解释器对同一程序进行不同折叠多个以太坊客户端实现

    与真实 EVM 的对应

    • 指令集（Free的变体，或Op枚举）对应 EVM 操作码集合。
    • 程序（Free树、嵌套延续或Vec<Op>）表示编译前后的合约。
    • 解释器（run、CPS 处理器或apply）是 Geth、Besu 或 Nethermind 等客户端所实现的部分。
    • 机器状态（stack、storage）是 EVM 的栈、内存与存储。
    • 真实的 EVM 字节码是去函数化后的形式：由程序计数器索引的扁平指令数组，恰如上文展示的去函数化编码。

    关于

    本书提炼了一种软件思维方式，灵感来自 Conal Elliott 的指称设计。核心思想简单而深刻：

    指称设计

    先定义程序的含义，再决定它如何运行。

    在这一视角下，计算不是不透明的步骤序列，而是透明的数学对象。我们从规范开始，以纯粹且可组合的方式描述程序意味着什么。这些描述采用代数结构表达，通常表现为 trait 或类型签名。实现——这些含义如何实现出来——则是独立且可互换的一层。

    将含义与机制分离后，我们便能获得：

    • 清晰性——程序读起来像精确的定义。
    • 可组合性——各部分可以按代数规则组合。
    • 可重构性——实现持续演进时，含义仍保持不变。
    • 正确性——推理程序时可以采用等式推理，而非操作层面的推理。

    这些指南旨在提供实用技术，帮助读者在现代编程语言中运用这一风格，尤其是 Rust，同时保留其数学根基的优雅与严谨。

    • 含义说明所设计的值、关系与变换。
    • 表示选择如何将这些含义编码为类型与数据。
    • 执行选择如何让一种表示在机器上运行。
